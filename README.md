# Axiom IDE

Собственный BASIC-подобный язык и настольная среда разработки на C#.

## Что это

Проект создаёт современный BASIC-подобный язык в духе QuickBASIC и собственную настольную среду разработки для повседневной работы с программами Axiom.

Проект состоит из двух основных частей:
- ядро языка: лексический анализатор, синтаксический анализатор, синтаксическое дерево, семантическая проверка и интерпретатор;
- среда разработки: редактор, запуск программы, вывод и диагностика ошибок.

## Текущий статус

Репозиторий уже содержит стартовый .NET-каркас и несколько первых рабочих слоёв языка:
- создано решение `Axiom.sln`;
- созданы проекты слоёв `Core`, `Lexing`, `Syntax`, `Parsing`, `Semantics`, `Runtime`, `Execution`, `Ide`;
- созданы тестовые проекты для `Lexing`, `Parsing`, `Semantics`, `Runtime`, `Execution`, `Ide`;
- настроены ссылки между проектами по `docs/ARCHITECTURE.md`;
- в `Axiom.Core` реализованы базовые типы диагностики и позиционирования в тексте;
- в `Axiom.Lexing` реализован рабочий лексический анализатор для Axiom v0.1 и покрыт модульными тестами;
- в `Axiom.Syntax` реализованы базовое синтаксическое дерево, `SyntaxKind`, `SyntaxToken` и узлы для выражений, инструкций и объявлений верхнего уровня;
- в `Axiom.Parsing` реализован минимально полноценный синтаксический анализатор с синтаксическими диагностическими сообщениями, восстановлением после ошибок и модульными тестами;
- в `Axiom.Semantics` реализован минимальный связыватель: символы, области видимости, связанное дерево, проверки имён/типов/вызовов/`RETURN` и диагностические сообщения семантического анализа;
- в `Axiom.Runtime` реализован первый исполняющий слой: значения времени выполнения, области видимости, кадры вызовов, граница ввода-вывода для `INPUT`/`PRINT`, интерпретатор, встроенные функции и диагностические сообщения времени выполнения;
- создан проект `Axiom.Bytecode` как нижний слой будущего байткодного направления; в нём уже есть начальная модель `LoweredProgram`, `LoweredRoutine`, `LoweredInstruction` и первый понижатель простого скалярного среза, включая скалярные `DIM` с инициализатором и без него, `IF / ELSEIF / ELSE`, `SELECT CASE / END SELECT`, `WHILE / END WHILE`, `FOR / NEXT / EXIT FOR`, `DO WHILE / LOOP`, `DO UNTIL / LOOP`, `DO ... LOOP WHILE`, `DO ... LOOP UNTIL`, `DO ... LOOP` без условия и `EXIT DO` без подключения к запуску; тестами отдельно подтверждены прямые вложенные локальные `SUB` и `FUNCTION`, чтение внешних переменных из локальной функции и прямая рекурсия;
- в `Axiom.Execution` реализованы единый путь `parse -> bind -> execute`, отдельный этап предварительной компиляции `parse -> bind` и внутренняя модель уже собранной программы для повторного запуска без повторной подготовки;
- в `Axiom.Execution` введены первые контракты будущих режимов исполнения `Auto`, `Interpreter`, `Bytecode` и фактического движка запуска; текущий рабочий движок остаётся интерпретатором, а принудительный байткодный режим честно возвращает ошибку backend-слоя до появления VM;
- в `Axiom.Ide` реализована WPF-оболочка с `AvalonEdit`, вкладками, файловой панелью, командами `Compile` и `Run`, панелями вывода и диагностик и `ProgramRunService` поверх `Axiom.Execution`;
- в `Axiom.Ide` добавлен выбор предпочтительного режима запуска через меню `Run -> Execution Mode`, сохранение этого выбора в состоянии оболочки и отображение фактически использованного движка в строке состояния после запуска;
- добавлены и проходят модульные и интеграционные тесты для семантического анализа, выполнения, сквозного запуска и сервиса запуска без пользовательского интерфейса;
- добавлен тестовый проект `Axiom.Bytecode.Tests` для понижения bound-программы в начальную линейную форму;
- ветка интерактивного ввода уже включает клавиатурные функции и обработчики, а также мышиные формы `MOUSEX()`, `MOUSEY()`, `MOUSEBUTTON()`, `MOUSEPRESS()` и `ON MOUSE`;
- в `samples/acceptance/` зафиксированы официальный позитивный проверочный пример `smoke_v0_1.axm` с ожидаемым выводом и набор коротких отрицательных программ для базовых ошибок;
- ручная стабилизация вспомогательного слоя оболочки в живом WPF-окне завершена: сценарии недавних файлов, отсутствующей записи в списке недавних файлов и последнего использованного пути проверены и работают штатно.
- в графическом слое добавлен первый современный срез изображений: тип `IMAGE`, функции `LOADIMAGE`, `IMAGEWIDTH`, `IMAGEHEIGHT` и оператор `DRAWIMAGE` работают через интерпретатор, `BytecodeVm` и хост IDE.

## Рабочий каталог и расширение

- Каноническая рабочая копия проекта и основная папка для новых Axiom-программ: `C:\Axiom`.
- Если у IDE ещё нет сохранённой истории последних файлов, файловая панель и диалоги открытия/сохранения стартуют из `C:\Axiom`.
- BASIC-исходники, примеры и пользовательские файлы проекта используют расширение `.axm`.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dotnet-test-artifacts.ps1 Axiom.sln
```

Для адресного прогона отдельного проекта или фильтра можно передать обычные аргументы `dotnet test` после пути:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dotnet-test-artifacts.ps1 tests/Axiom.Runtime.Tests/Axiom.Runtime.Tests.csproj --no-restore --filter "FullyQualifiedName~Execute_SmokeSampleReportsUnrecoverableReplacementMarkers"
```

## Как запустить WPF smoke harness

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj
```

Полезные детали:
- harness запускает реальный `Axiom.Ide.exe`, готовит временную workspace в `.artifacts/ui-smoke/` и восстанавливает shell-state после прогона;
- текущий smoke baseline покрывает tree-open, blocked `.exe`, `Find/Replace` включая режим `Regex`, `Run -> Output`, `Run -> Diagnostics`, toggle shell-панелей, persisted shell-state и context-menu/file-operations сценарии `File Manager` (`Show hidden files`, `New File`, `New Directory`, `Rename`, `Copy/Paste`, `Cut/Paste`, `Delete`);
- для отдельной проверки просмотра журнала действий IDE есть сфокусированный маршрут без полного прогона файловых операций:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --event-log-only
```

- этот режим проходит через меню `View`, `Run`, `Format`, `Help`, открывает встроенный просмотр журнала и проверяет, что в деталях видны корректные `commandName`, `menuName` и свойства событий;
- для отдельной проверки неблокирующего клавиатурного ввода `INKEY()` есть узкий пользовательский smoke-маршрут:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --inkey-only
```

- этот режим открывает `poll_keys.axm`, запускает его в IDE, переводит фокус в `Output` и отправляет клавишу `LEFT`, подтверждая реальный ввод через окно IDE;
- для отдельной приёмки графических `SCREEN`-сценариев `GET` / `PUT` есть узкий smoke-маршрут на настоящих sample из репозитория:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --get-put-only
```

- этот режим копирует `samples/operators/get/rectangle_capture.axm` и `samples/operators/put/default_xor_and_preset.axm` во временный workspace, запускает их через реальный `Axiom.Ide.exe` и ждёт в IDE trace события `screen.activated`, строки `screen.output` и финальное `screen.deactivated`;
- для отдельной приёмки договора `SCREEN 10` есть узкий smoke-маршрут:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --screen10-only
```

- этот режим копирует `samples/graphics/screen/best_fit_dimensions.axm` во временный workspace, запускает его через реальный `Axiom.Ide.exe` и проверяет по IDE trace фактические `SCREENWIDTH()` / `SCREENHEIGHT()`, расчёт `LOCATE` и выбор наибольшего вписываемого размера с отношением `16:9`;
- для отдельной приёмки `SPRITE` / `DRAWSPRITE` есть узкий smoke-маршрут:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --sprite-only
```

- этот режим копирует `samples/graphics/sprites/walk_cycle.axm`, `samples/graphics/sprites/page_flip_walk.axm` и `samples/graphics/sprites/assets/walk_sheet.png` во временную рабочую область, в копиях заменяет ручные паузы на автоматический smoke-вариант, запускает примеры в режиме `Bytecode`, проверяет строки `screen.output`, включая кадровый сценарий `DRAWSPRITE` + `PCOPY`, и трассу завершения с фактическим `BytecodeVm`;
- для отладки workspace можно оставить:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --keep-workspace
```

- при необходимости harness можно направить на явно собранный `Axiom.Ide.exe`:

```powershell
dotnet run --project src/Axiom.Ide.SmokeHarness/Axiom.Ide.SmokeHarness.csproj -- --ide-exe C:\path\to\Axiom.Ide.exe
```

- прогон требует обычную desktop-WPF сессию Windows и не является headless UI-тестом.

## Чистота сборки

В репозитории действует правило чистой рабочей копии для локальных прогонов:
- все результаты сборки и промежуточные файлы складываются централизованно в скрытый каталог `.artifacts/` в корне репозитория;
- для тестовых прогонов каталог результатов `trx` и сопутствующих файлов тоже должен идти через `scripts/dotnet-test-artifacts.ps1`, чтобы `dotnet test` не создавал `TestResults/` внутри `tests/`;
- каталоги `bin/` и `obj/` внутри `src/` и `tests/` считаются только создаваемыми артефактами и не должны использоваться как место хранения проектных файлов;
- локальные служебные каталоги `.dotnet-home/`, `.dotnet-cli/`, `.tmp-build/`, а также диагностические журналы сборки считаются временными и не относятся к исходникам проекта.

Если нужно очистить рабочую копию после локальных прогонов, достаточно удалить `.artifacts/` и временные служебные каталоги.

Для быстрой проверки этого правила есть отдельная команда:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/repo-sanity.ps1
```

## Проверочные примеры

В репозитории есть два связанных слоя проверочных примеров:
- `samples/functions/`, `samples/operators/`, `samples/control-flow/`, `samples/expressions/` держат короткие runnable `.axm`-примеры для поведения языка;
- `samples/smoke/engine-compare/` держит нагрузочные сценарии для сравнения `Interpreter` и `BytecodeVm`;
- `docs/BYTECODE_COVERAGE.md` фиксирует функциональное покрытие байткодного пути;
- `docs/BYTECODE_PERF_MATRIX.md` фиксирует, какие семейства языка уже представлены в нагрузочных сценариях и какие ещё остаются без адресного benchmark.
- текущий слой регрессионной проверки в `samples/acceptance/` с историческим сквозным примером и отрицательными программами;
- обязательная постоянная структура для всех новых запускаемых примеров поведения языка:
  - `samples/operators/<operator-name>/`
  - `samples/functions/<function-name>/`
  - `samples/smoke/`
  - при необходимости `samples/control-flow/<feature-name>/`
  - при необходимости `samples/expressions/<feature-name>/`

Постоянное правило проекта:
- одного модульного или интеграционного теста недостаточно, если меняется поведение языка;
- после каждой новой возможности языка, оператора, встроенной функции или изменения семантики должен появляться запускаемый `.axm` пример в правильной тематической подпапке;
- этот пример должен открываться в `Axiom.Ide` и использоваться как ручная проверка.
- если добавляется новая встроенная функция, оператор или меняется их наблюдаемое поведение, в том же наборе правок нужно обновлять и пользовательскую справку в `docs/manual/`;
- если новая сущность должна находиться через указатель справочника, в том же наборе правок нужно обновлять и `docs/manual/scripts/manual.js`.

Текущий каталог уже заполнен примерами для:
- операторов и объявлений;
- управления ходом выполнения;
- выражений;
- всех реализованных встроенных функций;
- отдельного сквозного примера в `samples/smoke/`.

Текущие исторические проверочные материалы:
- `samples/acceptance/smoke_v0_1.axm` — позитивная сквозная проверка для Axiom v0.1;
- `samples/acceptance/smoke_v0_1.expected.txt` — ожидаемый вывод при вводе `Иван` и `45`;
- `samples/acceptance/negative/` — короткие отрицательные программы на необъявленную переменную, неверный тип в `IF`, деление на ноль, неверный `INPUT`, `STEP 0` и неправильное число аргументов.

Текущий широкий ручной пример:
- `samples/smoke/full_language_bytecode.axm` — большая позитивная smoke-программа для запуска в `Axiom.Ide` в режиме `Bytecode`; включает `INPUT`, `PRINT USING`, управляющие конструкции, массивы, `TYPE`, функциональные значения, строки, числа, регулярные выражения, дату/время и файловые функции.

Новые примеры поведения языка должны добавляться уже по новой тематической структуре, а не в общую папку.

## Принцип работы

1. Сначала реализуется ядро языка.
2. Затем запуск через интерпретатор.
3. Затем полноценная IDE.
4. Потом последовательное расширение языка и среды.

Текущее уточнение этого принципа:
- между интерпретатором и будущим байткодным направлением теперь есть отдельный промежуточный слой предварительной компиляции;
- начальный проект `Axiom.Bytecode` пока строит только in-memory lowered-представление и не исполняет программу;
- команда `Compile` в IDE пока не создаёт `exe` и не создаёт отдельный байткодный файл, а только собирает и кэширует внутреннюю подготовленную программу в памяти;
- если после успешной `Compile` текст не менялся, команда `Run` выполняет уже эту подготовленную программу, а не заново проходит весь путь `parse -> bind`.

## Крупные направления, требующие отдельного проектирования

- полная QuickBASIC-совместимость;
- компиляция в исполняемый exe-файл;
- графика и файловые команды языка;
- сложный отладчик;
- тяжёлая проектная система.

## Следующий шаг

Axiom v0.1 остаётся историческим именем первой устойчивой базы проекта: язык, интерпретатор, путь сквозного запуска и среда разработки уже имеют рабочую основу.

Следующий шаг — развивать продукт как готовую среду: каждое крупное расширение языка или IDE сначала фиксируется в документации, затем реализуется и проверяется.
## Проверка математических функций по справочнику

В репозитории есть отдельная консольная программа для автоматической проверки математического пакета встроенных функций и сбора отчёта во временный файл.

Запуск по умолчанию:

```powershell
dotnet run --project src/Axiom.ManualChecks/Axiom.ManualChecks.csproj
```

Программа:
- прогоняет все реализованные математические встроенные функции первой волны;
- проверяет отрицательные сценарии для ошибок области определения и времени выполнения, а также несколько семантических ошибок по числу и типам аргументов;
- пишет подробный `.txt` отчёт во временный каталог и печатает путь к файлу в консоль.

Если нужен свой путь для отчёта:

```powershell
dotnet run --project src/Axiom.ManualChecks/Axiom.ManualChecks.csproj -- --out C:\Temp\axiom-math-report.txt
```

- `BytecodeDebugInfo`, `SourceInstructionMap`, таблица имён параметров и локальных переменных, диапазоны логических блоков;
- `BytecodeModuleValidator` и `BytecodeValidationResult` для проверки целостности модуля до появления VM.

Текущая валидация покрывает:
- корректность `routine-id` и точки входа;
- корректность индексов констант, global-slot и built-in id;
- корректность локальных и аргументных слотов;
- корректность целей переходов внутри routine;
- соответствие числа аргументов при `Call` и `CallBuiltin`;
- корректность базовых отладочных карт и диапазонов блоков.

Это внутренний шаг фазы 4. Пользовательское поведение языка пока не меняется: `BytecodeModule` ещё не строится из `Compile`, не кэшируется в IDE и не исполняется через `Run`.
## Обновление 2026-04-23 - первый эмиттер BytecodeModule

В `Axiom.Bytecode` добавлен первый рабочий эмиттер lowered-представления в байткодный модуль:
- `BytecodeCompiler` и `BytecodeCompilerResult` переводят `LoweredProgram` в `BytecodeModule`;
- покрыт первый скалярный слой: литералы, глобальные переменные, локальные слоты, аргументы, арифметика, логика, сравнения, вызовы процедур, вызовы built-in, `PRINT`, переходы, `Pop` и `Return`;
- в `Opcode` добавлен внутренний `PrintLine`, чтобы байткодный путь мог выразить обычный перевод строки `PRINT` без подмены пользовательской семантики;
- после эмиссии модуль сразу проходит через `BytecodeModuleValidator`.

Добавлены модульные тесты на:
- успешную эмиссию скалярной программы с глобалами, локалами, аргументами, вызовом routine и built-in;
- корректное разрешение переходов после удаления lowered-меток;
- диагностику дублированных меток внутри routine.

Это всё ещё внутренний шаг backend-ветки: `BytecodeModule` пока не подключён к `Compile`, не кэшируется в IDE и не исполняется через `Run`.
## Обновление 2026-04-23 - минимальная Bytecode VM

Во внутреннем рантайме `Axiom.Runtime` появился первый исполняющий байткодный путь:
- `BytecodeVm` исполняет `BytecodeModule` поверх уже существующих `RuntimeValue` и `IRuntimeHost`;
- покрыт первый скалярный срез: стек вычисления, глобалы, локалы, аргументы, вызовы процедур, часть built-in, `PRINT`, переходы и `RETURN`;
- `BuiltinBinding` теперь хранит канонический `BuiltinFunctionId`, чтобы VM вызывала встроенные функции по реальному идентификатору, а не по строковому имени.

Текущий built-in bridge VM пока минимальный и ориентирован на первый исполняемый слой:
- `LEN`, `STR`, `VAL`, `LCASE`, `UCASE`;
- `ABS`, `SGN`, `MIN`, `MAX`, `CLAMP`.

Добавлены первые тесты полного пути `Parse -> Bind -> Lower -> BytecodeCompiler -> BytecodeVm`.

Это всё ещё внутренний шаг backend-ветки: `Compile` и `Run` пока не переключены на VM, но теперь у проекта уже есть реальный исполняемый байткодный модуль внутри рантайма, а не только модель и эмиттер.

## Обновление 2026-04-23 - BytecodeVm подключена к Compile и Run

В `Axiom.Execution` сделан первый реальный мост между frontend-подготовкой и байткодным backend-ом:
- `Compile` теперь строит не только `BoundProgram`, но и `LoweredProgram` вместе с `BytecodeModule`;
- `CompiledProgram` хранит исходный `BoundProgram`, а также опциональные `LoweredProgram` и `BytecodeModule`;
- `CompilationResult` и `ExecutionResult` теперь возвращают отдельные времена frontend-подготовки, понижения и эмиссии байткода, а также признаки доступности байткода и использования backend-кэша;
- `Run` в режиме `Auto` для уже покрытого скалярного подмножества языка исполняет программу через `BytecodeVm`;
- режим `Interpreter` по-прежнему принудительно использует интерпретатор;
- режим `Bytecode` запускает `BytecodeVm` там, где для текущей программы уже есть валидный и поддержанный байткодный модуль.

Переходный договор rollout сейчас консервативный:
- если backend не смог собрать байткодный модуль, `Compile` всё равно считается успешной frontend-подготовкой, но отдельно сообщает backend-диагностики;
- `Auto` в таком случае честно уходит в интерпретатор и помечает это как fallback;
- `Bytecode` в таком случае возвращает ошибку backend-слоя, а не скрыто подменяет исполнение интерпретатором;
- для первого включённого среза `BytecodeVm` запуск через VM разрешён только там, где текущая таблица покрытия подтверждает поддержку нужных built-in и семантики.

Это уже не только внутренний backend-шаг: `Compile -> Run` и прямой `Run` в IDE теперь действительно могут использовать `BytecodeVm` на покрытом подмножестве языка. При этом полный паритет с интерпретатором ещё не достигнут, поэтому rollout остаётся постепенным и с явным fallback.

## Обновление 2026-04-23 - BytecodeVm покрывает FOR

Байткодный путь расширен ещё на один реальный кусок управляющей семантики:
- `FOR ... NEXT` больше не считается целиком интерпретаторным срезом;
- `Auto` и явный режим `Bytecode` теперь запускают простые покрытые циклы `FOR` через `BytecodeVm`;
- для сохранения паритета с интерпретатором в backend добавлена явная runtime-проверка `STEP 0`, чтобы VM возвращала ту же диагностику `MB3004`, а не уходила в бесконечный цикл.

Это всё ещё переходный этап rollout:
- локальные routine;
- локальные fixed-string переменные;
- объявления внутри вложенных блоков
пока остаются за интерпретатором.

## Обновление 2026-04-23 - локальные FUNCTION без захвата включены в VM-first срез

Байт-кодный путь расширен на первый безопасный участок локальной процедурной модели:
- локальные FUNCTION без захвата внешних переменных теперь считаются покрытыми для пользовательского запуска через BytecodeVm;
- режимы Auto и Bytecode реально запускают такие функции через VM;
- для локальных функций с захватом внешнего параметра backend по-прежнему честно возвращает диагностическую ошибку эмиттера BC5004;
- для локальных функций, захватывающих внешний локал, предикат покрытия теперь возвращает явную backend-диагностику MB4002;
- локальные SUB пока сознательно не включены в пользовательское VM-покрытие и в режиме Auto остаются на интерпретаторном пути.

Отдельно уточнён договор причин fallback:
- если байткодный модуль не собран из-за backend-диагностики, Auto теперь сохраняет успешное выполнение через интерпретатор, но причина fallback берётся из реальной backend-диагностики, а не из безымянного общего сообщения;
- это особенно важно для локальных функций с захватом внешнего параметра, где пользователь и IDE теперь видят, почему VM-путь не был использован.

Это всё ещё переходный шаг rollout: локальные FUNCTION без захвата уже идут через VM, но локальные SUB, захваты внешних переменных и дальнейшее выравнивание процедурной модели ещё остаются отдельными шагами плана.
## Обновление 2026-04-23 - локальные SUB без захвата включены в VM-first срез

Следующий участок процедурной модели переведён на байткодный путь:
- локальные SUB без захвата внешних переменных теперь считаются покрытыми для пользовательского запуска через BytecodeVm;
- режимы Auto и Bytecode реально выполняют такие локальные подпрограммы через VM;

Граница непокрытого среза после этого шага сужается ещё раз:

- захват внешнего локала по-прежнему возвращает ошибку покрытия MB4002.

## Правило временных артефактов

Все временные данные ручных запусков, проверочных примеров, отладки и локальных прогонов должны записываться только в `.artifacts/`.

Корень `C:\Axiom` предназначен для исходников, документации, решения, постоянных примеров и проектных файлов. Временные файлы вида `axiom_sample_*` в корне считаются мусором: их нужно создавать под `.artifacts/`, чтобы каталог артефактов можно было удалить целиком без риска потерять важные данные.
