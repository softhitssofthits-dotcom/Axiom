## Анализ слабых сторон проекта Axiom

### Краткое резюме

**Axiom** — зрелый BASIC-подобный язык с двумя движками (Interpreter и BytecodeVm), WPF-IDE, развитой современной графикой, тайловыми картами и обширной документацией. 306 исходных файлов, ~64K строк кода, 35 тестовых файлов. Сборка проходит без ошибок (1 предупреждение xUnit). Проект находится в хорошей технической форме, но накопил ряд архитектурных и процессных проблем.

---

### 1. Критические проблемы

#### 1.1. Утечка GCHandle в NativeGraphicsScreenWindow

`src/Axiom.Ide/Graphics/NativeGraphicsScreenWindow.cs:99`:
```csharp
SetWindowLongPtr(Hwnd, -21, GCHandle.ToIntPtr(GCHandle.Alloc(this)));
```
GCHandle аллоцируется при создании окна и освобождается в `HandleDestroyed()` (строка 525). Но если между созданием и уничтожением окна произойдёт исключение в коде конструктора после `CreateWindowEx`, `HandleDestroyed` может не вызваться — GCHandle утечёт. Кроме того, `Dispose()` (строка 144) вызывает `Close()`, но не проверяет GCHandle напрямую. Нет финализатора как страховки.

**Риск**: утечка неуправляемой памяти при редких краевых условиях.

#### 1.2. D3D11 renderer без try/catch при Disposing

`src/Axiom.Ide/Graphics/Direct3D11SwapChainRenderer.cs` — метод `Dispose()` последовательно вызывает `_renderTargetView?.Dispose()`, `_backBuffer?.Dispose()`, `_swapChain.Dispose()`, `_context.Dispose()`, `_device.Dispose()`. Если любой из промежуточных Dispose выбросит исключение (COM-ошибка, разрушенный объект), последующие ресурсы не освободятся.

**Риск**: утечка GPU-ресурсов при аварийном завершении.

---

### 2. Архитектурные проблемы

#### 2.1. Систематическое дублирование Interpreter ↔ BytecodeVm

Это самая масштабная архитектурная слабость. Каждая встроенная функция реализована **дважды** — один раз в Interpreter, второй раз в BytecodeVm:

| Область | Interpreter | BytecodeVm |
|---------|-------------|-------------|
| Array builtins | `Interpreter.Builtins.Array.cs` (1919 строк) | `BytecodeVm.Builtins.Array.cs` (1958 строк) |
| Graphics | `Interpreter.Graphics.cs` (1451 строк) | `BytecodeVm.Graphics.cs` (1692 строк) |
| FileSystem | `Interpreter.Builtins.FileSystem.cs` (1167 строк) | `BytecodeVm.Builtins.FileSystem.cs` (1011 строк) |
| DateTime | `Interpreter.Builtins.DateTime*.cs` (~1089 строк) | `BytecodeVm.Builtins.DateTime.cs` (1022 строк) |
| String builtins | ~775 строк (7 файлов) | ~792 строк (5 файлов) |
| Numeric | `Interpreter.Builtins.Numeric.cs` (386 строк) | `BytecodeVm.Builtins.Numeric.cs` (310 строк) |
| Regex | `Interpreter.Builtins.Regex.cs` (354 строк) | `BytecodeVm.Builtins.Regex.cs` (462 строк) |
| PrintUsing | `Interpreter.PrintUsing.cs` (559 строк) | `BytecodeVm.PrintUsing.cs` (768 строк) |

**Итого ~12 000 строк дублированной бизнес-логики** (считая только builtins и graphics). Графика уже частично вынесена в общие хелперы (`GraphicsDrawExecutor`, `GraphicsDrawParser`, `GraphicsCircleValidation` — 633 строки), но для built-in функций такого общего слоя нет.

**Следствия**: при каждом изменении семантики функции нужно менять два файла; высок риск расхождения договоров; BYTECODE_COVERAGE.md показывает множество записей «частично» по негативному паритету — это прямое следствие.

#### 2.2. BytecodeVm.cs — бог-объект (6001 строк, 86 private-методов)

Хотя файл уже разбит на partial-классы (~11 420 строк суммарно), основной файл `BytecodeVm.cs` остаётся монолитным dispatch-циклом с огромным switch по опкодам. Класс одновременно владеет: стеком вычисления, таблицей global-слотов, кадрами вызовов, графики, вводом и политикой останова.

Аналогично Interpreter.cs (~2500 строк) + partial-файлы (11 369 строк суммарно).

#### 2.3. MainWindowViewModel.cs — 3354 строки

Один ViewModel содержит всю логику IDE: команды, форматирование, привязки, состояние оболочки. Это нарушает SRP и затрудняет тестирование. Partial-файл `MainWindowViewModel.Formatting.cs` частично снимает проблему, но ядро остаётся слишком большим.

#### 2.4. Axiom.Syntax — без тестового проекта

`Axiom.Syntax` (3517 строк — SyntaxTree, SyntaxKind, узлы) — единственный проект языкового frontend без собственных модульных тестов. Покрытие происходит только косвенно через `Axiom.Parsing.Tests`.

---

### 3. Проблемы процесса и документации

#### 3.1. CURRENT_STATE.md устарел — ссылается на PLANS3 вместо PLANS4

`docs/agent/CURRENT_STATE.md` пять раз упоминает `docs/PLANS3.md` как активный план. Однако по AGENTS.md активный план — `docs/PLANS4.md`, а `PLANS3.md` — исторический. Все новые сессии, начиная с 832, зафиксированы в WORKLOG4, а последние записи PLANS4 относятся к tilemap (2026-06-08). CURRENT_STATE ведёт новые агенты к устаревшему документу.

#### 3.2. Test warning: невалидный тестовый метод

`tests/Axiom.Ide.Tests/ProgramRunServiceTests.cs:746` — публичный метод `Run_Screen10BestFitAcceptanceProgram_WritesExpectedGraphicsOutputOnBytecodeVm` без атрибута `[Fact]`. Либо забыли атрибут, либо метод мёртв.

#### 3.3. Отсутствие BDD/системных тестов для графического конвейера

Графический слой (SCREEN, CANVAS, VIEWPORT, CAMERA, спрайты, tilemap, D3D11 renderer) не имеет автоматизированных тестов, проверяющих реальный визуальный вывод. `SmokeHarness` покрывает только сценарии запуска IDE, а не корректность отрисовки.

## План устранения слабых сторон

Ниже — приоритизированный план, сгруппированный по волкам усилий. Каждая волна — самостоятельная, можно прерываться между ними.

### Волна 1: Безопасность и стабильность (1–2 сессии)

| # | Задача | Сложность | Влияние |
|---|--------|-----------|---------|
| 1.1 | Устранить утечку GCHandle: обернуть в try/catch в конструкторе, добавить страховочный Free в Dispose, рассмотреть SafeHandle | средняя | Критическое |
| 1.2 | Сделать Dispose D3D11 renderer атомарным: обернуть каждый Dispose в try/catch | низкая | Критическое |
| 1.3 | Починить мёртвый тестовый метод (добавить `[Fact]` или удалить) | тривиальная | Низкое |
| 1.4 | Обновить `docs/agent/CURRENT_STATE.md`: PLANS3 → PLANS4 | тривиальная | Среднее |

### Рекомендуемый порядок старта

1. **Волна 1** — немедленно, это исправления безопасности и точечные правки.
2. **Волна 2, задачи 2.2–2.3** — начать со строковых и числовых builtins как прототип общей архитектуры; если шаблон подтвердится, масштабировать на остальные.
3. **Волна 3, задача 3.1** — параллельно с волной 2, когда станет ясно, как выглядит общий слой.

Волны 4–5 можно отложить до завершения продуктовой нагрузки (tilemap, современная графика).
