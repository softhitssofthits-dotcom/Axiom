# План доводки байткода и виртуальной машины до зафиксированного статуса

## Краткий итог

Цель плана - зафиксировать зрелый статус байткодного направления без скрытого выбора движка и без неявного отката на интерпретатор.

Решение по режимам исполнения изменено: `ExecutionMode.Auto` больше не развивается и должен быть удалён. В Axiom остаются только два явных режима запуска:

- `ExecutionMode.Bytecode` - основной режим исполнения текущей публичной поверхности языка через `BytecodeVm`;
- `ExecutionMode.Interpreter` - явный эталонный режим для сравнения, диагностики и регрессионных проверок.

Дальнейшее развитие языка должно вестись параллельно в двух линиях: новая возможность реализуется и проверяется в интерпретаторе и в байткодной VM. Скрытый откат больше не используется как рабочая стратегия.

## 1. Удалить `Auto` и зафиксировать два явных режима

### Код исполнения

- Удалить значение `Auto` из `ExecutionMode`.
- Сделать `ExecutionMode.Bytecode` значением по умолчанию в публичных контрактах запуска, где сейчас используется `Auto`.
- Убрать из `AxiomExecutionPipeline` автоматический выбор движка и логику отката на интерпретатор.
- Правила запуска после изменения:
  - `Bytecode` всегда пытается выполнить программу через `BytecodeVm`;
  - если байткодный путь не может выполнить программу, возвращается явная backend-ошибка;
  - `Interpreter` всегда запускает только интерпретатор.
- Удалить или обнулить больше не нужные признаки отката:
  - `UsedInterpreterFallback`;
  - `InterpreterFallbackReason`.
- Обновить все места, где результат запуска, трассировка или тесты сейчас ожидают эти поля.

### IDE

- Убрать пункт меню `Run -> Execution Mode -> Auto`.
- Оставить в меню только:
  - `Interpreter`;
  - `Bytecode`.
- Удалить команду `UseAutoExecutionModeCommand` и свойства состояния, связанные с выбранным `Auto`.
- Сделать `Bytecode` выбранным режимом по умолчанию при первом запуске IDE.
- При чтении старого состояния оболочки:
  - сохранённое значение `Auto` заменить на `Bytecode`;
  - неизвестное значение режима также нормализовать в `Bytecode`.
- Строка состояния и техническая трассировка запуска должны показывать выбранный явный режим и фактический движок без упоминания отката.

### Документы

- В `docs/ARCHITECTURE.md` зафиксировать:
  - `Auto` удалён как переходный режим;
  - режимы исполнения теперь только явные;
  - `Bytecode` - основной путь;
  - `Interpreter` - эталонный сравнительный путь.
- В `docs/BYTECODE_COVERAGE.md` заменить прежний вопрос про VM-first:
  - функциональный паритет фиксируется через явный `Bytecode`;
  - положительные `.axm`-примеры обязаны идти через `BytecodeVm` без исключений;
  - скрытого отката больше нет.
- В `README.md` обновить описание режимов запуска, если там есть упоминание `Auto`.
- В `docs/PLANS2.md` и `docs/WORKLOG3.md` записывать ход реализации append-only.

### Критерий готовности

- В коде нет `ExecutionMode.Auto`.
- В IDE нет пункта `Auto`.
- Старое сохранённое значение `Auto` мигрирует в `Bytecode`.
- `Bytecode` является основным режимом по умолчанию.
- Скрытого отката на интерпретатор нет.

## 2. Обновить тесты исполнения и IDE

### Тесты исполнения

- Все тесты, которые раньше полагались на режим по умолчанию `Auto`, перевести на явный режим.
- Для обычного пользовательского запуска использовать `ExecutionMode.Bytecode`.
- Для эталонного сравнения использовать явный `ExecutionMode.Interpreter`.
- Удалить тесты, которые проверяют `Auto` или автоматический откат.
- Сохранить централизованный аудит положительных `.axm`-примеров:
  - запуск каждого положительного примера из `samples/` в явном `ExecutionMode.Bytecode`;
  - фактический движок `ExecutionEngineKind.BytecodeVm`;
  - успешный статус;
  - временных исключений нет.

### Отрицательные примеры и диагностики

- Разделить отрицательные проверки по смыслу:
  - синтаксические ошибки;
  - семантические ошибки;
  - ошибки времени выполнения.
- Для синтаксических и семантических ошибок проверить оба явных режима:
  - `Interpreter`;
  - `Bytecode`.
- Для ошибок времени выполнения проверить паритет между `Interpreter` и `Bytecode`:
  - одинаковый `ExecutionStatus`;
  - одинаковый основной код диагностики;
  - наличие координаты диагностики, если она уже выдаётся;
  - для `Bytecode` фактический движок должен быть `BytecodeVm`.
- На первом шаге не требовать побуквенного совпадения текста диагностики.
- Источником отрицательных программ оставить существующий список из `AcceptanceProgramTests` и отрицательные `.axm`-примеры в `samples/`.

### Тесты IDE

- Обновить тесты сохранения и восстановления режима запуска:
  - новый режим по умолчанию - `Bytecode`;
  - старое сохранённое `Auto` нормализуется в `Bytecode`;
  - неизвестное значение режима нормализуется в `Bytecode`.
- Обновить тесты команд меню:
  - переключение только между `Interpreter` и `Bytecode`;
  - пункта `Auto` нет.
- Обновить тесты запуска программы из IDE:
  - выбранный режим передаётся в `ProgramRunService`;
  - по умолчанию передаётся `Bytecode`.

### Критерий готовности

- `Axiom.Execution.Tests` не содержит ожиданий `Auto`.
- `Axiom.Ide.Tests` не содержит ожиданий пункта меню или команды `Auto`.
- Положительные `.axm`-примеры продолжают проходить через `BytecodeVm`.
- Отрицательные `.axm`-примеры проверяют паритет двух явных режимов.

## 3. Зафиксировать функциональный паритет текущего языка

- После удаления `Auto` терминология в документах должна быть точной:
  - не “байткод и VM полностью закрыты навсегда”;
  - а “закрыт функциональный паритет `BytecodeVm` для текущей публичной поверхности языка”.
- Подтверждение паритета:
  - все положительные `.axm`-примеры из `samples/` проходят через `BytecodeVm`;
  - исключений для положительных примеров нет;
  - отрицательные примеры проверяют ожидаемые статусы и коды диагностик в двух явных режимах;
  - сборка решения чистая.
- Новые операторы, встроенные функции и изменения поведения языка в этом этапе не добавляются.
- Новые страницы `docs/manual/` и новые `.axm`-примеры не требуются, пока меняется только инфраструктура запуска и проверки.

## 4. Спроектировать и реализовать сериализацию `BytecodeModule`

Этап начинается только после удаления `Auto` и зелёных проверок двух явных режимов.

### Формат

- Ввести внутренний формат сохранения `BytecodeModule` в файл.
- На первом шаге не обещать совместимость формата между будущими версиями Axiom.
- Минимальный формат должен сохранять и восстанавливать:
  - заголовок модуля;
  - таблицу констант;
  - таблицу процедур;
  - таблицу глобальных значений;
  - таблицу встроенных функций;
  - инструкции;
  - отладочную информацию.

### Валидация и исполнение

- После чтения файла обязательно запускать `BytecodeModuleValidator`.
- Невалидный файл не должен исполняться.
- Сначала закрыть надёжность формата на уровне ядра, без подключения пользовательской функции в IDE.

### Тесты

- Добавить тесты в байткодном слое:
  - круговой проход: скомпилировать программу, сохранить модуль, прочитать модуль, выполнить через VM;
  - сохранение и восстановление отладочной информации;
  - отказ на повреждённом заголовке;
  - отказ на неподдержанной версии;
  - отказ на повреждённой таблице.

### Критерий готовности

- Байткодный модуль можно сохранить, прочитать, провалидировать и выполнить с тем же результатом, что и модуль в памяти.

## 5. Подготовить основу отладки VM

Этап не блокирует признание функционального паритета текущего языка.

- Использовать уже существующие `BytecodeDebugInfo` и карты исходных инструкций.
- Сначала добавить внутренний API для получения текущей исходной позиции VM.
- Затем отдельно проектировать:
  - точки останова;
  - пошаговое исполнение;
  - остановку по ошибке;
  - интеграцию в IDE.
- Интеграцию в IDE делать только после устойчивых тестов слоя выполнения.

### Критерий готовности

- Есть внутренняя, тестируемая основа для связи текущей инструкции VM с исходной позицией.
- Пользовательский отладчик остаётся отдельной будущей задачей.

## 6. Подготовить отчёт по производительности

Этап не должен превращаться в жёсткий тест на миллисекунды.

- Добавить повторяемый набор сравнительных сценариев:
  - выражения;
  - циклы;
  - функции;
  - массивы;
  - строки;
  - файлы.
- Измерять `Interpreter` и `BytecodeVm` одинаковым входом.
- Результат фиксировать как отчёт, а не как обязательный порог прохождения тестов.
- Документировать методику, чтобы будущие сравнения были воспроизводимыми.

### Критерий готовности

- Есть первый воспроизводимый отчёт сравнения интерпретатора и VM.
- Производительность не блокирует функциональный статус байткода.

## Проверки

После удаления `Auto` и обновления тестов выполнить последовательно:

```powershell
dotnet test tests\Axiom.Execution.Tests\Axiom.Execution.Tests.csproj --no-restore -m:1 -p:UseSharedCompilation=false --logger "console;verbosity=minimal"
dotnet build Axiom.sln --no-restore -m:1 -p:UseSharedCompilation=false
dotnet test Axiom.sln --no-restore -m:1 -p:UseSharedCompilation=false --logger "console;verbosity=minimal"
```

После этапа сериализации дополнительно выполнить:

```powershell
dotnet test tests\Axiom.Bytecode.Tests\Axiom.Bytecode.Tests.csproj --no-restore -m:1 -p:UseSharedCompilation=false --logger "console;verbosity=minimal"
```

Все `dotnet`-команды выполнять последовательно, без параллельной записи в общий `obj`.

## Принятые решения

- `Auto` больше не является частью целевой архитектуры исполнения.
- `Bytecode` становится основным режимом по умолчанию.
- `Interpreter` остаётся явным режимом для сравнения и проверки.
- Скрытый откат на интерпретатор запрещается как рабочая стратегия.
- При будущих расширениях языка интерпретатор и байткодная VM развиваются параллельно.
- Новое поведение языка в этом плане не добавляется; план меняет инфраструктуру запуска, проверки и дальнейшей стабилизации.
