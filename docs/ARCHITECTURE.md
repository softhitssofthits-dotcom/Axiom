# Архитектура проекта

## 1. Общий подход

Проект строится по принципу:
- сначала ядро языка;
- затем интерпретатор;
- затем полноценная IDE;
- затем последовательное расширение языка и среды до готового продукта.

Axiom не обязан быть полным клоном QuickBASIC, но может брать из BASIC-семейства полезные решения. Компиляция в машинный код остаётся отдельным архитектурным направлением, а не заменой текущего интерпретатора без явного решения.

## 2. Базовый стек

- язык реализации: C#
- платформа: .NET
- формат решения: `Axiom.sln`
- IDE продукта: настольное приложение
- выбранный графический стек стартового IDE-проекта: WPF
- тесты: .NET test projects
- редакторский компонент для M6: AvalonEdit

На текущем этапе каркас создан на SDK `.NET 10.0.x`, поэтому библиотечные проекты таргетят `net10.0`, а IDE — `net10.0-windows`.

## 3. Структура solution

Фактическая структура на этапе M0-M6:

```text
Axiom.sln
src/
  Axiom.Core/
  Axiom.Lexing/
  Axiom.Syntax/
  Axiom.Parsing/
  Axiom.Semantics/
  Axiom.Runtime/
  Axiom.Execution/
  Axiom.Ide/
  Axiom.Ide.SmokeHarness/

tests/
  Axiom.Lexing.Tests/
  Axiom.Parsing.Tests/
  Axiom.Semantics.Tests/
  Axiom.Runtime.Tests/
  Axiom.Execution.Tests/
  Axiom.Ide.Tests/
```

Локальные результаты сборки не считаются частью этой структуры исходников: начиная с правил чистоты рабочей копии после v0.1.10 все `bin/`/`obj/` и прочие служебные артефакты сборки должны уходить в централизованный скрытый каталог `.artifacts/` в корне репозитория, а не накапливаться внутри `src/` и `tests/`.

## 4. Назначение слоёв

### 4.1 Axiom.Core
Общие сущности, не зависящие от интерфейса и логики выполнения:
- `TextSpan`
- `TextLocation`
- `Diagnostic`
- `DiagnosticBag`
- общие перечисления и базовые типы

### 4.2 Axiom.Lexing
Лексический анализ:
- `TokenKind`
- `Token`
- `Lexer`
- разбор комментариев, строк, чисел, ключевых слов и операторов

### 4.3 Axiom.Syntax
Синтаксическое дерево:
- `SyntaxKind`
- `SyntaxNode`
- `SyntaxToken`
- `ExpressionSyntax`
- `StatementSyntax`
- `MemberSyntax`
- `ProgramSyntax`
- узлы программы, деклараций, выражений и операторов

`Syntax` хранит собственные `SyntaxToken`, чтобы дерево сохраняло ключевые токены для диагностики и будущих IDE-функций, но не зависело напрямую от `Axiom.Lexing`.

### 4.4 Axiom.Parsing
Парсер:
- преобразование последовательности токенов в AST
- обработка приоритетов операций
- синтаксические диагностические сообщения
- восстановление после синтаксических ошибок, чтобы не останавливаться на первой проблеме
- возврат `ProgramSyntax` как единой точки входа в синтаксическое дерево

### 4.5 Axiom.Semantics
Семантический анализ:
- таблица символов
- области видимости
- `TypeSymbol`
- `VariableSymbol`
- `FunctionSymbol`
- `ParameterSymbol`
- `BoundScope`
- `Binder`
- `BoundProgram` и минимальный bound tree
- связывание идентификаторов
- проверка типов
- подготовка модели к интерпретации

Начиная с M7.1 связанная модель также хранит `TextLocation` на `BoundNode`, чтобы диагностические сообщения времени выполнения могли стабильно ссылаться на исходный код без знания деталей синтаксического анализатора в слое выполнения или интерфейсе.

Рекомендуемая внутренняя структура слоя:
- `Symbols/`
- `Scopes/`
- `BoundNodes/`
- `Binding/`

Дополнительное правило для `Binding/`:
- `Binder.cs` держит только корневую композицию binder, общее состояние и запуск `BindProgram`;
- логика должна раскладываться по профильным partial-файлам, а не возвращаться в общий монолит;
- текущая рабочая раскладка binder включает `Binder.Expressions.cs`, `Binder.InvocationExpressions.cs`, `Binder.Statements.cs`, `Binder.DeclarationStatements.cs`, `Binder.IoStatements.cs`, `Binder.ControlFlowStatements.cs`, `Binder.SelectCaseStatements.cs`, `Binder.Diagnostics.cs`, `Binder.Declarations.cs`, `Binder.Routines.cs`, `Binder.TypeResolution.cs`, `Binder.ScopeHelpers.cs`, `Binder.SyntaxHelpers.cs` и компактный `Binder.Helpers.cs` для оставшихся общих числовых вспомогательных методов.

### 4.6 Axiom.Runtime
Исполнение программы:
- хранение окружения и областей видимости
- стек вызовов
- значения переменных
- `IRuntimeHost` как абстракция ввода/вывода
- `RuntimeResult` как результат исполнения
- `Interpreter` как исполнитель уже связанного `BoundProgram`
- встроенные функции
- исполнение операторов и выражений
- диагностические сообщения времени выполнения

Рекомендуемая внутренняя структура слоя:
- `Values/`
- `Environment/`
- `Host/`
- `Execution/`

### 4.7 Axiom.Execution
Интеграционный координирующий слой поверх уже готовых слоёв:
- единая точка входа `parse -> bind -> execute`
- единая модель результата выполнения
- различение синтаксических, семантических ошибок и ошибок времени выполнения
- граница взаимодействия с внешней средой для ввода, вывода и диагностики
- чистая точка интеграции для будущего `Axiom.Ide`

Рекомендуемая внутренняя структура слоя:
- `Requests/`
- `Results/`
- `Hosting/`
- `Pipeline/`

### 4.8 Axiom.Ide
Настольная IDE в духе Thonny (базовый вариант после переработки):
- редактор кода с вкладками документов
- левая панель `File Manager` (дерево дисков, папок и файлов)
- нижняя панель с вкладками `Output` и `Diagnostics`
- строка состояния с позицией курсора, путём, признаком несохранённых изменений и состоянием запуска
- компактная панель инструментов (`New`, `Open`, `Save`, `Run`, `Find`)
- полноценное меню (File, Edit, Search, Run, View, Help)
- запуск программы из IDE через `ProgramRunService -> AxiomExecutionPipeline`
- консольный `INPUT` внутри журнала `Output`
- подсветка синтаксиса через централизованное описание подсветки AvalonEdit
- переход к месту в исходном тексте из диагностических сообщений
- хранение недавних файлов для `File > Open Recent`
- светлая тема, близкая к Thonny

Фактическая внутренняя структура после переработки:
- `Commands/` — команды интерфейса (команды-посредники и редакторские команды)
- `Documents/` — модель вкладки документа и служба рабочей области документов
- `Editor/` — вспомогательный слой привязки AvalonEdit и описание подсветки
- `Editor/Highlighting/` — централизованное описание подсветки синтаксиса
- `Editor/Navigation/` — безопасный переход редактора к месту диагностического сообщения
- `Files/` — модель представления файловой панели и сервис дерева файлов
- `Output/` — модель представления нижней панели вывода и диагностики
- `Resources/` — отдельные словари ресурсов по зонам ответственности (цвета и кисти, отступы и размеры, меню и панель инструментов, панели и вкладки, строка состояния)
- `Services/Documents/` — граница открытия и сохранения документов редактора: по умолчанию редактируемый режим для файловых форматов, блокировка `.exe`
- `Services/Execution/` — адаптер службы запуска вне пользовательского интерфейса поверх `Axiom.Execution`
- `Services/Input/` — граница на стороне IDE для консольного `INPUT` в `Output`
- `Services/Persistence/` — хранение недавних файлов для `File > Open Recent`
- `Services/Prompts/` — запросы вида Сохранить / Не сохранять / Отмена и другие запросы уровня оболочки
- `Status/` — модель представления строки состояния
- `ViewModels/` — корневая модель представления оболочки (`MainWindowViewModel`) и композиция дочерних моделей представления

Код окна должен оставаться тонким: оболочка интерфейса инициализируется через `App`, а логика запуска, работы с файлами и диагностики не должна уходить в `MainWindow.xaml.cs`.

Для автоматизированного WPF smoke-pass рядом с IDE добавлен отдельный проект `Axiom.Ide.SmokeHarness`:
- harness запускает собранный `Axiom.Ide.exe`, готовит временную workspace и управляет shell через `System.Windows.Automation`;
- для команд, которые оказались нестабильны через обычный UIA-вызов меню, `MainWindow.xaml.cs` держит узкий `WM_APP` automation bridge только для smoke harness (`Find/Replace`, `Run`, `Close Tab`, toggle shell panes);
- текущий automation baseline покрывает не только open/run/find shell-сценарии, но и context-menu/file-operations в `File Manager`: показ скрытых файлов, создание файла и каталога, переименование, копирование, перенос, удаление и `Find/Replace` в режиме `Regex`;
- harness умеет принимать явный путь к собранному `Axiom.Ide.exe`, чтобы живой WPF smoke можно было прогонять и по изолированной build-папке, не упираясь в заблокированный стандартный apphost;
- bridge не переносит бизнес-логику в harness: все действия всё так же выполняются через уже существующие viewmodel-команды и shell-состояние IDE.

Архитектура оболочки базируется на композиции:
- `MainWindowViewModel` — корневая модель представления оболочки, координирует дочерние модели представления;
- shell-level внешние действия (например, `Help -> Open Manual` и открытие файла во внешнем приложении) проходят через узкий `IExternalNavigationService`, чтобы UI-команды не были жёстко привязаны к прямому `Process.Start` и оставались тестируемыми;
- `DocumentTabViewModel` — одна вкладка редактора (FilePath, DisplayName, SourceText, IsDirty, IsUntitled, IsReadOnly);
- `FilesPaneViewModel` — состояние левой файловой панели (узлы, выбор, видимость);
- `BottomPaneViewModel` — вкладки `Output` / `Diagnostics` и состояние активной нижней вкладки;
- `StatusBarViewModel` — текущая позиция курсора, путь, признак несохранённых изменений, состояние запуска и переключатель видимости строки состояния.

Сценарий работы с документами:
- `Open...` открывает файл в новой вкладке; уже открытый файл просто активирует существующую вкладку без дублирования;
- `Save` для новых безымянных документов ведёт в `Save As...`;
- `Save All` сохраняет все вкладки с несохранёнными изменениями;
- `Close Tab` для вкладки с несохранёнными изменениями показывает запрос: `Save` / `Discard` / `Cancel`;
- кнопка закрытия (`X`) в заголовке каждой вкладки закрывает именно этот документ через тот же сценарий `Save` / `Discard` / `Cancel`;
- `Exit` при наличии несохранённых вкладок запускает общий сценарий `Save` / `Discard` / `Cancel` для нескольких документов;
- если последняя вкладка закрыта, оболочка сразу создаёт новую пустую вкладку;
- восстановление сеанса в этом этапе не вводится.

Файловая панель `File Manager`:
- `View -> File Manager` управляет не только видимостью дерева, но и всей компоновкой оболочки: при выключении панели её колонка и разделитель визуально исчезают, а область редактора занимает всю ширину;
- при включённой нижней панели (`Output/Diagnostics`) `File Manager` живёт только в верхнем ряду редактора и не перекрывает нижнюю область;
- вертикальный разделитель между `File Manager` и областью редактора тоже ограничен верхним рядом редактора и не продолжается в нижнюю панель;
- корневой уровень панели строится по доступным дискам (режим файлового менеджера вместо режима только текущего каталога);
- дерево папок раскрывается с отложенной загрузкой дочерних узлов при расширении;
- порядок внутри каталога: сначала папки, потом файлы;
- раскрывающий маркер дерева использует знак `+/-`, а не треугольный индикатор;
- для узлов используются отдельные значки папки и файла;
- щелчок по файлу открывает его во вкладке через существующий сценарий работы с документами;
- все открываемые через файловую панель файлы по умолчанию идут в редактируемом режиме (включая `.axm`, `.txt`, `.md`, `.json`, `.css` и другие текстовые форматы);
- `.exe` блокируются и не открываются в редакторе;
- панель можно скрыть как через `View -> File Manager`, так и через отдельную кнопку `X` в заголовке панели;
- дерево файловой панели использует автоматические полосы прокрутки по вертикали и горизонтали;
- у `TreeViewItem` файловой панели есть контекстное меню узла; правый щелчок сначала переводит выбор на соответствующий узел и не должен запускать обычное открытие по щелчку;
- контекстное меню поддерживает команды открытия, перехода и просмотра свойств (`Открыть в Axiom IDE`, `Перейти в`, `Открыть во внешнем приложении по умолчанию`, `Показать скрытые файлы`, `Свойства`);
- файловые операции (`Новый файл...`, `Новый каталог...`, `Вырезать`, `Скопировать`, `Вставить`, `Переименовать`, `Удалить`) идут через отдельный `IFileOperationsService` и запросы оболочки, а не через код окна;
- перестроение дерева после файловых операций восстанавливает состояние раскрытия и выбор по состоянию, привязанному к пути, чтобы обновление не схлопывало ветку пользователя обратно до корневого диска;
- сами узлы дерева (`FileTreeNode`) должны быть моделью с уведомлениями, чтобы WPF стабильно синхронизировал `IsExpanded` и другие свойства оболочки между интерфейсом и моделью представления;
- переключатель скрытых файлов реализован внутри `FilesPaneViewModel` и `IFileTreeService` и перезагружает дерево без отдельной кнопки обновления;
- выбранный узел оформлен контрастно: текст и значок используют белый цвет поверх акцентного фона;
- без отдельной модели проекта, множественного выбора и перетаскивания файлов мышью.

Поведение запуска, вывода и диагностики:
- `Run` работает для активной вкладки;
- нижняя панель автоматически переключается на `Output` при запуске;
- при любой ветке ошибки (синтаксической, семантической, времени выполнения или инфраструктурной) нижняя панель переключается на `Diagnostics` и получает фокус;
- выбор строки в `Diagnostics` переводит активный `AvalonEdit` к исходной позиции этой диагностики;
- INPUT остаётся внутри журнала Output и получает фокус автоматически;
- `View -> Output` и `View -> Diagnostics` работают как переключатели видимости с флажком для вкладок нижней панели;
- в заголовках вкладок `Output` и `Diagnostics` есть кнопки закрытия `X`;
- если вкладка скрыта вручную, следующий `Run` открывает `Output`, а любой запуск с ошибкой открывает `Diagnostics` автоматически;
- когда обе вкладки скрыты, нижняя панель и её разделитель полностью схлопываются в разметке;
- нижняя панель поддерживает ручное изменение высоты через вертикальный `GridSplitter`;
- Output и Diagnostics — общие панели оболочки, а не отдельные панели для каждой вкладки;
- параллельные запуски не поддерживаются;
- во время выполнения или `INPUT` запрещены повторный `Run` и разрушающие действия над документами.

Синхронизация оболочки и интерфейса:
- `MainWindow.xaml.cs` остаётся тонким кодом окна, но отвечает за чисто интерфейсную синхронизацию, которую неудобно держать в модели представления:
  - подписка на события каретки активного `AvalonEdit` и передача `Ln / Col` в `StatusBarViewModel`;
  - реакция на запросы перевода фокуса от `BottomPaneViewModel` для `Output`, `Diagnostics` и встроенной строки ввода.
  - обработка выбора строки диагностики и вызов вспомогателя навигации редактора;
  - настройка мягкой подсветки текущей строки в `AvalonEdit`, чтобы после перехода к ошибке активная строка была визуально заметна.

Поведение `INPUT` (сохранённый базовый вариант):
Слой выполнения передаёт в `IInputProvider` только минимальный `InputRequest` (текст приглашения и количество ожидаемых значений), а `Axiom.Ide` ведёт `INPUT` через консольный журнал внутри `Output`: отдельные диалоговые окна и панели для ввода не используются, активная строка ввода подтверждается по `Enter`, а потоковый вывод идёт через ту же консольную службу на стороне IDE.

Подсветка синтаксиса:
Категории токенов и палитра определяются в одном централизованном описании и ресурсе подсветки: отдельные категории для ключевых слов, строк, чисел, комментариев, имён типов и встроенных функций; семантическая раскраска и встроенные в текст диагностические сообщения не входят.

Визуальная система:
вместо одного растущего `ShellResources.xaml` используются отдельные словари ресурсов: цвета и кисти, отступы и размеры, стили меню и панели инструментов, стили панелей и вкладок, стили строки состояния. Светлая тема близка к Thonny; `Segoe UI` используется для элементов оболочки; `Consolas` или `Cascadia Mono` — для редактора и вывода; без тяжёлых `GroupBox`.

Сохранение состояния:
Сохранение состояния оболочки строго ограничено, но теперь включает также состояние IDE: недавние файлы, последний использованный каталог, видимость `File Manager` и `WindowState` (`Normal` / `Maximized` / `Minimized`); сериализация изолирована в отдельной службе сохранения состояния без универсальной системы пользовательских настроек, восстановления сеанса или расширенного состояния оболочки.

## 5. Границы между слоями

Правила зависимостей:
- `Core` не зависит ни от чего выше;
- `Lexing` зависит только от `Core`;
- `Syntax` зависит только от `Core`;
- `Parsing` зависит от `Core`, `Lexing`, `Syntax`;
- `Semantics` зависит от `Core`, `Syntax`;
- `Runtime` зависит от `Core`, `Syntax`, `Semantics`;
- `Execution` зависит от `Core`, `Syntax`, `Parsing`, `Semantics`, `Runtime`;
- `Ide` зависит от `Execution` как от основной границы запуска; прямое знание о внутренних деталях `Parsing`, `Semantics` и `Runtime` на стороне интерфейса не допускается.

IDE не должна содержать доменную логику языка, кроме вызова сервисов ядра и отображения результатов.
Предпочтительная граница запуска для IDE: `Ide -> Execution -> Parsing/Semantics/Runtime`.
Это конкретизировано как `MainWindowViewModel -> IProgramRunService -> AxiomExecutionPipeline`.

В рамках переработки IDE архитектура оболочки базируется на композиции дочерних моделей представления и отдельных служб по зонам ответственности (рабочая область документов, файловая панель, запросы, сохранение состояния), при этом граница выполнения остаётся прежней.

## 6. Обязательное правило против монолитных файлов

Для фронтенда языка в этом репозитории действует обязательное архитектурное правило: монолитные файлы запрещены.

Требования:
- лексический анализатор, синтаксическое дерево, синтаксический анализатор, связыватель и слой выполнения должны оставаться разделёнными по ответственности;
- синтаксический анализатор не должен смешиваться с семантическим анализом;
- семантический анализ не должен смешиваться с выполнением программы;
- при росте файла или смешении обязанностей код должен быть сначала разбит на отдельные файлы или части файла по ответственности, и только потом можно продолжать добавление функциональности;
- разнос по папкам и отдельным файлам считается допустимым и рекомендуемым способом поддерживать архитектуру фронтенд-слоёв.

Рекомендуемая структура фронтенд-слоёв:
- `Syntax/Expressions`
- `Syntax/Statements`
- `Syntax/Declarations`
- `Parser/Expressions`
- `Parser/Statements`
- `Parser/Declarations`
- `Parser/Helpers`
- `Parser/Recovery`

Если конкретный подслой пока маленький, допускается стартовать с нескольких компактных файлов, но без объединения несвязанных обязанностей в один растущий файл.

Для слоя выполнения применяется тот же обязательный принцип:
- модель значений, окружение, абстракция внешней среды и само выполнение должны оставаться разделёнными по ответственности;
- `Runtime` не должен смешиваться с `Parsing` или связыванием в `Semantics`;
- абстракция внешней среды обязана оставаться независимой от интерфейса, чтобы IDE могла подключаться к `Runtime` без переписывания интерпретатора.

## 7. Основные архитектурные решения

### 7.1 Сначала интерпретатор
Текущая архитектура исполняет язык интерпретатором.

Причины:
- быстрее доказать жизнеспособность языка;
- проще отладка;
- проще встроить в IDE;
- меньше риск преждевременного усложнения внутренней части реализации.

### 7.2 Документы — источник правды
Спецификация и архитектура должны обновляться вместе с изменениями в коде.

### 7.3 Ядро языка отдельно от IDE
Язык должен быть пригоден к использованию независимо от графического интерфейса, чтобы позже можно было сделать консольный запуск, тестовый раннер или другой хост.

### 7.4 Минимальные зависимости
Нельзя тащить тяжёлые зависимости без практической необходимости.

## 8. Диагностики

Все уровни должны возвращать структурированные диагностические сообщения:
- код ошибки;
- сообщение;
- координаты в тексте;
- длина диапазона.

Минимальная схема кодов:
- `MB0xxx` — лексический анализ
- `MB1xxx` — синтаксический анализ
- `MB2xxx` — семантический анализ
- `MB3xxx` — время выполнения

На этапе M0 базовый контракт диагностики зафиксирован типами `TextSpan`, `TextLocation`, `Diagnostic`, `DiagnosticBag` в `Axiom.Core`.

Начиная с M7.1 привязка ошибок времени выполнения к исходному коду строится так:
- синтаксический анализатор создаёт `SyntaxToken` с `TextLocation`;
- связыватель переносит нужные координаты синтаксических узлов в `BoundNode.Location`;
- слой выполнения использует `BoundNode.Location` при формировании диагностик `MB3xxx`;
- конвейер выполнения и IDE передают эти диагностики дальше без дополнительного вычисления исходных координат в интерфейсном слое.

## 9. Тестовая стратегия

На ранних этапах тесты важнее графического интерфейса.

Приоритеты тестов:
1. лексический анализ
2. синтаксический анализ
3. семантический анализ
4. время выполнения
5. проверочный запуск IDE

Минимальный набор:
- корректная токенизация;
- корректный разбор выражений и блоков;
- ошибки при неверном синтаксисе;
- ошибки при несовместимых типах;
- корректное выполнение простых программ.

### 9.1 Запускаемые примеры поведения языка

Кроме модульных и интеграционных тестов проект поддерживает отдельные запускаемые примеры поведения языка в формате `.axm`.

Назначение:
- ручная проверка поведения языка через `Axiom.Ide`;
- короткие проверочные сценарии для новых операторов, встроенных функций и изменений семантики;
- репозиторный слой ручной регрессионной проверки, который дополняет автоматические тесты, а не заменяет их.

Обязательная структура для новых примеров поведения языка:

```text
samples/
  operators/<operator-name>/
  functions/<function-name>/
  smoke/
  control-flow/<feature-name>/
  expressions/<feature-name>/
```

Правила размещения:
- каждый оператор получает собственную подпапку, например `samples/operators/print/`, `samples/operators/input/`, `samples/operators/if/`;
- каждая встроенная функция получает собственную подпапку, например `samples/functions/len/`, `samples/functions/left/`, `samples/functions/val/`;
- смешанные примеры поведения кладутся либо в наиболее подходящую основную подпапку, либо в `samples/smoke/`, если это интеграционный сценарий;
- плоская свалка `.axm` файлов в одной общей папке для новых примеров поведения языка запрещена.

Правила содержимого:
- один файл = одна основная проверяемая возможность или небольшой связанный набор;
- пример должен быть коротким, предметным и запускаться вручную в IDE;
- при необходимости в начале файла допускается краткий комментарий об ожидаемом поведении;
- запускаемые примеры не заменяют модульные и интеграционные тесты: языковая задача считается завершённой только при наличии и автоматических тестов, и запускаемого `.axm`-примера.

Соглашения по именам:
- имена файлов короткие, читаемые и привязаны к поведению;
- для `PRINT`: `basic_expression.axm`, `empty_print.axm`, `separator_semicolon.axm`, `separator_comma.axm`, `mixed_list.axm`;
- для `INPUT`: `single_variable.axm`, `multiple_variables.axm`, `prompt_semicolon.axm`, `prompt_comma.axm`;
- дымовые и интеграционные сценарии живут отдельно в `samples/smoke/`.

Исторические материалы ручной проверки из раннего регрессионного слоя могут временно оставаться в `samples/acceptance/` до отдельной миграции, но все новые примеры поведения языка обязаны следовать структуре выше.

## 11. Конвейер форматирования IDE

Для построчного форматирования в IDE используется отдельный конвейер оболочки, который не вмешивается в `Axiom.Parsing`, `Axiom.Semantics` и `Axiom.Runtime`.

Принципы:
- `MainWindow.xaml.cs` запускает форматирование на событиях перехода между строками редактора: уход каретки на другую строку и потеря фокуса клавиатуры;
- форматирование применяется только к одной строке и должно быть защищено от повторного входа, чтобы замена текста в `AvalonEdit` не запускала вторичное форматирование;
- включение и выключение базового режима `Classic` живёт в модели представления оболочки (`IsClassicFormattingEnabled`);
- ядро форматирования вынесено в `ICodeFormattingService` и `AxiomCodeFormattingService`, чтобы привязка к событиям интерфейса и логика нормализации текста не смешивались;
- словарь для перевода ключевых слов в верхний регистр берётся из `Axiom.xshd` через `AxiomHighlightingVocabulary`, а не из второго жёстко заданного списка IDE, чтобы подсветка синтаксиса и форматирование развивались согласованно;
- режим `Modern` должен оставаться следующим слоем над той же сервисной границей, без переписывания событийного контура редактора.

## 12. Трассировка диагностики IDE

Для расследования проблем на поверхности IDE введён отдельный слой трассировки, не связанный с контрактами `Axiom.Parsing` и `Axiom.Runtime`.

Принципы:
- граница оформлена через `IIdeTraceService`;
- `NullIdeTraceService` используется как безопасная пустая реализация для модульных тестов и мест, где трассировка явно не нужна;
- `FileIdeTraceService` пишет журнал сеанса с добавлением в конец в каталог `Logs` под `AppContext.BaseDirectory`;
- корень композиции в `App.xaml.cs` создаёт службу трассировки на старте и прокидывает её в:
  - `ProgramConsoleService`;
  - `ProgramRunService`;

## 13. Сценарий сохранения перед запуском

Правило оболочки для выполнения программы:
- `Run` не опирается на текущий несохранённый буфер редактора;
- перед выполнением `MainWindowViewModel` гарантирует, что активный документ сохранён;
- после успешного подтверждённого сохранения IDE повторно читает файл через `IDocumentFileService.LoadDocument(...)` и только затем передаёт текст в `IProgramRunService`.

## 14. Выбор стиля форматирования IDE

- оболочка хранит активный режим форматирования IDE как выбранный `CodeFormattingStyle`, а не как жёстко зашитый переключатель только для Classic;
- `MainWindowViewModel` публикует выбранный стиль и команды переключения `Classic` / `Modern`;
- `MainWindow.xaml.cs` применяет построчное форматирование через общий `ICodeFormattingService`, передавая текущий выбранный стиль.

Дополнение:
- `ICodeFormattingService` теперь обслуживает и форматирование всего документа, чтобы оболочка могла переоформлять весь активный `.axm`-документ без зависимости от событийного контура `AvalonEdit`;
- решение о применении форматирования всего документа принимается на уровне `MainWindowViewModel` и зависит от типа открытого документа: участвуют только редактируемые вкладки `.axm`;
- смена активной вкладки использует ту же сервисную границу, поэтому построчное и полное форматирование документа остаются согласованными по правилам пробелов и регистра букв.

## 15. Конвейер структурного редактирования IDE

Для автозавершения блоков и структурного отступа в `Axiom.Ide` введён отдельный слой на стороне редактора, не зависящий от `Parsing` и `Runtime`.

Принципы:
- оболочка по-прежнему остаётся источником логики редакторского поведения: структурное автозавершение не переносится в `Axiom.Parsing`, `Axiom.Semantics` или `Axiom.Runtime`;
- в `Editor/StructuralEditing/` живёт отдельный `AxiomBlockEditingService`, который работает поверх `AvalonEdit` `TextDocument` и знает только про построчное поведение IDE;
- служба вызывается из `MainWindow.xaml.cs` на событиях перехода между строками рядом с уже существующим конвейером построчного форматирования;
- `AxiomBlockEditingService` отвечает за:
  - распознавание поддерживаемых открывающих и закрывающих строк блока;
  - проверку, что соответствующая закрывающая строка ещё не существует ниже по документу;
  - вставку строки тела и закрывающей строки для новых блоков;
  - вычисление структурного отступа для пустой следующей строки;
  - сохранение каретки на корректном рабочем уровне после вставок со стороны IDE;
- приведение закрывающих строк к нужному регистру делегируется существующему `ICodeFormattingService`, чтобы стили `Classic` и `Modern` оставались согласованными;
- модульное тестирование основной логики редактирования блоков идёт без автоматизации интерфейса, напрямую через `TextDocument`, а подключение в коде окна страхуется IDE-тестами на уровне исходников и интеграционными проверками оболочки.

## 16. Плановая модель блочной видимости языка

Языковая спецификация закрепляет переход к строгой C#-подобной модели видимости:
- отдельные области видимости должны существовать не только у уровня файла и `Sub` / `Function`, но и у блоков операторов;
- `If` / `ElseIf` / `Else`, `For`, `While`, `Do ... Loop`, `Case`, `Case Else` должны открывать собственные блочные области видимости;
- управляющая переменная `FOR` рассматривается как локальное имя области видимости самого цикла, а не как имя, которое обязано заранее жить во внешней области видимости;
- язык работает в режиме, эквивалентном всегда включённому `Option Explicit`: неявные локальные переменные по присваиванию не поддерживаются.

Технические следствия для будущей реализации:
- связыватель должен перейти от двухуровневой модели к вложенным `BoundScope` для блоков операторов;
- диагностики должны различать:
  - повторное объявление в той же самой области видимости;
  - недоступность имени после выхода из блока;
  - недопустимое затенение имени из внешних локальных областей видимости;
- слой выполнения должен поддержать время жизни блочных `Dim` / `Const` внутри блоков операторов, а не только хранение на уровне процедуры или функции.

## 17. Реализованная модель выполнения с блочной видимостью

Решение из спецификации теперь реализовано в ядре языка.

Фактическая схема:
- связыватель использует вложенные `BoundScope` не только для уровня файла и уровня процедуры или функции, но и для блоков операторов;
- дочерняя область видимости открывается для:
  - `If`-ветви;
  - каждой `ElseIf`-ветви;
  - `Else`;
  - `While`;
  - `Do ... Loop`;
  - каждого `Case`;
  - `Case Else`;
  - `For`, включая его управляющую переменную;
- управляющая переменная `FOR` больше не ищется во внешней области видимости:
  - символ создаётся самой строкой `FOR`;
  - живёт только внутри данного цикла;
  - после `NEXT` становится недоступен;
- связыватель различает:
  - повторное объявление в текущей области видимости;
  - запрещённое затенение имени из внешней области видимости;
  - обычное использование неизвестного имени после выхода из блока.

Модель выполнения:
- интерпретатор ведёт стек `RuntimeScope`, а не только область видимости кадра вызова процедуры или функции;
- вход в `If`/`ElseIf`/`Else`, `While`, `Do`, `Case`, `Case Else` и каждую итерацию тела `For` создаёт отдельную дочернюю область видимости времени выполнения;
- область видимости цикла `FOR` живёт дольше, чем область видимости тела отдельной итерации:
  - управляющая переменная хранится в области видимости самого цикла;
  - `Dim` внутри тела цикла создаётся заново на каждой итерации и исчезает после завершения этой итерации;
- вызов `Sub`/`Function` продолжает стартовать с собственной области видимости процедуры или функции поверх глобальной области и не наследует блочные локальные переменные вызывающей стороны.

## 18. Понятные пользователю диагностики блочной видимости

- связыватель централизует человекопонятные метки контекста объявления для блочных областей видимости в одном месте, а сами сообщения строятся через единый шаблон семантической диагностики;
- это решение должно использоваться не только для уже существующих `IF` / `ELSEIF` / `ELSE`, `FOR`, `WHILE`, `DO`, `CASE`, `CASE ELSE`, но и для любых будущих блочных конструкций;
- если в язык добавляется новая блочная конструкция с собственной областью видимости, набор изменений обязан одновременно:
  - зарегистрировать её метку контекста объявления;
  - подключить эту метку к диагностике затенения;
  - обновить автоматические тесты на текст диагностических сообщений для нового контекста.
## 19. Каталог встроенных функций на основе метаданных

- Встроенные функции больше не должны разрастаться через разовые строковые ветвления в связывателе.
- В `Axiom.Semantics` для встроенных функций введены:
  - `BuiltinFunctionId` как стабильный идентификатор для слоя выполнения и связывателя;
  - `BuiltinFunctionDescriptor` как описание имени, арности, параметров и правил связывания с определением типа результата;
  - расширенный `FunctionSymbol`, который умеет хранить канонический идентификатор встроенной функции.
- Связыватель больше не ограничивается точечными особыми случаями для отдельных встроенных функций. Для числовых встроенных функций используется единый путь на основе описателей:
  - сохранить числовые аргументы без изменения;
  - повысить числовые аргументы до более широкого типа;
  - привести числовые аргументы к `DOUBLE`;
  - вычислить итоговый тип результата на этапе связывания и создать готовый `FunctionSymbol` встроенной функции.
- Такой подход позволяет оставлять `BoundCallExpression` простым: после связывания он уже содержит точную сигнатуру встроенной функции, готовую к выполнению, с итоговым `ReturnType`.
- Выбор встроенной функции во время выполнения должен идти по `BuiltinFunctionId`, а не по строковому имени.
- Вспомогательные реализации встроенных функций в слое выполнения разделяются по зонам ответственности на части файла, чтобы не превращать `Interpreter` в монолит:
  - строковые функции и функции преобразования;
  - числовые и математические функции;
  - общее выполнение выражений и операторов.
- Каталог встроенных функций в `Axiom.Semantics` должен расти тематическими файлами, а не одним бесконечно растущим списком:
  - отдельные части файла для базовых строковых функций;
  - отдельные части файла для группы обрезки пробелов;
  - отдельные части файла для форматирующих и заполняющих строковых функций;
  - по тому же принципу в будущем выносятся файловые, регулярные и другие семейства встроенных функций.
- Для встроенных функций допускается несколько сигнатур у одного публичного имени, но это специальное правило именно встроенного каталога:
  - связыватель подбирает нужную форму по имени, числу аргументов и их типам;
  - пользовательские `SUB` и `FUNCTION` при этом не получают общую перегрузку имён.

## 20. Локальные вложенные процедуры и функции с лексическим захватом внешних данных

Локальные `SUB` и `FUNCTION` реализованы как отдельный слой поверх уже существующей модели процедур и функций с лексическим захватом внешних локальных переменных и параметров.

Ключевые решения:
- парсер допускает локальные объявления процедур и функций только в прямом теле `SUB`/`FUNCTION`;
- для этого тело процедуры или функции разбирается в специальном режиме, а обычные блочные инструкции продолжают принимать только обычные операторы;
- синтаксический слой хранит локальные объявления как операторные обёртки вокруг обычных `SubDeclarationSyntax` и `FunctionDeclarationSyntax`, чтобы не смешивать объявления верхнего уровня и объявления уровня операторов.

Модель связывания:
- связыватель по-прежнему собирает исполняемые инструкции отдельно от связанных процедур и функций;
- при входе в процедуру или функцию связыватель сначала объявляет параметры, затем первым проходом регистрирует все локальные `SUB`/`FUNCTION` в текущей области видимости имён процедур и функций;
- вторым проходом связыватель связывает тело внешней процедуры или функции в текстовом порядке: обычные инструкции сразу попадают в исполняемый список, а локальные процедуры и функции связываются в точке своего объявления;
- это даёт возможность вызывать локальные процедуры и функции до их объявления и поддерживает локальную рекурсию без выполнения строк объявления во время интерпретации;
- за счёт текстового порядка тело локальной процедуры или функции может захватывать только те внешние локальные имена, которые уже объявлены к моменту её собственного объявления.

Модель областей видимости:
- `BoundScope` больше не использует единственного родителя для всего сразу;
- область видимости переменных и область видимости имён процедур и функций разделены;
- для обычных блочных областей видимости обе цепочки совпадают;
- для локальной процедуры или функции цепочка переменных и цепочка имён процедур и функций обе идут во внешнюю лексическую процедуру или функцию;
- благодаря этому локальная процедура или функция видит собственные имена, внешние захваченные данные и внешние имена процедур и функций, но только в рамках уже объявленных к этому месту текстовых имён.

Исполнение:
- во время выполнения пользовательские процедуры и функции по-прежнему хранятся в плоском реестре по `FunctionSymbol`;
- вызов локальной процедуры или функции не требует отдельного исполняемого оператора объявления: к моменту исполнения она уже присутствует в связанной программе;
- каждый `FunctionSymbol` локальной процедуры или функции хранит ссылку на свою объявляющую внешнюю процедуру или функцию;
- при вызове интерпретатор ищет активный кадр вызова объявляющей процедуры или функции и строит новый `RuntimeScope` поверх найденной внешней области видимости, а не только поверх глобальной области;
- за счёт этого захваченные переменные и параметры разделяют ту же модель хранения времени выполнения, что и обычные лексические цепочки `RuntimeScope`;
- полноценные замыкания как значения языка при этом не добавляются: вызов по-прежнему происходит только по имени локальной процедуры или функции внутри активной цепочки вызовов.

## 21. Диагностика времени выполнения для вложенных вызовов

Слой выполнения дополнительно расширен текстовой моделью цепочки вызовов для ошибок времени выполнения.

Ключевые решения:
- `CallFrame` хранит не только символ вызываемой процедуры или функции и её `RuntimeScope`, но и точку вызова;
- все пользовательские процедуры и функции создают кадр вызова через единый путь, поэтому формат цепочки одинаков для обычных и локальных вызовов;
- общий помощник диагностики времени выполнения дополняет исходное сообщение блоком `Цепочка вызовов`, не меняя саму модель `Diagnostic`;
- для локальной процедуры или функции формат цепочки дополнительно показывает внешнюю процедуру или функцию, внутри которой она объявлена;
- координаты самой диагностики не смещаются и продолжают указывать на исходную проблемную строку.

## 22. Функциональные типы, значения функций и замыкания

Слой фронтенда и слой выполнения расширены так, чтобы функции теперь были значениями языка и могли образовывать полноценные замыкания.

Ключевые решения:
- в синтаксическом слое появилось отдельное дерево типов `TypeSyntax` с реализациями `NamedTypeSyntax` и `FunctionTypeSyntax`;
- вызов больше не завязан только на идентификатор: `CallExpressionSyntax` хранит любое целевое выражение, чтобы поддержать вызов через переменную или немедленный вызов возвращаемой функции;
- в семантическом слое введены `FunctionTypeSymbol` и `BoundFunctionExpression`;
- `BoundCallExpression` теперь хранит не символ вызываемой функции, а связанное целевое выражение и список аргументов;
- связыватель различает имя переменной, имя функции и имя подпрограммы `SUB`; попытка использовать `SUB` как значение даёт `MB2019`;
- вызов значения нефункционального типа останавливается в связывателе с диагностикой `MB2020`.

Слой выполнения:
- в слое выполнения введён `RuntimeFunctionValue`, который содержит `FunctionSymbol` и захваченную `RuntimeScope`;
- при вычислении `BoundFunctionExpression` интерпретатор создаёт значение функции со снимком её внешней лексической области видимости;
- при вызове такого значения новая область видимости строится поверх захваченной области, а не поверх только текущей глобальной области;
- это даёт полноценное поведение замыкания: возвращённая внутренняя функция продолжает видеть и менять захваченные данные после выхода внешней функции;
- пустое значение функционального типа представляется как отсутствие функции внутри `RuntimeValue`, а его вызов даёт `MB3009`.

Границы этапа:
- анонимных функций и отдельного синтаксиса литералов функции пока нет;
- `SUB` остаётся только вызываемой конструкцией и не участвует в модели значений;
- типовое равенство функций сейчас строится на точном совпадении сигнатуры без отдельной модели ковариантности и контрвариантности.

## Update 2026-04-20 - Array Value Model

- `Axiom.Syntax` now includes `ArrayTypeSyntax` for type-position forms such as `INTEGER()`.
- `Axiom.Semantics` now includes `ArrayTypeSymbol`, and array variables/parameters/results are typed explicitly instead of relying only on a boolean flag.
- `BoundArrayAccessExpression` now reports the element type rather than the whole array type.
- `Axiom.Runtime` keeps element storage in `RuntimeArrayValue`, while array expressions travel through the language as `RuntimeValue` instances whose `Type` is an `ArrayTypeSymbol`.
- Runtime parameter binding and whole-array assignment preserve shared-reference semantics for this stage.
- General postfix indexing of arbitrary expressions is still intentionally deferred; the current grammar keeps named-array indexing only.

## Update 2026-04-20 - REDIM Lifecycle Step

- `Axiom.Lexing` and `Axiom.Parsing` now recognize `REDIM` as a standalone statement rather than as part of declarations.
- The syntax layer models this with a dedicated `RedimStatementSyntax`, reusing the existing `ArrayBoundsSyntax` shape contract.
- `Axiom.Semantics` now represents the operation through `BoundRedimStatement`.
- The binder keeps `REDIM` intentionally narrow in this stage:
  - target must already resolve to an array name;
  - bounds are rebound through the existing numeric-expression path;
  - preservation of old elements is not part of this node or contract.
- `Axiom.Runtime` executes `REDIM` by mutating the existing `RuntimeArrayValue` storage through `Allocate(lowerBound, upperBound)`.
- This preserves the current shared-reference array model: reallocating an aliased array is observable through every reference to the same runtime array object.

## Update 2026-04-20 - REDIM PRESERVE Lifecycle Step

- `Axiom.Lexing` now recognizes `PRESERVE` as a keyword, but only the `REDIM PRESERVE` statement currently uses it.
- The syntax layer keeps a single `RedimStatementSyntax` node and models preservation as an optional keyword on that node instead of splitting the lifecycle surface into separate statement kinds.
- `Axiom.Semantics` keeps the same approach with one `BoundRedimStatement` plus a `Preserve` flag, so later lifecycle work can stay on the same statement backbone.
- `Axiom.Runtime` now exposes two array reallocation paths on `RuntimeArrayValue`:
  - `Allocate(lowerBound, upperBound)` for reset semantics;
  - `AllocatePreserving(lowerBound, upperBound)` for overlap-preserving semantics.
- Preservation is implemented in the runtime storage layer by copying the logical index intersection from the previous bounds into a freshly allocated element buffer.
- Because the runtime still mutates the same `RuntimeArrayValue` object, aliasing behavior stays consistent between `REDIM` and `REDIM PRESERVE`.

## Update 2026-04-20 - ERASE Lifecycle Step

- `Axiom.Lexing` and `Axiom.Parsing` now recognize `ERASE` as a standalone statement.
- The syntax layer models this with a dedicated `EraseStatementSyntax`.
- `Axiom.Semantics` represents the operation through `BoundEraseStatement`.
- The binder keeps the first `ERASE` slice intentionally narrow:
  - only one target name per statement;
  - target must already resolve to an array name.
- `Axiom.Runtime` now exposes `Deallocate()` on `RuntimeArrayValue` and uses it to return an array to the same unallocated state that follows `DIM name() AS TYPE`.
- Because `Deallocate()` mutates the existing runtime array object, aliasing behavior stays consistent with the rest of the current array lifecycle model.

## Обновление 2026-04-20 - Архитектурная опора для информационных функций массива

- Каталог встроенных функций получил отдельный путь связывания для функций, которые принимают массив любого допустимого типа элемента, а не только заранее перечисленные конкретные сигнатуры.
- Для этого в описателях встроенных функций введён специальный режим связывания для информационных функций массива.
- Связыватель сначала проверяет, что фактический аргумент действительно имеет тип массива, затем подставляет реальный тип аргумента в вызов и строит обычное связанное выражение вызова.
- Благодаря этому один и тот же публичный идентификатор `LBOUND`, `UBOUND`, `ARRAYLENGTH` или `ARRAYISALLOCATED` теперь работает единообразно для `INTEGER()`, `STRING()` и других одномерных массивов без дублирования большого числа почти одинаковых сигнатур.
- Слой выполнения оставлен простым:
  - логика чтения нижней и верхней границы живёт рядом с остальными встроенными функциями;
  - проверка выделенности опирается на уже существующее состояние `RuntimeArrayValue`;
  - никаких новых изменяющих операций в этом шаге не добавлялось.

## Обновление 2026-04-20 - Пустой выделенный массив в слое выполнения

- `RuntimeArrayValue` теперь различает три важных состояния:
  - невыделенный массив: внутренний буфер отсутствует;
  - выделенный непустой массив: буфер содержит элементы;
  - выделенный пустой массив: буфер существует, но имеет длину `0`.
- Каноническая пустая форма закреплена как `LowerBound = 1`, `UpperBound = 0`.
- Проверка выделенности по-прежнему строится на наличии буфера, поэтому пустой массив считается выделенным.
- Число элементов теперь читается через свойство длины массива, а не вычисляется вручную как `UpperBound - LowerBound + 1`, чтобы пустой диапазон оставался безопасным.
- Операции `REDIM` и `REDIM PRESERVE` используют общий контракт допустимых границ: обычный включительный диапазон или ровно `1 TO 0` для пустого выделенного массива.

## Проектный договор 2026-04-20 - Чистые операции над одномерными массивами

- Следующий слой операций над массивами начинается с функций, которые создают новый массив и не меняют исходный.
- `ARRAYCLONE` должна сохранять состояние исходного массива:
  - невыделенный массив остаётся невыделенным в результате;
  - выделенный непустой массив сохраняет нижнюю и верхнюю границы;
  - выделенный пустой массив сохраняет форму `1 TO 0`.
- `ARRAYSLICE` должна возвращать компактный результат:
  - непустой срез получает границы `1 TO N`;
  - пустой срез получает форму `1 TO 0`.
- Обе функции должны создавать новое хранилище элементов, чтобы дальнейшее изменение результата не меняло исходный массив.
- Для связывания таких функций потребуется расширить путь встроенных функций массива: результат зависит от фактического типа аргумента массива, а не от одной заранее заданной сигнатуры.
- На уровне выполнения удобно выделить общий помощник создания массива с произвольным типом элемента, чтобы не дублировать текущий частный путь для `STRING()`.

## Обновление 2026-04-20 - ARRAYCLONE как первый чистый срез

- Каталог встроенных функций массива получил общий путь связывания для функций, у которых первый аргумент обязан быть массивом, а тип результата может зависеть от фактического типа этого аргумента.
- На этом пути:
  - связыватель сначала подтверждает, что первый аргумент действительно имеет тип массива;
  - затем подставляет реальный тип массива в сигнатуру вызова;
  - итоговый тип результата выбирается по политике функции, а не только по заранее записанному типу описателя.
- `ARRAYCLONE` стала первой функцией, которая использует этот общий путь и возвращает массив того же типа, что и входной аргумент.
- В слое выполнения выделен общий помощник построения массива произвольного типа элемента:
  - он умеет создавать компактный массив `1 TO N` или `1 TO 0`;
  - на нём же строится копия массива с сохранением исходных границ.
- Это решение убирает жёсткую привязку общего пути создания массивов только к `STRING()` и подготавливает основу для следующего шага с `ARRAYSLICE`.

## Обновление 2026-04-20 - ARRAYSLICE как второй чистый срез

- `ARRAYSLICE` переиспользует тот же общий путь связывания функций массива, что и `ARRAYCLONE`: фактический тип массива берётся из первого аргумента, а итоговая сигнатура строится уже после проверки этого аргумента.
- В слое выполнения `ARRAYSLICE` использует общий помощник построения компактного массива:
  - непустой результат создаётся с границами `1 TO N`;
  - пустой результат создаётся как каноническая форма `1 TO 0`.
- Проверка диапазона среза остаётся в слое выполнения, потому что зависит от текущих границ уже выделенного массива.
- Благодаря этому `ARRAYSLICE` не дублирует частные пути для строковых массивов и сразу работает для любых уже поддержанных одномерных массивов.

## Обновление 2026-04-20 - Indexed mutating-операции одномерного массива

- Каталог встроенных функций массива расширен операциями `ARRAYINSERT` и `ARRAYREMOVE`.
- `ARRAYINSERT` оформлен как built-in-процедура (`VOID`), а `ARRAYREMOVE` — как built-in-функция с результатом типа элемента массива.
- В binder сохранён общий array-binding путь:
  - первый аргумент обязан быть массивом;
  - параметр `value` у `ARRAYINSERT` связывается с типом элемента массива;
  - результат `ARRAYREMOVE` выводится как тип элемента первого аргумента массива.
- В runtime обе операции мутируют тот же `RuntimeArrayValue`, а не создают новый контейнер.
- Реализация использует уже существующий путь переаллокации на месте через `AllocatePreserving`, а логический сдвиг элементов выполняется явно в рантайме:
  - `ARRAYINSERT` сначала расширяет диапазон вправо, затем сдвигает хвост вправо и записывает новое значение;
  - `ARRAYREMOVE` сначала запоминает удаляемый элемент, затем сдвигает хвост влево и сужает диапазон.
- Каноническая пустая форма `1 TO 0` сохраняется как единое состояние после полного опустошения массива, поэтому после удаления единственного элемента `ARRAYREMOVE` нормализует массив именно к этой форме.

## Обновление 2026-04-20 - Predicate higher-order-подпакет массива

- Первый минимальный higher-order-срез массива зафиксирован как predicate-подпакет `ARRAYEVERY` и `ARRAYSOME`.
- Оба built-in остаются в том же array-binding-пути, что и предыдущие массивные функции: первый аргумент обязан быть массивом, но второй аргумент теперь резолвится не как тип элемента, а как функциональный тип `FUNCTION(T) AS BOOLEAN`, где `T` берётся из типа элемента первого аргумента.
- Такое решение не требует нового синтаксиса языка: binder переиспользует уже существующие функциональные типы и значения функций.
- В runtime higher-order built-ins переиспользуют уже существующий механизм вызова значения функции и замыкания:
  - callback может быть как именованной функцией, так и возвращённым замыканием;
  - выполнение callback идёт в обычной модели `RuntimeFunctionValue` с захваченной внешней областью видимости;
  - пустое значение функционального типа сообщает тот же `MB3009`, что и обычный прямой вызов значения функции.
- `ARRAYEVERY` и `ARRAYSOME` реализованы как read-only операции над уже выделенным `RuntimeArrayValue`: они обходят текущий диапазон логических индексов и не меняют хранилище массива.

## Обновление 2026-04-20 - договор producer higher-order-шага ARRAYFILTER

- Следующий higher-order-срез закреплён как `ARRAYFILTER(array, predicate)`.
- `ARRAYFILTER` должен использовать тот же binder/runtime-механизм callback-вызова, что уже введён для `ARRAYEVERY` и `ARRAYSOME`.
- Тип callback-а остаётся минимальным: `FUNCTION(T) AS BOOLEAN` без добавления индекса, массива или нового синтаксического sugar.
- Producer-результат проектно нормализуется к компактной форме `1 TO N`; `ARRAYFILTER` не наследует логические границы исходного массива.
- Для пустого результата используется уже принятая каноническая выделенная форма `1 TO 0`.
- Этот шаг расширяет только producer-ветку higher-order API и не требует новых frontend-слоёв сверх уже существующих function values / closures.

## Обновление 2026-04-20 - ARRAYFILTER реализован

- `ARRAYFILTER` добавлен в тот же array-binding-путь, что уже использовался для `ARRAYEVERY` и `ARRAYSOME`: тип первого аргумента задаёт и тип массива-результата, и тип callback-а.
- Binder резолвит `predicate` как `FUNCTION(T) AS BOOLEAN`, где `T` — тип элемента исходного массива, а возвращаемый тип built-in остаётся `SameAsFirstArgument`.
- Runtime реализует `ARRAYFILTER` как read-only producer-операцию:
  - обход идёт по текущим логическим индексам уже выделенного массива;
  - callback вызывается через уже существующий путь `RuntimeFunctionValue` / closure invocation;
  - прошедшие predicate элементы собираются в новый компактный массив `1 TO N` или в канонический пустой `1 TO 0`.
- Тем самым producer higher-order-ветка стартует без новой polymorphic result-type machinery: `ARRAYFILTER` переиспользует уже существующие array-type и function-value механизмы.

## Обновление 2026-04-20 - договор same-type ARRAYMAP

- Следующий шаг закреплён как минимальный `ARRAYMAP(array, selector)` без polymorphic-расширения.
- `ARRAYMAP` должен использовать тот же binder/runtime-механизм callback-вызова, что уже введён для `ARRAYEVERY`, `ARRAYSOME` и `ARRAYFILTER`.
- Тип callback-а в первом варианте фиксируется как `FUNCTION(T) AS T`, где `T` задаётся типом элемента первого аргумента массива.
- Producer-результат, как и у `ARRAYFILTER`, проектно нормализуется к компактной форме `1 TO N` или `1 TO 0`.
- Этот договор сознательно откладывает общий случай `T -> U`: новый result-type inference для higher-order built-ins в этот шаг не вводится.

## Обновление 2026-04-20 - ARRAYMAP реализован

- `ARRAYMAP` добавлен в тот же array-binding-путь, что уже используется для `ARRAYFILTER`: тип первого аргумента задаёт и тип массива-результата, и форму callback-а.
- Binder резолвит `selector` как `FUNCTION(T) AS T`, где `T` совпадает с типом элемента исходного массива; возвращаемый тип built-in остаётся `SameAsFirstArgument`.
- Runtime реализует `ARRAYMAP` как read-only producer-операцию:
  - обход идёт по текущим логическим индексам уже выделенного массива;
  - callback вызывается через тот же путь `RuntimeFunctionValue` / closure invocation;
  - значения, возвращённые selector-ом, собираются в новый компактный массив `1 TO N` или в канонический пустой `1 TO 0`.
- Тем самым same-type `ARRAYMAP` расширяет higher-order API без новой polymorphic result-type machinery и без смешивания этого шага с `ARRAYREDUCE`.

## Обновление 2026-04-20 - договор same-type ARRAYREDUCE

- Следующий шаг закреплён как минимальный `ARRAYREDUCE(array, seed, reducer)` без polymorphic accumulator-расширения.
- `ARRAYREDUCE` должен использовать тот же binder/runtime-механизм callback-вызова, что уже введён для `ARRAYEVERY`, `ARRAYSOME`, `ARRAYFILTER` и `ARRAYMAP`.
- Тип `seed` в первом варианте фиксируется как `T`, где `T` задаётся типом элемента первого аргумента массива.
- Тип callback-а в первом варианте фиксируется как `FUNCTION(T, T) AS T`, где первый параметр — аккумулятор, второй — текущее значение элемента массива.
- Результат `ARRAYREDUCE` проектно совпадает с типом элемента массива, а для пустого массива возвращается `seed` без отдельного special-case syntax.
- Этот договор сознательно откладывает общий случай `FUNCTION(A, T) AS A`: новый result-type inference и отдельный тип аккумулятора в этот шаг не вводятся.

## Обновление 2026-04-20 - ARRAYREDUCE реализован

- `ARRAYREDUCE` добавлен в тот же array-binding-путь, что уже используется для higher-order built-ins над массивами: тип первого аргумента задаёт и тип `seed`, и форму callback-а, и результирующий тип built-in.
- Binder резолвит `seed` как тип элемента массива `T`, а `reducer` как `FUNCTION(T, T) AS T`, сохраняя результат built-in в политике `SameAsFirstArgument`.
- Runtime расширен до общего callback-вызова с произвольным числом аргументов, чтобы переиспользовать уже существующий путь `RuntimeFunctionValue` / closure invocation и для unary producer/predicate built-ins, и для binary reducer-а.
- `ARRAYREDUCE` реализован как read-only accumulator-операция:
  - обход идёт по текущим логическим индексам уже выделенного массива слева направо;
  - стартовым аккумулятором становится переданный `seed`;
  - каждый шаг вычисляет новый аккумулятор через `reducer(acc, element)`;
  - для пустого выделенного массива возвращается `seed` без построения промежуточного массива.
- Тем самым minimal higher-order array API теперь покрывает predicate, producer и accumulator сценарии без новой polymorphic result-type machinery.

## Обновление 2026-04-20 - polymorphic higher-order отложен отдельным этапом

- Текущая архитектурная граница higher-order API по массивам зафиксирована как завершённый minimal same-type пакет.
- Вне текущего стабильного среза остаются только polymorphic-расширения:
  - result-type inference для `ARRAYMAP` в форме `FUNCTION(T) AS U`;
  - отдельный accumulator-type inference для `ARRAYREDUCE` в форме `FUNCTION(A, T) AS A`.
- Эти расширения не должны добавляться как локальные правки поверх уже существующих same-type built-ins; при возвращении к ним нужен отдельный архитектурный шаг с явным описанием binder/result-type machinery.

## Обновление 2026-04-20 - архитектурная рамка пакета даты и времени

- Первый пакет built-ins даты и времени должен оставаться внутри уже существующей descriptor-based модели built-in функций:
  - без нового синтаксиса;
  - без новых литералов даты и времени;
  - без нового публичного type keyword на первом этапе.
- Публичный контракт первого поколения должен быть string-first:
  - `DATE`, `TIME`, `NOW`, `DATESERIAL`, `TIMESERIAL` возвращают канонические строки;
  - `TIMER` возвращает числовое значение;
  - extractors (`YEAR`, `MONTH`, `DAY`, `HOUR`, `MINUTE`, `SECOND`, `WEEKDAY`) возвращают числа.
- Runtime-реализация не должна опираться на locale-sensitive `DateTime.Parse` / `Convert.ToDateTime` и аналогичные host-зависимые shortcuts.
- Для пакета даты и времени нужен отдельный узкий helper-слой runtime-нормализации, который:
  - разбирает только явно разрешённые форматы;
  - форматирует результат только в канонические формы спецификации;
  - централизует календарную валидацию и будущую арифметику дат.
- Внутренне этот helper-слой может использовать .NET `DateOnly`, `TimeOnly`, `DateTimeOffset` и `TimeSpan`, но эти внутренние представления не должны просачиваться в публичную модель типов Axiom первого поколения.
- Из-за уже существующих string-returning file-system built-ins пакет даты и времени должен проектироваться так, чтобы их результаты можно было напрямую передавать в новые date/time built-ins без locale conversion.
- Исторические statement-формы `DATE$ = ...` и `TIME$ = ...`, меняющие системные часы хоста, не входят в архитектурный scope Axiom:
  - они несут побочный эффект на среду выполнения;
  - они не нужны для текущей интерпретаторной модели;
  - если когда-либо такой сценарий понадобится, он должен рассматриваться отдельно как host-capability, а не как обычный expression built-in.
- Если в будущем проект всё же захочет first-class `DATE` / `TIME` / `DATETIME` type, это должен быть отдельный этап со своими правками во все слои:
  - lexer/syntax/type syntax;
  - binder/type conversions;
  - runtime storage;
  - `PRINT` / `INPUT` / file-system interoperability;
  - manual и sample catalog.

## Обновление 2026-04-21 - архитектурная рамка arithmetic layer даты и времени

- Arithmetic layer пакета даты и времени должен оставаться внутри уже существующей descriptor-based модели built-in функций и не вводить новый public type.
- DATEADD и DATEDIFF должны работать поверх того же helper-слоя канонического разбора/форматирования, который уже обслуживает DATESERIAL, TIMESERIAL, YEAR, MONTH, DAY, HOUR, MINUTE, SECOND, WEEKDAY.
- В runtime нужен следующий узкий helper-срез поверх существующего date/time helper слоя:

  - обратное форматирование результата в ту же публичную каноническую форму.
- Внутреннее представление может опираться на DateOnly, TimeOnly, DateTime и DateTimeOffset, но наружу должны выходить только canonical strings, INTEGER, LONG и BOOLEAN.

## Обновление 2026-04-21 - локальный часовой пояс как часть runtime-хоста

## Обновление 2026-04-23 - предварительная компиляция и повторный запуск подготовленной программы

В `Axiom.Execution` введён отдельный внутренний слой предварительной компиляции:
- `Compile` проходит путь `parse -> bind` без выполнения программы;
- результатом является `CompiledProgram`, который хранит исходный текст, синтаксическое дерево и уже связанный `BoundProgram`;
- `Run` по исходному тексту теперь логически раскладывается на два шага: подготовка программы и её выполнение;
- `RunCompiled` выполняет уже готовый `BoundProgram` без повторного синтаксического и семантического прохода.

Граница для IDE уточнена так:
- `ProgramRunService.Compile(sourceText)` строит и кэширует последний успешный `CompiledProgram`;
- `ProgramRunService.Run(sourceText)` использует кэшированную подготовленную программу, если текст не менялся;
- при изменении текста кэш считается устаревшим, и следующий запуск снова проходит подготовительный этап.

Важно зафиксировать, чем этот слой пока не является:
- это не собственный байткод;
- это не `MSIL`/CIL и не генерация `exe`;
- это не отдельный формат сериализации на диск.

Почему слой всё равно архитектурно полезен:
- он отделяет frontend-подготовку программы от runtime-исполнения;
- он даёт естественную точку расширения для будущего backend-этапа вида `BoundProgram -> BytecodeModule`;
- будущая байткодная ветка сможет переиспользовать lexer, parser, syntax, binder, диагностику и сам договор предварительной компиляции, меняя в основном нижнюю часть конвейера.

- Для синтаксиса добавлен отдельный узел формы `STRING * <expression>`, чтобы парсер различал обычный `STRING` и объявление фиксированной длины.
- В семантическом слое эта форма не создаёт новый `TypeSymbol`:
  - `STRING * N` разрешается к обычному `TypeSymbol.String`;
  - сама длина хранится как дополнительная метаинформация на `VariableSymbol` и `TypeFieldSymbol`.
- Такой выбор удерживает единый язык выражений:
  - строковые built-in функции не требуют отдельной ветки типов;
  - преобразования и сравнения остаются на существующем пути `STRING`;
  - особая логика сосредоточена в местах хранения значений.
- Binder вычисляет длину фиксированной строки тем же семейством константных вычислений, что уже использовалось для фиксированных массивных полей:
  - для верхнего уровня доступны верхнеуровневые целочисленные `CONST`, включая объявления ниже по файлу;
  - для локальных объявлений используется отдельный словарь уже связанных целочисленных `CONST`.
- Binder дополнительно отделяет поддержанные и неподдержанные позиции:
  - прямой `STRING * N` разрешён только для `DIM` и строковых полей `TYPE`;
  - в `CONST`, параметрах и типах результата функций, а также внутри функциональных типов связующее звено не пытается молча свести форму к обычному `STRING`, а выдаёт `MB2026`;
  - для этого поиск фиксированной строки идёт рекурсивно по `TypeSyntax`, чтобы не оставлять скрытых лазеек через `FUNCTION(...) AS ...`.
- Runtime нормализует фиксированные строки на всех путях записи значения:
  - при создании значения по умолчанию;
  - при инициализации и последующих присваиваниях переменной;
  - при создании и копировании полей записи;
  - при хранении элементов строкового массива, если массив несёт метаданные фиксированной длины элемента.

## Обновление 2026-04-23 - целевая архитектура собственного байткода и виртуальной машины

Следующее крупное backend-направление зафиксировано как параллельное внедрение собственного байткода и стековой виртуальной машины. Текущий интерпретатор не удаляется и не считается устаревшим: он остаётся эталонным исполнителем, резервным путём и инструментом сравнения поведения во время стабилизации.

Целевой полный конвейер:

```text
SourceText -> Parse -> Bind -> CompiledProgram -> LoweredProgram -> BytecodeModule -> BytecodeVm -> RuntimeResult
```

После введения байткодного слоя в системе должны существовать два исполняющих пути:
- интерпретаторный путь: `CompiledProgram -> Interpreter`;
- байткодный путь: `CompiledProgram -> LoweredProgram -> BytecodeModule -> BytecodeVm`.

`AxiomExecutionPipeline` становится координатором режимов исполнения, а не только оболочкой над frontend-подготовкой. Он должен выбирать движок, учитывать кэши подготовленной программы, пониженного представления и байткодного модуля, а также возвращать пользователю и IDE честные метрики по стадиям.

Новый отдельный проект `Axiom.Bytecode` вводится как граница backend-слоя. Рекомендуемая структура:
- `Model/` - модель байткодного модуля, инструкций, таблиц, версий и отладочных данных;
- `Lowering/` - понижение `BoundProgram` в линейную форму, удобную для backend-а;
- `Emission/` - генерация `BytecodeModule` из пониженного представления;
- `Diagnostics/` - ошибки генерации байткода и проверки целостности модуля.

`Axiom.Runtime` расширяется вторым исполнителем, но не теряет роль интерпретаторного рантайма:
- текущие `Execution/Interpreter*` остаются основным эталонным путём на переходный период;
- новые `Execution/BytecodeVm*` добавляются как второй путь исполнения;
- `Values/`, `Environment/`, `Host/` остаются общим основанием для интерпретатора и виртуальной машины.

`Axiom.Execution` получает роль фасада исполнения:
- выбор режима запуска;
- кэширование frontend- и backend-артефактов;
- возврат детальных метрик по подготовке, понижению, генерации байткода и исполнению;
- единый контракт для IDE.

`Axiom.Ide` должна получить пользовательскую настройку предпочтительного режима запуска, показывать фактически использованный движок и отдельно отображать время понижения, генерации байткода и исполнения виртуальной машиной.

Основные типы, которые должны появиться в `Axiom.Bytecode`:
- `BytecodeModule`;
- `BytecodeHeader`;
- `BytecodeFormatVersion`;
- `BytecodeRoutine`;
- `BytecodeInstruction`;
- `Opcode`;
- `ConstantPool`;
- `BuiltinBinding`;
- `BytecodeDebugInfo`;
- `SourceInstructionMap`;
- `LoweredProgram`;
- `LoweredRoutine`;
- `LoweredInstruction`;
- `BytecodeCompiler`;
- `BytecodeCompilerResult`.

Основные типы, которые должны появиться или расшириться в `Axiom.Execution`:
- `ExecutionMode` со значениями `Auto`, `Interpreter`, `Bytecode`;
- `ExecutionEngineKind` со значениями `Interpreter`, `BytecodeVm`;
- `CompiledProgram`, хранящий `ProgramSyntax`, `BoundProgram`, опциональный `LoweredProgram` и опциональный `BytecodeModule`;
- `CompilationResult`, различающий успех frontend-подготовки, успех backend-подготовки и доступность байткода;
- `ExecutionResult`, возвращающий фактический движок, времена стадий, суммарное время, признаки использования кэша подготовленной программы и кэша байткода.

Байткодная модель строится вокруг стековой виртуальной машины. Канонический модуль первой волны живёт в памяти и не обязан сериализоваться в файл, но структура должна быть рассчитана на будущую сериализацию без ломки публичной модели.

`BytecodeModule` должен содержать:
- `Header`;
- `ConstantPool`;
- `RoutineTable`;
- `GlobalLayout`;
- `BuiltinTable`;
- `DebugInfo`.

`Header` должен хранить версию формата, версию языкового договора, флаги возможностей и контрольную информацию совместимости. `ConstantPool` хранит числовые, строковые и логические литералы, а также имена процедур и встроенных функций для отладки и трассировки. `RoutineTable` хранит стабильный индекс процедуры, имя, тип результата, число параметров, число локальных слотов, диапазон инструкций и имена параметров и локальных переменных для отладки. `GlobalLayout` хранит слот глобальной переменной, символ, runtime-тип, признак константы и стратегию инициализации.

Начальный набор `Opcode` проектируется группами:
- загрузка и хранение: `PushConst`, `LoadGlobal`, `StoreGlobal`, `LoadLocal`, `StoreLocal`, `LoadArgument`, `StoreArgument`, `Dup`, `Pop`;
- арифметика и логика: `Negate`, `Add`, `Subtract`, `Multiply`, `Divide`, `Modulo`, `Not`, `And`, `Or`, `Xor`, `Eqv`, `Imp`;
- сравнения: `CompareEqual`, `CompareNotEqual`, `CompareLess`, `CompareLessOrEqual`, `CompareGreater`, `CompareGreaterOrEqual`;
- управление потоком: `Jump`, `JumpIfTrue`, `JumpIfFalse`, `Call`, `Return`;
- составные значения и контейнеры: `CreateArray`, `RedimArray`, `EraseArray`, `LoadElement`, `StoreElement`, `CreateRecord`, `LoadField`, `StoreField`;
- службы рантайма: `CallBuiltin`, `PrintValue`, `PrintSeparator`, `BeginInput`, `EndInput`, `OpenFile`, `CloseFile`.

Правило проектирования инструкций:
- не вводить отдельный opcode на каждую встроенную функцию;
- встроенные функции вызывать через таблицу встроенных функций и `CallBuiltin`;
- новые возможности языка по возможности раскладывать в уже существующие инструкции;
- новый opcode добавлять только тогда, когда семантика не выражается текущим набором без потери ясности или корректности.

Между `BoundProgram` и генератором байткода обязателен слой `LoweredProgram`. Он должен убрать зависимость backend-а от высокоуровневой формы связанного дерева, превратить `IF`, циклы, `SELECT CASE`, `EXIT` и `RETURN` в линейный поток с метками и переходами, нормализовать порядок вычисления выражений и сохранить `TextLocation` на пониженных инструкциях. `Binder` остаётся только семантическим слоем и не должен знать о байткоде.

Первая полноценная волна виртуальной машины использует существующую runtime-модель значений:
- `RuntimeValue`;
- `RuntimeArrayValue`;
- `RuntimeRecordValue`;
- `RuntimeFunctionValue`;
- `IRuntimeHost`.

Это архитектурное решение означает, что байткод меняет способ исполнения, но не ломает текущий контракт значений и взаимодействия с внешней средой.

`BytecodeDebugInfo` должен закладываться с первого этапа. Минимально он обязан хранить:
- соответствие инструкции строке и позиции исходника;
- соответствие инструкции процедуре или функции;
- таблицу имён параметров и локальных переменных;
- диапазоны инструкций по логическим блокам процедуры.

Эти данные нужны для runtime-диагностики виртуальной машины, показа позиции ошибки в IDE и будущего отладчика. Полный отладчик этой архитектурной записью не вводится, но формат не должен закрывать путь к точкам останова и пошаговому исполнению.

Правила кадров виртуальной машины:
- каждая процедура получает собственный кадр вызова;
- аргументы кладутся в выделенные слоты кадра;
- локальные значения и временный evaluation-stack не смешиваются;
- evaluation-stack очищается по соглашению о вызове на границе процедуры.

Правила ошибок виртуальной машины:
- runtime-ошибки VM должны переводиться в тот же понятный диагностический уровень, который сейчас даёт интерпретатор;
- сообщение должно иметь ссылку на исходную позицию;
- если точная позиция недоступна, используется ближайшая карта инструкции, а не безымянная внутренняя ошибка.

## Обновление 2026-04-23 - начало проекта `Axiom.Bytecode` и пониженной формы

Начата фаза 3 байткодного направления. В решение добавлен отдельный проект `Axiom.Bytecode`, который зависит от `Axiom.Core`, `Axiom.Syntax` и `Axiom.Semantics`. Это сохраняет границу слоёв: binder остаётся в `Axiom.Semantics`, а backend-преобразования начинаются после `BoundProgram`.

В проекте заведены первые зоны:
- `Model/` - начальная модель `LoweredProgram`, `LoweredRoutine`, `LoweredInstruction` и перечисление `LoweredInstructionKind`;
- `Lowering/` - результат понижения и первый понижатель `BoundProgramLowerer`;
- `Diagnostics/` - диагностическая модель `BytecodeDiagnostic` для ошибок backend-слоя.

Начальная lowered-форма пока не является байткодом и не исполняется VM. Она фиксирует линейный backend-удобный поток инструкций для простого скалярного среза:
- объявление переменной с инициализатором;
- присваивание в скалярную переменную;
- выражение как оператор с последующим `Pop`;
- `PRINT`;
- `RETURN`;
- литералы, чтение переменной, унарные и бинарные операции, приведение типа и прямой вызов функции.

Каждая lowered-инструкция хранит `TextLocation`, чтобы будущие эмиттер и VM не потеряли связь с исходным текстом. Для неподдержанных конструкций понижатель возвращает backend-диагностику `BC3001`, а не пытается молча пропустить узел bound-дерева.

Текущий шаг не подключает `LoweredProgram` к `Compile`, `Run` или `ProgramRunService`. Интерпретаторный путь остаётся неизменным, а принудительный режим `Bytecode` по-прежнему честно возвращает `MB4001` до появления VM.

## Обновление 2026-04-23 - метки, переходы и lowering `IF`

Lowered-модель расширена первыми инструкциями управления ходом выполнения:
- `Label` - именованная точка внутри линейного потока routine;
- `Jump` - безусловный переход к метке;
- `JumpIfFalse` - условный переход к метке после вычисления условия.

Метки представлены стабильными строковыми идентификаторами вида `L0001`, `L0002` и создаются детерминированно в порядке обхода `BoundProgram`. Это временный человекочитаемый формат для фазы lowering; будущий эмиттер байткода сможет преобразовать такие метки в числовые смещения инструкций.

`BoundProgramLowerer` теперь понижает `BoundIfStatement`:
- условие вычисляется перед `JumpIfFalse`;
- ветка `THEN` остаётся линейной последовательностью инструкций;
- при наличии `ELSE` после ветки `THEN` добавляется `Jump` к общей конечной метке;
- `ELSEIF` используется в bound-дереве как вложенный `BoundIfStatement` внутри `ElseStatements`, поэтому текущий lowering обрабатывает его тем же рекурсивным правилом;
- каждая новая инструкция перехода и метки сохраняет `TextLocation`.

Это по-прежнему не меняет исполнительный путь IDE: `LoweredProgram` не строится автоматически в `Compile` и не исполняется в `Run`. Изменение расширяет только внутренний backend-слой и его unit-тесты.

## Обновление 2026-04-23 - lowering `WHILE / END WHILE`

`BoundProgramLowerer` расширен понижением `BoundWhileStatement`. Цикл `WHILE / END WHILE` представляется через уже введённые инструкции lowered-формы и не требует нового вида инструкции:
- начальная `Label` перед проверкой условия;
- вычисление условия;
- `JumpIfFalse` к конечной метке;
- линейное тело цикла;
- `Jump` обратно к начальной метке;
- конечная `Label` после тела цикла.

Метки цикла создаются тем же детерминированным счётчиком `L0001`, `L0002`, что и метки `IF`. Вложенные `WHILE` получают собственные пары меток в порядке обхода связанного дерева, поэтому одинаковый исходный текст даёт одинаковую форму lowered-инструкций.

Этот шаг остаётся внутренним изменением backend-слоя. `Compile`, `Run`, `ProgramRunService`, IDE и интерпретаторный путь не начинают исполнять `LoweredProgram`; пользовательское поведение `WHILE` не меняется.

## Обновление 2026-04-23 - lowering `DO WHILE / LOOP`

`BoundProgramLowerer` начал покрывать семейство `DO ... LOOP` с первой формы: `DO WHILE / LOOP`. В bound-модели она представлена как `BoundDoLoopStatement` с `ConditionKind = While`, `EvaluateConditionAfterBody = false` и непустым условием.

Для этой формы используется тот же pre-check шаблон, что и для `WHILE / END WHILE`:
- начальная `Label` перед проверкой условия;
- вычисление условия;
- `JumpIfFalse` к конечной метке;
- линейное тело цикла;
- `Jump` обратно к начальной метке;
- конечная `Label`.

Остальные формы `DO ... LOOP` пока намеренно остаются непокрытыми в lowered-слое и дают backend-диагностику `BC3001`. Это сохраняет явную границу фазы 3: сначала добавлена форма с проверкой перед телом, затем должны быть спроектированы `DO UNTIL`, `LOOP WHILE`, `LOOP UNTIL`, бесконечная форма и стек меток выхода для `EXIT DO`. Запись оставлена как состояние на момент внедрения `DO WHILE`; последующие обновления ниже уточняют текущее покрытие.

Изменение не подключает lowered-форму к исполнению. Интерпретаторный путь, IDE-команды `Compile` и `Run`, а также пользовательское поведение `DO WHILE` остаются прежними.

## Обновление 2026-04-23 - lowering `DO UNTIL / LOOP`

Lowered-модель расширена условным переходом `JumpIfTrue`. Он нужен для прямого выражения семантики `UNTIL`: цикл с проверкой перед телом должен выйти, когда условие истинно. Этот вид перехода уже входит в целевой набор инструкций управления ходом выполнения будущего байткода, поэтому отдельная инверсия условия через искусственный `NOT` не вводится.

`BoundProgramLowerer` теперь покрывает вторую pre-check форму семейства `DO ... LOOP`: `DO UNTIL / LOOP`. В bound-модели она представлена как `BoundDoLoopStatement` с `ConditionKind = Until`, `EvaluateConditionAfterBody = false` и непустым условием.

Форма `DO UNTIL / LOOP` понижается так:
- начальная `Label` перед проверкой условия;
- вычисление условия;
- `JumpIfTrue` к конечной метке;
- линейное тело цикла;
- `Jump` обратно к начальной метке;
- конечная `Label`.

После этого pre-check формы `DO WHILE` и `DO UNTIL` покрыты lowered-слоем. Post-check формы `DO ... LOOP WHILE`, `DO ... LOOP UNTIL`, бесконечная форма `DO ... LOOP` и `EXIT DO` остаются следующими задачами фазы 3.

Изменение остаётся внутренним: `LoweredProgram` не подключён к `Compile` и `Run`, а наблюдаемое пользовательское поведение `DO UNTIL` не меняется.

## Обновление 2026-04-23 - lowering `DO ... LOOP WHILE`

`BoundProgramLowerer` расширен первой формой семейства `DO ... LOOP` с проверкой после тела: `DO ... LOOP WHILE`.

Для этой формы используется отдельный шаблон, потому что условие проверяется после выполнения тела:
- начальная `Label` ставится перед телом цикла;
- тело цикла понижается линейно в обычном порядке;
- после тела вычисляется условие `WHILE`;
- `JumpIfTrue` возвращает выполнение к начальной метке;
- конечная `Label` ставится после условного перехода.

Такое представление сохраняет семантику цикла с проверкой после тела: тело выполняется минимум один раз. Вложенные `DO ... LOOP WHILE` получают детерминированные пары меток в порядке обхода `BoundProgram`, как и уже покрытые формы `WHILE`, `DO WHILE` и `DO UNTIL`.

Поддержка остаётся внутренней частью backend-слоя: `LoweredProgram` всё ещё не строится автоматически в `Compile` и не исполняется в `Run`. Пользовательское поведение языка, интерпретатор и IDE не изменяются.

Следующие непокрытые формы этого семейства в lowered-слое: `DO ... LOOP UNTIL`, бесконечная форма `DO ... LOOP` и `EXIT DO`.

## Обновление 2026-04-23 - понижение `DO ... LOOP UNTIL`

Для этой формы используется тот же общий путь понижения циклов с проверкой после тела, что и для `DO ... LOOP WHILE`, но условный переход разворачивается в сторону продолжения цикла при ложном условии:

## Обновление 2026-04-23 - понижение бесконечной формы `DO ... LOOP`

`BoundProgramLowerer` расширен формой `DO ... LOOP` без условия. В bound-модели она представлена как `BoundDoLoopStatement` с `ConditionKind = None`, `Condition = null` и списком инструкций тела.

Технический договор:

## Обновление 2026-04-23 - понижение `FOR / NEXT`

В этом шаге `BoundProgramLowerer` получил поддержку `BoundForStatement` без `EXIT FOR`. Последующее обновление ниже фиксирует покрытие `EXIT FOR`.

Технический договор пониженной формы:
- начальное значение управляющей переменной вычисляется один раз и сохраняется в переменную цикла;
- конечное значение и шаг вычисляются один раз перед входом в цикл и сохраняются во внутренние синтетические переменные пониженной формы;
- проверка цикла делится на ветку положительного шага и ветку неположительного шага;
- при положительном шаге цикл завершается, когда текущее значение больше конечного;
- при отрицательном шаге цикл завершается, когда текущее значение меньше конечного;
- тело цикла понижается линейно после проверок;
- после тела управляющая переменная увеличивается на сохранённый шаг, затем выполнение возвращается к проверке.

Синтетические переменные нужны, чтобы сохранить текущий договор интерпретатора: выражения `TO` и `STEP` вычисляются один раз перед циклом, а не повторяются на каждой итерации. Нулевой шаг не превращается в отдельную диагностику на этапе понижения; это остаётся ответственностью будущего исполнения байткода, как сейчас является диагностикой времени выполнения интерпретатора.

На момент этой записи `EXIT FOR` оставался отдельной следующей задачей и давал `BC3001` в текущем понижателе. Последующая запись ниже закрывает эту часть. ## Обновление 2026-04-23 - понижение `SELECT CASE`

`BoundProgramLowerer` теперь поддерживает `BoundSelectCaseStatement` для уже реализованного пользовательского блока `SELECT CASE / END SELECT`.

Технический договор пониженной формы:
- выражение после `SELECT CASE` вычисляется один раз и сохраняется во внутреннюю переменную пониженной формы;
- каждый обычный `CASE` получает метку тела ветки и метку проверки следующей ветки;
- каждый селектор внутри `CASE` вычисляет логический результат и при истинном значении выполняет `JumpIfTrue` к телу этой ветки;
- если ни один селектор ветки не подошёл, выполняется `Jump` к проверке следующей ветки;
- после выполнения тела подходящей ветки выполняется `Jump` к общей конечной метке `SELECT CASE`;
- `CASE ELSE` понижается как обычный линейный блок после всех проверок без дополнительного условия.

Покрытые формы селекторов:
- `CASE value` понижается как сравнение сохранённого значения `SELECT CASE` с выражением через `EqualsToken`;
- `CASE low TO high` понижается как `(test >= low) AND (test <= high)`;
- `CASE IS <op> value` понижается как сравнение сохранённого значения `SELECT CASE` с выражением через исходный оператор `CASE IS`.

Это изменение не вводит отдельный вид lowered-инструкции: достаточно уже существующих `LoadVariable`, `StoreVariable`, `BinaryOperation`, `JumpIfTrue`, `Jump` и `Label`. В `Axiom.Bytecode` добавлен первый полный модульный слой байткодного направления.

Новые зоны ответственности:
- `Model/` теперь содержит не только lowered-представление, но и модель байткодного модуля:

   - это упрощает первый эмиттер;

   - это fallback-уровень для диагностики;
   - более точная привязка к исходнику приходит из `BytecodeDebugInfo`.
6. `BytecodeDebugInfo` уже умеет выдавать ближайшую инструкционную позицию по `routineId` и индексу инструкции.

Текущая граница ответственности:
- `BoundProgramLowerer` отвечает за нормализацию bound-представления;
- будущий эмиттер будет отвечать за преобразование `LoweredProgram` в `BytecodeModule`;
- `BytecodeModuleValidator` отвечает за структурную корректность модуля до передачи в VM;
- `Axiom.Runtime` и `Axiom.Execution` пока не используют этот модульный слой напрямую.

## Обновление 2026-04-23 - эмиссия lowered-представления

В `Axiom.Bytecode` появилась отдельная зона `Emission/`:
- `BytecodeCompiler` строит in-memory `BytecodeModule` из `LoweredProgram`;
- `BytecodeCompilerResult` переносит либо модуль, либо список backend-диагностик.

Текущий договор между слоями:
1. `Lowering/` отвечает за линейную нормализацию bound-представления и сохранение `TextLocation`.
2. `Emission/` отвечает за:
   - выделение глобальных, аргументных и локальных слотов;
   - построение `ConstantPool`;
   - построение таблицы built-in;
   - преобразование lowered-инструкций в `Opcode`;
   - преобразование lowered-меток в конечные индексы переходов;
   - сборку `BytecodeDebugInfo`.
3. `Diagnostics/BytecodeModuleValidator` отвечает за структурную проверку уже собранного модуля до VM.

Архитектурные решения этого шага:
- `Opcode` расширен внутренней инструкцией `PrintLine`, потому что байткодному пути нужен явный способ завершить обычный `PRINT` переводом строки без дублирования пользовательской семантики во внешнем слое;
- в первом варианте эмиттер работает по routine-границам и не требует общего плоского буфера инструкций на весь модуль;
- отладочная карта собирается уже после удаления lowered-меток, поэтому `SourceInstructionMap` хранит итоговые индексы инструкций VM-уровня;
- таблица built-in заполняется по фактически использованным built-in вызовам, а не заранее по полному списку языка.

Текущая граница покрытия:
- скалярные литералы, переменные, арифметика, логика, сравнения, вызовы, `PRINT`, переходы и `RETURN` уже эмитируются;
- массивы, записи, `REDIM`, `ERASE`, файловые инструкции и полноценная runtime-модель VM остаются следующими шагами.

## Обновление 2026-04-23 - исполнение байткода в рантайме

Архитектурный разрыв между `Axiom.Bytecode` и `Axiom.Runtime` на первом исполняемом шаге закрыт так:
- `Axiom.Bytecode` отвечает за lowered-представление, эмиссию и валидацию модуля;
- `Axiom.Runtime` теперь содержит `BytecodeVm`, который исполняет `BytecodeModule`;
- модель значений остаётся общей для интерпретатора и VM: обе ветки используют `RuntimeValue` и `IRuntimeHost`.

Новые решения этого шага:
1. `BuiltinBinding` расширен каноническим `BuiltinFunctionId`:
   - внутренний built-in id модуля остаётся компактным идентификатором таблицы;
   - канонический id нужен VM для честного runtime-bridge без строковых догадок.
2. Кадр вызова VM оформлен отдельным типом `BytecodeCallFrame`:
   - routine;
   - instruction pointer;
   - аргументы;
   - локальные слоты;
   - evaluation-stack кадра;
   - позиция вызова для цепочки диагностики.
3. Evaluation-stack выбран покадровым, а не общим глобальным стеком:
   - это проще для ранней VM;
   - это напрямую соответствует правилу очистки вычислительного стека на границе routine.
4. Вывод `PRINT` в VM повторяет текущий рантайм-договор интерпретатора через отложенный буфер и `IRuntimeHost.WriteOutput`.
5. Runtime-ошибки VM не выбрасываются наверх как безымянные внутренние исключения:
   - они переводятся в `DiagnosticBag`;
   - для них используется тот же пользовательский уровень кодов, что и в интерпретаторе.

Текущая граница phase 5:
- есть минимальная стековая VM для скалярного модуля;
- есть первый built-in bridge для скалярных встроенных функций;
- есть тесты полного внутреннего прохода `Parse -> Bind -> Lower -> BytecodeCompiler -> BytecodeVm`;
- следующая архитектурная точка уже не внутри одной VM, а на стыке с `Axiom.Execution`.

## Обновление 2026-04-23 - подключение BytecodeVm к Axiom.Execution

Архитектурная граница между backend-слоем и пользовательским запуском теперь замкнута в `Axiom.Execution`.

Новый фактический конвейер в рабочем коде:
- `Compile`:
  - `Parse -> Bind -> BoundProgram`;
  - `BoundProgram -> LoweredProgram`;
  - `LoweredProgram -> BytecodeModule`;
- `Run`:
  - `Interpreter path`: `CompiledProgram -> Interpreter`;
  - `Bytecode path`: `CompiledProgram -> BytecodeVm`.

Новый договор `CompiledProgram`:
- `CompiledProgram` больше не является только контейнером frontend-подготовки;
- он хранит:
  - `ProgramSyntax`;
  - `BoundProgram`;
  - опциональный `LoweredProgram`;
  - опциональный `BytecodeModule`.

Новая роль `AxiomExecutionPipeline`:
- координирует оба backend-пути, а не только frontend и интерпретатор;
- умеет возвращать frontend- и backend-диагностики раздельно;
- умеет запускать:
  - `Interpreter`;
  - `BytecodeVm`;
- умеет принимать решение о fallback в режиме `Auto`.

Временный архитектурный механизм rollout:
- между наличием `BytecodeModule` и фактическим запуском через VM введён отдельный предикат покрытия;
- этот слой сейчас проверяет:
  - что байткодный модуль вообще собран;
  - что используются только поддержанные built-in;
  - что программа не попадает в известные пока непокрытые семантические зоны;
- именно этот слой делает переход на VM консервативным и не даёт `Auto` раньше времени объявить VM полным эквивалентом интерпретатора.

Текущие известные ограничения VM-покрытия закреплены архитектурно, а не оставлены как неявные совпадения:
- локальные routine пока не считаются покрытыми для пользовательского запуска через VM;
- `FOR`;
- локальные fixed-string переменные;
- объявления внутри вложенных блоков.

Договор режимов исполнения после этого шага:
- `Interpreter` всегда идёт в интерпретатор;
- `Auto` использует `BytecodeVm` только при успешной backend-подготовке и прохождении предиката покрытия;
- `Auto` при непокрытом срезе уходит в интерпретатор с явным `UsedInterpreterFallback`;
- `Bytecode` не подменяет выполнение интерпретатором и возвращает backend-ошибку, если текущая программа ещё не готова для VM.

Это первый шаг фазы 9: байткодный backend уже включён в реальный путь исполнения, но пока работает как ограниченный VM-first rollout для покрытого скалярного подмножества языка.

## Обновление 2026-04-23 - runtime-проверка шага FOR в байткоде

При расширении VM-покрытия на `FOR ... NEXT` зафиксировано отдельное архитектурное решение:
- проверка `STEP 0` не остаётся внешним исключением в `Axiom.Execution`;
- она выражается внутри backend-цепочки через отдельную lowered-инструкцию и отдельный opcode байткода;
- `BytecodeVm` сама отвечает за диагностику `MB3004` по карте исходных инструкций.

Причина такого решения:
- простой допуск `FOR` в таблицу покрытия без runtime-проверки давал бы расхождение с интерпретатором;
- перенос проверки внутрь байткода сохраняет локальность семантики цикла и не размывает слой `Axiom.Execution` специальными условиями под отдельные конструкции языка.

После этого временная блокировка `FOR` в предикате VM-покрытия снимается. Непокрытыми архитектурно остаются локальные routine, локальные fixed-string переменные и объявления внутри вложенных блоков.

## Обновление 2026-04-23 - частичное включение локальных routine в VM-first rollout

Предикат покрытия в Axiom.Execution уточнён для локальной процедурной модели.

Новый архитектурный договор:
- локальные FUNCTION без захвата внешних переменных разрешены для пользовательского запуска через BytecodeVm;
- локальные SUB временно остаются за пределами пользовательского VM-покрытия, даже если не захватывают внешние переменные;
- захват внешнего параметра остаётся backend-ошибкой эмиттера BC5004;
- захват внешнего локала определяется уже на уровне execution-предиката и возвращает отдельную диагностическую ошибку покрытия MB4002;
- общий fallback в Auto теперь может брать причину не только из общего предиката покрытия, но и из реальной backend-диагностики эмиттера.

Это решение зафиксировано как сознательно консервативное:
- lowered-представление и прямой вызов локальных routine уже позволяют выполнять локальные функции без захвата;
- локальные SUB пока не выпущены в пользовательский VM-first слой, потому что процедурный путь для них ещё не доведён до стабильного паритета;
- модель захватов всё ещё не переводится в отдельную runtime-структуру замыканий, а до этого шага разрешается только безопасный неперехватывающий срез.
## Обновление 2026-04-23 - стековый контракт вызова SUB в lowered-представлении

При расширении VM-покрытия на локальные SUB зафиксировано важное внутреннее правило lowered-слоя:
- вызов SUB в операторной позиции остаётся обычным CallFunction к routine с ReturnType == VOID;
- такой вызов не должен завершаться служебным Pop, потому что VM по соглашению о вызове не кладёт значение VOID на evaluation-stack;
- тем самым стековый контракт вызова SUB и FUNCTION расходится не на уровне opcode, а на уровне наличия или отсутствия последующего Pop в lowered-инструкциях.

После этого архитектурная граница локальной процедурной модели выглядит так:
- локальные routine без захвата уже допускаются в пользовательский VM-first rollout;
- захваты внешних параметров и локалов всё ещё не переводятся в отдельную runtime-модель замыканий и потому остаются за пределами текущего покрытия.
## Обновление 2026-04-23 - shared-slot модель захватов в BytecodeVm

Архитектура локальных routine в байт-кодном пути расширена до прямых захватов внешнего окружения без ввода отдельного нового формата значений.

Новый внутренний договор:
1. `LoweredRoutine` хранит собственный список объявленных локальных переменных:
   - это нужно, чтобы эмиттер различал собственные локалы routine и реальные захваты внешних значений;
   - в этот список входят и синтетические временные переменные lowered-слоя.
2. `BytecodeRoutine` хранит три отдельные таблицы видимых переменных:
   - `ParameterVariables`;
   - `LocalVariables`;
   - `CapturedVariables`.
3. В набор инструкций `Opcode` добавлены:
   - `LoadCapture`;
   - `StoreCapture`.
4. `BytecodeVm` использует не голые `RuntimeValue` для локальных кадров, а изменяемые ячейки `BytecodeVariableSlot`:
   - аргументы, локалы и захваты представлены одинаковым типом слота;
   - локальная routine получает для захвата ту же ячейку, что и охватывающая routine;
   - благодаря этому запись в захваченную переменную меняет общее хранилище, а не временную копию.
5. `BytecodeCallFrame` строит карту видимых переменных routine:
   - по ней VM разрешает захваты во время `Call`;
   - это позволяет локальным `SUB` и `FUNCTION` читать и менять внешние параметры и локалы без отдельной интерпретаторной ветки.

Текущая архитектурная граница:
- покрыты прямые локальные вызовы с захватом;
- полноценные значения-функции и возвращаемые замыкания в байт-кодном пути ещё не считаются завершённым слоем.

## Обновление 2026-04-23 - fixed-string слоты и метки после lowered no-op

При следующем расширении покрытия VM зафиксированы ещё два внутренних решения.

1. Fixed-string нормализация перенесена прямо в байт-кодный runtime-контракт хранения:
   - `BytecodeGlobal` теперь хранит `FixedStringLength`;
   - `BytecodeVariableSlot` хранит длину fixed-string для локального слота, если она есть;
   - `BytecodeVm` нормализует строку при записи в глобал, локал или захват через `CopyForStorage(fixedStringLength)`;
   - это даёт тот же наблюдаемый результат, что и интерпретатор, без отдельного обходного пути.
2. Разрешение меток в `BytecodeCompiler` больше не считает lowered-инструкции, которые не эмитятся в байткод:
   - это особенно важно для lowered `Convert` и других no-op инструкций эмиттера;
   - после правки переходы в `SELECT CASE` и других конструкциях не получают смещённые цели из-за инструкций, исчезающих на стадии эмиссии.

После этого вложенные `DIM` внутри блочных конструкций больше не требуют отдельного execution-запрета: их корректность обеспечивается самим lowered/bytecode/VM-путём.

Архитектура VM-пути расширена ещё одним целевым слоем без изменения общей схемы модулей.

Новый договор этого шага:
1. `BytecodeVm` получает не отдельные разовые исключения в `Axiom.Execution`, а собственную реализацию строковых built-in внутри рантайма.

## Обновление 2026-04-24 - функции даты и времени в BytecodeVm

Мост встроенных функций VM расширен на календарно-временную группу без добавления нового формата значений.

Архитектурные решения:
- `BytecodeVm.Builtins.DateTime.cs` содержит отдельную реализацию функций даты и времени рядом со строковыми и числовыми частичными файлами VM.
- VM продолжает работать поверх обычного `RuntimeValue`: даты, время и дата-время остаются каноническими строками, как в интерпретаторе.
- Текущее время, локальная зона и разрешение имён зон идут через общий `IRuntimeHost`; байт-кодный модуль не хранит текущее время и не привязывается к зоне машины во время эмиссии.
- Диспетчер `CallBuiltin` по-прежнему выбирает реализацию по `BuiltinFunctionId`; отдельные опкоды для `DATE`, `TIME`, `DATEADD` и подобных функций не вводятся.
- Ошибки аргументов остаются частью слоя VM и возвращаются как обычные runtime-диагностики `MB3007`, а не как внутренние исключения.

`Axiom.Execution` расширяет предикат покрытия VM на эту группу. Поэтому программы, которые используют функции даты и времени и не выходят за другие текущие границы байт-кодного пути, в режимах `Auto` и `Bytecode` исполняются через `BytecodeVm`.

После этого шага из крупных непокрытых групп остаются массивные функции, `TYPE`, fixed-string внутри контейнеров, файловый слой и функции регулярных выражений, возвращающие массивы.

## Обновление 2026-04-24 - базовый массивный слой в BytecodeVm

Первый массивный слой байткодного пути реализован без отдельного формата хранения данных. `BytecodeVm` по-прежнему работает поверх общей модели `RuntimeValue` и `RuntimeArrayValue`, поэтому `REDIM`, `REDIM PRESERVE`, `ERASE`, чтение и запись элемента мутируют тот же объект массива, что и интерпретаторный путь.

В `Axiom.Bytecode` lowered-модель расширена инструкциями `RedimArray`, `EraseArray`, `LoadElement` и `StoreElement`. Они отделяют массивную семантику от высокоуровневого bound-дерева: объявление массива с фиксированными границами понижается в загрузку текущего массива, вычисление нижней и верхней границы и `RedimArray`; доступ `values(index)` понижается в загрузку массива, индекса и `LoadElement`; присваивание элементу вычисляет значение, затем массив и индекс, чтобы сохранить текущий порядок вычисления интерпретатора.

Эмиттер байткода использует уже зарезервированные опкоды `RedimArray`, `EraseArray`, `LoadElement` и `StoreElement`. Для диагностики в инструкцию записывается индекс строковой константы с отладочным именем массива, а для `RedimArray` дополнительно хранится признак `PRESERVE`. Валидатор модуля теперь проверяет двухоперандную форму `RedimArray` и индексы констант у массивных инструкций.

В `BytecodeVm` массивная логика вынесена в `BytecodeVm.Arrays.cs`, а простые функции сведений о массиве вынесены в `BytecodeVm.Builtins.Array.cs`. На этом этапе в VM-покрытие входят `LBOUND`, `UBOUND`, `ARRAYLENGTH` и `ARRAYISALLOCATED`; более сложные функции вроде `ARRAYCLONE`, `ARRAYSLICE`, `ARRAYCONCAT`, сортировки, поиска и higher-order функций остаются следующей очередью.

`Axiom.Execution` расширяет предикат покрытия VM на эту первую массивную группу. Поэтому программы с поддержанными одномерными массивами, `REDIM`, `ERASE` и простыми функциями сведений о массиве могут исполняться через `BytecodeVm` в режимах `Auto` и `Bytecode`, если остальная часть программы уже входит в текущий VM-срез.

## Обновление 2026-04-24 - мутирующие массивные built-in в BytecodeVm

Массивный мост VM расширен на функции и процедуры, которые меняют `RuntimeArrayValue` на месте: `ARRAYFILL`, `ARRAYREVERSE`, `ARRAYSORT`, `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE`.

Генератор байткода теперь явно отвергает любое lowered-преобразование `Convert`, для которого нет кода целевого типа в `BytecodeScalarTypeCode`.

Архитектурные решения:
- `Opcode.Convert` остаётся инструкцией только для числовых скалярных типов `INTEGER`, `LONG`, `DOUBLE` и `DECIMAL`;
- преобразования к `STRING`, `BOOLEAN`, массивам, функциям, пользовательским типам и файлам не должны молча исчезать из потока инструкций;
- `BytecodeCompiler` сообщает `BC5008` для любого неподдержанного целевого типа, а не только для части составных типов;
- это сохраняет границу между семантическим анализом и VM: передние слои решают, какие преобразования допустимы для пользовательской программы, а генератор байткода защищает внутренний договор lowered-формы.

Пользовательская семантика языка не изменена: это уточнение внутренней диагностической границы байткодного пути.

Валидатор байткодного модуля теперь проверяет не только существование индекса константы, но и ожидаемый вид константы для инструкций, где это является частью договора формата.

Архитектурные решения:

- ошибки вида константы останавливаются на границе `BytecodeModuleValidator`, а не проявляются позднее в `BytecodeVm` как запасное имя или неверное значение стека;

Пользовательская семантика языка не изменена: это уточнение внутренней проверки байткодного формата.

## Обновление 2026-04-24 - стековая проверка байткодного модуля

`BytecodeModuleValidator` расширен с проверки отдельных инструкций до лёгкой проверки стековой формы процедуры.

Архитектурные решения:
- валидатор проверяет коды `PrintSeparator`, флаг `PRESERVE` в `RedimArray` и защищает расчёт переменной формы `Input` от переполнения;
- для каждой процедуры валидатор проходит достижимые инструкции и отслеживает высоту стека вычислений;
- инструкция, которая снимает больше значений, чем доступно на стеке, сообщает диагностическое сообщение до запуска VM;
- `Return` должен видеть пустой стек в процедуре без результата и ровно одно значение в функции;
- если разные пути управления сходятся к одной инструкции с разной высотой стека, модуль считается невалидным;
- стековая проверка запускается только после успешной проверки отдельных инструкций процедуры, чтобы не создавать каскадные сообщения поверх уже найденной ошибки формата.

Это не заменяет семантический анализ типов и не меняет пользовательское поведение языка. Проверка защищает внутренний договор: модуль, принятый валидатором, не должен падать в VM из-за очевидной стековой несогласованности.

## Обновление 2026-04-24 - проверка метаданных процедур байткодного модуля

`BytecodeModuleValidator` теперь проверяет целостность таблиц переменных внутри каждой процедуры до стековой проверки.

Архитектурные решения:
- таблица параметров процедуры должна иметь столько записей, сколько объявлено в `ParameterCount`;
- таблица локальных переменных должна иметь столько записей, сколько объявлено в `LocalSlotCount`;
- запись параметра должна быть `ParameterSymbol` с порядковым номером, совпадающим со слотом;
- локальная запись не должна быть глобальной переменной или параметром;
- захваченная запись не должна быть глобальной переменной;
- один и тот же символ переменной не должен повторяться в таблицах видимых переменных процедуры.

Эта проверка нужна потому, что `BytecodeVm` использует метаданные переменных не только для отладки: они определяют значения по умолчанию локальных слотов, длину fixed-string, цели `INPUT` и передачу захваченных переменных в локальные функции. Ошибки теперь останавливаются на границе валидатора, а не проявляются позже как внутренний сбой VM.

Пользовательская семантика языка не изменилась: это усиление внутреннего договора байткодного формата.

## Обновление 2026-04-24 - проверка метаданных built-in таблицы байткодного модуля

`BytecodeModuleValidator` теперь проверяет согласованность записей `BuiltinBinding` с исходным `FunctionSymbol`, когда такой символ сохранён в модуле.

Архитектурные решения:
- неизвестный числовой код `BuiltinFunctionId` считается ошибкой формата модуля;
- если `BuiltinBinding.Function` задан, он обязан быть встроенным `FunctionSymbol`, а не пользовательской функцией;
- канонический идентификатор записи должен совпадать с `FunctionSymbol.BuiltinId`;
- имя записи должно совпадать с именем символа без учёта регистра;
- число параметров в записи должно совпадать с числом параметров символа;
- признак возвращаемого значения должен совпадать с типом результата символа.

Эта проверка защищает путь значений встроенных функций: `LoadBuiltinFunction` создаёт функциональное значение из сохранённого символа, а последующий вызов VM ищет соответствующую запись built-in таблицы. Противоречивая таблица теперь отвергается валидатором до исполнения.

Пользовательская семантика языка не изменилась: это уточнение внутреннего договора байткодного модуля.

## Обновление 2026-04-24 - проверка отрицательных операндов байткодных инструкций

`BytecodeInstruction` больше не отбрасывает отрицательные операнды в конструкторе. Это осознанное разделение ответственности: модель инструкции хранит данные байткодного формата, а `BytecodeModuleValidator` отвечает за смысловую проверку пригодности модуля к исполнению.

Архитектурные решения:
- отрицательный индекс константы сообщает `BC4081` до обращения к `ConstantPool`;
- отрицательная цель перехода сообщает `BC4082` до расчёта достижимых инструкций;
- отрицательные глобальные, локальные, аргументные и захваченные слоты сообщают `BC4083`-`BC4086` до обращения к таблицам и массивам VM;
- `Input` проверяет отрицательное количество значений отдельной диагностикой `BC4087` и дополнительно применяет проверки отрицательных целевых слотов для всех поддержанных видов цели;
- `PrintSeparator` и `RedimArray` теперь явно отвергают отрицательные коды разделителя и флага `PRESERVE`, а не полагаются на прежний общий запрет в конструкторе инструкции;
- стековая проверка по-прежнему запускается только после успешной проверки отдельных инструкций процедуры, поэтому отрицательные операнды не создают каскадных сообщений в анализе графа переходов.

Это изменение усиливает границу между хранением байткодных данных и проверкой исполнимого договора. Пользовательская семантика языка не изменилась, поэтому новые `.axm`-примеры и страницы справочника не требуются.

Модель байткодного модуля продолжает разделяться на хранение данных формата и проверку пригодности к исполнению. `BytecodeModule`, `BytecodeRoutine`, `BytecodeGlobal` и `BuiltinBinding` больше не отбрасывают отрицательные идентификаторы, слоты и счётчики в конструкторах. Это сохраняет границу ответственности: исполняющий слой получает только модуль, прошедший `BytecodeModuleValidator`, а модель байткода остаётся пригодной для тестов повреждённых модулей и будущего загрузчика байткодных данных.

`BytecodeHeader` теперь хранит пробельные строки версии языка и токена совместимости как данные формата, а не отбрасывает их в конструкторе. Пригодность этих значений определяет `BytecodeModuleValidator`: пустая версия языка становится диагностикой `BC4100`, а несовместимый или пустой токен совместимости по-прежнему останавливается как `BC4069`.

`BytecodeModuleValidator` также проверяет форму записей `ConstantPool` до запуска VM:
- неизвестный `BytecodeConstantKind` сообщает `BC4102`;
- значение константы должно соответствовать её виду: `Integer` хранит `int`, `Long` хранит `long`, `Double` хранит `double`, `Decimal` хранит `decimal`, `String`, `RoutineName` и `BuiltinName` хранят `string`, `Boolean` хранит `bool`, а `Null` хранит `null`;

Эта проверка защищает `BytecodeVm.ReadConstant`, где значение константы приводится к типу по `BytecodeConstantKind`. Повреждённый модуль теперь должен быть отвергнут валидатором, а не проявляться поздним исключением при исполнении `PushConst`. Пользовательская семантика языка не изменилась.

Отрицательные ссылки теперь отделены от неизвестных, но неотрицательных ссылок, которые по-прежнему проходят через существующие диагностики отсутствующей процедуры или встроенной функции. `BytecodeModuleValidator` теперь проверяет не только форму операндов `Input`, но и типы целевых переменных по таблицам глобальных, локальных, параметрических и захваченных слотов процедуры.

Архитектурные решения:

Это закрывает путь, где повреждённый модуль раньше мог пройти форматную проверку и дойти до внутренней ошибки VM вроде `INPUT does not support array`. Пользовательская семантика языка не изменилась: семантический анализ по-прежнему отвечает за пользовательскую корректность программы, а валидатор защищает исполняемый байткодный формат.

## Обновление 2026-04-24 - лёгкая проверка типов стека байткодного модуля

`BytecodeModuleValidator` получил второй стековый проход поверх уже существующей проверки высоты стека. Новый проход отслеживает только те типы, которые можно уверенно вывести из констант, таблиц переменных, ссылок на процедуры и записей встроенных функций. Если тип значения неизвестен, валидатор не делает предположений и не сообщает ошибку.

Архитектурные решения:
- проверка типов запускается только после успешной проверки отдельных инструкций и высоты стека процедуры;
- при слиянии путей управления несовпадающие типы одной и той же стековой позиции превращаются в неизвестный тип, а не в ошибку;
- `OpenFile` проверяет, что путь имеет тип `STRING`, а файловая переменная имеет тип `FILE`;
- `CloseFile` проверяет значение `FILE`;
- `RedimArray`, `EraseArray`, `LoadElement` и `StoreElement` проверяют массивную цель и числовые границы или индекс;
- `LoadField` и `StoreField` проверяют, что целевое значение является пользовательским `TYPE`, а указанное поле существует;
- `PrintUsing` проверяет, что форматная строка имеет тип `STRING`;
- условные переходы проверяют логический тип условия.

Новые диагностики формата:
- `BC4111` для ожидаемого точного типа стекового значения;
- `BC4112` для ожидаемого массива;
- `BC4113` для ожидаемого числового значения;
- `BC4114` для ожидаемого пользовательского `TYPE`;
- `BC4115` для отсутствующего поля в известном `TYPE`;
- `BC4116` для значения, несовместимого с типом элемента массива или поля.

Это не заменяет семантический анализ и не пытается вывести типы всех выражений байткода. Цель прохода уже: отсеивать повреждённые модули, которые иначе доходят до `AsString`, `AsFile`, `AsArray` или `AsRecord` внутри VM и превращаются во внутренние ошибки исполнения. Пользовательская семантика языка не изменилась.

## Обновление 2026-04-24 - проверка записей в слоты в стековом проходе

Лёгкий стековый проход `BytecodeModuleValidator` теперь проверяет не только операции с файлами, массивами, записями, форматированным выводом и условными переходами, но и запись значения в переменные.

Архитектурные решения:
- `StoreGlobal` сверяет выведенный тип значения на стеке с типом записи в таблице глобальных переменных;
- `StoreLocal`, `StoreArgument` и `StoreCapture` сверяют значение с типом соответствующего слота процедуры;
- проверка выполняется только после базовой проверки существования слота, поэтому сообщения о несуществующих слотах остаются отдельной ответственностью уже существующих проверок;
- неизвестный тип значения остаётся допустимым состоянием анализа и не создаёт ошибку;
- несовместимость известного значения и известного целевого типа остаётся общей диагностикой `BC4116`.

Такой слой сохраняет разделение ответственности: семантический анализ по-прежнему отвечает за пользовательскую корректность исходной программы, а валидатор байткода отсеивает повреждённые или вручную собранные исполнимые модули до запуска VM.

## Обновление 2026-04-24 - проверка вызовов и возврата в стековом проходе

Лёгкий стековый проход `BytecodeModuleValidator` расширен на инструкции `Call`, `CallBuiltin` и `Return`.

Архитектурные решения:
- для `Call` валидатор снимает типы аргументов со стека в порядке параметров целевой процедуры и сверяет их с `ParameterVariables`;
- для `CallBuiltin` валидатор сверяет аргументы с параметрами сохранённого `FunctionSymbol` встроенной функции;
- числовые встроенные функции сохраняют уже существующее поведение привязчика и VM: если параметр записан как `DOUBLE`, валидатор допускает любой известный числовой тип аргумента;
- для `Return` валидатор сверяет вершину стека с типом результата процедуры;
- неизвестный тип значения остаётся допустимым состоянием анализа и не создаёт ошибку;
- все несовместимости этого слоя используют общую диагностику `BC4116`.

Проверка остаётся проверкой исполнимого байт-кодного модуля, а не повторной реализацией семантического анализа исходной программы.

## Обновление 2026-04-24 - проверка видимости захваченных переменных

`BytecodeModuleValidator` теперь проверяет ещё одно предположение `BytecodeVm`: процедура может передать захваты целевой процедуре только тогда, когда эти переменные видны в текущем кадре.

Архитектурные решения:
- для `Call` и `LoadFunction` валидатор строит множество видимых переменных текущей процедуры из параметров, локальных переменных и захваченных переменных;
- каждая запись `CapturedVariables` целевой процедуры должна входить в это множество;
- если захваченная переменная не видна из текущей процедуры, валидатор сообщает `BC4117`;
- проверка применяется к прямым вызовам и к созданию функциональных значений, поэтому она также закрывает пользовательские функции, передаваемые в массивные встроенные функции как обратный вызов;
- точная совместимость типа функционального значения в массивных обратных вызовах остаётся частью проверки аргументов `CallBuiltin`.

Это сохраняет границу ответственности: привязчик строит корректные замыкания из исходной программы, а валидатор отсекает повреждённые исполнимые модули, которые не могут собрать массив захваченных слотов для VM.

## Обновление 2026-04-24 - проверка операторных инструкций в стековом проходе

Лёгкий стековый проход `BytecodeModuleValidator` расширен на операторные инструкции, которые раньше могли дойти до внутренних проверок `BytecodeVm` вроде `AsInteger`, `AsDouble`, `AsString`, `AsBoolean` или до неподдерживаемого преобразования.

Архитектурные решения:
- `Negate` и `ValidateForStep` проверяют числовой тип операнда через уже существующую диагностику `BC4113`;
- `Not` допускает `BOOLEAN`, `INTEGER` и `LONG`, как текущая VM;
- `Convert` сверяет известный исходный тип с допустимыми скалярными преобразованиями VM;
- бинарные арифметические, логические операции и операции сравнения сверяют совместимость известных типов операндов по границам текущего `BytecodeVm`;
- для операций сравнения стековый проход выводит результат `BOOLEAN`, чтобы последующие `JumpIfTrue` и `JumpIfFalse` могли проверяться без потери типа;
- неизвестный тип остаётся допустимым состоянием анализа и не создаёт ошибку.

Несовместимые известные типы операторных операндов и неподдерживаемые преобразования используют общую диагностику `BC4116`. Это по-прежнему не является повторной реализацией семантического анализа исходной программы: валидатор проверяет только исполнимую стековую форму модуля перед запуском VM.

## Обновление 2026-04-24 - запасные сигнатуры встроенных функций для валидатора байткода

`BytecodeModuleValidator` теперь может проверять `CallBuiltin` даже тогда, когда запись `BuiltinBinding` не содержит сохранённого `FunctionSymbol`. Для этого слой семантических описателей встроенных функций открыл поиск описателя по `BuiltinFunctionId`.

Архитектурные решения:
- `BuiltinFunctions.TryGetDescriptor(BuiltinFunctionId, out BuiltinFunctionDescriptor)` является узким доступом к уже существующей таблице описателей и не дублирует список встроенных функций в байткодном слое;
- если в `BuiltinBinding` есть `FunctionSymbol`, валидатор использует его как наиболее точную сигнатуру;
- если символа нет, валидатор берёт параметры и объявленный тип результата из канонического описателя встроенной функции;
- числовые встроенные функции сохраняют прежнюю совместимость: обобщённый параметр `DOUBLE` в описателе принимает известные числовые стековые типы;
- массивные встроенные функции в запасном режиме проверяются по факту массивного аргумента, потому что точные типы элементов для обобщённых массивных описателей могут быть разрешены только при наличии конкретной сигнатуры;
- тип результата без `FunctionSymbol` выводится из политики результата описателя, когда это безопасно: объявленный тип, тип первого аргумента или тип элемента первого массива.

Это уменьшает зависимость проверок байткода от полноты сериализованного символа функции и не переносит семантический анализ исходной программы в валидатор. Валидатор по-прежнему работает только с теми типами, которые можно вывести из исполнимого модуля.

## Обновление 2026-04-24 - точные массивные callback-сигнатуры в запасном режиме

Запасная проверка `CallBuiltin` для массивных встроенных функций стала точнее: она больше не принимает любой `FunctionTypeSymbol` для callback-параметров, если по стеку уже известен тип массива.

Архитектурные решения:
- проверка обобщённой массивной built-in получает весь список фактических стековых типов аргументов, а не только текущий аргумент;
- тип элемента первого массива используется как источник `<T>` для параметров `value`, `predicate`, `selector` и `reducer`;
- `predicate` проверяется как `FUNCTION(<T>) AS BOOLEAN`;
- `selector` проверяется как `FUNCTION(<T>) AS <R>` с запретом `VOID` и вложенного массива в результате;
- `reducer` проверяется как `FUNCTION(<A>, <T>) AS <A>`, где `<A>` берётся из seed-аргумента;
- результат `ARRAYMAP` без сохранённого `FunctionSymbol` выводится как `ARRAY OF <R>`;
- результат `ARRAYREDUCE` без сохранённого `FunctionSymbol` выводится как тип seed-аргумента.

Это остаётся лёгкой проверкой байткодного формата: если нужный тип неизвестен, валидатор не создаёт предположений. Когда типы известны, повреждённый модуль теперь отсеивается до запуска VM.

## Обновление 2026-04-24 - арифметические инструкции байткодной VM

Байткодный слой расширен четырьмя операторными инструкциями:
- `Power` для оператора `^`;
- `IntegralDivide` для оператора `\`;
- `ShiftLeft` для оператора `<<`;
- `ShiftRight` для оператора `>>`.

Распределение ответственности:
- `BoundProgramLowerer` по-прежнему передаёт оператор как `LoweredInstructionKind.BinaryOperation`;
- `BytecodeCompiler` сопоставляет `SyntaxKind.CaretToken`, `SyntaxKind.BackslashToken`, `SyntaxKind.LessLessToken` и `SyntaxKind.GreaterGreaterToken` с новыми `Opcode`;
- `BytecodeVm` исполняет новые инструкции теми же правилами, что интерпретатор;
- `BytecodeModuleValidator` учитывает новые инструкции в проверке высоты стека и в лёгкой проверке типов стековых значений.

Покрытие VM расширено без изменения семантического слоя и без нового пользовательского синтаксиса. Старый сценарий отката `Auto` теперь закреплён на косвенном вызове функционального значения, потому что прямые арифметические операторы больше не являются границей байткодного исполнения.
## Обновление 2026-04-24 - CallValue для косвенных вызовов функциональных значений

Байткодный слой получил отдельную инструкцию `CallValue` для вызова функционального значения, которое уже вычисляется выражением и лежит на стеке.

Распределение ответственности:
- `BoundProgramLowerer` оставляет прямые вызовы пользовательских и встроенных функций на существующем пути `CallFunction`, а для недиректной цели сначала понижает целевое выражение, затем аргументы и добавляет `CallValue`;
- `BytecodeCompiler` выпускает `Opcode.CallValue` с числом аргументов и признаком наличия возвращаемого значения;
- `BytecodeVm` снимает аргументы и функциональное значение со стека, затем использует уже существующий путь `InvokeBytecodeFunction`, поэтому пользовательские функции, замыкания и встроенные функции вызываются теми же правилами, что и в массивных обратных вызовах;
- `BytecodeModuleValidator` проверяет форму `CallValue`, высоту стека, функциональный тип цели, число аргументов, совместимость типов аргументов и признак возвращаемого значения.

Это расширяет исполняемое покрытие VM для программ вида `op = AddOne : PRINT op(4)` без изменения синтаксиса, привязки имён или пользовательской семантики языка.

## Обновление 2026-04-25 - два явных режима исполнения

`ExecutionMode.Auto` удалён из целевой архитектуры запуска. В `Axiom.Execution` остаются два режима:
- `Bytecode` - основной режим по умолчанию, который запускает `BytecodeVm` и при неподдержанном байткодном срезе возвращает диагностированную ошибку слоя байткода;
- `Interpreter` - явный эталонный режим для сравнения поведения, диагностики и регрессионных проверок.

Слой `Axiom.Execution` больше не принимает решение о скрытом откате на интерпретатор. `UsedInterpreterFallback` остаётся в модели результата только как совместимое поле результата и не используется как рабочая стратегия для текущего публичного запуска.

В `Axiom.Ide` меню выбора режима запуска сокращено до `Interpreter` и `Bytecode`. Сохранённое состояние оболочки нормализует старую строку `Auto` в `Bytecode`, чтобы старые локальные настройки не ломали запуск IDE.

## Обновление 2026-04-25 - сериализуемый снимок BytecodeModule

В `Axiom.Bytecode` добавлен отдельный слой `Serialization` для внутреннего JSON-снимка байткодного модуля.

Новые архитектурные элементы:
- `BytecodeModuleArtifact` и связанные записи описывают переносимый снимок данных `BytecodeModule`;
- `BytecodeModuleSerializer` строит снимок и сериализует его в JSON;
- сериализатор не подключён к `Axiom.Execution`, `BytecodeVm` или IDE и не влияет на запуск программ.

Граница ответственности:
- `BytecodeModule` остаётся исполняемой in-memory моделью;
- `BytecodeModuleArtifact` является диагностическим и будущим файловым представлением;
- полный семантический граф символов не переносится в JSON, вместо него сохраняются имена, типы, признаки и коды встроенных функций;
- обратная загрузка JSON в исполняемый модуль пока не реализована и должна проектироваться отдельным шагом после стабилизации формы снимка.

## Обновление 2026-04-25 - чтение JSON-снимка и явная запись из конвейера

`BytecodeModuleSerializer` стал двусторонним для текущей внутренней формы снимка:
- `ToArtifact` и `SerializeToJson` сохраняют `BytecodeModule` в JSON;
- `DeserializeArtifactFromJson`, `DeserializeModuleFromJson` и `FromArtifact` восстанавливают артефакт или модуль;
- восстановленный модуль остаётся обязанностью `BytecodeModuleValidator`, а не считается доверенным только из-за успешного чтения JSON.

`Axiom.Execution` получил явную служебную точку записи снимка:
- `CompilationRequest.BytecodeSnapshotPath` просит `Compile` записать JSON после успешной эмиссии байткода;
- `ExecutionRequest.BytecodeSnapshotPath` передаёт тот же запрос через `Run`;
- запись выполняется только после успешного `BytecodeCompiler`;
- неудачная запись оформляется как backend-диагностика `MB4003` и не запускает программу при явно запрошенном снимке;
- без заданного пути конвейер не создаёт файлов и сохраняет прежний путь запуска.

JSON остаётся внутренним диагностическим и будущим файловым представлением. Он пока не является автоматическим входом для IDE или обычного запуска программы, потому что полная идентичность локальных символов и пользовательских типов ещё не закреплена в формате снимка.

## Обновление 2026-04-25 - идентификаторы символов в переносимом снимке

Переносимая форма `BytecodeModuleArtifact` получила устойчивые идентификаторы символов:
- `BytecodeFunctionSymbolArtifact.SymbolId`;
- `BytecodeFunctionSymbolArtifact.ContainingRoutineSymbolId`;
- `BytecodeVariableSymbolArtifact.SymbolId`.

`BytecodeModuleSerializer` назначает эти идентификаторы внутри одного снимка в порядке обхода модуля. Это не меняет исполняемую модель `BytecodeModule`, но делает JSON менее зависимым от совпадений имён. При чтении снимка сериализатор сначала использует `SymbolId`, а если старый снимок не содержит такого поля, возвращается к прежнему ключу по имени, типу и признакам.

Главная закрытая граница: две разные локальные переменные с одинаковыми именем и типом больше не объединяются при чтении нового JSON-снимка. Это приближает JSON-представление к будущему двоичному артефакту, где ссылочная идентичность символов должна быть частью формата, а не следствием семантического графа в памяти.

## Обновление 2026-04-25 - определения TYPE в переносимом снимке

`BytecodeModuleArtifact` получил таблицу `TypeDefinitions`, которая переносит форму пользовательских записей вместе с байткодным модулем. Это закрывает прежнюю слабую границу, где JSON сохранял только имя `UserDefinedTypeSymbol`, а после чтения получал незаполненный тип без полей.

Новые записи:
- `BytecodeTypeDefinitionArtifact` описывает один пользовательский `TYPE`;
- `BytecodeTypeFieldArtifact` описывает поле, его тип, fixed-string длину и границы фиксированного массива.

`BytecodeModuleSerializer` собирает пользовательские типы из всех типовых позиций модуля: процедур, параметров, локальных и захваченных переменных, глобальных переменных, встроенных функций и полей уже найденных пользовательских типов. При чтении снимка сначала создаются все типы по именам, затем выполняется заполнение полей. Такой порядок нужен для вложенных записей и массивов пользовательских типов.

JSON остаётся внутренним представлением, но теперь переносит достаточно данных, чтобы `BytecodeModuleValidator` и `BytecodeVm` могли проверять и исполнять доступ к полям восстановленного модуля без повторного семантического анализа исходного текста.

## Обновление 2026-04-25 - версия схемы JSON-снимка байткода

Корневой объект JSON-снимка `BytecodeModuleArtifact` теперь содержит `ArtifactSchemaVersion`.

Архитектурное решение:
- `BytecodeModuleSerializer.CurrentArtifactSchemaVersion` задаёт текущую поддерживаемую схему снимка;
- запись JSON всегда добавляет текущую версию схемы;
- восстановление `BytecodeModule` выполняет раннюю проверку схемы, версии формата байткода и совместимого токена;
- отсутствие `ArtifactSchemaVersion` временно допускается для старых переходных снимков и трактуется как совместимая первая схема.

Эта проверка находится в слое `Axiom.Bytecode.Serialization` и не переносится в VM: виртуальная машина должна получать уже восстановленный и проверенный `BytecodeModule`.

## Обновление 2026-04-25 - основа наблюдения за текущей инструкцией VM

`BytecodeVm` получил минимальную наблюдаемую точку выполнения для будущей отладки.

Архитектурные решения:
- `BytecodeVmExecutionSnapshot` находится в `Axiom.Runtime` рядом с VM и описывает текущую инструкцию без доступа к внутреннему кадру вызова;
- `BytecodeVm.Execute` сохраняет прежний путь запуска и принимает необязательный `Action<BytecodeVmExecutionSnapshot>`;
- наблюдатель вызывается перед выполнением инструкции, после проверки допустимости `InstructionPointer` и до изменения состояния инструкцией;
- исходная позиция определяется через `BytecodeDebugInfo.TryGetLocation`, а при отсутствии отладочной карты используется прежняя логика `ResolveLocation`;
- слой IDE пока не подключается к этому API, чтобы не смешивать инфраструктуру VM с пользовательским отладчиком.

Такой слой даёт тестируемую основу для будущих точек останова и пошагового выполнения, не меняя модель байткода и пользовательское поведение языка.
## Обновление 2026-04-25 - остановка VM перед инструкцией

Runtime-слой получил второй элемент будущей основы отладки байткодной VM. После `BytecodeVmExecutionSnapshot` в `BytecodeVm.Execute` добавлен необязательный предикат остановки `Func<BytecodeVmExecutionSnapshot, bool>`.

Порядок обработки инструкции теперь такой:
1. VM находит текущую инструкцию и строит `BytecodeVmExecutionSnapshot`.
2. Если задан наблюдатель, VM сообщает ему снимок.
3. Если задан предикат остановки и он возвращает `true`, VM сохраняет снимок в `RuntimeResult.StoppedAt` и завершает выполнение без исполнения этой инструкции.
4. Если остановки нет, VM увеличивает указатель инструкции и выполняет обычный `switch` по opcode.

Такой порядок оставляет будущему отладчику возможность останавливаться именно перед инструкцией, соответствующей исходной строке. IDE, модель точек останова и продолжение выполнения после остановки пока не проектировались в этом шаге.
## Обновление 2026-04-25 - набор точек останова VM

В runtime-слое добавлена небольшая модель точек останова поверх существующего предиката остановки `BytecodeVm`.

Архитектурные роли:
- `BytecodeSourceBreakpoint` - переносимое описание исходной строки или точной исходной позиции;
- `BytecodeBreakpointSet` - быстрый проверяющий набор строк и позиций;
- `BytecodeVm` - исполнитель, который объединяет набор точек останова с низкоуровневым предикатом `Func<BytecodeVmExecutionSnapshot, bool>`.

`BytecodeVm` по-прежнему не знает об IDE, вкладках редактора, пользовательском интерфейсе или хранении точек останова. Он видит только `BytecodeVmExecutionSnapshot` и проверяемый набор исходных координат. Такое разделение оставляет будущей IDE задачу преобразовать пользовательский щелчок в редакторе в `BytecodeBreakpointSet`, не меняя цикл исполнения VM.

## Обновление 2026-04-25 - состояние остановленного VM-запуска

В runtime-слое выделена модель состояния остановленного запуска VM.

Архитектурные роли:
- `BytecodeVmStopState` - контейнер остановки, который отделяет сам факт остановки от обычного результата выполнения;
- `BytecodeVmExecutionSnapshot` - снимок текущей инструкции внутри `BytecodeVmStopState`;
- `RuntimeResult.StopState` - основная точка доступа к состоянию остановленного запуска;
- `RuntimeResult.StoppedAt` - совместимое свойство для старого кода и тестов, возвращающее `StopState.Snapshot`.

`BytecodeVm` пока создаёт `BytecodeVmStopState` только с `CanResume = false`. Это сознательная граница: текущий слой описывает остановку, но не сохраняет полный исполнительный контекст для продолжения. Следующий архитектурный шаг должен отдельно определить, какие данные кадра, указателя инструкции, стека значений, открытых файлов и незавершённого вывода нужны для безопасного продолжения.

## Обновление 2026-04-25 - первый слой продолжения VM после остановки

В runtime-слое добавлено минимальное продолжение остановленного запуска `BytecodeVm`.

Архитектурное решение:
- `BytecodeVmStopState` теперь может удерживать ссылку на живой экземпляр `BytecodeVm`, если остановка создана внутри исполняемого запуска;
- `BytecodeVmStopState.Resume()` передаёт управление обратно VM и возвращает новый `RuntimeResult`;
- `BytecodeVm.ResumeFrom(...)` продолжает уже созданные кадры вызовов вместо повторного входа через `ExecuteModule`;
- старое состояние остановки можно использовать только один раз;
- при возобновлении VM пропускает проверку остановки ровно для той же routine-id/инструкции, на которой была остановлена, чтобы выполнить саму остановленную инструкцию.

Граница решения остаётся узкой: это не пользовательский отладчик и не интеграция с IDE. Текущий слой не вводит отдельную сериализацию исполнительного контекста и не обещает долговременное хранение остановленного запуска между процессами. Это живое продолжение в памяти одного runtime-запуска.

## Обновление 2026-04-25 - политика продолжения для строковых точек останова VM

В `BytecodeVm` добавлена отдельная политика продолжения после строковой точки останова.

Архитектурные детали:
- `BytecodeBreakpointSet` теперь отдельно проверяет строковые точки через `ShouldStopBeforeLineBreakpoint(...)` и точные позиции через `ShouldStopBeforePositionBreakpoint(...)`;
- `BytecodeVm` хранит строку, на которой нужно временно подавить только строковые точки останова после `Resume()`;
- пока VM остаётся на этой исходной строке, строковая точка не останавливает выполнение повторно;
- точные позиционные точки и ручной предикат остановки остаются отдельными механизмами и не превращаются в строковую пользовательскую политику.

Такое разделение сохраняет две модели: удобную пользовательскую строковую точку останова для будущей IDE и точный низкоуровневый контроль для runtime-тестов и внутренних сценариев.

## Обновление 2026-04-25 - проверка повторного захода на строковую точку VM

Для политики продолжения после строковой точки останова добавлена регрессионная проверка повторного захода на ту же исходную строку.

Архитектурно это закрепляет важную границу `_suppressLineBreakpointsUntilDifferentLine`: подавление строковой точки действует только пока VM остаётся на исходной строке, где было выполнено `Resume()`. Как только выполнение переходит на другую исходную строку, подавление снимается, и будущий заход на прежнюю строку снова проходит обычную проверку `BytecodeBreakpointSet`.

Это поведение нужно будущей IDE: команда продолжения не должна застревать внутри одной строки, но строковая точка в цикле должна срабатывать на каждой новой итерации.

В архитектуре основы отладки VM уточнена роль точных позиционных точек остановки.

`BytecodeBreakpointSet` сохраняет отдельные проверки для строковых точек и точных позиций. `BytecodeVm` использует это разделение при `Resume()`: пока строковые точки на исходной строке остановки временно подавлены, проверка точных позиций продолжает выполняться через `ShouldStopBeforePositionBreakpoint(...)`.

Такой порядок нужен, чтобы будущая IDE могла использовать строковые точки как пользовательское удобство без зацикливания на одной строке, а runtime-тесты и внутренние сценарии могли проверять конкретные инструкции той же строки по точным координатам.

## Обновление 2026-04-26 - архитектурная граница шага назад

Шаг назад в отладчике нельзя добавлять как новый метод продолжения в текущий `BytecodeVmStopState`.

Причина:
- `BytecodeVmStopState` хранит ссылку на живую остановленную VM и одноразово потребляется продолжением;
- после выполнения следующей инструкции исходное состояние VM уже потеряно;
- простое движение указателя инструкции назад не восстанавливает стек выражений, локальные переменные, глобальные переменные, кадры вызовов, незавершённый вывод, открытые файлы и состояние ввода.

Архитектурное решение для следующего этапа:
- ввести отдельный внутренний слой истории отладочного запуска;
- сохранять снимки состояния VM до выполнения инструкций или перед остановками;
- держать снимки в runtime-слое, чтобы IDE не знала внутреннюю форму стеков, кадров и значений;
- экспортировать в IDE только признак доступности шага назад и результат восстановления;
- сначала поддержать ограниченный чистый срез без внешних побочных эффектов;
- для `INPUT`, файлов, случайных чисел и других внешних эффектов ввести отдельное явное правило: запретить шаг назад в таких сеансах или позже реализовать журнал восстановления.

Граница ответственности:
- `Axiom.Runtime` отвечает за снимки и восстановление VM;
- `Axiom.Execution` переносит состояние доступности и результат восстановления в общий результат запуска;
- `Axiom.Ide` отвечает только за команду, доступность пункта меню и отображение восстановленного места;
- текущие режимы `Resume`, `StepOver`, `StepInto` и `StepOut` остаются основанными на одноразовом `BytecodeVmStopState`.

Это решение не меняет формат `BytecodeModule` и не требует изменений языка.

## Обновление 2026-04-26 - первый слой снимка состояния байткодной VM

В `Axiom.Runtime` добавлен внутренний объект снимка состояния VM для будущего шага назад.

Структура:
- `BytecodeVmStateSnapshot` хранит место выполнения, глобальные значения, кадры вызовов и незавершённый буфер вывода;
- `BytecodeCallFrameSnapshot` хранит процедуру, слоты аргументов, локальные слоты, захваченные слоты, стек выражений и указатель инструкции;
- `BytecodeVariableSlotSnapshot` хранит значение слота и длину фиксированной строки, если она есть.

`BytecodeVm` создаёт снимок перед выполнением инструкции и передаёт предыдущий доступный снимок в `BytecodeVmStopState` при остановке. Поэтому слой IDE в будущем сможет включать кнопку шага назад по признаку доступности, не зная внутреннего устройства VM.

Текущий снимок намеренно ограничен скалярными значениями. История сбрасывается при внешних эффектах: чтении `INPUT`, файловых операциях, записи накопленного вывода во внешний хост и вызовах встроенных функций. Это сохраняет архитектурное правило: обратимое выполнение сначала поддерживает только чистый управляемый участок состояния, а не имитирует откат внешнего мира.

## Обновление 2026-04-26 - восстановление runtime-состояния VM

`BytecodeVm` получил внутренний путь восстановления из `BytecodeVmStateSnapshot`.

Восстановление выполняет только runtime-слой:
- пересоздаёт словарь глобальных значений;
- пересобирает стек вызовов снизу вверх;
- восстанавливает аргументы, локальные слоты, захваченные слоты и стек выражений каждого кадра;
- восстанавливает незавершённый буфер вывода;
- сбрасывает временные границы пошагового выполнения и подавления точек остановки.

Для захваченных переменных восстановление сначала пытается связать захват с уже восстановленным видимым слотом внешнего кадра. Это сохраняет обычную модель замыкания, где захваченная переменная остаётся тем же слотом, а не независимой копией.

`BytecodeVmStopState.StepBack()` остаётся одноразовым действием над остановленной VM. После успешного отката создаётся новое остановленное состояние, указывающее на восстановленную инструкцию и на более ранний снимок, если он был сохранён.

## Обновление 2026-04-26 - прокладка шага назад до IDE

Доступность шага назад вынесена из runtime-слоя наружу без раскрытия внутренней формы снимка.

Слои:
- `Axiom.Runtime`: `BytecodeVmStopState` хранит внутреннюю ссылку на предыдущий снимок и выполняет `StepBack()`;
- `Axiom.Execution`: `ExecutionResult.CanStepBack` показывает только внешний признак доступности;
- `Axiom.Ide`: `ProgramRunResult.CanStepBack`, `ProgramRunService.StepBack()` и `MainWindowViewModel.StepBackCommand` используют этот признак и не знают структуру снимка.

В WPF-оболочке команда добавлена в меню `Отладка` и на панель быстрых действий. Горячая клавиша пока не назначена, чтобы не вводить конфликтный или случайный пользовательский договор.

## Обновление 2026-04-26 - обратимые function-value без захватов

Runtime-снимок VM теперь допускает bytecode-значения функций и процедур без захватов.

Причина:
- прямой вызов процедуры или функции перед `CallValue` может держать function-value на стеке выражений;
- прежний снимок считал любое function-value необратимым;
- из-за этого после `Step Into` внутрь процедуры первый останов внутри процедуры не имел доступного шага назад.

Новое правило:
- `FunctionTypeSymbol` со значением `null` обратим;
- встроенная функция обратима как ссылка на встроенный символ;
- bytecode-функция или процедура без захваченных слотов обратима как ссылка на символ;
- function-value с захваченными слотами пока не копируется, чтобы не потерять идентичность замыкания и не обещать неполный откат.

В IDE для шага назад назначена клавиша `Ctrl+F10`; она добавлена как обычный `InputBinding` рядом с остальными командами отладки.

## Обновление 2026-04-26 - обратимый вывод для шага назад

Для поддержки шага назад после `PRINT` добавлен необязательный интерфейс `IReversibleOutputWriter`.

Архитектурное решение:
- `IReversibleOutputWriter` расширяет вывод контрольной точкой и восстановлением к ней;
- `BytecodeVmStateSnapshot` хранит контрольную точку вывода, если хост её поддерживает;
- `BytecodeVm` восстанавливает эту контрольную точку при `StepBack`;
- `ExecutionRuntimeHostAdapter` откатывает свой список строк вывода и прокидывает откат дальше во внешний writer;
- `ProgramConsoleService` откатывает текст панели вывода IDE;
- `NullRuntimeHost` поддерживает только контрольную точку `0`;
- для хостов без `IReversibleOutputWriter` запись вывода остаётся внешним эффектом и сбрасывает историю обратимого выполнения.

Это сохраняет прежнюю границу ответственности: runtime знает только интерфейс обратимого вывода, а IDE остаётся владельцем конкретного текстового буфера.

## Обновление 2026-04-26 - синхронизация вывода и trace остановок

`MainWindowViewModel` теперь применяет `ProgramRunResult.OutputText` к панели вывода даже при пустом значении. Это нужно для обратного шага, который откатывает последний оставшийся вывод.

Добавлено trace-событие `run.stop-state`:
- при установке остановленного состояния пишет строку, колонку, opcode, глубину вызовов, `canResume`, `canStepBack`, документ и текущий вывод;

Это временно улучшает наблюдаемость отладчика до введения полноценного структурированного журнала IDE.

## Обновление 2026-04-26 - первый инфраструктурный слой структурированного журнала IDE

В `Axiom.Ide` введён отдельный слой событийного журнала:
- `IIdeEventLogService` - общий интерфейс структурированного журнала;
- `FileIdeEventLogService` - файловая реализация JSONL с фоновой записью;
- `NullIdeEventLogService` - безопасная заглушка для тестов и fallback-сценариев;
- `IdeEventLogEntry` и `IdeEventStatusBarSnapshot` - типизированная модель события и снимка статус-бара.

Архитектурное разделение:
- `IIdeTraceService` остаётся технической текстовой трассировкой для диагностических строк;
- `IIdeEventLogService` отвечает за машинно-читаемый событийный журнал пользовательских действий;
- оба сервиса живут параллельно и не заменяют друг друга.

Интеграция по слоям:
- `App` фиксирует события жизненного цикла (`startup`, `shutdown`, `exception.unhandled`);
- `IdeShellCompositionRoot` создаёт и передаёт `IIdeEventLogService` в `ProgramRunService`, `ProgramConsoleService` и `MainWindowViewModel`;
- `ProgramRunService` пишет события запуска/остановки/шагов отладки;
- `ProgramConsoleService` пишет события `input`/`output`;
- `MainWindowViewModel` пишет события команд оболочки, документов, файловых операций, смены вкладок и `status-bar.changed`.

Производительность и надёжность:
- запись идёт через ограниченную `Channel`-очередь и один фоновый writer;
- UI-поток только отправляет короткое событие в очередь;
- при перегрузке создаётся `events.dropped`, а IDE не блокируется;
- при выходе приложения выполняется `Flush`, затем `Dispose` сервиса.

Хранение:
- базовая папка: `%LOCALAPPDATA%\Axiom\Logs\Events` (fallback: `AppContext.BaseDirectory\Logs\Events`);
- файл сессии: `ide-events-YYYYMMDD-HHMMSS.jsonl`;
- ротация файла по лимиту размера и очистка каталога по сроку/объёму.

Разделение ответственности:
- `MainWindowViewModel` отвечает только за команду `ShowIdeEventLogViewerCommand`, сброс текущего журнала перед открытием и запись события `event-log.viewer-opened`;

Это сохраняет независимость слоя записи журнала `IIdeEventLogService`: запись событий, хранение и ротация файлов не зависят от того, открыт ли встроенный просмотр.

## Обновление 2026-04-26 - разделённое чтение активного файла журнала

`IdeEventLogViewerWindow` больше не использует `File.ReadLines` для чтения активного файла журнала. Окно открывает файл через явный `FileStream` с режимом `FileShare.ReadWrite | FileShare.Delete`.

Причина решения:
- `FileIdeEventLogService` держит активный `.jsonl` открытым для записи и разрешает чтение;
- стандартное чтение через `File.ReadLines` на Windows само запрещает уже открытую запись, поэтому активный файл мог давать ошибку `being used by another process`;
- явный режим разделённого доступа позволяет читать сброшенные строки без остановки фоновой записи журнала.

Для проверки сценария чтение вынесено в тестируемый метод `IdeEventLogViewerWindow.ReadEntries`, который используется и окном просмотра, и регрессионным тестом.

## Обновление 2026-04-26 - детализация и действия встроенного просмотра журнала

`IdeEventLogViewerWindow` расширен без изменения слоя записи журнала:
- таблица остаётся основным списком событий;
- выбранная строка преобразуется во внутренний `ViewerEntry`, который хранит краткую строку для таблицы, многострочные подробности и JSON-строку для копирования;

Такой подход оставляет просмотр однооконным и предсказуемым: окно не держит постоянный watcher файла, а пользователь сам решает, когда перечитать текущий журнал.

- По профилю `array_cube_rollup.axm` после этого шага `Convert` исчезает из горячего списка полностью, а его место занимает `AddLongInteger` с тем же числом срабатываний, что подтверждает именно структурное сжатие байткода, а не случайный шум замеров.
