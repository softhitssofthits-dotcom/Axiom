# План развития `TYPE` от записи к объектному ядру

## Кратко
Развиваем `TYPE` широкой, но поэтапной программой: сначала усиливаем текущую модель записи-значения, затем добавляем объектные механизмы внутри `TYPE`, и только после этого оставляем задел под наследование и полиморфизм.

Порядок этапов выбран так, чтобы:
- не ломать уже работающие поля, массивные поля, фиксированные строки и литералы `TypeName(Field := ...)`;
- сначала закрыть базовую семантику данных;
- потом на той же основе ввести методы, `SELF` и конструкторы;
- не фиксировать наследование слишком рано, но не закрыть к нему дорогу синтаксисом и runtime-моделью.

## Этапы реализации

### Этап 1. Значения полей по умолчанию в объявлении `TYPE`
Добавить и зафиксировать форму:
```basic
TYPE Person
    Name AS STRING = "Unknown"
    Age AS INTEGER = 18
END TYPE
```

Что меняется:
- внутри `TYPE` поле получает не только тип, но и необязательный инициализатор по умолчанию;
- `DIM user AS Person`, `Person()` и `Person(Name := "Ada")` используют эти значения по умолчанию для незаполненных полей;
- для полей без явного инициализатора сохраняются текущие стандартные значения;
- инициализаторы должны быть константными или безопасно вычислимыми без зависимости от runtime-контекста; это нужно зафиксировать сразу и не оставлять двусмысленности;
- для массивных полей и вложенных `TYPE` нужно отдельно определить допустимый минимум v1:
  - скалярные и строковые значения по умолчанию поддержать сразу;
  - сложные массивные и объектные литералы по умолчанию не включать в первый шаг, если они требуют отдельного контракта инициализации хранилища.

Технически:
- parser: разрешить `= expression` в объявлениях полей;
- semantics: хранить default initializer в символе поля;
- runtime и `BytecodeVm`: применять defaults при создании записи через `DIM`, `CreateRecord`, `TypeName()` и именованные литералы;
- manual и acceptance: обновить `docs/manual/type.html` и добавить отдельные `.axm`-сценарии.

### Этап 2. Структурное сравнение `TYPE`
Добавить для текущего `TYPE` структурную семантику `=` и `<>`.

Что меняется:
- `a = b` и `a <> b` для одного и того же `TYPE` сравнивают поля по значению;
- вложенные `TYPE` сравниваются рекурсивно;
- поля примитивных типов сравниваются по уже существующим правилам языка;
- для массивных полей в этой волне не вводить глубокий element-by-element compare автоматически, если это меняет существующую модель массивов; нужно зафиксировать одно из безопасных правил:
  - либо массивные поля структурного сравнения пока не поддерживают и дают явную диагностику;
  - либо сравниваются по уже существующей семантике массивного значения, если она уже точно определена и стабильна.
- сравнение разных `TYPE` должно быть семантической ошибкой.

Технически:
- semantics: разрешить бинарное сравнение пользовательских `TYPE` по новому правилу;
- runtime и `BytecodeVm`: добавить выполнение структурного compare;
- negative parity: проверить несопоставимые типы, неподдержанный вид поля, если такой останется;
- manual: описать отдельно, что текущий `TYPE` остаётся value-oriented.

### Этап 3. Явный договор передачи и возврата `TYPE`
Зафиксировать и, где нужно, довести семантику передачи записей в `SUB` и `FUNCTION`.

Что должно быть явно решено и реализовано:
- параметр `AS Person` по умолчанию передаётся по значению или по ссылке;
- если вводится `BYREF`/`BYVAL`, это делается уже здесь как общий языковой контракт, а не только для `TYPE`;
- возврат `FUNCTION ... AS Person` должен иметь полностью определённую семантику копирования;
- присваивание `TYPE` целиком, возврат из функции и передача в параметр должны согласованно работать в interpreter и `BytecodeVm`;
- литералы `TYPE(...)` должны быть допустимыми аргументами и значениями возврата там, где это типово корректно.

Рекомендуемый договор для этой программы:
- ввести явные `BYREF` и `BYVAL` как общий механизм;
- для `TYPE` по умолчанию сохранить value-oriented поведение;
- `BYREF` использовать как явный opt-in для мутации исходного экземпляра.

Технически:
- parser и symbols: поддержка `BYREF`/`BYVAL` в объявлениях параметров, если их ещё нет;
- binder: правила передачи для `TYPE`, массивов и вложенных пользовательских типов;
- runtime/VM: единая модель аргументов, возврата и записи обратно в вызывающий кадр для `BYREF`;
- manual: обновить `sub.html`, `function.html`, `type.html`.

### Этап 4. Методы внутри `TYPE`
Ввести `TYPE` как место не только для полей, но и для методов.

Целевая форма этапа:
```basic
TYPE Person
    Name AS STRING
    Age AS INTEGER

    FUNCTION IsAdult() AS BOOLEAN
        RETURN Age >= 18
    END FUNCTION

    SUB Rename(newName AS STRING)
        Name = newName
    END SUB
END TYPE
```

Что меняется:
- внутри `TYPE` кроме полей разрешаются объявления `SUB` и `FUNCTION`;
- методы принадлежат конкретному `TYPE`;
- внутри метода доступ к полям разрешён без префикса или через явный `SELF` в зависимости от выбранной формы;
- вызов идёт через точку: `user.IsAdult()`, `user.Rename("Ada")`.

Рекомендуемый договор:
- ввести неявный `SELF` как текущий экземпляр и одновременно разрешить явное ключевое слово `SELF`;
- методы пока не перегружаются по имени;
- статические методы не вводить в том же шаге, чтобы не смешивать два разных вида dispatch.

Технически:
- parser: разрешить routine-declarations внутри `TYPE`;
- symbols: добавить method symbols и принадлежность методу конкретного user-defined type;
- binder: отдельная область видимости метода с `SELF`;
- lowering/runtime/VM: вызов метода как обычной routine с неявным первым аргументом текущего экземпляра;
- IDE/manual: подсветка и структура страницы `TYPE` должны обновиться.

### Этап 5. Конструкторы и инициализация объекта
После появления методов ввести специальный инициализационный слой.

Рекомендуемая форма:
- либо специальный `SUB New(...)` внутри `TYPE`;
- либо явно именованный конструкторный метод вроде `INIT`, если `NEW` пока конфликтует с будущими планами;
- итоговый выбор должен быть единым и не требовать потом синтаксической миграции.

Рекомендуемый путь:
- использовать `SUB New(...)` внутри `TYPE`;
- вызов экземпляра через `Person(...)` постепенно переопределить так:
  - если нет конструктора, это текущий record-literal через `:=`;
  - если есть конструктор, он вызывается через отдельную форму, не смешанную с именованным литералом;
- не перегружать текущий литерал `Person(Name := ...)` ролью конструктора, чтобы не сломать уже обещанный договор.

Что включает этап:
- объектная инициализация после allocate/default-fill;
- возможность сочетать field defaults и конструктор;
- чёткий порядок: defaults -> явные field initializers literal-а -> конструктор, либо другой единый порядок, но он должен быть один раз жёстко зафиксирован.

### Этап 6. Минимальный объектный слой поверх `TYPE`
После методов и конструкторов добавить минимальные объектные удобства, не трогая наследование.

Сюда входит:
- `SELF` как официальная часть языка;
- явный вызов одного метода из другого через `SELF`;
- единые правила доступа к полям и методам внутри экземпляра;
- при необходимости — запрет на обращение к нестабильно инициализированному `SELF` внутри конструктора до завершения обязательных шагов инициализации.

Сюда не входит:
- наследование;
- виртуальные методы;
- переопределение;
- интерфейсы;
- protected/private/public, если отдельный договор модификаторов ещё не принят.

### Этап 7. Резерв под наследование и полиморфизм
Не реализовывать в этой волне, но принять ограничения, чтобы текущий синтаксис не запер будущее.

Нужно заранее не сломать:
- место для возможного `EXTENDS`/`INHERITS`;
- различие instance-методов и будущих type-level членов;
- internal shape method dispatch в binder и `BytecodeVm`;
- семантику `SELF`, чтобы позже можно было ввести полиморфный dispatch без ломки базового вызова.

В документах этот этап должен быть описан как резерв, а не как уже поддержанная возможность.

## Публичный контракт и синтаксис, который появится
В этой программе работ планируются такие пользовательские формы:

```basic
TYPE Person
    Name AS STRING = "Unknown"
    Age AS INTEGER = 18
END TYPE
```

```basic
IF a = b THEN
IF a <> b THEN
```

```basic
SUB Update(BYREF person AS Person)
FUNCTION Clone(BYVAL person AS Person) AS Person
```

```basic
TYPE Person
    Name AS STRING

    FUNCTION DisplayName() AS STRING
        RETURN Name
    END FUNCTION
END TYPE

PRINT user.DisplayName()
```

```basic
TYPE Person
    Name AS STRING

    SUB New(name AS STRING)
        SELF.Name = name
    END SUB
END TYPE
```

При этом пока сохраняются ограничения:
- `:=` остаётся локальным синтаксисом литералов `TYPE(...)`;
- наследование и полиморфизм не включаются;
- сравнение `TYPE` строится как value-oriented, а не identity-oriented.

Для каждого этапа нужны:
- parser tests;
- binder tests;
- `InterpreterTests`;
- `BytecodeVmTests`;
- `ExecutionPipelineTests` или acceptance через `Axiom.Execution.Tests`;
- runnable `.axm`-примеры в `samples/operators/type/`.

Минимальные новые acceptance-сценарии:

- `samples/operators/type/partial_named_literal_defaults.axm`
- `samples/operators/type/structural_equality.axm`

- `samples/operators/type/type_methods_self.axm`

Негативные сценарии:
- повторный default initializer, если форма окажется неоднозначной;
- недопустимый non-constant default для поля;
- сравнение разных `TYPE`;
- сравнение `TYPE` с неподдержанным видом поля, если такой случай останется закрытым;
- недопустимый `BYREF`/`BYVAL`;
- вызов метода как обычной функции без экземпляра;
- доступ к `SELF` вне метода;
- конфликт имён поля и метода;
- недопустимый вызов конструктора.

## Принятые допущения
- `TYPE` развивается как основа будущей объектности, а не только как запись.
- Первая программа работ широкая: значения по умолчанию, сравнение, передача, методы, конструкторы.
- Методы планируются внутри `TYPE`, а не только как внешние `SUB`/`FUNCTION`.
- Наследование и полиморфизм сейчас не реализуются, но под них сохраняется резерв.
- Базовая семантика сравнения текущего `TYPE` — структурная по полям.
- `:=` пока не расширяется на обычные вызовы и остаётся локальным для литералов записи.
- Документация и `.axm`-приёмка обновляются на каждом этапе, а не в конце всей программы.
