## Обновление 2026-04-27 - проектное решение первого среза многомерных массивов

Этот шаг фиксирует **целевой договор ближайшего кодового среза**, а не объявляет уже завершённую реализацию. Задача первого шага — добавить в язык плотные прямоугольные двумерные и N-мерные массивы без смешивания этого ядра с подмассивами, представлениями без копирования, broadcasting и другими следующими этапами.

### Цель первого шага

Первый срез многомерных массивов должен дать:
- многомерное объявление через `DIM`;
- многомерное перераспределение через `REDIM` и `REDIM PRESERVE`;
- индексирование в форме `array(i, j, ...)`;
- согласованную работу interpreter и `BytecodeVm` с одной и той же моделью измерений;
- многомерные формы `LBOUND` и `UBOUND` без ввода новых пользовательских имён.

В этом шаге **не** вводятся:
- подмассивы и срезы без копирования;
- новые специальные built-in для ранга, extents и shape;
- поэлементная арифметика между массивами;
- broadcasting;
- обобщение всех существующих `ARRAY...` built-in на многомерный случай.

### Общая модель

- Массив получает фиксированный ранг: одномерный, двумерный, трёхмерный и так далее.
- Ранг является частью типа массива и после объявления не меняется.
- Каждое измерение имеет собственные включительные границы `lower TO upper`.
- Первый срез вводит только плотные прямоугольные массивы. Рваные структуры и массивы массивов не входят в договор.
- Внутреннее хранение должно быть единым для interpreter и `BytecodeVm`: одно прямоугольное хранилище плюс метаданные измерений. Конкретный порядок линейзации в памяти остаётся внутренней деталью реализации, если пользовательское наблюдаемое поведение одинаково.
- Ссылочная семантика массива как значения сохраняется для любого ранга: присваивание массива целиком, передача в параметр и возврат из `FUNCTION` не создают автоматическую глубокую копию.
- Если элемент массива имеет пользовательский тип записи, присваивание значения в один элемент по-прежнему копирует саму запись как значение.

### Синтаксис объявления и типа

Одномерные формы сохраняются без изменений:
- `DIM values(1 TO 3) AS INTEGER`
- `DIM values() AS INTEGER`
- `INTEGER()`

Для двумерных и N-мерных массивов вводятся следующие формы:
- `DIM matrix(rowLower TO rowUpper, colLower TO colUpper) AS INTEGER`
- `DIM cube(xLower TO xUpper, yLower TO yUpper, zLower TO zUpper) AS DOUBLE`
- `DIM matrix(,) AS INTEGER`
- `DIM cube(,,) AS DOUBLE`
- `INTEGER(,)`
- `DOUBLE(,,)`

Правила:
- число измерений определяется числом диапазонов в объявлении или числом запятых в безразмерной форме типа;
- форма `DIM matrix(,) AS INTEGER` объявляет двумерный динамический массив без выделенного диапазона элементов;
- форма `DIM cube(,,) AS DOUBLE` объявляет трёхмерный динамический массив без выделенного диапазона элементов;
- форма `DIM values() AS INTEGER` остаётся одномерной;
- смешанная форма вида `DIM matrix() AS INTEGER` не означает «массив неизвестного ранга»: пустые скобки без запятых по-прежнему означают только одномерный динамический массив;
- параметры и тип результата функции используют ту же запись ранга, например `SUB Fill(grid AS INTEGER(,))` и `FUNCTION Clone(grid AS INTEGER(,)) AS INTEGER(,)`;
- тот же синтаксис ранга теперь допустим и для массивных полей внутри `TYPE`, например `Grid(,) AS INTEGER`, `Cube(,,) AS DOUBLE` и `Cells(1 TO 8, 1 TO 8) AS Cell`.
- после доступа к такому полю применяются те же правила полного индексирования, частичного индексирования и диапазонных срезов-представлений, что и для обычной массивной переменной.

### Индексирование

Новая целевая форма индексирования:
- `matrix(i, j)`
- `cube(x, y, z)`
- `cells(i, j).Name`

Правила:
- число индексов в обращении должно в точности совпадать с рангом массива;
- каждый индекс вычисляется по тем же числовым правилам, что и текущий одномерный индекс;
- доступ к полю записи у элемента массива записывается после полного индексирования, например `cells(i, j).Name`;
- использование меньшего или большего числа индексов считается ошибкой семантики;
- имя массива без индексов по-прежнему означает значение массива целиком, а не его первый элемент.

### REDIM и REDIM PRESERVE

Для многомерных массивов сохраняются уже существующие BASIC-линейные имена:
- `REDIM matrix(1 TO 10, 1 TO 20)`
- `REDIM PRESERVE matrix(1 TO 10, 1 TO 20)`

Правила:
- `REDIM` и `REDIM PRESERVE` принимают столько диапазонов, каков ранг целевого массива;
- `REDIM` не может менять число измерений у уже объявленного массива;
- обычный `REDIM` заново выделяет всё хранилище и сбрасывает элементы к значениям по умолчанию;
- `REDIM PRESERVE` сохраняет только область пересечения старых и новых диапазонов **по всем измерениям сразу**;
- если по хотя бы одному измерению пересечение пусто, сохраняемых элементов нет и новый массив заполняется значениями по умолчанию;
- ссылочная семантика остаётся общей: `REDIM` и `REDIM PRESERVE` меняют то же массивное значение, которое видят все его алиасы;
- пустая форма `REDIM name()` остаётся неподдерживаемой;
- в первом многомерном срезе специальная пустая выделенная форма `1 TO 0` сохраняется только для одномерных массивов; многомерная нормальная форма пустого, но уже выделенного массива выносится в отдельный следующий этап.

### Информационные built-in для массивов

Существующие имена сохраняются и расширяются без переименования:
- `LBOUND(array)`
- `LBOUND(array, dimension)`
- `UBOUND(array)`
- `UBOUND(array, dimension)`
- `ARRAYLENGTH(array)`
- `ARRAYISALLOCATED(array)`

Правила:
- `LBOUND(array)` и `UBOUND(array)` без второго аргумента означают первое измерение;
- второй аргумент у `LBOUND` и `UBOUND` является 1-основанным номером измерения;
- `ARRAYLENGTH(array)` для многомерного массива возвращает общее число элементов во всём прямоугольном хранилище;
- `ARRAYISALLOCATED(array)` для любого ранга возвращает только факт выделения, а не сведения о размере;
- для невыделенного массива `LBOUND` и `UBOUND` по-прежнему дают `MB3005`;
- для невыделенного массива `ARRAYLENGTH` по-прежнему возвращает `0`;
- для невыделенного массива `ARRAYISALLOCATED` по-прежнему возвращает `FALSE`;
- если аргумент `dimension` меньше `1`, больше ранга массива или не приводится к корректному целому индексу измерения, выполнение сообщает `MB3007`.

### Границы первого шага для остальных ARRAY-built-in

В первом многомерном срезе функции семейства `ARRAY...`, которые сейчас описывают одномерный порядок элементов, **не** становятся автоматически многомерными.

Правило первого шага:
- в первом многомерном срезе только часть семейства `ARRAY...` сохраняла чисто одномерный договор, но после последующих уточнений это ограничение уже не относится к `ARRAYCLONE`, `ARRAYFILL`, `ARRAYCONTAINS`, `ARRAYCOUNT`, `ARRAYEVERY`, `ARRAYSOME`, `ARRAYFILTER`, `ARRAYMAP`, `ARRAYREDUCE`, `ARRAYDISTINCT`, `ARRAYREVERSE`, `ARRAYTOREVERSED`, `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP`, `ARRAYCONCAT`, `ARRAYINDEXOF`, `ARRAYLASTINDEXOF`, `ARRAYFINDALL`, `ARRAYSORT`, `ARRAYTOSORTED` и `ARRAYBINARYSEARCH`, для которых отдельные многомерные договоры уже зафиксированы ниже;
- передавать в них многомерный массив нельзя;
- нарушение этого ограничения должно диагностироваться на семантическом уровне через существующий путь ошибок несовместимого аргумента, а не через скрытое молчаливое уплощение массива.

### Диагностика и ограничения

- Выход по любому измерению за выделенные границы остаётся ошибкой времени выполнения `MB3002`.
- Обращение к ещё невыделенному многомерному массиву остаётся ошибкой времени выполнения `MB3005`.
- Попытка вызвать `LBOUND` или `UBOUND` для невыделенного массива остаётся ошибкой времени выполнения `MB3005`.
- Недопустимый номер измерения в `LBOUND(array, dimension)` и `UBOUND(array, dimension)` сообщает `MB3007`.
- Нижняя граница `-2147483648` по-прежнему запрещена; в многомерном случае это правило применяется к каждому измерению отдельно и сообщает `MB3007`.
- В первом многомерном срезе все диапазоны каждого измерения должны быть непустыми, кроме уже существующего одномерного специального случая `1 TO 0`; попытка задать многомерный диапазон с пустым измерением выносится в ошибку времени выполнения `MB3005`.
- `REDIM` и `REDIM PRESERVE` с числом диапазонов, не совпадающим с рангом массива, считаются ошибкой семантики, а не поздней runtime-ошибкой.

### Что должно заработать вместе с этим срезом

После реализации этого проектного решения язык должен уметь:
- объявить `DIM board(1 TO 8, 1 TO 8) AS INTEGER`;
- объявить `DIM board(,) AS INTEGER`, затем выделить его через `REDIM`;
- присвоить и прочитать `board(x, y)`;
- передать двумерный массив в `SUB` или `FUNCTION`;
- вернуть двумерный массив из `FUNCTION`;
- вызвать `LBOUND(board, 1)`, `UBOUND(board, 1)`, `LBOUND(board, 2)`, `UBOUND(board, 2)`;
- получить `ARRAYLENGTH(board)` как произведение длин всех измерений;
- выполнить `REDIM PRESERVE` с копированием только общей прямоугольной области пересечения.

### Что сознательно отложено после этого шага

- подмассивы;
- срезы без копирования;
- представления и окна над тем же хранилищем;
- многомерные `ARRAYSLICE` и подобные функции;
- ранг-специфичные built-in вроде отдельного получения числа измерений;
- нормальная форма пустого, но уже выделенного многомерного массива;
- неявное уплощение многомерного массива в одномерный.

## Обновление 2026-04-28 - проектное решение второго среза подмассивов и представлений

Этот шаг фиксирует **следующий проектный договор ветки массивов** после уже реализованного первого многомерного среза. Его цель — добавить подмассивы как представления без копирования и не смешать этот шаг с более широкой многомерной переработкой всех `ARRAY...`-функций.

### Цель второго шага

Второй срез должен дать:
- получение подмассива из уже выделенного многомерного массива через частичное индексирование;
- представление без копирования, которое разделяет то же хранилище элементов с исходным массивом;
- сохранение уже реализованной одномерной линии `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP` и других одномерных функций без переименования;
- возможность использовать одномерный подмассив как обычный одномерный массив там, где текущий договор языка уже принимает `T()`.

В этом шаге **не** вводятся:
- новый специальный пользовательский синтаксис диапазонов внутри списка индексов;
- отдельный видимый тип наподобие `VIEW`, `SPAN` или другого нового имени;
- немедленное обобщение всех `ARRAY...`-функций на многомерные корневые массивы;
- копирующие многомерные `ARRAYSLICE`/`ARRAYTAKE`/`ARRAYSKIP` с параметром измерения;
- поэлементная арифметика, broadcasting и другие производные массивные операции.

### Пользовательская форма

Новый пользовательский договор строится на уже существующем синтаксисе индексирования:
- `row = board(2)`
- `plane = cube(3)`
- `line = cube(3, 4)`

Правила:
- если число индексов в точности равно рангу массива, выражение по-прежнему означает доступ к одному элементу;
- если число индексов больше нуля, но меньше ранга массива, выражение означает подмассив по оставшимся измерениям;
- если индексов нет, имя массива по-прежнему означает массивное значение целиком;
- фиксируются ведущие измерения, а результат охватывает оставшиеся хвостовые измерения в их естественном порядке;
- для одномерного массива новый подмассивный режим не появляется: запись `values(i)` остаётся доступом к элементу.

Примеры результата по рангу:
- для `INTEGER(,)` выражение `board(2)` имеет тип `INTEGER()`;
- для `DOUBLE(,,)` выражение `cube(3)` имеет тип `DOUBLE(,)`;
- для `DOUBLE(,,)` выражение `cube(3, 4)` имеет тип `DOUBLE()`.

### Модель представления

- Подмассив не создаёт новое независимое хранилище элементов.
- Подмассив разделяет то же физическое хранилище с исходным массивом.
- Присваивание в элемент подмассива меняет исходный массив, а присваивание в исходный массив видно через уже полученный подмассив.
- Если подмассив присваивается переменной, передаётся в параметр или возвращается из `FUNCTION`, передаётся именно представление на ту же область, а не скрытая копия.
- Нижние и верхние границы оставшихся измерений сохраняются без переупаковки и без принудительного уплотнения в `1 TO N`.
- Ранг результата всегда равен `исходный ранг - число зафиксированных индексов`.

### Взаимодействие с текущими ARRAY-функциями

- Одномерный подмассив считается обычным одномерным массивным значением для уже существующего одномерного договора языка.
- Поэтому `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP`, `ARRAYCLONE`, `ARRAYCONCAT`, `ARRAYTOREVERSED` и другие уже реализованные одномерные функции могут принимать такой одномерный подмассив без новых пользовательских имён.
- При этом их собственная семантика не меняется: они, как и раньше, создают независимый результат там, где текущий договор уже требует копию.
- Многомерные корневые массивы и многомерные подмассивы ранга больше `1` пока не становятся автоматически допустимыми аргументами для функций, чей договор до сих пор одномерен.
- Во втором срезе `ARRAYSLICE`, `ARRAYTAKE` и `ARRAYSKIP` не получают новый параметр измерения и не становятся отдельным многомерным copy-срезом.

### Ограничения второго шага

- `REDIM`, `REDIM PRESERVE` и `ERASE` не поддерживаются для подмассива-представления, потому что представление не является самостоятельным владельцем хранилища.
- Если переменная в момент выполнения ссылается именно на подмассив-представление, попытка `REDIM`, `REDIM PRESERVE` или `ERASE` для неё должна завершаться диагностикой времени выполнения `MB3007`.
- Новый синтаксис диапазонов вида `matrix(2, 3 TO 5)` или `matrix(2 TO 4, 7)` в этом шаге не вводится.
- Явные окна по произвольному измерению без фиксации ведущих осей выносятся в следующий отдельный этап.

## Обновление спецификации - 2026-05-09 - первый опросный срез мыши

Добавлен минимальный пользовательский договор мыши без отдельной событийной очереди:
- `MOUSEX()`;
- `MOUSEY()`;
- `MOUSEBUTTON(buttonNumber)`.

Цель среза:
- дать программе текущее состояние указателя и кнопок мыши;
- не вводить пока отдельные mouse-события, колесо, захват указателя и графическую поверхность `SCREEN`;
- закрепить единый host-договор, который одинаково работает в interpreter, `BytecodeVm`, execution pipeline и IDE.

### Возвращаемые значения

- `MOUSEX()` возвращает `LONG` с текущей горизонтальной координатой указателя;
- `MOUSEY()` возвращает `LONG` с текущей вертикальной координатой указателя;
- `MOUSEBUTTON(buttonNumber)` возвращает `BOOLEAN` и проверяет текущее удержание кнопки.

### Договор по умолчанию

- если среда выполнения не знает положение указателя, `MOUSEX()` и `MOUSEY()` возвращают `-1`;
- если среда выполнения не знает состояние кнопок, `MOUSEBUTTON(...)` возвращает `FALSE`;
- функции не блокируют выполнение программы и не создают новую очередь событий;
- `MOUSEBUTTON(1)` означает левую кнопку;
- `MOUSEBUTTON(2)` означает правую кнопку;
- `MOUSEBUTTON(3)` означает среднюю кнопку;
- любой другой номер кнопки в этом срезе даёт `FALSE`, а не runtime-ошибку.

### Граница первого среза

В этот шаг не входят:
- `ON MOUSE`;
- отдельные события нажатия, отпускания, двойного щелчка и перемещения;
- колесо мыши;
- различение координат разных будущих графических поверхностей;
- пользовательский синтаксис захвата мыши или ограничений области.

### IDE-договор

- в текущем IDE-срезе источником мыши служит активная область `Output`, которая уже используется как поверхность интерактивного выполнения программы;
- координаты обновляются по текущему положению указателя над `Output`;
- при уходе указателя с поверхности состояние мыши сбрасывается к договору «нет данных»;
- этот же маршрут считается подготовкой к будущему подключению `SCREEN`, чтобы не заводить второй несовместимый способ доставки мыши в runtime.

### Диагностика

- Частичное индексирование невыделенного массива остаётся ошибкой времени выполнения `MB3005`.
- Выход за границы любого уже зафиксированного измерения остаётся ошибкой времени выполнения `MB3002`.
- Число индексов больше ранга массива остаётся ошибкой семантики, а не поздней runtime-ошибкой.
- Передача многомерного подмассива ранга больше `1` в одномерную `ARRAY...`-функцию по-прежнему диагностируется тем же семантическим путём, что и передача обычного многомерного массива в одномерный built-in.

### Что должно заработать вместе с этим срезом

После реализации этого проектного решения язык должен уметь:
- объявить `DIM board(1 TO 8, 1 TO 8) AS INTEGER`, затем получить `row = board(2)` как одномерный подмассив;
- выполнить `row(3) = 9` и затем прочитать `board(2, 3)` с тем же значением;
- передать `board(2)` в `SUB PrintRow(values AS INTEGER())`;
- получить `plane = cube(3)` из трёхмерного массива как двумерное представление;
- вызвать `ARRAYSLICE(board(2), 3, 2)` и получить независимую одномерную копию части строки;
- вызвать `LBOUND`, `UBOUND`, `ARRAYLENGTH` и `ARRAYISALLOCATED` для подмассива и получить результат по его собственному рангу и границам.

### Что сознательно откладывается после второго шага

- диапазонные формы индексирования вроде `matrix(2, 3 TO 5)`;
- copyless-срезы по произвольному измерению, а не только по хвосту после фиксации ведущих осей;
- обобщение `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP` и родственных функций на многомерные корневые массивы;
- отдельные built-in для ранга, формы и extents;
- представления с перестановкой осей, транспонированием или неявным уплотнением.

## Обновление 2026-04-28 - проектное решение третьего среза диапазонных срезов в индексном списке

Этот шаг фиксирует следующий договор ветки массивов после уже реализованных многомерных массивов и подмассивов-представлений через частичное индексирование. Цель третьего среза - добавить диапазоны прямо внутри индексного списка, сохраняя модель представления без копирования и не вводя новые пользовательские имена.

### Цель третьего шага

Третий срез должен дать:
- диапазонный срез по одной или нескольким осям через уже знакомое слово `TO`;
- сочетание фиксированных индексов и диапазонов в одном индексном списке;
- представление без копирования, которое разделяет то же хранилище элементов с исходным массивом;
- возможность получать одномерный результат и дальше использовать его с уже существующими одномерными `ARRAY...`-функциями;
- одинаковое поведение в интерпретаторе и в `BytecodeVm`.

В этом шаге не вводятся:
- новый оператор или новая встроенная функция для срезов;
- шаг диапазона вида `1 TO 10 STEP 2`;
- открытые диапазоны вида `TO 5`, `3 TO` или `TO`;
- перестановка осей, транспонирование и неявное уплотнение;
- копирующие многомерные версии `ARRAYSLICE`, `ARRAYTAKE` и `ARRAYSKIP` для корневых многомерных массивов.

### Пользовательская форма

Диапазон задаётся внутри обычных скобок индексирования:
- `row = board(2, 3 TO 6)`
- `block = board(2 TO 4, 3 TO 6)`
- `plane = cube(2, 1 TO 4, 1 TO 5)`
- `line = cube(2 TO 3, 4, 1 TO 5)`

Правила:
- элемент индексного списка может быть либо одиночным индексом, либо включительным диапазоном `lower TO upper`;
- `lower` и `upper` вычисляются по тем же числовым правилам, что и обычный индекс массива;
- число элементов индексного списка по-прежнему не может превышать ранг исходного массива;
- если все элементы списка являются одиночными индексами и их число равно рангу массива, выражение остаётся доступом к одному элементу;
- если в списке есть хотя бы один диапазон или число элементов меньше ранга массива, выражение возвращает массивное представление;
- фиксированный одиночный индекс удаляет соответствующее измерение из результата;
- диапазон оставляет соответствующее измерение в результате с указанными включительными границами;
- неуказанные хвостовые измерения сохраняются в результате целиком и в исходном порядке.

Примеры ранга результата:
- для `INTEGER(,)` выражение `board(2, 3 TO 6)` имеет тип `INTEGER()`;
- для `INTEGER(,)` выражение `board(2 TO 4, 3 TO 6)` имеет тип `INTEGER(,)`;
- для `DOUBLE(,,)` выражение `cube(2, 1 TO 4, 1 TO 5)` имеет тип `DOUBLE(,)`;
- для `DOUBLE(,,)` выражение `cube(2 TO 3, 4, 1 TO 5)` имеет тип `DOUBLE(,)`;
- для `DOUBLE(,,)` выражение `cube(2 TO 3, 4, 5)` имеет тип `DOUBLE()`, потому что остаётся только первая ось.

### Модель представления

- Диапазонный срез не создаёт независимую копию элементов.
- Результат хранит ссылку на то же физическое хранилище, набор исходных измерений, смещения и собственные видимые границы.
- Присваивание в элемент результата меняет исходный массив.
- Присваивание в исходный массив видно через уже полученное представление.
- Видимые нижние и верхние границы результата соответствуют указанным диапазонам и сохранённым хвостовым измерениям.
- Если диапазон задан как `lower TO upper`, где `lower > upper`, результат является выделенным пустым представлением по этой оси; обращение к его элементу остаётся выходом за границы.
- `LBOUND`, `UBOUND`, `ARRAYLENGTH` и `ARRAYISALLOCATED` работают с результатом по его видимому рангу и видимым границам.

### Диагностика

- Если одиночный индекс или граница диапазона выходит за границы соответствующего измерения, выполнение сообщает `MB3002`.
- Если выражение диапазона не приводится к корректному целому индексу, выполнение сообщает `MB3007`.
- Если число элементов индексного списка больше ранга массива, это остаётся семантической ошибкой.
- Если результат диапазонного индексирования имеет ранг больше `1`, передача его в пока одномерную `ARRAY...`-функцию диагностируется тем же путём, что и передача обычного многомерного массива.
- `REDIM`, `REDIM PRESERVE` и `ERASE` для результата диапазонного среза запрещены так же, как для подмассива-представления второго среза, и должны завершаться `MB3007`.

### Что должно заработать вместе с этим срезом

После реализации этого договора язык должен уметь:
- создать `DIM board(1 TO 8, 1 TO 8) AS INTEGER`, заполнить часть строки через `row = board(2, 3 TO 6)` и увидеть изменения в `board`;
- получить прямоугольный блок `block = board(2 TO 4, 3 TO 6)`, затем изменить `block(2, 4)` и прочитать соответствующий элемент исходного массива;
- получить одномерную линию из трёхмерного массива через сочетание фиксированных индексов и диапазона;
- вызвать `ARRAYLENGTH`, `LBOUND`, `UBOUND` и `ARRAYISALLOCATED` для результата диапазонного среза;
- сохранить запрет на `REDIM` и `ERASE` для представлений.

### Что сознательно откладывается после третьего шага

- шаг диапазона `STEP`;
- открытые диапазоны без одной из границ;
- срезы с перестановкой осей;
- обобщение копирующих `ARRAY...`-функций на многомерные корневые массивы;
- отдельные встроенные функции для ранга, формы и размеров по измерениям;
- оптимизации хранения представлений, не меняющие наблюдаемое поведение.
## Обновление 2026-04-28 - решение по развитию ARRAY-функций до многомерных массивов

Принято проектное решение: конечная цель для семейства `ARRAY...` - развить до многомерных массивов все функции, для которых многомерное поведение можно определить честно и понятно. Текущие одномерные ограничения считаются этапными, а не постоянными, если функция по своей природе работает с уже существующим массивом и может быть обобщена на видимую форму массива или среза.

Общий принцип:
- функции, которые читают или меняют все видимые элементы без изменения формы, должны первыми получить поддержку массивов любого ранга и частичных срезов;
- функции, которые меняют форму, добавляют или удаляют элементы, должны расширяться только после явного договора об измерении, совместимости форм и результате;
- функции, которые возвращают индекс, порядок или набор позиций, не должны получать поспешную двумерную семантику через неочевидный плоский индекс; для них сначала нужен договор о координатах, порядке обхода или новой форме результата;
- функции, которые только создают одномерный список из внешнего источника, например строк или файлов, могут оставаться одномерными по природе результата, пока не появится отдельная пользовательская задача на табличный результат.

Первая группа для расширения:
- `ARRAYCLONE` - должен копировать видимую форму массива или среза любого ранга в независимое хранилище с теми же границами видимых измерений;
- `ARRAYFILL` - должен заполнять все видимые элементы массива или среза любого ранга;
- `ARRAYCONTAINS` и `ARRAYCOUNT` - должны обходить все видимые элементы массива любого ранга в стабильном порядке обхода и возвращать скалярный результат;
- `ARRAYEVERY` и `ARRAYSOME` - должны применять предикат ко всем видимым элементам массива любого ранга;
- `ARRAYMAP` - должен сохранять форму и границы исходного массива или среза, меняя только значения результата;
- `ARRAYREDUCE` - должен обходить все видимые элементы в стабильном порядке и сводить их к одному значению.

Вторая группа расширяется после договора о форме и измерении:
- `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP` - для многомерных массивов должны получить явную семантику измерения или заранее описанное правило работы с видимым порядком обхода;
- `ARRAYCONCAT` - для ранга выше одного должен объединять совместимые формы по явно выбранному измерению;
- `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE` - для многомерных массивов должны работать не с произвольной ячейкой, а с согласованной строкой, столбцом или срезом выбранного измерения;
- `ARRAYTOREVERSED` - должен быть расширен только после выбора правила: разворот по измерению или разворот всего видимого порядка обхода.

Третья группа требует отдельного договора о координатах, порядке или результате:
- `ARRAYINDEXOF` и `ARRAYLASTINDEXOF` не должны молча возвращать плоский номер для двумерного массива; перед расширением нужен координатный результат или явно документированная форма результата;
- `ARRAYFINDALL` для многомерных массивов должен возвращать не простой список одномерных индексов, а согласованное представление координат или срезов;
- `ARRAYSORT`, `ARRAYTOSORTED` и `ARRAYBINARYSEARCH` зависят от порядка сортировки и выбранного измерения, поэтому остаются одномерными до отдельного договора;
- `ARRAYDISTINCT` может быть расширен как получение одномерного списка уникальных значений из видимого обхода, но это изменение ранга результата должно быть отдельно описано в руководстве и примерах.

Функции, которые по смыслу создают одномерный массив из внешнего источника или строки, не входят в обязательную первую волну многомерного расширения. Если позднее для них понадобится табличная форма, она должна проектироваться отдельно и не должна смешиваться с текущим договором `ARRAY...`-функций.
## Обновление 2026-04-28 - первая реализованная группа многомерных ARRAY-функций

Реализована первая группа `ARRAY...`-функций, для которых многомерное поведение уже определено проектным договором и не требует нового пользовательского имени.

Поддерживаемые формы:
- `ARRAYCLONE(array)` принимает выделенный или невыделенный массив любого ранга, включая частичные и диапазонные представления;
- `ARRAYFILL array, value` принимает массив или представление любого ранга и заполняет все видимые элементы;
- `ARRAYCONTAINS(array, value)` принимает массив или представление любого ранга и возвращает скалярный логический результат;
- `ARRAYCOUNT(array, value)` принимает массив или представление любого ранга и возвращает скалярное количество совпадающих видимых элементов.

Правила поведения:
- `ARRAYCLONE` создаёт независимое хранилище с тем же рангом, видимой формой и видимыми нижними и верхними границами, что у исходного массива или представления;
- если исходный массив для `ARRAYCLONE` не выделен, результат остаётся невыделенным массивом того же элементного типа и ранга;
- копия, полученная через `ARRAYCLONE`, не разделяет элементы с исходным массивом или представлением;
- `ARRAYFILL` меняет исходное хранилище; если аргументом является срез или частичное представление, меняются только его видимые элементы;
- `ARRAYCONTAINS` и `ARRAYCOUNT` обходят все видимые элементы в стабильном порядке по измерениям и не зависят от физического расположения представления в исходном хранилище;
- пустое выделенное представление обходится как массив без видимых элементов: `ARRAYCONTAINS` возвращает `FALSE`, `ARRAYCOUNT` возвращает `0`, `ARRAYFILL` не меняет элементы.

Остальные `ARRAY...`-функции пока сохраняют прежние ограничения, если для них ещё не зафиксирован отдельный многомерный договор. В первую очередь это касается функций, возвращающих позицию, меняющих форму массива, сортирующих элементы или создающих результат с новым рангом.
## Обновление 2026-04-28 - вторая реализованная группа многомерных ARRAY-функций

Реализована вторая безопасная группа `ARRAY...`-функций, которые обходят все видимые элементы массива или представления через обратный вызов:
- `ARRAYEVERY(array, predicate)`;
- `ARRAYSOME(array, predicate)`;
- `ARRAYFILTER(array, predicate)`;
- `ARRAYMAP(array, selector)`;
- `ARRAYREDUCE(array, seed, reducer)`.

Правила поведения:
- `ARRAYEVERY` и `ARRAYSOME` принимают выделенный массив или представление любого ранга и обходят все видимые элементы в стабильном порядке по измерениям;
- `ARRAYEVERY` для пустого выделенного массива или пустого представления возвращает `TRUE`;
- `ARRAYSOME` для пустого выделенного массива или пустого представления возвращает `FALSE`;
- `ARRAYFILTER` принимает выделенный массив или представление любого ранга и тоже обходит все видимые элементы в стабильном порядке по измерениям;
- `ARRAYFILTER` всегда возвращает новый компактный одномерный массив `T()` с границами `1 TO N`, а при отсутствии совпадений — выделенный пустой массив `1 TO 0`;
- для многомерного массива или представления `ARRAYFILTER` не сохраняет исходный ранг и форму, а строит линейный список тех видимых значений, для которых `predicate` вернул `TRUE`;
- `ARRAYREDUCE` для пустого выделенного массива или пустого представления возвращает исходный `seed` без вызова `reducer`;
- `ARRAYMAP` создаёт новый массив того же ранга, с теми же видимыми нижними и верхними границами, что и исходный массив или представление;
- `ARRAYMAP` меняет только тип и значения элементов результата; исходный массив или представление не изменяются;
- если исходное представление пусто по одной из осей, `ARRAYMAP` сохраняет именно эту видимую пустую форму, а не нормализует результат к компактному `1 TO 0`.

Контракт callback-аргументов сохраняется прежним:
- `ARRAYEVERY` и `ARRAYSOME` требуют `FUNCTION(T) AS BOOLEAN`;
- `ARRAYFILTER` тоже требует `FUNCTION(T) AS BOOLEAN`;
- `ARRAYMAP` требует `FUNCTION(T) AS U`, где `U` не может быть типом массива;
- `ARRAYREDUCE` требует `FUNCTION(A, T) AS A`.

Остальные многомерные расширения по-прежнему не входят в этот шаг. Функции, меняющие форму массива, и функции с координатным результатом остаются на отдельном проектном договоре.

## Обновление 2026-04-28 - предопределённые константы PI, ROW и COLUMN

В язык добавлены три предопределённые константы, доступные без `CONST`:
- `PI` — встроенное значение типа `DOUBLE`, равное числу пи;
- `ROW` — встроенное значение типа `INTEGER`, равное `1`;
- `COLUMN` — встроенное значение типа `INTEGER`, равное `2`.

Правила поведения:
- эти имена доступны в любом выражении без предварительного объявления;
- `ROW` и `COLUMN` являются читаемыми синонимами чисел `1` и `2`, а не отдельным новым синтаксисом;
- числовые формы `1` и `2` остаются полностью допустимыми там же, где используются `ROW` и `COLUMN`;
- для третьего и следующих измерений массива по-прежнему используются обычные числовые индексы измерений;
- предопределённые константы нельзя переобъявить через `DIM`, `CONST`, `SUB` или `FUNCTION`;
- попытка присвоить им новое значение диагностируется так же, как присваивание обычной константе;
- `ROW` и `COLUMN` разрешены в местах, где требуется целочисленная константа времени связывания, например в фиксированных границах `TYPE`-полей и длинах `STRING * N`, если типовой контракт этого места и так требует целого.

Проектное решение:
- `ROW` и `COLUMN` вводятся как встроенные именованные константы, а не как новые ключевые слова;
- это сохраняет язык простым для чтения и не лишает пользователя числовой формы там, где она уже привычна;
- для справки и пользовательских примеров предпочтительна именованная форма `ROW` и `COLUMN`, когда речь идёт именно о строках и столбцах двумерной таблицы.

## Обновление 2026-04-28 - договор для ARRAY-функций, меняющих форму массива

Этот шаг пока **не добавляет реализацию**, а фиксирует простой и однозначный пользовательский договор для следующей группы `ARRAY...`-функций, которые не просто обходят элементы, а меняют видимую форму результата.

Идея по-простому:
- `ARRAYSLICE`, `ARRAYTAKE` и `ARRAYSKIP` должны работать не «как-нибудь по плоскому списку», а **по явно выбранному измерению**;
- `ARRAYCONCAT` для многомерных массивов должен **склеивать по явно выбранному измерению**;
- функции, которые меняют размер массива на месте (`ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE`), в этот шаг **не входят** и пока остаются только одномерными.

Такой договор выбран потому, что для двумерного и трёхмерного массива пользователю важно понимать, что именно происходит: мы режем строку, столбец или другое измерение, а не «магически» гуляем по скрытому линейному порядку.

### Что входит в договор

В этом шаге вводится многомерная семантика только для:
- `ARRAYSLICE`
- `ARRAYTAKE`
- `ARRAYSKIP`
- `ARRAYCONCAT`

В этом шаге **не** вводится многомерная семантика для:
- `ARRAYPUSH`
- `ARRAYPOP`
- `ARRAYINSERT`
- `ARRAYREMOVE`
- координатной группы `ARRAYINDEXOF`, `ARRAYLASTINDEXOF`, `ARRAYFINDALL`
- сортировочной группы `ARRAYSORT`, `ARRAYTOSORTED`, `ARRAYBINARYSEARCH`
- `ARRAYDISTINCT`

### Общий принцип

- Если функция меняет форму многомерного массива, она должна принимать **номер измерения** явно.
- Для двумерных примеров в справке предпочтительны `ROW` и `COLUMN`, но числовые формы `1` и `2` остаются полностью допустимыми.
- Для третьего и следующих измерений используются обычные числа `3`, `4` и так далее.
- Результат таких функций остаётся массивом того же ранга, если ниже не сказано иное.
- Порядок измерений не меняется.
- Неявного уплощения многомерного массива в одномерный здесь нет.

### ARRAYSLICE

Поддерживаемые формы:
- `ARRAYSLICE(array, startIndex, length)`
- `ARRAYSLICE(array, startIndex, length, dimension)`

Правила:
- для одномерного массива форма без `dimension` сохраняет старое поведение;
- для массива ранга выше `1` аргумент `dimension` обязателен;
- `dimension` задаёт, вдоль какого измерения берётся срез;
- остальные измерения сохраняют свои видимые границы как есть;
- по выбранному измерению результат получает новую непрерывную видимую область длины `length`, начиная с `startIndex`;
- если исходный аргумент является представлением или диапазонным срезом, операция применяется к его **видимой** форме, а не к корневым границам исходного хранилища;
- результат является **новым независимым массивом**, а не представлением без копирования.

Примеры:
- `ARRAYSLICE(board, 3, 4, COLUMN)` для `board(1 TO 8, 1 TO 8)` даёт массив с теми же строками и только столбцами `3 TO 6`;
- `ARRAYSLICE(board, 2, 3, ROW)` даёт массив со строками `2 TO 4` и всеми исходными столбцами.

### ARRAYTAKE

Поддерживаемые формы:
- `ARRAYTAKE(array, count)`
- `ARRAYTAKE(array, count, dimension)`

Правила:
- для одномерного массива форма без `dimension` сохраняет старое поведение;
- для массива ранга выше `1` аргумент `dimension` обязателен;
- `ARRAYTAKE` оставляет первые `count` видимых элементов по выбранному измерению;
- остальные измерения сохраняются без изменений;
- результат является новым независимым массивом того же ранга;
- если `count` больше видимой длины выбранного измерения, берётся вся видимая длина;
- если `count` меньше или равен `0`, результатом становится пустой выделенный массив той же формы по всем остальным измерениям и с пустым выбранным измерением.

### ARRAYSKIP

Поддерживаемые формы:
- `ARRAYSKIP(array, count)`
- `ARRAYSKIP(array, count, dimension)`

Правила:
- для одномерного массива форма без `dimension` сохраняет старое поведение;
- для массива ранга выше `1` аргумент `dimension` обязателен;
- `ARRAYSKIP` пропускает первые `count` видимых элементов по выбранному измерению и возвращает остаток;
- остальные измерения сохраняются без изменений;
- результат является новым независимым массивом того же ранга;
- если `count` меньше или равен `0`, возвращается копия всей видимой формы;
- если `count` больше либо равен видимой длине выбранного измерения, результатом становится пустой выделенный массив той же формы по всем остальным измерениям и с пустым выбранным измерением.

### ARRAYCONCAT

Поддерживаемые формы:
- `ARRAYCONCAT(left, right)`
- `ARRAYCONCAT(left, right, dimension)`

Правила:
- для одномерных массивов форма без `dimension` сохраняет старое поведение;
- для массивов ранга выше `1` аргумент `dimension` обязателен;
- `left` и `right` должны иметь одинаковый ранг и совместимую форму по всем измерениям, кроме выбранного;
- по выбранному измерению длины складываются друг за другом;
- по всем остальным измерениям видимые границы и длины должны совпадать;
- результат является новым независимым массивом;
- объединение идёт в порядке `left`, затем `right`;
- если один из аргументов по выбранному измерению пуст, результат равен копии другого аргумента при сохранении общей формы.

Пример по-простому:
- если есть две таблицы `top` и `bottom` одинаковой ширины, то `ARRAYCONCAT(top, bottom, ROW)` склеивает их по строкам;
- если есть две таблицы `leftPart` и `rightPart` одинаковой высоты, то `ARRAYCONCAT(leftPart, rightPart, COLUMN)` склеивает их по столбцам.

### Пустой результат

- В этом шаге допускается нормальная пустая выделенная форма многомерного результата для копирующих функций `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP` и `ARRAYCONCAT`.
- Это не представление и не невыделенный массив, а обычный новый массив с тем же рангом и с пустой длиной по выбранному измерению.
- Такое поведение нужно, чтобы функции могли честно возвращать «пустую строку», «пустой столбец» или другой пустой срез без подмены результата на невыделенный массив.

### Диагностика

- Если многомерный массив передан в `ARRAYSLICE`, `ARRAYTAKE`, `ARRAYSKIP` или `ARRAYCONCAT` без обязательного `dimension`, семантика должна сообщить ошибку несовместимого вызова.
- Если `dimension` меньше `1`, больше ранга массива или не приводится к корректному целому номеру измерения, выполнение сообщает `MB3007`.
- Если для `ARRAYCONCAT` формы аргументов несовместимы по измерениям, отличным от выбранного, выполнение сообщает диагностическую ошибку несовместимой формы массива; точный код можно зафиксировать в кодовом шаге, но без молчаливой нормализации.
- Если `startIndex` или границы результирующего отрезка в `ARRAYSLICE` выходят за видимые границы выбранного измерения, выполнение сообщает `MB3002`.
- Если `length` для `ARRAYSLICE` отрицательна, выполнение сообщает `MB3007`.
- `count` в `ARRAYTAKE` и `ARRAYSKIP` не обязан попадать в видимый диапазон: отрицательные и слишком большие значения не являются ошибкой, а приводят к корректному пустому или полному результату по правилам выше.

### Что должно заработать вместе с этим шагом

После реализации этого договора язык должен уметь:
- взять из `board(1 TO 8, 1 TO 8)` центральные столбцы через `ARRAYSLICE(board, 3, 4, COLUMN)`;
- взять верхние три строки через `ARRAYTAKE(board, 3, ROW)`;
- пропустить первые две строки через `ARRAYSKIP(board, 2, ROW)`;
- склеить две совместимые таблицы по строкам через `ARRAYCONCAT(top, bottom, ROW)`;
- склеить две совместимые таблицы по столбцам через `ARRAYCONCAT(leftPart, rightPart, COLUMN)`;
- получить пустой, но выделенный двумерный результат там, где операция логично отдаёт пустой срез.

### Что сознательно откладывается после этого шага

- многомерные `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE`;
- многомерный `ARRAYTOREVERSED`;
- координатные результаты для `ARRAYINDEXOF`, `ARRAYLASTINDEXOF`, `ARRAYFINDALL`;
- многомерный `ARRAYDISTINCT`;
- правила сортировки и поиска по выбранному измерению;
- любые варианты неявного уплощения массива в плоский список.

## Обновление 2026-04-28 - динамические операции роста и удаления отложены до коллекций

Принято отдельное проектное решение по `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT` и `ARRAYREMOVE`.

Что считается зафиксированным:
- для одномерных массивов эти функции сохраняют текущий договор без расширения;
- для многомерных массивов эти функции **не** получают новый договор в ветке массивов;
- будущая поддержка таких операций должна вводиться уже в ветке коллекций, где динамическое изменение состава данных является естественной частью модели.

Причина решения:
- для многомерного массива операции вида «добавить», «вставить» и «удалить» перестают быть очевидными на уровне отдельного элемента;
- такие действия ближе по смыслу к динамической коллекции, чем к массиву с фиксированной формой;
- это позволяет сохранить для массива ясную модель: массив отвечает за форму, границы и индексный доступ, а коллекция — за динамический рост и сжатие.

Следствие для текущей ветки:
- дальше расширяются только те `ARRAY...`-функции, которые логично переносятся на многомерную форму без превращения массива в динамический контейнер;
- отдельные договоры для таких функций продолжают фиксироваться в ветке массивов по мере готовности.

## Обновление 2026-04-28 - многомерный ARRAYDISTINCT

Следующим чистым копирующим расширением в ветке массивов становится `ARRAYDISTINCT`.

Поддерживаемые формы:
- `ARRAYDISTINCT(array)` сохраняется для одномерного массива;
- для многомерного массива или представления новая отдельная форма вызова не вводится: используется та же запись `ARRAYDISTINCT(array)`.

Правила поведения:
- функция принимает уже выделенный массив или представление любого ранга;
- обход идёт только по видимым элементам в стабильном порядке обхода массива;
- результатом всегда становится новый компактный одномерный массив того же типа элементов;
- нижняя и верхняя границы результата всегда нормализуются к форме `1 TO N`, а при отсутствии элементов к форме `1 TO 0`;
- если значение встретилось несколько раз, в результат попадает только его первое видимое вхождение;
- исходный массив и его видимая форма не меняются.

Что это значит по-простому:
- для `ARRAYDISTINCT(line)` всё работает как раньше;
- для `ARRAYDISTINCT(board)` функция не возвращает новую таблицу той же формы, а строит один линейный список уникальных значений из видимого обхода `board`;
- для подмассива-представления учитываются только его видимые элементы, а не весь исходный корневой массив.

Диагностика и состояние:
- невыделенный аргумент по-прежнему даёт `MB3005`;
- специального аргумента `dimension` для `ARRAYDISTINCT` в этом шаге не вводится, потому что функция не режет форму массива по одному измерению, а строит одномерный результат из всего видимого обхода.

Поддерживаемые формы:

## Обновление 2026-04-28 - ARRAYFLATTEN и ARRAYRESHAPE как штатный путь для многомерной сортировки

Следующим проектным шагом в ветке массивов вводится явная пара `ARRAYFLATTEN` и `ARRAYRESHAPE`.

Поддерживаемые формы:
- `ARRAYFLATTEN(array)` принимает уже выделенный массив или представление любого ранга и возвращает новый компактный одномерный массив того же типа элементов;
- `ARRAYRESHAPE(source, template)` принимает уже выделенный источник значений и уже выделенный массив-шаблон, после чего возвращает новый массив формы `template`, заполненный значениями `source`.

Правила поведения `ARRAYFLATTEN`:
- функция не меняет исходный массив;
- результат всегда имеет форму `1 TO N` или `1 TO 0`;
- для многомерного входа обход идёт по обычному видимому порядку элементов без отдельного аргумента `dimension`;
- исходная многомерная форма в результате не сохраняется.

Правила поведения `ARRAYRESHAPE`:
- функция не меняет ни `source`, ни `template`;
- тип элементов у `source` и `template` должен совпадать;
- число видимых элементов у `source` и `template` должно совпадать;
- форма результата полностью берётся у `template`: его ранг, видимые нижние и верхние границы и порядок обхода;
- если число элементов не совпадает, выполнение завершается диагностикой ошибки аргумента времени выполнения.

Проектное решение по именам:
- в классической линии BASIC нет устоявшейся пары имён для такого общего маршрута уплощения и обратной сборки массива;
- поэтому `ARRAYFLATTEN` и `ARRAYRESHAPE` фиксируются как явный проектный выбор Axiom, а не как унаследованные названия из исторического BASIC;
- это решение считается допустимым именно потому, что имена честно описывают поведение и поддерживают уже выбранную ветку `ARRAY...`-функций.

Что это значит по-простому:
- если нужно взять значения из таблицы как один список, используется `ARRAYFLATTEN(board)`;
- если потом нужно собрать новый массив обратно по форме другой таблицы, используется `ARRAYRESHAPE(values, board)`;
- именно эта связка теперь считается штатным путём для многомерного сценария `ARRAYFLATTEN` → `ARRAYTOSORTED` → `ARRAYRESHAPE`.

Решение по сортировочной группе:
- `ARRAYSORT` и `ARRAYTOSORTED` пока сознательно остаются одномерными;
- многомерная сортировка не получает скрытого режима «сортировать таблицу как плоский список»;
- если пользователю нужно отсортировать значения многомерного массива, он должен сначала явно сплющить их через `ARRAYFLATTEN`, а затем при необходимости вернуть форму через `ARRAYRESHAPE`.

## Обновление 2026-04-28 - координатная группа поиска по многомерным массивам

Реализован отдельный договор для координатной группы:
- `ARRAYINDEXOF(array, value)` и `ARRAYLASTINDEXOF(array, value)` сохраняют старое скалярное поведение для `1D`, но для массива ранга `2+` возвращают новый массив `INTEGER()` длины, равной рангу исходного массива;
- если многомерное совпадение не найдено, `ARRAYINDEXOF` и `ARRAYLASTINDEXOF` возвращают пустой выделенный массив `1 TO 0`, а не плоский индекс-заглушку;
- `ARRAYFINDALL(array, value)` сохраняет старый договор `INTEGER()` для `1D`, но для массива ранга `2+` возвращает таблицу координат `INTEGER(,)`, где каждая строка описывает одно совпадение, а число столбцов равно рангу исходного массива;
- если в многомерном `ARRAYFINDALL` совпадений нет, первая размерность результата становится пустой `1 TO 0`, а вторая сохраняет число координат в строке.

Порядок обхода:
- все три функции обходят видимые элементы в стабильном порядке, уже принятом для других многомерных ARRAY-операций;
- `ARRAYINDEXOF` берёт первое совпадение в этом порядке;
- `ARRAYLASTINDEXOF` берёт последнее совпадение в этом же порядке;
- скрытого перехода к плоскому индексу для `2D`, `3D` и выше нет.

## Обновление 2026-04-29 - сортировочная группа по многомерным массивам

Для `ARRAYSORT`, `ARRAYTOSORTED` и `ARRAYBINARYSEARCH` принят отдельный многомерный договор. В отличие от связки `ARRAYFLATTEN` -> `ARRAYTOSORTED` -> `ARRAYRESHAPE`, здесь речь идёт не о глобальном уплощении всей таблицы, а о работе **по одному явно выбранному измерению** с сохранением общей формы массива.

Поддерживаемые формы:
- `ARRAYSORT(array)` сохраняется для одномерного массива;
- `ARRAYSORT(array, dimension)` вводится для массива ранга выше `1`;
- `ARRAYTOSORTED(array)` сохраняется для одномерного массива;
- `ARRAYTOSORTED(array, dimension)` вводится для массива ранга выше `1`;
- `ARRAYBINARYSEARCH(array, value)` сохраняется для одномерного массива;
- `ARRAYBINARYSEARCH(array, value, dimension)` вводится для массива ранга выше `1`;
- в двумерных примерах предпочтительны `ROW` и `COLUMN`, но числовые формы `1` и `2` тоже допустимы.

Общий смысл выбранного `dimension`:
- функция работает не с плоским списком всех элементов, а с набором видимых линий вдоль указанного измерения;
- каждая такая линия определяется фиксированными координатами по всем остальным измерениям;
- внутри одной линии меняется или проверяется порядок только вдоль выбранного измерения;
- остальные измерения, их нижние и верхние границы и их взаимное расположение сохраняются без перепаковки;
- скрытого перехода к плоскому индексу или скрытого режима «отсортировать весь многомерный массив как один список» в этой группе нет.

Правила поведения `ARRAYSORT`:
- для `1D` процедура сохраняет текущий договор без изменений;
- для массива ранга `2+` `ARRAYSORT(array, dimension)` сортирует **каждую видимую линию вдоль выбранного измерения отдельно** по неубыванию;
- сортировка выполняется на месте в том же массиве или представлении;
- логические границы массива по всем измерениям сохраняются;
- дубликаты сохраняются;
- пустой уже выделенный массив допустим и остаётся пустым;
- невыделенный аргумент по-прежнему даёт `MB3005`;
- недопустимый номер измерения или значение `dimension`, не приводимое к корректному номеру измерения, даёт `MB3007`.

Правила поведения `ARRAYTOSORTED`:
- для `1D` функция сохраняет текущий договор без изменений;
- для массива ранга `2+` `ARRAYTOSORTED(array, dimension)` возвращает новый независимый массив той же формы, что и исходный;
- каждая видимая линия вдоль выбранного измерения сортируется отдельно по тем же правилам, что и в `ARRAYSORT`;
- исходный массив или представление не меняется;
- результат не разделяет хранилище элементов с исходным массивом;
- нижние и верхние границы результата по всем измерениям совпадают с исходным массивом;
- диагностические правила по `MB3005` и `MB3007` совпадают с `ARRAYSORT`.

Правила поведения `ARRAYBINARYSEARCH`:
- для `1D` функция сохраняет текущий договор без изменений, включая результат `LBOUND(array) - 1`, если совпадения нет;
- для массива ранга `2+` `ARRAYBINARYSEARCH(array, value, dimension)` считает, что **каждая видимая линия вдоль выбранного измерения уже отсортирована по неубыванию**;
- поиск выполняется отдельно по каждой такой линии бинарным поиском;
- если совпадения найдены в нескольких линиях, функция возвращает координаты первого найденного совпадения в стабильном видимом порядке обхода линий;
- результатом при успешном поиске становится массив координат `INTEGER()` длины, равной рангу исходного массива;
- внутри найденной линии выбирается первое равное значение по выбранному измерению, то есть координата минимального элемента среди равных в этой линии;
- если совпадения нет ни в одной линии, функция возвращает пустой выделенный массив `1 TO 0`, а не плоский индекс-заглушку;
- невидимые элементы вне переданного представления в поиске не участвуют;
- невыделенный аргумент по-прежнему даёт `MB3005`;
- недопустимый номер измерения или значение `dimension`, не приводимое к корректному номеру измерения, даёт `MB3007`;
- фактическую отсортированность линий функция не проверяет; если передан неотсортированный многомерный массив, результат не определён договором этой функции.

Что это значит по-простому:
- `ARRAYSORT(board, COLUMN)` для таблицы сортирует значения слева направо **внутри каждой строки отдельно**;
- `ARRAYSORT(board, ROW)` для таблицы сортирует значения сверху вниз **внутри каждого столбца отдельно**;
- `ARRAYTOSORTED(board, COLUMN)` делает новую таблицу той же формы, где каждая строка уже отсортирована;
- `ARRAYBINARYSEARCH(board, 20, COLUMN)` ищет значение `20` в строках, которые считаются отсортированными по столбцам, и возвращает координаты первой найденной ячейки;
- если нужен именно сценарий «взять все значения таблицы как один список, отсортировать его и потом вернуть форму», штатным путём остаётся связка `ARRAYFLATTEN` -> `ARRAYTOSORTED` -> `ARRAYRESHAPE`, а не новая многомерная форма сортировочной группы.

## Обновление 2026-04-29 - многомерный договор динамической группы `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE`

Этим шагом отменяется прежняя отсрочка динамической группы до отдельной ветки коллекций. Для активной ветки многомерных массивов принимается исполняемый договор, который меняет размер массива **только по явно выбранному измерению** и работает не с одиночной ячейкой, а с целым согласованным срезом этого измерения.

Поддерживаемые формы:
- `ARRAYPUSH(array, value)` сохраняется для одномерного массива без изменений;
- `ARRAYPUSH(array, value, dimension)` вводится для массива ранга выше `1`;
- `ARRAYPOP(array)` сохраняется для одномерного массива без изменений;
- `ARRAYPOP(array, dimension)` вводится для массива ранга выше `1`;
- `ARRAYINSERT(array, index, value)` сохраняется для одномерного массива без изменений;
- `ARRAYINSERT(array, index, value, dimension)` вводится для массива ранга выше `1`;
- `ARRAYREMOVE(array, index)` сохраняется для одномерного массива без изменений;
- `ARRAYREMOVE(array, index, dimension)` вводится для массива ранга выше `1`;
- в двумерных примерах предпочтительны `ROW` и `COLUMN`, но числовые формы `1` и `2` тоже допустимы.

Общий принцип выбранного `dimension`:
- операция меняет длину массива только вдоль выбранного измерения;
- все остальные измерения, их нижние и верхние границы и их взаимный порядок сохраняются;
- для каждого набора фиксированных координат по остальным измерениям существует одна видимая линия вдоль выбранного измерения;
- `ARRAYPUSH` и `ARRAYINSERT` добавляют или вставляют по одному элементу в каждую такую линию;
- `ARRAYPOP` и `ARRAYREMOVE` снимают по одному элементу из каждой такой линии;
- скрытого уплощения многомерного массива в плоский список нет;
- неявного расширения одного скаляра на весь срез тоже нет.

Договор формы данных:
- для массива ранга `N > 1` аргумент `value` в `ARRAYPUSH` и `ARRAYINSERT` должен быть уже выделенным массивом или представлением ранга `N - 1` того же типа элементов;
- видимые границы `value` должны по порядку совпадать с границами исходного массива по всем измерениям, кроме выбранного;
- для `2D` это означает:
  - `ARRAYPUSH(board, newColumn, COLUMN)` и `ARRAYINSERT(board, index, newColumn, COLUMN)` принимают одномерный массив значений по строкам;
  - `ARRAYPUSH(board, newRow, ROW)` и `ARRAYINSERT(board, index, newRow, ROW)` принимают одномерный массив значений по столбцам;
- `ARRAYPOP` и `ARRAYREMOVE` для массива ранга `N > 1` возвращают новый независимый массив ранга `N - 1` с теми же видимыми границами, что у исходного массива по всем невыбранным измерениям;
- для `2D` это означает:
  - `ARRAYPOP(board, COLUMN)` и `ARRAYREMOVE(board, index, COLUMN)` возвращают одномерный массив удалённого столбца, индексированный по строкам;
  - `ARRAYPOP(board, ROW)` и `ARRAYREMOVE(board, index, ROW)` возвращают одномерный массив удалённой строки, индексированный по столбцам.

Правила поведения `ARRAYPUSH`:
- для `1D` сохраняется текущий договор;
- для ранга `2+` `ARRAYPUSH(array, value, dimension)` добавляет новый логический индекс в конец выбранного измерения;
- каждая линия вдоль выбранного измерения получает ровно один новый элемент из согласованного `value`;
- нижняя граница выбранного измерения сохраняется, верхняя увеличивается на `1`;
- остальные измерения и их границы не меняются;
- результатом является мутация исходного массива или представления на месте.

Правила поведения `ARRAYINSERT`:
- для `1D` сохраняется текущий договор;
- для ранга `2+` `ARRAYINSERT(array, index, value, dimension)` вставляет новый логический индекс в выбранное измерение;
- аргумент `index` задаётся в логических индексах выбранного измерения;
- для непустого диапазона выбранного измерения допустимы индексы от `LBOUND_d(array)` до `UBOUND_d(array) + 1`;
- вставка внутрь диапазона сдвигает хвост по выбранному измерению вправо, а вставка по `UBOUND_d(array) + 1` эквивалентна `ARRAYPUSH`;
- нижняя граница выбранного измерения сохраняется, верхняя увеличивается на `1`;
- остальные измерения и их границы не меняются;
- результатом является мутация исходного массива или представления на месте.

Правила поведения `ARRAYPOP`:
- для `1D` сохраняется текущий договор;
- для ранга `2+` `ARRAYPOP(array, dimension)` снимает последний логический индекс выбранного измерения;
- из каждой линии вдоль выбранного измерения берётся её последний элемент;
- эти элементы собираются в новый независимый массив ранга `N - 1` по уже описанному правилу формы;
- сам исходный массив сужается на месте: верхняя граница выбранного измерения уменьшается на `1`, остальные измерения не меняются.

Правила поведения `ARRAYREMOVE`:
- для `1D` сохраняется текущий договор;
- для ранга `2+` `ARRAYREMOVE(array, index, dimension)` удаляет существующий логический индекс выбранного измерения;
- удаляемые элементы собираются в новый независимый массив ранга `N - 1` по тем же правилам формы, что и у `ARRAYPOP`;
- все элементы правее удаляемого индекса по выбранному измерению сдвигаются на одну позицию влево;
- сам исходный массив сужается на месте: верхняя граница выбранного измерения уменьшается на `1`, остальные измерения не меняются.

Диагностика и ограничения:
- невыделенный исходный массив по-прежнему даёт `MB3005`;
- недопустимый номер измерения или значение `dimension`, не приводимое к корректному номеру измерения, даёт `MB3007`;
- для `ARRAYINSERT` и `ARRAYREMOVE` индекс вне допустимого диапазона выбранного измерения даёт `MB3007`;
- `ARRAYPOP` и `ARRAYREMOVE` не поддерживаются для пустого диапазона выбранного измерения и дают `MB3007`;
- `ARRAYPUSH` и `ARRAYINSERT` при несовместимой форме `value`, неверном ранге `value` или несогласованных видимых границах дают `MB3007`;
- текущая реализация изменения размера поддерживается только для уже выделенного корневого массива; подмассивы-представления для этой группы пока отклоняются диагностикой `MB3007`;
- многомерная форма этой группы не вводит неявного broadcasting, не вводит специального скалярного сокращения для `value` и не меняет порядок оставшихся измерений.

Проектное решение по представлениям:
- ограничение на подмассивы-представления для `ARRAYPUSH`, `ARRAYPOP`, `ARRAYINSERT`, `ARRAYREMOVE` считается не временным компромиссом, а постоянным правилом текущей модели массивов;
- операции изменения размера в Axiom относятся только к самому выделенному массиву, а не к его срезам-представлениям;
- если когда-либо понадобится отдельная модель динамических операций поверх представлений, она должна вводиться уже как новая проектная возможность, а не как молчаливое расширение договора этой группы.

Что это значит по-простому:
- `ARRAYPUSH(board, newColumn, COLUMN)` добавляет новый столбец в таблицу, беря по одному значению из `newColumn` для каждой строки;
- `ARRAYINSERT(board, 3, newRow, ROW)` вставляет новую строку перед логической строкой `3`, не меняя число столбцов;
- `removedColumn = ARRAYPOP(board, COLUMN)` возвращает снятый последний столбец как отдельный одномерный массив и одновременно укорачивает саму таблицу по столбцам;
- `removedRow = ARRAYREMOVE(board, 2, ROW)` возвращает удалённую строку как отдельный одномерный массив и сдвигает все следующие строки вверх.

## Обновление 2026-04-29 - metadata-built-in для ранга и полной формы массива

Этим шагом над уже существующими `LBOUND`, `UBOUND`, `ARRAYLENGTH` и `ARRAYISALLOCATED` вводится отдельная metadata-подгруппа для случаев, когда пользователю нужно получить **число измерений** массива и его **полную видимую форму целиком**, а не по одному измерению за вызов.

Поддерживаемые формы:
- `ARRAYRANK(array)` возвращает число измерений массива как `INTEGER`;
- `ARRAYBOUNDS(array)` возвращает новый двумерный массив `INTEGER(1 TO rank, 1 TO 2)`;
- первый столбец результата `ARRAYBOUNDS` хранит `LBOUND` каждого измерения;
- второй столбец результата `ARRAYBOUNDS` хранит `UBOUND` каждого измерения.

Правила поведения:
- `ARRAYRANK(array)` работает и для уже выделенного, и для ещё невыделенного массива;
- `ARRAYRANK(array)` возвращает ранг, зафиксированный объявлением типа массива;
- `ARRAYBOUNDS(array)` работает только для уже выделенного массива;
- для измерения `d` выполняется правило:
  - `ARRAYBOUNDS(array)(d, 1) = LBOUND(array, d)`
  - `ARRAYBOUNDS(array)(d, 2) = UBOUND(array, d)`
- `ARRAYBOUNDS(array)` всегда возвращает независимую копию метаданных, а не представление;
- `ARRAYBOUNDS(array)` не вводит нового способа менять форму массива и не заменяет `LBOUND`/`UBOUND` там, где нужен один конкретный размерный индекс.

Диагностика:
- если `array` у `ARRAYBOUNDS` ещё не выделен, выполнение сообщает `MB3005`;
- `ARRAYRANK` для невыделенного массива не считается ошибкой, потому что число измерений известно по самому типу массива;
- дополнительных аргументов `dimension` эта подгруппа не принимает.

Проектное решение по именам:
- в классической линии BASIC нет устоявшейся пары встроенных имён для общего получения ранга и полной формы многомерного массива;
- поэтому `ARRAYRANK` и `ARRAYBOUNDS` фиксируются как явный проектный выбор Axiom;
- имя `ARRAYBOUNDS` выбрано вместо более размытого `ARRAYSHAPE`, потому что Axiom хранит не только длины измерений, но и видимые нижние и верхние границы, и именно они составляют полную форму массива в текущей модели.

Что это значит по-простому:
- `ARRAYRANK(board)` отвечает на вопрос «сколько у массива измерений»;
- `ARRAYBOUNDS(board)` отвечает на вопрос «какие у каждого измерения нижняя и верхняя границы»;
- если нужен только один конкретный предел, по-прежнему удобнее вызывать `LBOUND(board, d)` или `UBOUND(board, d)`.

## Обновление 2026-04-30 - верхний предел ранга массива пока не зафиксирован отдельным договором

После пользовательского вопроса о «максимальной массивности» зафиксировано текущее состояние договора и реализации.

Текущее правило:
- пользовательский договор массива требует только положительный ранг;
- явного верхнего предела ранга вроде `32` сейчас не зафиксировано ни в языке, ни в реализации;
- текущие `ArrayTypeSymbol` и `RuntimeArrayValue` отвергают только ранг меньше `1`.

Что это означает для документации и примеров:
- manual не должен обещать конкретный верхний предел ранга, пока не принято отдельное проектное решение;
- примеры высокого ранга допустимы как демонстрация текущей работоспособности, но не как доказательство некоторого навсегда гарантированного максимума;
- практический предел сейчас определяется только общей сложностью сценария, доступной памятью и другими внутренними ограничениями реализации, а не отдельной языковой константой.

Следствие для будущего решения:
- если понадобится совместимый с Visual Basic или QuickBASIC верхний предел, его нужно принять отдельным проектным договором и затем одинаково отразить в semantics, runtime, bytecode и manual;
- до такого решения отсутствие явного лимита считается осознанным текущим состоянием, а не скрытым обещанием совместимости с CLR-массивами или с каким-либо чужим языком.

## Обновление 2026-05-04 - значения полей по умолчанию и структурное сравнение TYPE

Принято и реализовано следующее расширение пользовательских записей TYPE: поле записи теперь может иметь собственное значение по умолчанию в объявлении, а записи одного и того же пользовательского типа можно сравнивать через = и <> по значениям полей.

Целевые формы:
- TYPE Person с полями вида Name AS STRING = "Unknown" и Age AS INTEGER = 18.
- Person()
- Person(Name := "Ada")
- left = right
- left <> right

### Значения полей по умолчанию

- Поле внутри TYPE может объявляться в форме FieldName AS FieldType = expression.
- В этом шаге expression должен быть константным или безопасно вычислимым на этапе связывания без зависимости от runtime-контекста.
- В текущем срезе значения по умолчанию поддерживаются только для скалярных и строковых полей.
- Для массивных полей и вложенных полей пользовательского типа явный инициализатор в объявлении пока не включается.
- Если у поля нет собственного инициализатора, сохраняется прежнее стандартное значение типа.

### Где используются значения по умолчанию

- DIM user AS Person создаёт запись с учётом объявленных значений по умолчанию полей.
- Person() создаёт запись, где для каждого поля применяется либо собственное значение по умолчанию, либо обычное значение типа.
- Частичный литерал Person(Name := "Ada") оставляет неуказанные поля в объявленных значениях по умолчанию.
- Для фиксированной строки значение по умолчанию после связывания подчиняется тому же правилу нормализации длины, что и обычное присваивание в поле.

### Ограничения и диагностика значений по умолчанию

- Нельзя использовать неконстантное выражение вроде вызова функции, обращения к переменной времени выполнения или другого runtime-зависимого значения.
- Нельзя задавать в этом шаге значение по умолчанию массивному полю или полю пользовательского типа.
- Для таких случаев используется диагностика MB2027.

### Структурное сравнение записей

- Операции = и <> теперь допустимы для двух значений одного и того же пользовательского TYPE.
- Сравнение выполняется по значениям всех полей записи.
- Если поле само имеет пользовательский тип, сравнение идёт рекурсивно по тем же правилам.
- Для скалярных, строковых и логических полей используются уже существующие правила сравнения соответствующих типов.
- Сравнение разных пользовательских TYPE остаётся семантической ошибкой.

### Граница первого шага структурного сравнения

- В этом шаге структурное сравнение не распространяется на записи, в которых есть массивные поля.
- Такое ограничение принято осознанно, чтобы не менять существующий договор массивных значений скрытым глубинным сравнением без отдельного проектного решения.
- Если в записи есть массивное поле, попытка сравнить такие записи через = или <> остаётся семантической ошибкой.

### Семантика выполнения

- TYPE в этом шаге остаётся value-oriented: присваивание записи целиком создаёт независимую запись-значение.
- Структурное сравнение не вводит identity-семантику и не делает запись ссылочным объектом.
- Одна и та же логика значений по умолчанию и структурного сравнения должна одинаково проходить через interpreter и BytecodeVm.

## Обновление 2026-05-07 - следующий договор TYPE: временные получатели методов без ссылочной объектной модели

После расширения TYPE-методов на поля и элементы массива следующая отдельная ветка закрепляется не как пользовательский конструктор с телом, а как открытие вызова метода у временных значений пользовательского типа.

Цель шага:
- закрыть текущую асимметрию между устойчивыми и временными значениями `TYPE`, чтобы методы записи можно было вызывать не только у переменной, поля или элемента массива, но и у результата выражения;
- сохранить value-oriented модель `TYPE` и не превращать запись в ссылочный объект;
- не вводить отдельные пользовательские имена вроде `NEW`, `INIT`, `SUB New` или другой объектный слой инициализации раньше времени.

### Что должно стать разрешено

- вызов метода у литерала `TYPE`, например `PRINT Counter(1).Current()`;
- вызов метода у результата функции, например `PRINT GetCounter().Current()`;
- вызов метода у другого выражения, если его результирующий тип — пользовательский `TYPE`, например `PRINT ChooseCounter(flag).Current()`.

### Что это означает семантически

- Если получатель метода является устойчивой lvalue-целью записи, сохраняется уже действующий договор: скрытый `SELF` привязан к исходному месту хранения, а присваивания через `SELF.Field = ...` записываются обратно.
- Если получатель метода является временным значением, перед вызовом метода создаётся скрытое временное хранилище записи на время текущего вызова.
- Внутри такого вызова `SELF` по-прежнему работает как скрытый `BYREF`, но уже по отношению к этому временному хранилищу.
- Изменения через `SELF` у временного получателя видны только внутри текущего вызова и исчезают после завершения вызова, если пользователь явно не сохраняет возвращаемое значение другим уже поддержанным способом.
- Такой договор сохраняет единообразие тела метода: метод не должен знать, был ли вызван на переменной или на временном значении.

### Что этот шаг сознательно не вводит

- не вводятся пользовательские конструкторы с телом, инвариантами и отдельными точками инициализации;
- не вводится отдельная ссылочная идентичность записи;
- не вводится автоматическая цепочка сохранения мутаций временного `SELF` обратно в источник выражения, если источник не является устойчивой lvalue-целью;
- не вводятся новые пользовательские правила fluent-цепочек и каскадного вызова методов сверх уже существующего общего синтаксиса вызова.

### Диагностический договор

- `MB2030` перестаёт быть диагностикой для временного получателя метода `TYPE`, если сам тип получателя корректен и метод существует.
- Ошибка должна оставаться только для тех случаев, где после точки вообще нет корректного пользовательского `TYPE`-получателя или имя метода не разрешается в типе.
- Отдельная диагностика о «потере мутации временного получателя» в первом шаге не вводится: поведение считается допустимым и осознанным, а не ошибочным.

### Почему выбран именно этот шаг

- У `TYPE` уже есть простая пользовательская форма создания значения через `TypeName()` / `TypeName(Field := ...)` / `TypeName(value1, ...)`, поэтому отдельная конструкторная подсистема с телом сейчас дала бы меньше пользы, чем завершение базовой модели вызова методов.
- Этот шаг остаётся в русле value-oriented записи: пользователь получает более полный договор работы с временными значениями, но не отдельную объектную модель.
- Такой порядок лучше подготавливает дальнейшие решения по чистым helper-методам и вычислимым записям, не вынуждая раньше времени проектировать `SUB New`, инварианты и сложный жизненный цикл объекта.

### Acceptance-ориентиры

- положительный sample в `samples/operators/type/` для вызова метода у литерала `TYPE`;
- положительный sample в `samples/operators/type/` для вызова метода у результата `FUNCTION`, возвращающей `TYPE`;
- negative-coverage для прежнего `MB2030` должна быть пересмотрена так, чтобы эта диагностика больше не использовалась на временном `TYPE`-получателе и оставалась только на действительно неподдержанном получателе;
- manual-страница `docs/manual/type.html` должна явно объяснять различие между устойчивым и временным получателем метода и судьбу изменений через `SELF`.

## Обновление 2026-05-07 - пользовательский конструктор TYPE через SUB New

После закрытия временных получателей методов следующий шаг TYPE вводит не новую ссылочную объектную модель, а минимальный пользовательский конструктор для value-oriented записи.

Цель шага:
- дать пользователю способ дополнять значение записи телом конструктора после применения значений полей по умолчанию;
- сохранить уже существующую форму литералов TYPE и не ломать именованную инициализацию через :=;
- не вводить отдельный пользовательский оператор NEW, INIT или другую внешнюю конструкторную подсистему.

### Какая форма считается конструктором

- внутри TYPE конструктором считается только объявление SUB New(...) ... END SUB;
- FUNCTION New(...) AS ... не допускается и должно диагностироваться как неподдерживаемая форма члена TYPE;
- пользовательский конструктор остаётся методом записи со скрытым SELF, но не участвует в обычном разрешении вызова через точку как отдельный публичный метод .New().

### Как связывается TypeName(...)

- именованная форма TypeName(Field := value, ...) всегда остаётся литералом записи и не вызывает SUB New(...);
- если внутри TYPE нет пользовательского конструктора, формы TypeName() и TypeName(value1, value2, ...) сохраняют прежний смысл литерала записи;
- если внутри TYPE есть SUB New(...), любой вызов TypeName(...) без именованных аргументов связывается уже как вызов конструктора;
- число и типы пользовательских аргументов в таком вызове проверяются по явной сигнатуре SUB New(...), без скрытого SELF.

### Что делает конструктор семантически

- перед входом в SUB New(...) создаётся обычное значение записи с уже применёнными значениями полей по умолчанию;
- затем тело конструктора получает скрытый SELF по ссылке на это локальное значение и может менять поля записи;
- результатом выражения TypeName(...), связанного с конструктором, становится итоговое значение SELF после завершения тела;
- конструктор не возвращает значение через RETURN и не имеет отдельного типа результата.

### Что этот шаг сознательно не вводит

- не вводятся перегрузки нескольких конструкторов на одном TYPE;
- не вводятся цепочки вызова одного конструктора из другого;
- не вводятся инварианты ссылочной идентичности, наследование или отдельный объектный жизненный цикл;
- не вводится переопределение именованной формы TypeName(Field := ...) в пользу конструктора.

### Acceptance-ориентиры

- положительный sample в samples/operators/type/constructor_new.axm должен показать, что SUB New(...) видит значения полей по умолчанию и может их изменить через SELF;

- binder/runtime/BytecodeVm должны иметь отдельные проверки на недопустимый FUNCTION New внутри TYPE и на различие между конструкторным и литеральным путём TypeName(...);

- не вводится выбор перегрузки по типам аргументов при одинаковой арности;

После шага с арностными перегрузками конструкторный путь TYPE расширяется ещё на один уровень: несколько SUB New(...) одинаковой арности теперь допустимы, если они различаются типами или режимами передачи пользовательских параметров.

- сделать перегрузки конструктора полезными не только по числу аргументов, но и по их типам;

### Как различаются перегрузки

- внутри одного TYPE допускается несколько SUB New(...) с одинаковой пользовательской арностью;
- различающимися считаются конструкторы, у которых отличается хотя бы один пользовательский параметр по типу или режиму BYVAL/BYREF;
- два конструктора с полностью одинаковой сигнатурой пользовательских параметров считаются повторным объявлением.

- затем из них остаются только те, для которых каждый аргумент совместим по уже действующим правилам binder, включая допустимые преобразования типов;
- если ровно один конструктор подходит, выбирается он;
- если подходят несколько конструкторов, binder предпочитает тот, у которого больше точных совпадений типов без преобразования;
- если после этого остаётся несколько одинаково подходящих вариантов, вызов считается неоднозначным и получает отдельную семантическую ошибку.

### Инварианты этого шага

- именованная форма TypeName(Field := ...) по-прежнему не участвует в перегрузке и остаётся литералом записи;
- наличие хотя бы одного SUB New(...) по-прежнему переводит всю неименованную форму TypeName(...) в конструкторный путь;
- одинаковая арность сама по себе больше не является ошибкой, если сигнатуры действительно различаются;
- текущий шаг не распространяет перегрузку по сигнатуре на обычные методы TYPE.

### Acceptance-ориентиры

- sample samples/operators/type/constructor_new.axm должен явно показывать выбор между конструкторами одинаковой арности по типам параметров;

- внутри TYPE специальным инвариантом считается только FUNCTION IsValid() AS BOOLEAN ... END FUNCTION;
- инвариант не принимает пользовательских параметров и использует скрытый SELF по тем же правилам, что и обычный метод записи;
- формы SUB IsValid, FUNCTION IsValid(...) с параметрами или FUNCTION IsValid() AS <не BOOLEAN> недопустимы и диагностируются как неверное объявление специального члена TYPE.

### Когда инвариант выполняется

- инвариант запускается автоматически только после успешного завершения выбранного SUB New(...);

### Инварианты этого шага

- value-oriented природа TYPE сохраняется: инвариант проверяет уже собранное значение записи и не переводит TYPE в ссылочную объектную модель.

## Обновление 2026-05-07 - договор перегрузки обычных методов TYPE по сигнатуре

После того как SUB New(...) уже получил перегрузку по полной сигнатуре, следующий самостоятельный договор для TYPE распространяет такой же принцип на обычные методы записи, но не расширяет его дальше в полноценную объектную систему с наследованием, виртуальностью или ссылочной идентичностью.

Цель шага:
- разрешить несколько обычных методов TYPE с одним и тем же именем, если они честно различаются пользовательской сигнатурой;
- сохранить для вызова через точку тот же объяснимый и детерминированный выбор, который уже действует у SUB New(...);
- не вводить выбор перегрузки по возвращаемому типу, контекстному ожиданию или другим скрытым правилам.

### Какие методы участвуют в перегрузке

- внутри одного TYPE обычные методы SUB и FUNCTION с одним и тем же коротким именем могут образовывать набор перегрузок;
- в сигнатуру перегрузки входят только пользовательские параметры метода, без скрытого SELF;
- различающимися считаются методы, у которых отличается хотя бы один пользовательский параметр по типу или режиму BYVAL/BYREF;
- два метода с одинаковым именем и полностью одинаковой пользовательской сигнатурой считаются повторным объявлением, даже если один объявлен как SUB, а другой как FUNCTION, или если различается только тип результата.

### Какие специальные члены не входят в этот договор

- SUB New(...) по-прежнему живёт в отдельном конструкторном договоре и не становится обычным методом .New(...);
- FUNCTION IsValid() AS BOOLEAN по-прежнему остаётся специальным постконструкторным хуком, а не частью обычного набора перегруженных методов;
- перегрузка не распространяется автоматически на свободные глобальные SUB и FUNCTION вне TYPE этим шагом.

### Как выбирается перегруженный метод

- сначала по имени через точку отбираются только методы соответствующего TYPE с нужным коротким именем;
- затем остаются только перегрузки с нужным числом пользовательских аргументов;
- затем из них остаются только те, для которых каждый аргумент совместим по уже действующим правилам binder, включая допустимые преобразования типов;
- если подходит ровно один метод, выбирается он;
- если подходят несколько методов, binder предпочитает вариант с большим числом точных совпадений типов без преобразования;
- если после этого остаётся несколько одинаково подходящих вариантов, вызов считается неоднозначным и получает ту же семантическую ошибку MB2033, что и неоднозначный вызов конструктора.

### Что остаётся неизменным в поведении вызова

- скрытый SELF по-прежнему передаётся отдельно и не участвует в пользовательской сигнатуре перегрузки;

- если выбранный метод принимает пользовательский параметр BYREF, действуют уже существующие правила совместимости и copy-back для аргументов;
- именованные литералы TypeName(Field := ...), конструкторный путь TypeName(...) и инвариант IsValid() этим договором не меняют своего поведения.

### Инварианты этого шага

- возвращаемый тип не участвует в выборе перегрузки и не может быть единственным отличием между двумя методами одного имени;
- шаг не вводит виртуальную диспетчеризацию, переопределение методов, наследование, интерфейсы или ссылочную объектную модель;
- шаг не меняет value-oriented природу TYPE: перегруженный метод работает с тем же SELF, что и неперегруженный.

### Acceptance-ориентиры

- sample samples/operators/type/method_overloads.axm должен показать выбор между методами одного имени по типам и арности пользовательских параметров;

## Обновление 2026-05-07 - проектное решение первого среза управляемой обработки ошибок

Этот шаг фиксирует новый участок работы: Axiom должен получить обработку ошибок, узнаваемую для пользователя BASIC, но без переноса неструктурированного `ON ERROR GOTO` как основной модели. Исторические формы `ON ERROR`, `RESUME`, `ERR` и `ERL` остаются полезным ориентиром по задачам: перехватить ошибку времени выполнения, узнать её номер и место, при необходимости продолжить выполнение. Однако первый срез Axiom выбирает блочную форму, близкую к современному Visual Basic: `TRY`, `CATCH`, `FINALLY`, `END TRY`.

### Цель первого среза

Первый срез должен дать:
- локальный блок обработки ошибок без перехода по метке;
- возможность перехватить обычную ошибку времени выполнения Axiom, включая существующие `MB30xx`;
- значение ошибки, доступное в `CATCH` как обычная переменная;
- гарантированное выполнение очистки через `FINALLY`;
- одинаковую семантику interpreter и `BytecodeVm`.

В этом шаге не вводятся:
- `ON ERROR GOTO`, `GOTO`, `RESUME` и переход к произвольной строке;
- пользовательское создание ошибок через отдельный оператор `ERROR`, `THROW` или `RAISE`;
- иерархия классов исключений;
- фильтры `WHEN`, сопоставление по типу исключения и несколько специализированных видов `CATCH`;
- восстановление выполнения с той же инструкции, которая вызвала ошибку.

### Пользовательская форма

Базовая форма:

```axiom
TRY
    PRINT 10 / value
CATCH err
    PRINT err.Code
    PRINT err.Message
END TRY
```

Форма с очисткой:

```axiom
TRY
    OPEN path FOR INPUT AS f
    PRINT READLINE(f)
CATCH err
    PRINT "Ошибка: "; err.Code
FINALLY
    IF ISOPEN(f) THEN CLOSE f
END TRY
```

Правила:
- `TRY` начинает защищённый блок операторов;
- `CATCH name` объявляет локальную переменную ошибки только внутри блока `CATCH`;
- `FINALLY` необязателен и выполняется после `TRY` либо `CATCH`;
- допустимы формы `TRY ... CATCH ... END TRY`, `TRY ... FINALLY ... END TRY` и `TRY ... CATCH ... FINALLY ... END TRY`;
- `TRY ... END TRY` без `CATCH` и без `FINALLY` не имеет смысла и должен диагностироваться парсером;
- несколько `CATCH` в первом срезе не поддерживаются.

### Значение ошибки

Для `CATCH err` вводится встроенный пользовательский тип значения ошибки времени выполнения. Его точное внутреннее имя остаётся технической деталью, но в пользовательском коде доступны поля:
- `err.Code AS STRING` - диагностический код, например `MB3007`;
- `err.Message AS STRING` - человекочитаемое сообщение диагностики;
- `err.Line AS INTEGER` - номер строки исходного текста или `0`, если позиция неизвестна;
- `err.Column AS INTEGER` - номер колонки исходного текста или `0`, если позиция неизвестна.

В первом срезе значение ошибки является только снимком диагностической информации. Пользователь не может менять ошибку и продолжать выполнение той же упавшей инструкции.

### Семантика выполнения

- Если в `TRY` не возникла ошибка времени выполнения, `CATCH` пропускается.
- Если в `TRY` возникла ошибка времени выполнения, выполнение текущего оператора прекращается, создаётся значение ошибки и управление переходит в `CATCH`.
- Если `CATCH` отсутствует, ошибка остаётся необработанной, но перед выходом из блока должен выполниться `FINALLY`.
- Если `CATCH` сам создаёт новую ошибку времени выполнения, эта новая ошибка заменяет исходную как активная ошибка блока.
- Если `FINALLY` создаёт ошибку времени выполнения, ошибка из `FINALLY` становится итоговой ошибкой блока.
- `FINALLY` выполняется и при обычном выходе из `TRY`, и при перехваченной ошибке, и при неперехваченной ошибке.
- В первом срезе `RETURN`, `EXIT SUB`, `EXIT FUNCTION`, `EXIT FOR`, `EXIT DO` и похожие выходы изнутри `TRY`/`CATCH` должны сначала выполнить `FINALLY`, если он есть.
- Если ошибка обработана в `CATCH` и `FINALLY` не создал новую ошибку, выполнение продолжается после `END TRY`.

### Области видимости

- Переменная из `CATCH err` видима только внутри соответствующего блока `CATCH`.
- Имя переменной `CATCH` не должно конфликтовать с уже объявленным локальным именем в той же области видимости.
- Переменные, объявленные внутри `TRY`, `CATCH` или `FINALLY`, подчиняются обычным правилам блочной области, которые уже действуют для управляющих конструкций Axiom.

### Диагностика и ограничения

- Синтаксические ошибки внутри `TRY`/`CATCH`/`FINALLY` остаются обычными синтаксическими ошибками и не перехватываются.
- Семантические ошибки не перехватываются, потому что программа с ними не запускается.
- Перехватываются только ошибки времени выполнения, которые уже идут через пользовательский runtime-диагностический путь.
- В первом срезе отладочные остановки, точки останова и служебные остановленные состояния `BytecodeVmStopState` не считаются ошибками языка и не попадают в `CATCH`.

### Почему не `ON ERROR GOTO`

Решение намеренно не переносит `ON ERROR GOTO` как основной путь, потому что Axiom уже строится вокруг структурных блоков, семантического анализа и двух согласованных движков выполнения. Переход к метке из произвольной точки усложнил бы binder, lowering, VM, область видимости локальных переменных и будущую отладку. При этом основные пользовательские задачи BASIC сохраняются: ошибку можно перехватить рядом с опасным кодом, узнать код и место, выполнить очистку и продолжить после блока.

### Acceptance-ориентиры

- sample `samples/control-flow/error-handling/try_catch_runtime_error.axm` должен показать перехват runtime-ошибки и вывод `err.Code`;
- sample `samples/control-flow/error-handling/try_finally_cleanup.axm` должен показать выполнение `FINALLY` при ошибке;
- negative sample `samples/acceptance/negative/try_without_catch_or_finally.axm` должен фиксировать синтаксическую диагностику пустой обработки;
- interpreter, lowering и `BytecodeVm` должны иметь parity-проверки для обработанной ошибки, неперехваченной ошибки с `FINALLY` и ошибки внутри `FINALLY`;
- manual должен получить отдельную страницу по обработке ошибок или ближайший правильный раздел управляющих конструкций с примерами `TRY ... CATCH ... END TRY` и `TRY ... FINALLY ... END TRY`.

## Обновление спецификации - 2026-05-07 - семантический срез TRY/CATCH/FINALLY

Первый семантический срез управляемой обработки ошибок добавляет привязку конструкции `TRY ... CATCH ... FINALLY ... END TRY` без исполнения в интерпретаторе и байткодной машине.

Текущие правила привязки:
- тело `TRY`, тело `CATCH` и тело `FINALLY` получают отдельные дочерние области видимости;
- `CATCH err` объявляет локальную доступную только внутри `CATCH` переменную только для чтения встроенного типа `ERROR`;
- для значения ошибки доступны поля `Code AS STRING`, `Message AS STRING`, `Line AS INTEGER`, `Column AS INTEGER`;
- имя переменной `CATCH` не должно конфликтовать с внешними именами по обычному правилу затенения блочных областей;
- обращение к переменной `CATCH` вне блока `CATCH` считается обращением к необъявленному имени;
- обращение к неизвестному полю значения ошибки выдаёт обычную диагностику неизвестного поля.

Ограничения текущего среза:
- `TRY/CATCH/FINALLY` пока не выполняется в интерпретаторе и `BytecodeVm`;
- пользовательский выброс ошибки, фильтры `CATCH`, повторный выброс и возобновление выполнения после точки ошибки не входят в этот срез;
- пользовательская документация и `.axm`-пример будут добавлены вместе с исполняемым поведением, чтобы не описывать неработающий в IDE оператор как готовый.

## Обновление спецификации - 2026-05-07 - исполняемый срез TRY/CATCH/FINALLY в интерпретаторе

Первый исполняемый срез `TRY ... CATCH ... FINALLY ... END TRY` реализован для интерпретатора.

Текущее поведение:
- ошибка времени выполнения внутри `TRY` передаёт управление в `CATCH`, если он указан;
- обработанная ошибка не остаётся в результате выполнения как runtime-диагностика;
- переменная `CATCH err` получает значение встроенного типа `ERROR`;
- поля `err.Code`, `err.Message`, `err.Line`, `err.Column` доступны внутри `CATCH`;
- `Code` содержит полный диагностический код, например `MB3001`;
- `Line` и `Column` указывают место исходной runtime-ошибки;
- `FINALLY` выполняется после обычного тела, после обработанной ошибки и перед выходом с необработанной ошибкой;
- если ошибка возникает в `CATCH` или `FINALLY`, она становится обычной ошибкой выполнения и может быть перехвачена внешним `TRY`.

Ограничения:
- `BytecodeVm` пока не исполняет `TRY/CATCH/FINALLY`;
- для положительного acceptance-аудита через байткод sample `samples/operators/try/handled_runtime_error.axm` временно исключён до появления VM-поддержки;
- пользовательский выброс ошибки и фильтры `CATCH` не входят в текущий срез.

## Обновление спецификации - 2026-05-07 - IDE-поддержка первого среза TRY/CATCH/FINALLY

Для первого интерпретаторного среза `TRY/CATCH/FINALLY` добавлен пользовательский слой IDE, чтобы новая форма была удобна в редакторе.

Текущее поведение IDE:
- светлая и тёмная схемы подсветки считают `TRY`, `CATCH` и `FINALLY` ключевыми словами;
- словарь подсветки также синхронизирован с уже существующими ключевыми словами `BYREF`, `BYVAL` и `SELF`;
- при нажатии Enter после строки `TRY` редактор автоматически вставляет тело блока и строку `END TRY`;
- строки `CATCH name` и `FINALLY`, набранные с лишним отступом внутри блока, выравниваются на уровень соответствующего `TRY`, а следующая строка получает отступ тела ветви;
- обычный запуск из IDE в режиме `Bytecode` при единственной backend-диагностике `MB4001` автоматически повторяет выполнение через интерпретатор, чтобы уже реализованная языковая форма работала из редактора до появления поддержки в `BytecodeVm`;
- отладочный запуск с точками останова и запуск с остановкой перед первой инструкцией не используют этот откат, потому что текущая пошаговая отладка привязана к байткодной машине.

Ограничения:
- `BytecodeVm` всё ещё не исполняет `TRY/CATCH/FINALLY`;
- строгий слой `Axiom.Execution` по-прежнему может вернуть `MB4001` для неподдержанной байткодом программы;
- IDE-откат является временной оболочечной мерой, а не заменой реализации `TRY/CATCH/FINALLY` в VM.

## Обновление спецификации - 2026-05-08 - пользовательский оператор ERROR

Для управляемой обработки ошибок добавлен пользовательский оператор `ERROR`. Имя выбрано по линии BASIC: оно честно связано с традиционным созданием ошибки времени выполнения, но в Axiom не возвращает модель `ON ERROR GOTO`.

Поддерживаемые формы:
- `ERROR code`;
- `ERROR code, message`.

Правила:
- `code` имеет тип `STRING` и становится полем `err.Code`;
- `message` имеет тип `STRING` и становится полем `err.Message`;
- если `message` не указан, интерпретатор формирует сообщение `Пользовательская ошибка <code>.`;
- пустой или состоящий только из пробелов `code` считается ошибкой аргумента времени выполнения;
- `ERROR` прекращает выполнение текущего пути и создаёт диагностику времени выполнения с указанным кодом и сообщением;
- внутри `TRY` такая ошибка перехватывается обычным `CATCH`;
- если обработчика нет, программа завершается ошибкой времени выполнения.

Текущий статус исполнения:
- интерпретатор исполняет `ERROR` и передаёт его через уже реализованный механизм `TRY/CATCH/FINALLY`;
- `BytecodeVm` пока не исполняет `ERROR` и `TRY/CATCH/FINALLY`;
- строгий байткодный путь для программ с `ERROR`/`TRY` остаётся временно неподдержанным и может вернуть `MB4001`.

## Обновление спецификации - 2026-05-08 - байткодное исполнение TRY/CATCH/FINALLY и ERROR

`TRY/CATCH/FINALLY` и пользовательский оператор `ERROR` теперь имеют исполняемый путь в `BytecodeVm`.

Текущее поведение байткодного пути:
- понижение создаёт служебные инструкции установки и снятия обработчика ошибки;
- runtime-ошибка внутри защищённого блока передаёт управление в `CATCH`, если он указан;
- обработанная ошибка удаляется из итоговой диагностики и материализуется как значение `ERROR`;
- `err.Code`, `err.Message`, `err.Line` и `err.Column` доступны в байткодном пути так же, как в интерпретаторе;
- `ERROR code` и `ERROR code, message` исполняются VM-инструкцией `RaiseError`;
- `FINALLY` выполняется после обычного тела, после обработанной ошибки и перед необработанной ошибкой.

Ограничения текущего байткодного среза:
- семантика раннего выхода `RETURN`, `EXIT FOR` и `EXIT DO` через `FINALLY` требует отдельной досверки;
- фильтры `CATCH`, повторный выброс и `RESUME` остаются вне текущего договора.

## Обновление спецификации - 2026-05-08 - RETURN через FINALLY в BytecodeVm

Байткодный путь `TRY/CATCH/FINALLY` расширен для раннего выхода `RETURN` из функции или процедуры.

Правило:
- если `RETURN` выполняется внутри активного `TRY` или `CATCH`, а у обработчика есть `FINALLY`, VM сохраняет возвращаемое значение, выполняет `FINALLY`, затем завершает текущую процедуру исходным значением `RETURN`;
- если `RETURN` выполняется внутри самого `FINALLY`, этот новый `RETURN` считается обычным выходом из процедуры и перекрывает ранее ожидавшееся продолжение;
- для `EXIT FOR` и `EXIT DO` отдельное правило пока не закреплено в байткодном договоре, потому что они сейчас понижаются как переходы по меткам и требуют контекстного lowering переходов через `FINALLY`.

## Обновление спецификации - 2026-05-08 - EXIT FOR и EXIT DO через FINALLY в BytecodeVm

Байткодное понижение `TRY/CATCH/FINALLY` теперь учитывает ранние выходы из циклов.

Правило:
- если `EXIT FOR` или `EXIT DO` покидает активный `TRY`/`CATCH` с `FINALLY`, lowerer перед переходом наружу снимает обработчик и исполняет соответствующие операторы `FINALLY`;
- если цикл находится внутри того же `TRY`, а `EXIT FOR` или `EXIT DO` остаётся внутри защищённого блока, `FINALLY` не выполняется досрочно и запускается обычным путём после завершения `TRY`;
- для вложенных `TRY` выполняются только те `FINALLY`, чьи защищённые области реально покидаются переходом.

## Обновление спецификации - 2026-05-08 - вложенные FINALLY и IDE-запуск без fallback

Байткодный путь `TRY/CATCH/FINALLY` дополнительно закреплён для вложенных обработчиков.

Правила:
- при необработанной ошибке во вложенном `TRY` блоки `FINALLY` выполняются изнутри наружу;
- если ошибка возникает внутри `FINALLY`, она становится текущей ошибкой выполнения и может быть перехвачена внешним `CATCH`;
- обычный запуск из IDE в режиме `Bytecode` больше не выполняет специальный повторный запуск через интерпретатор по диагностике `MB4001` для `TRY`/`ERROR`: поддержанные формы должны идти через `BytecodeVm`, а неподдержанные формы должны оставаться явной backend-диагностикой.

## Обновление спецификации - 2026-05-08 - повторный проброс ERROR err

Оператор `ERROR` расширен BASIC-похожей формой повторного проброса пойманной ошибки:
- `ERROR err`.

Правила:
- выражение после `ERROR` без запятой может иметь тип `STRING` или встроенный тип `ERROR`;
- если выражение имеет тип `STRING`, сохраняется прежнее поведение `ERROR code`;
- если выражение имеет тип `ERROR`, оператор повторно поднимает уже пойманную ошибку;
- повторно поднятая ошибка сохраняет исходные `Code`, `Message`, `Line` и `Column`;
- форма `ERROR err, message` не поддерживается, потому что при запятой первый аргумент трактуется как строковый код новой пользовательской ошибки;
- `ERROR err` поддерживается интерпретатором и `BytecodeVm`.

Смысл формы: внутренний `CATCH` может выполнить локальное действие и передать ошибку внешнему обработчику без переходов по меткам и без потери места первоначального возникновения ошибки.

## Обновление спецификации - 2026-05-08 - функция INKEY()

Добавлена встроенная функция неблокирующего клавиатурного ввода:
- `INKEY()`.

Контракт:
- функция не принимает аргументы;
- тип результата - `STRING`;
- если в очереди клавиатуры есть обычная клавиша, возвращается сам символ, например `"A"`;
- если клавиши нет, возвращается пустая строка `""`;
- специальные клавиши возвращаются строковыми именами, например `"LEFT"`, `"RIGHT"`, `"UP"`, `"DOWN"`, `"F1"`, `"ESC"`, `"ENTER"`, `"BACKSPACE"`;
- DOS-формат `CHR(0)+код` не используется;
- имя функции только `INKEY()`, без суффикса `$` и без алиасов;
- функция не блокирует выполнение и не ждёт пользователя;
- если среда выполнения не предоставляет источник клавиатуры, результатом считается `""`;
- функция поддерживается интерпретатором и `BytecodeVm`.

Ограничения первого среза:
- события клавиатуры вроде `ON KEY` не входят в реализацию;
- удержание клавиш и отдельные состояния клавиатуры не входят в реализацию;
- мышь проектируется отдельно после закрытия клавиатурного ввода.

## Обновление спецификации - 2026-05-08 - оператор ON KEY

После закрытия первого опросного среза `INKEY()` добавлен отдельный событийный слой клавиатуры:
- `ON KEY(keyText), HandlerName`;
- `ON KEY(keyText), OFF`.

Контракт:
- `keyText` - строковое выражение, которое во время выполнения нормализуется тем же способом, что и результат `INKEY()`;
- `HandlerName` - видимая процедура `SUB` без параметров;
- для одной клавиши активен только один обработчик; повторная регистрация заменяет предыдущую;
- форма `OFF` отключает обработчик для этой клавиши;
- обработчики вызываются между операторами, а не посреди вычисления выражения;
- совпавшая клавиша считается обработанной и не попадает в последующий `INKEY()`;
- клавиша, для которой нет подходящего обработчика, остаётся в очереди и может быть прочитана через `INKEY()`;
- вложенный повторный вход в другой клавиатурный обработчик во время активного обработчика не выполняется;
- оператор поддерживается интерпретатором и `BytecodeVm`.

Диагностика и ограничения:
- `ON KEY` принимает только процедуру `SUB` без параметров; иные callable-формы дают `MB2034`;
- прямой анонимный callable, список нескольких обработчиков на одну клавишу, модификаторы, удержание клавиш и мышиные события в этот срез не входят;
- `INKEY()` и `ON KEY` делят одну очередь клавиатуры, поэтому их совместное поведение считается частью общего пользовательского контракта клавиатурного ввода.

## Обновление спецификации - 2026-05-09 - функция KEYDOWN()

Добавлена встроенная функция проверки текущего состояния клавиши:
- `KEYDOWN(keyText)`.

Пользовательский договор:
- `keyText` - строковое имя клавиши, нормализуемое тем же правилом, что и `INKEY()` и `ON KEY`;
- результат имеет тип `BOOLEAN`;
- функция возвращает `TRUE`, если указанная клавиша сейчас удерживается;
- функция возвращает `FALSE`, если клавиша не удерживается, имя пустое или среда выполнения не предоставляет состояние клавиатуры;
- `KEYDOWN()` не читает очередь клавиш и не влияет на последующий `INKEY()` или `ON KEY`;
- модификаторы проверяются как обычные клавиши: `KEYDOWN("SHIFT")`, `KEYDOWN("CTRL")`, `KEYDOWN("ALT")`;
- сочетания задаются обычными логическими выражениями, например `KEYDOWN("CTRL") AND KEYDOWN("LEFT")`;
- строки сочетаний вроде `"CTRL+LEFT"` в этот срез не входят.

Поддерживаемые имена первого среза:
- стрелки: `"LEFT"`, `"RIGHT"`, `"UP"`, `"DOWN"`;
- служебные клавиши: `"ESC"`, `"ENTER"`, `"BACKSPACE"`, `"TAB"`, `"DELETE"`, `"INSERT"`, `"HOME"`, `"END"`, `"PAGEUP"`, `"PAGEDOWN"`, `"SPACE"`;
- модификаторы: `"SHIFT"`, `"CTRL"`, `"ALT"`;
- функциональные клавиши: `"F1"` ... `"F12"`;
- буквенно-цифровые клавиши: `"A"` ... `"Z"`, `"0"` ... `"9"`.

Ограничения:
- `KEYDOWN()` не является событием и не вызывает обработчик;
- одноразовая семантика "клавиша была нажата с прошлого опроса" не входит в этот срез и может проектироваться отдельно;
- мышь и более широкий событийный договор остаются отдельными будущими темами.

## Обновление спецификации - 2026-05-09 - канонические имена клавиш и алиасы

Для `INKEY()`, `KEYDOWN()` и `ON KEY` закреплена единая таблица строковых имён клавиш:
- `INKEY()` возвращает канонические имена;
- `KEYDOWN(keyText)` и `ON KEY(keyText), ...` принимают канонические имена и алиасы;
- регистр букв не важен;
- пробелы, дефисы и подчёркивания в алиасах не меняют смысл;
- обычные односимвольные строки остаются обычными печатными клавишами и не резервируют идентификаторы языка.

Канонические имена и алиасы:

- `"RIGHT"`: `"RIGHTARROW"`, `"ARROWRIGHT"`;
- `"UP"`: `"UPARROW"`, `"ARROWUP"`;
- `"DOWN"`: `"DOWNARROW"`, `"ARROWDOWN"`;
- `"ESC"`: `"ESCAPE"`;
- `"ENTER"`: `"RETURN"`;
- `"BACKSPACE"`: `"BACK"`, `"BKSP"`;

## Обновление спецификации - 2026-05-09 - функция KEYPRESS()

Добавлена встроенная функция одноразовой проверки события нажатия клавиши:
- `KEYPRESS(keyText)`.

Пользовательский договор:
- `keyText` - строковое имя клавиши, нормализуемое общей таблицей канонических имён и алиасов;
- результат имеет тип `BOOLEAN`;
- функция возвращает `TRUE`, если в очереди клавиатуры есть ещё не прочитанное нажатие указанной клавиши;
- найденное подходящее событие удаляется из очереди, поэтому повторный вызов для той же клавиши вернёт `FALSE`, пока пользователь не нажмёт её снова;
- неподходящие клавиши не теряются и сохраняют порядок для последующих `INKEY()`, `KEYPRESS()` или `ON KEY`;
- если имя пустое, подходящего события нет или среда выполнения не предоставляет клавиатурную очередь, результатом считается `FALSE`;
- `KEYPRESS()` поддерживается интерпретатором и `BytecodeVm`.

Различие с соседними формами:
- `INKEY()` возвращает следующую клавишу как строку;
- `KEYDOWN()` проверяет текущее удержание клавиши и не читает очередь;
- `KEYPRESS()` проверяет одно событие нажатия и удаляет только это событие;
- `ON KEY` остаётся обработчиком между операторами и может перехватить совпавшую клавишу раньше, чем управление дойдёт до последующего `KEYPRESS()`.

Решение по названию: имя `KEYPRESS` выбрано по BASIC/VB-линии как понятное имя события нажатия. Поведение Axiom шире классического GUI-события Visual Basic `KeyPress`: функция работает и со специальными клавишами через общую таблицу имён, а не только с печатными ANSI-символами.

## Обновление спецификации - 2026-05-09 - ON KEY("ANY")

Оператор `ON KEY` расширен запасным обработчиком любой клавиши:
- `ON KEY("ANY"), HandlerName`;
- `ON KEY("ANY"), OFF`.

Пользовательский договор:
- строка `"ANY"` не обозначает физическую клавишу, а включает обработчик для доступных клавиш, у которых нет более точного зарегистрированного обработчика;
- алиасы `"ANYKEY"`, `"ANY KEY"` и `"ANY-KEY"` нормализуются к той же форме `"ANY"`;
- точный обработчик клавиши имеет приоритет над обработчиком `"ANY"`;
- если точного обработчика нет, событие клавиши передаётся обработчику `"ANY"` и считается обработанным;
- обработанная таким образом клавиша не попадает в последующие `INKEY()` или `KEYPRESS()`;
- `ON KEY("ANY"), OFF` отключает только запасной обработчик и не влияет на точные обработчики отдельных клавиш;
- обработчик остаётся процедурой `SUB` без параметров и не получает текст клавиши как аргумент.

Ограничения:
- `KEYDOWN("ANY")` не получает специальной семантики и не проверяет состояние любой клавиши;
- `KEYPRESS("ANY")` не вводится в этом срезе;
- передача события клавиши в обработчик параметром, сочетания клавиш и режимы паузы обработчиков остаются отдельными будущими темами.

Решение по названию: форма `"ANY"` выбрана как строковое псевдоимя внутри уже существующего договора `ON KEY(keyText), ...`, чтобы не вводить новый оператор и не занимать новое ключевое слово языка.

## Обновление спецификации - 2026-05-09 - параметр имени клавиши в ON KEY

Оператор `ON KEY` теперь допускает две сигнатуры обработчика:
- `SUB HandlerName()`;
- `SUB HandlerName(keyName AS STRING)`.

Пользовательский договор:
- обработчик по-прежнему должен быть процедурой `SUB`, а не функцией;
- форма без параметров сохраняет прежнее поведение;
- если обработчик объявлен с одним параметром `STRING`, runtime передаёт в него нормализованное имя фактической клавиши;
- для точного обработчика передаётся нормализованное имя сработавшей клавиши;
- для `ON KEY("ANY"), HandlerName` передаётся не строка `"ANY"`, а нормализованное имя конкретного события, например `"LEFT"`, `"ESC"` или `"PAGEUP"`;
- обработчики с параметрами других типов, с несколькими параметрами или с `BYREF`-параметром не являются допустимой сигнатурой `ON KEY`.

Ограничения:
- структура события клавиатуры не вводится, передаётся только строковое имя клавиши;
- сочетания клавиш, включение и пауза обработчиков остаются отдельными будущими срезами;
- `KEYDOWN("ANY")` и `KEYPRESS("ANY")` не получают новой семантики от этой формы.

## Обновление спецификации - 2026-05-09 - доставка модифицированных клавиш в IDE

Строковые сочетания вида `"CTRL+LEFT"` не вводятся как отдельный синтаксис языка. Для пользовательских программ сочетание выражается обычным условием:
- `KEYDOWN("SHIFT") AND KEYPRESS("A")`;
- `KEYDOWN("CTRL") AND KEYPRESS("LEFT")`;
- `KEYDOWN("CTRL") AND KEYDOWN("ALT") AND KEYPRESS("DELETE")`.

Пользовательский договор:
- `KEYDOWN()` отвечает за состояние модификаторов и других удерживаемых клавиш;
- `KEYPRESS()` отвечает за одно событие основной клавиши;
- `Axiom.Ide` при запущенной программе и фокусе в активной поверхности ввода программы доставляет в клавиатурную очередь специальные клавиши с `CTRL` или `ALT`, например `CTRL+LEFT` как событие `"LEFT"` при удержанном `"CTRL"`;
- для печатных клавиш с `CTRL` или `ALT` IDE доставляет имя физической клавиши, например `CTRL+A` как событие `"A"` при удержанном `"CTRL"`;
- обычный ввод без `CTRL` или `ALT` продолжает идти через текстовое событие, чтобы `SHIFT+A` мог дать строку `"A"`;
- клавиша Windows не доставляется в очередь программы.

Решение: не добавлять строковый мини-язык сочетаний, пока комбинации можно ясно выразить через существующие `KEYDOWN()` и `KEYPRESS()`.

Текущая активная поверхность ввода программы в IDE - панель `Output`. Будущий графический режим `SCREEN` должен подключаться к тому же маршрутизатору клавиатурного ввода, а не заводить отдельную несовместимую схему.

## Обновление спецификации - 2026-05-09 - строковые аккорды клавиш

Для клавиатурных форм добавлен строковый сахар аккордов через знак `+`:
- `KEYPRESS("CTRL+LEFT")`;
- `KEYDOWN("CTRL+ALT+DELETE")`;
- `ON KEY("CTRL+F"), HandlerName`.

Пользовательский договор:
- строка аккорда разбирается по символу `+`;
- каждая часть нормализуется теми же правилами имён клавиш и алиасов, что обычные вызовы;
- для `KEYPRESS(...)` последняя часть строки является основной клавишей события, а все предыдущие части должны быть удержаны;
- для `ON KEY(...)` действует тот же событийный договор, что для `KEYPRESS(...)`: последняя часть строки является событием, предыдущие части должны быть удержаны;
- если обработчик `ON KEY` принимает параметр `STRING`, для аккорда он получает каноническую строку аккорда, например `"CTRL+LEFT"`;
- для `KEYDOWN(...)` все части строки равноправны: каждая перечисленная клавиша должна быть удержана прямо сейчас;
- длинные формы вроде `"CTRL+F+A+X"` допустимы; для `KEYPRESS()` и `ON KEY` это значит, что `CTRL`, `F` и `A` удержаны, а событием пришла клавиша `X`.

Ограничения:
- знак `+` в этом договоре является разделителем аккорда; отдельная клавиша `+` как печатный символ пока не получает специальной формы экранирования;
- клавиша Windows не включается в пользовательские аккорды IDE.

## Обновление спецификации - 2026-05-09 - режимы ON KEY ON / STOP / OFF

Оператор `ON KEY` получил режимы управления уже зарегистрированным обработчиком:
- `ON KEY(keyText), ON`;
- `ON KEY(keyText), STOP`;
- `ON KEY(keyText), OFF`.

Пользовательский договор:
- `ON KEY(keyText), HandlerName` регистрирует обработчик и включает его;
- `ON KEY(keyText), STOP` временно ставит уже зарегистрированный обработчик на паузу, но не удаляет саму регистрацию;
- `ON KEY(keyText), ON` возобновляет ранее зарегистрированный обработчик;
- `ON KEY(keyText), OFF` полностью снимает регистрацию обработчика;
- если обработчик на паузе, совпавшая клавиша не считается обработанной и остаётся доступной для `INKEY()` или `KEYPRESS()`;
- для `ON KEY("ANY")` режимы применяются только к запасному обработчику `"ANY"`;
- если `ON` или `STOP` указаны для клавиши без зарегистрированного обработчика, это не создаёт новый обработчик и не выдаёт ошибку.

Уточнение по времени: `ON KEY` проверяет клавиатурную очередь на границах операторов. Если клавиша уже накопилась до строки `ON KEY(...), STOP`, она может быть обработана прежним включённым обработчиком до выполнения команды паузы.

Решение по названию: `ON`, `OFF` и `STOP` оставлены в BASIC-линии управления обработчиками событий. В Axiom `STOP` здесь не останавливает выполнение программы, а приостанавливает только указанную регистрацию `ON KEY`.

## Обновление спецификации - 2026-05-09 - опрос очереди нажатий мыши через MOUSEPRESS()

Добавлена встроенная функция одноразовой проверки нажатия кнопки мыши:
- `MOUSEPRESS(buttonNumber)`.

Пользовательский договор:
- `buttonNumber` имеет тип `INTEGER`;
- результат имеет тип `BOOLEAN`;
- `MOUSEPRESS(1)` проверяет левую кнопку, `MOUSEPRESS(2)` - правую, `MOUSEPRESS(3)` - среднюю;
- функция возвращает `TRUE`, если в очереди мыши есть ещё не прочитанное нажатие указанной кнопки;
- найденное подходящее событие удаляется из очереди, поэтому повторный вызов для той же кнопки вернёт `FALSE`, пока пользователь не нажмёт её снова;
- неподходящие нажатия не теряются и сохраняют порядок для последующих вызовов `MOUSEPRESS(...)`;
- если номер кнопки не поддержан, очередь пуста или среда выполнения не предоставляет mouse-события, результатом считается `FALSE`;
- `MOUSEPRESS()` поддерживается интерпретатором и `BytecodeVm`.

Различие с соседними формами:
- `MOUSEBUTTON(...)` проверяет текущее удержание кнопки и не читает очередь нажатий;
- `MOUSEPRESS(...)` проверяет одно событие нажатия и удаляет только это событие;
- `MOUSEX()` и `MOUSEY()` по-прежнему читают только текущее положение указателя.

Ограничения:
- это договор именно нажатия кнопки, а не полного клика и не отпускания;
- отдельный пользовательский обработчик `ON MOUSE`, колесо мыши, захват указателя и графическая поверхность `SCREEN` в этот срез не входят.

Решение по названию: в BASIC-линии нет одного общеобязательного имени для очереди mouse-событий, поэтому для Axiom выбран `MOUSEPRESS` как прямое и согласованное расширение уже принятого пользовательского договора `KEYPRESS()`.

## Обновление спецификации - 2026-05-09 - обработчик нажатия мыши ON MOUSE

Оператор `ON MOUSE` добавляет событийный обработчик нажатия кнопки мыши поверх уже существующей очереди `MOUSEPRESS()`:
- `ON MOUSE(buttonNumber), HandlerName`;
- `ON MOUSE(buttonNumber), ON`;
- `ON MOUSE(buttonNumber), STOP`;
- `ON MOUSE(buttonNumber), OFF`.

Пользовательский договор:
- `buttonNumber` имеет тип `INTEGER`;
- поддерживаются кнопки `1`, `2` и `3`: левая, правая и средняя;
- `ON MOUSE(buttonNumber), HandlerName` регистрирует обработчик и сразу включает его;
- `ON MOUSE(buttonNumber), STOP` временно ставит существующий обработчик на паузу;
- `ON MOUSE(buttonNumber), ON` возобновляет существующий обработчик;
- `ON MOUSE(buttonNumber), OFF` полностью снимает регистрацию;
- если обработчик включён, совпавшее нажатие считается обработанным и не попадает в последующий `MOUSEPRESS(buttonNumber)`;
- если обработчик отсутствует или стоит на паузе, нажатие остаётся доступным для `MOUSEPRESS(...)`;
- `ON MOUSE` проверяет очередь нажатий на границах операторов так же, как `ON KEY` проверяет очередь клавиатуры.

Допустимые сигнатуры обработчика:
- `SUB HandlerName()`;
- `SUB HandlerName(button AS INTEGER, x AS LONG, y AS LONG)`.

Во второй форме `button` получает номер фактической кнопки, а `x` и `y` получают текущие координаты указателя на активной поверхности программы в момент вызова обработчика.

Ограничения:
- обработчик отпускания кнопки, колесо мыши, двойной клик, захват указателя и отдельный `SCREEN`-договор координат в этот срез не входят;
- режимы `ON` и `STOP` для кнопки без зарегистрированного обработчика не создают обработчик и не являются ошибкой;
- обработчик с другим числом параметров, другими типами параметров или `BYREF`-параметрами не считается допустимым обработчиком `ON MOUSE`.

Решение по названию: `ON MOUSE` выбран как прямое продолжение уже принятой BASIC-линии `ON KEY` и событийного договора `MOUSEPRESS()`, без введения нового объекта события или отдельного синтаксиса для мыши.

## Обновление спецификации - 2026-05-09 - ON MOUSE для отпускания и перемещения

Оператор `ON MOUSE` расширен с события нажатия на отпускание кнопки и перемещение указателя.

Новые формы:
- `ON MOUSE(buttonNumber, "UP"), HandlerName`;
- `ON MOUSE(buttonNumber, "UP"), ON`;
- `ON MOUSE(buttonNumber, "UP"), STOP`;
- `ON MOUSE(buttonNumber, "UP"), OFF`;
- `ON MOUSE("MOVE"), HandlerName`;
- `ON MOUSE("MOVE"), ON`;
- `ON MOUSE("MOVE"), STOP`;
- `ON MOUSE("MOVE"), OFF`.

Сохранённая совместимость:
- `ON MOUSE(buttonNumber), HandlerName` по-прежнему означает событие нажатия кнопки;
- `ON MOUSE(buttonNumber), ON / STOP / OFF` по-прежнему управляют обработчиком нажатия;
- `MOUSEPRESS(buttonNumber)` по-прежнему читает только события нажатия кнопки и не считает отпускание или перемещение подходящими событиями.

Пользовательский договор:
- для отпускания кнопки используются строковые имена `"UP"`, `"RELEASE"` или `"RELEASED"`;
- для перемещения указателя используются строковые имена `"MOVE"`, `"MOVED"` или `"MOUSEMOVE"`;
- для `MOVE` номер кнопки не указывается, а обработчик с параметрами получает `button = 0`;
- обработчик с параметрами остаётся тем же: `SUB Handler(button AS INTEGER, x AS LONG, y AS LONG)`;
- для `UP` параметр `button` получает фактический номер отпущенной кнопки;
- `x` и `y` получают текущие координаты активной поверхности программы в момент обработки события;
- если обработчик отсутствует или стоит на паузе, событие остаётся в очереди для более поздней обработки тем же механизмом `ON MOUSE`, кроме того что `MOUSEPRESS()` выбирает из очереди только события нажатия.

Ограничения:
- колесо мыши, двойной клик, событие входа/выхода указателя из поверхности, захват указателя и отдельная графическая система координат `SCREEN` остаются вне этого среза;
- форма `ON MOUSE(buttonNumber, "MOVE")` не используется: перемещение регистрируется как `ON MOUSE("MOVE"), ...`;
- строковые имена события проверяются на семантическом уровне; неизвестное имя события даёт диагностику договора `ON MOUSE`.

Решение: расширять уже существующий оператор `ON MOUSE`, а не вводить отдельные операторы `ON MOUSEUP` или `ON MOUSEMOVE`. Это сохраняет одну точку регистрации мышиных событий и повторяет уже выбранную модель `ON KEY`, где цель обработчика задаётся внутри аргументов оператора.

## Обновление спецификации - 2026-05-10 - ON MOUSE для колеса мыши

Оператор `ON MOUSE` расширен на событие прокрутки колеса мыши.

Новые формы:
- `ON MOUSE("WHEEL"), HandlerName`;
- `ON MOUSE("WHEEL"), ON`;
- `ON MOUSE("WHEEL"), STOP`;
- `ON MOUSE("WHEEL"), OFF`.

## Обновление спецификации - 2026-05-10 - CHR и ASC используют IBM CP866 для кодов 0..255

Уточнён общий строковый договор функций `CHR()` и `ASC()`.

Правило:
- `CHR(code)` для кодов `0..255` возвращает символ из таблицы IBM CP866;

- `CHR(196)` возвращает `─`;
- `CHR(219)` возвращает `█`;
- `ASC("Я")` возвращает `159`;
- `ASC("█")` возвращает `219`;
- `CHR(128512)` по-прежнему возвращает Unicode-символ с кодом `128512`.

Решение:
- перенести совместимость с BASIC/DOS-псевдографикой из частного слоя `SCREEN` в общий строковый договор языка;
- сохранить возможность использовать Unicode-коды выше `255`, чтобы язык не ограничивался только CP866.

Добавлен оператор временной остановки программы `SLEEP`.

Формы:
- `SLEEP milliseconds`;
- `SLEEP`.

Пользовательский договор:
- `SLEEP milliseconds` приостанавливает выполнение программы на указанное число миллисекунд;

- значение должно быть неотрицательным и помещаться в диапазон, который среда выполнения может передать системному ожиданию;

- временная строка ввода должна быть снята до публикации кадра с подтверждённым вводом, чтобы пользователь не видел вторую копию той же строки на следующей позиции курсора.

Решение:
- при подтверждении экранного `INPUT` состояние `IsWaitingForInput` сбрасывается до финальной публикации framebuffer-кадра.
## Обновление спецификации - 2026-05-11 - оператор строковой конкатенации &

Добавлен BASIC-подобный оператор `&` для явного построения строк из скалярных значений.

Правило:
- форма `<скалярное выражение> & <скалярное выражение>` возвращает значение типа `STRING`;
- допустимые типы операндов: `STRING`, `INTEGER`, `LONG`, `DOUBLE`, `DECIMAL` и `BOOLEAN`;
- каждый операнд переводится в текст тем же отображаемым форматом, который использует `PRINT`;
- оператор левоассоциативный и имеет тот же приоритет, что `+` и `-`;
- массивы, записи `TYPE`, файловые значения, значения функций и runtime-ошибки не являются допустимыми операндами `&` и получают существующую семантическую диагностику `MB2003`;
- строковая форма `+` остаётся строгой и по-прежнему объединяет только `STRING + STRING`, без неявного преобразования чисел в строки.

Решение по имени:
- выбран оператор `&`, потому что в BASIC-линейке он исторически используется именно для строковой конкатенации и лучше подходит для смешанных строко-числовых выражений, чем расширение арифметического `+`.

## Обновление спецификации - 2026-05-11 - закрытие окна SCREEN прерывает запуск

Уточнён договор пользовательского закрытия native-окна `SCREEN`.

Правило:
- если программа явно открыла окно `SCREEN 0` или графический `SCREEN 1..10`, системная кнопка закрытия окна считается запросом на прерывание текущего запуска;
- после такого закрытия среда выполнения должна остановиться кооперативно между инструкциями, без выполнения последующих операторов программы;
- закрытие окна не должно имитировать клавишу `ESC`, потому что это могло бы дать программе продолжить сценарий выхода через `SCREEN 0` и последующий `PRINT`;
- IDE должна снять состояние «программа выполняется» и снова включить команды после завершения отменённого запуска;
- штатное программное закрытие через `SCREEN 0`, завершение запуска или сброс сеанса не считается пользовательской отменой, если окно закрывается самим host-слоем.

Решение:
- host-слой выставляет отдельный флаг отмены при пользовательском `Closed` native-окна;
- `BytecodeVm` и интерпретатор проверяют этот флаг между инструкциями и возвращают результат `Cancelled` без runtime-диагностики.

## Обновление спецификации - 2026-05-12 - Unicode-пара ASCW и CHRW

Добавлены строковые функции `ASCW()` и `CHRW()` для прямой работы с Unicode-кодами символов.

Правило:
- `ASC(text)` сохраняет существующий BASIC/DOS-договор: для первого символа, представимого в IBM CP866, возвращается CP866-код, а для остальных символов возвращается Unicode-код;
- `CHR(code)` сохраняет существующий BASIC/DOS-договор: значения `0..255` читаются как коды IBM CP866, а значения выше `255` читаются как Unicode-коды;
- `ASCW(text)` возвращает Unicode-код первого символа строки без CP866-подмены;
- `CHRW(code)` возвращает символ по Unicode-коду без CP866-подмены, включая диапазон `0..255`;
- пустая строка у `ASCW(text)` сообщает runtime-диагностику `MB3007`, как и `ASC(text)`;
- отрицательный или недопустимый Unicode-код у `CHRW(code)` сообщает runtime-диагностику `MB3007`, как и `CHR(code)`.

Следствие:
- `ASC("Я")` возвращает `159`, а `ASCW("Я")` возвращает `1071`;
- `ASC("█")` возвращает `219`, а `ASCW("█")` возвращает `9608`;
- `CHR(159)` возвращает `Я`, а `CHRW(1071)` возвращает `Я`;
- для восстановления битой русской кодировки и других низкоуровневых задач, где важен настоящий Unicode-код символа, нужно использовать `ASCW()`.

Решение по имени:
- выбраны имена `ASCW` и `CHRW`, потому что они идут по BASIC/Visual Basic-линейке и честно показывают отличие от байтового `ASC`/`CHR`;
- отдельное имя `UNICODE()` не вводится, чтобы не дублировать уже узнаваемую пару функций.

## Обновление спецификации - 2026-05-12 - массовая строковая замена REPLACEMANY

Добавлена встроенная функция `REPLACEMANY(text, oldItems, newItems)` для табличной замены многих строковых фрагментов за один проход по исходной строке.

Правило:
- `text` имеет тип `STRING`;
- `oldItems` и `newItems` должны быть одномерными массивами `STRING`;
- массивы правил должны иметь одинаковую длину;
- элемент `oldItems(i)` задаёт искомый фрагмент, а `newItems(i)` задаёт замену;
- пустой элемент в `oldItems` недопустим и сообщает runtime-диагностику `MB3007`;
- разная длина массивов правил сообщает runtime-диагностику `MB3007`;
- если правил нет или совпадений нет, функция возвращает исходную строку;
- замена выполняется слева направо без повторной обработки уже вставленного текста;
- в каждой позиции выбирается самое длинное совпадение, а при равной длине побеждает более раннее правило;
- сравнение строк точное, с учётом регистра.

Решение по имени:
- в BASIC-линейке есть узнаваемая функция `Replace`, но устойчивого стандартного имени для пакетной таблицы замен нет;
- выбрано проектное имя `REPLACEMANY`, потому что оно явно продолжает `REPLACE` и описывает массовую форму без введения нового публичного типа вроде `STRINGBUILDER`.

Практический договор:
- функция предназначена для случаев, где цепочка из десятков или сотен последовательных `REPLACE` создаёт много полных проходов по строке;
- пример восстановления битой русской кодировки `samples/smoke/repair_plans_mojibake.axm` использует `REPLACEMANY` для основной таблицы mojibake-правил.
