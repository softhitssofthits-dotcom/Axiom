# План: клавиатурный ввод `INKEY()` в Axiom

## Кратко
Сделать первый полноценный срез неблокирующего клавиатурного ввода в стиле BASIC, но без устаревших суффиксов и алиасов: только `INKEY()`.

`INKEY()` будет возвращать `STRING`:
- обычная клавиша: сам символ, например `"A"`;
- нет клавиши: пустая строка `""`;
- специальная клавиша: читаемое имя, например `"LEFT"`, `"RIGHT"`, `"UP"`, `"DOWN"`, `"F1"`, `"ESC"`, `"ENTER"`, `"BACKSPACE"`.

Мышь, события `ON KEY`, удержание клавиш и отдельные состояния клавиатуры не входят в этот срез.

## Изменения
- Добавить чистую абстракцию клавиатуры в слой выполнения: неблокирующее чтение одной клавиши без прямой зависимости интерпретатора или байткод-машины от IDE.
- Добавить встроенную функцию `INKEY()` без параметров и без алиасов вроде `INKEY$`.
- Поддержать `INKEY()` одинаково в интерпретаторе и в байткод-режиме через общий механизм встроенных функций.
- Добавить очередь клавиш в IDE во время запуска программы, чтобы пользователь мог вручную проверить `INKEY()` в окне Axiom IDE.
- Зафиксировать формат специальных клавиш как строковые имена, а не DOS-скан-коды `CHR(0)+код`.

## Проверки
- Тест семантики: `INKEY()` имеет тип `STRING`, вызов с параметрами даёт диагностическую ошибку.
- Тест интерпретатора: очередь клавиш возвращает обычный символ, специальную клавишу и затем `""`.
- Тест байткода: тот же сценарий проходит в `ExecutionMode.Bytecode` без отката в интерпретатор.
- Тест IDE/runtime-адаптера: если клавиатурный источник не поддержан, `INKEY()` не блокирует выполнение и возвращает `""`.
- Запустить последовательные `.NET` проверки без параллельного доступа к одному `obj`.

## Принятые решения
- Имя только `INKEY()`.
- `$` в имени не используется.
- Алиасы не добавляются.
- Специальные клавиши возвращаются строковыми именами.
- `INKEY()` не блокирует выполнение и не ждёт ввода.
- Первый срез делает клавиатуру; мышь проектируется отдельным этапом после завершения `INKEY()`.
