# План системного разгона `Bytecode VM`

## Кратко

Цель первого большого этапа: довести байткодную VM до состояния, где она **не медленнее интерпретатора на базовых профильных сценариях** и получает выигрыш на части из них уже за счёт общей архитектуры, а не за счёт точечных правок отдельных функций.

Главный принцип: **сначала ускоряем общий тракт VM**, который автоматически наследуют нынешние и будущие built-in, и только потом делаем редкие точечные fast-path для действительно горячих случаев.

## Основные изменения

### 1. Зафиксировать постоянную программу измерений
- Оставить `compare-engines` основным сравнительным стендом для `Interpreter` и `Bytecode`.
- Расширить набор сценариев ещё на 2-3 профиля: тяжёлые файловые проходы, тяжёлые `ARRAY...`-операции изменения формы, более плотные regex-цепочки.
- Разделить сценарии по классам нагрузки: built-in вызовы, пользовательские функции, циклы, массивы, regex, файловые операции.
- Для каждого этапа оптимизации сравнивать не один пример, а весь профильный набор, чтобы не принимать частный выигрыш за общий.

### 2. Перестроить архитектуру вызова built-in в VM
- Убрать зависимость VM от большого runtime-`switch` по `CanonicalId` как основного пути выполнения built-in.
- Ввести для built-in единый исполняемый дескриптор: семантический идентификатор, признак поддержки VM, арность, вид привязки аргументов, ссылка на VM-обработчик.
- На этапе подготовки VM заранее строить прямое отображение `builtin id -> vm handler`, чтобы во время исполнения не было линейных поисков и лишних ветвлений.
- Разделить пути вызова по арности: отдельные быстрые тракты для `0`, `1`, `2`, `3` аргументов и отдельный общий тракт для variadic built-in.
- Убрать обязательное создание нового `RuntimeValue[]` на каждый вызов built-in малого размера; для малых арностей использовать безмассивный вызов или переиспользуемый буфер кадра.
- Для вызова built-in как значения функции убрать линейный поиск по `_builtins.Values` и заменить его прямой связью с дескриптором built-in.

### 3. Снизить общий накладной расход VM, а не только стоимость отдельных функций
- Пересобрать горячий цикл `BytecodeVm` так, чтобы максимум разборов инструкции, поиска метаданных и разрешения обработчиков происходил один раз до исполнения, а не на каждой инструкции.
- Отдельно оптимизировать вызовы маленьких пользовательских `FUNCTION`/`SUB`: уменьшить стоимость упаковки аргументов, создания кадра и возврата результата.
- Сохранить точечные string fast-path только как дополнение, а не как основную модель ускорения.
- Для новых built-in по умолчанию использовать тот же быстрый тракт вызова без отдельной ручной оптимизации, если они укладываются в стандартные схемы арности и привязки аргументов.

### 4. Отдельный этап для массивов и плотных циклов
- Вынести в общий быстрый путь работу с многомерными индексами: заранее рассчитанные strides, короткий flattening-helpers, минимизация повторных проверок.
- Проверить стоимость `FOR/NEXT`, доступа к локальным слотам и арифметики индексов в плотных циклах; именно это сейчас похоже на один из источников проигрыша на array-heavy сценариях.
- Все улучшения массива делать общими для интерпретатора и VM там, где это даёт одинаковую семантику, но VM-путь оптимизировать отдельно на уровне исполнения инструкций.

### 5. Ввести правило “новый built-in сразу дружит с VM”
- Каждая новая встроенная функция должна регистрироваться через один общий дескрипторный слой, а не через разрозненные списки, `switch` и отдельные special-case.
- Для новой функции обязательны:
  - семантическое описание;
  - VM-дескриптор вызова;
  - признак поддержки в bytecode pipeline;
  - хотя бы один сценарий в профильной группе `compare-engines`, если функция относится к горячему классу.
- Ручной fast-path для конкретного built-in добавлять только после замера, если общий быстрый тракт всё ещё недостаточен.

## Порядок реализации

1. Расширить профильный набор `compare-engines` и зафиксировать текущий baseline.
2. Переделать вызов built-in в VM на дескрипторную модель с прямым диспетчингом и арностными быстрыми путями.
3. Убрать линейный поиск built-in при вызове функции-значения и минимизировать выделения аргументов.
4. Отдельно пройтись по стоимости пользовательских вызовов и кадров VM.
5. Отдельно пройтись по массивам, индексированию и плотным циклам.
6. Только после этого возвращаться к выборочным ручным fast-path для действительно горячих built-in.
7. После каждого шага прогонять весь набор сценариев и сверять, что выигрыш не локальный, а системный.

## Проверка и критерии готовности

- Автотесты `Runtime`, `Execution` и связанные VM-тесты должны оставаться зелёными.
- `compare-engines` должен подтверждать одинаковые статус, вывод и диагностику у интерпретатора и байткода на всех эталонных сценариях.
- Критерий завершения первого этапа:
  - байткод **не медленнее интерпретатора** на базовом наборе профильных сценариев;
  - хотя бы часть сценариев уже показывает устойчивый выигрыш за счёт общей архитектуры;
  - новая built-in функция стандартной формы получает быстрый VM-тракт автоматически, без нового ручного `switch`-ускорения.
- Ручная приёмка через `Axiom.Ide` остаётся обязательной минимум для одного большого smoke-сценария и для одного array-heavy сценария в режиме `Bytecode`.

## Принятые допущения

- Этот план развивает именно `Bytecode VM` как быстрый управляемый движок и не переводит задачу в ветку нативного компилятора.
- Первый этап ориентирован на критерий `не медленнее`, а не на обещание “байткод всегда быстрее всего”.
- Главная ставка делается на архитектурное ускорение общего пути вызова и исполнения, чтобы будущие функции наследовали ускорение автоматически.
- Точечные оптимизации отдельных built-in допустимы только как второй слой поверх общей архитектуры, а не вместо неё.
