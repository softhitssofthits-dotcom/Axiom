# План внедрения быстрой строковой сборки в Axiom

## Кратко
Внедряем пользу от `StringBuilder` как внутреннюю оптимизацию языка, без нового публичного типа `STRINGBUILDER` в v1. Пользователь продолжает писать обычный BASIC-код:

```basic
s = s & piece
s = s + piece
```

А компилятор/исполнитель распознаёт накопление строки и выполняет его через быстрый внутренний накопитель. Семантика строк для пользователя остаётся прежней: строки неизменяемые, присваивание не создаёт скрытых ссылочных побочных эффектов.

## Ключевые изменения

- Добавить проверочный сценарий производительности `samples/smoke/engine-compare/string_concat_accumulator.axm`.
  Он должен отдельно нагружать накопление через `&`, строковый `+`, и фрагменты, возвращаемые функцией.

- В байт-кодном пути распознавать шаблон:
  ```basic
  s = s & expr
  s = s + expr
  ```
  когда левая часть присваивания совпадает с левым операндом конкатенации.

- Для этого добавить внутренний механизм вроде `StringConcatAccumulator` / `RuntimeStringAccumulator` в runtime-слой.
  Он не становится частью языка и не виден из `.axm`.

- Предпочтительная реализация: специализированная инструкция байт-кода, например `AppendStringLocal` / `AppendStringGlobal`, либо эквивалентное по смыслу lowering-правило в `BytecodeCompiler`.
  Текущий `Opcode.Concat` оставить для обычных выражений.

- Для интерпретатора добавить аналогичный быстрый путь в выполнении присваивания, чтобы интерпретатор и байт-код оставались сопоставимыми по поведению.
  Если реализация окажется слишком рискованной, допустимый v1-вариант: оптимизировать только байт-код, но явно зафиксировать это в документах и матрице производительности.

- Сохранить текущую семантику `ToDisplayString()` для `&`: смешанные значения должны конкатенироваться так же, как сейчас.

## Проверки

- Добавить автоматические проверки для:
  - `s = s & "x"` в цикле;
  - `s = s + "x"` для строк;
  - смешанных значений через `&`;
  - случая:
    ```basic
    t = s
    s = s & "x"
    PRINT t
    PRINT s
    ```
    где `t` обязан сохранить старое значение.

- Проверить паритет вывода интерпретатора и байт-кода на новом `.axm`-сценарии.

- Запустить существующие релевантные тесты runtime/bytecode.

- Запустить `engine-compare` до и после оптимизации.
  Цель: убрать квадратичное поведение на накоплении строк и получить заметное ускорение на сценарии восстановления кодировки.

## Документация

- Обновить `docs/BYTECODE_PERF_MATRIX.md`: добавить сценарий накопления строк в цикле.

- Обновить `docs/BYTECODE_COVERAGE.md`: отметить, что строковая конкатенация получила отдельный профильный сценарий.

- Обновить `docs/ARCHITECTURE.md`, если будет добавлен новый внутренний runtime-компонент для строкового накопления.

- Обновить `docs/PLANS3.md` и `docs/WORKLOG4.md`.

- Пользовательскую manual-страницу не менять, потому что новый публичный оператор или функция не появляется, а поведение языка остаётся тем же.

## Принятые допущения

- В v1 не вводим публичный `STRINGBUILDER`, чтобы не расширять язык преждевременно.
- Оптимизируем именно частый пользовательский паттерн накопления строк.
- Строки в Axiom остаются пользовательски неизменяемыми.
- Если позднее понадобится публичный API, его нужно проектировать отдельно по BASIC-линейке имён и с отдельной документацией/manual/sample.
