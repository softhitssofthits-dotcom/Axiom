# План пилота Headroom для Axiom

Этот документ не меняет продуктовый план `Axiom`.
Он описывает отдельный рабочий контур для агентных сессий над этим репозиторием.

Источник внешних команд и ограничений:
- `https://github.com/chopratejas/headroom`
- `https://headroom-docs.vercel.app/docs`
- `https://headroom-docs.vercel.app/docs/proxy`
- `https://headroom-docs.vercel.app/docs/mcp`
- `https://headroom-docs.vercel.app/docs/limitations`
- `https://headroom-docs.vercel.app/docs/cache-optimization`

## Зачем это нам

У `Axiom` уже тяжёлый контекст для ИИ-сессий:
- очень большие `docs/PLANS3.md`, `docs/SPECIFICATION3.md`, `docs/ARCHITECTURE.md`, `docs/WORKLOG4.md`;
- большой `docs/manual/`;
- много `samples/`;
- крупные `dotnet test`, smoke и acceptance-логи.

Поэтому для нас `Headroom` интересен прежде всего как слой между инструментами и моделью, а не как часть самого продукта.

## Что именно пробуем

Пилот делится на два независимых режима.

### Режим 1. Обёртка над Codex

Базовый путь из README проекта `Headroom`:

```bash
pip install "headroom-ai[all]"
headroom wrap codex
headroom perf
```

Рабочая идея:
- запускать обычные исследовательские и обзорные сессии по `Axiom` через `headroom wrap codex`;
- не менять код `Axiom` ради этого режима;
- сравнивать работу на одинаковых типах задач с обычным запуском без `Headroom`.

### Режим 2. MCP-инструменты поверх обычного запуска

Когда хочется не оборачивать весь агент, а дать ему точечные инструменты:

```bash
pip install "headroom-ai[mcp]"
headroom mcp install
headroom mcp status
```

По документации `Headroom` это даёт инструменты:
- `headroom_compress`
- `headroom_retrieve`
- `headroom_stats`

Этот режим полезен, если мы хотим сначала проверить точечное сжатие длинных логов и документов, не меняя основной способ запуска агента.

## Что считаем успешным пилотом

Пилот считается полезным, если выполняются оба условия:

1. На длинных сессиях по `Axiom` уменьшается объём контекста или косвенные расходы на него без ухудшения качества ответа.
2. Рабочий ритм не становится заметно хуже из-за лишней задержки, повторных retrieval-шагов или неудобства запуска.

## Какие сценарии меряем

Нужно прогонять не абстрактные запросы, а типичные для `Axiom` задачи.

### Сценарий A. Поднятие контекста проекта

Задача:
- понять текущее состояние проекта;
- определить, где остановилась работа;
- назвать следующий шаг.

Набор входов:
- `AGENTS.md`
- `PROJECT.md`
- `README.md`
- `docs/SPECIFICATION3.md`
- `docs/ARCHITECTURE.md`
- `docs/PLANS3.md`
- `docs/WORKLOG4.md`
- `docs/BYTECODE_COVERAGE.md`
- `docs/BYTECODE_PERF_MATRIX.md`

### Сценарий B. Разбор большого документа

Задача:
- извлечь текущий договор по одной теме, например `CANVAS`, `DRAWRECT`, `SPRITE`, `PAINT` или массивам;
- не перечитывать весь активный массив документов вручную.

Набор входов:
- `docs/SPECIFICATION3.md`
- `docs/ARCHITECTURE.md`
- `docs/PLANS3.md`
- `docs/WORKLOG4.md`

### Сценарий C. Разбор длинного test output

Задача:
- понять, почему упал `dotnet test`;
- быстро увидеть первый полезный сбой и его окружение.

Набор входов:
- вывод `dotnet test`
- `.trx`
- при необходимости журналы из `.artifacts/`

### Сценарий D. Обзор изменённой области

Задача:
- прочитать большой `git diff`;
- понять затронутые слои, риски, пробелы в тестах и документации.

Набор входов:
- `git diff`
- выборочные файлы из `src/`, `tests/`, `docs/`

## Метрики пилота

Для каждого сценария фиксируем в таблице:
- дата;
- режим: `без Headroom`, `wrap codex`, `mcp only`;
- задача;
- объём входа в символах или строках;
- заявленную экономию `Headroom`, если она показана инструментом;
- субъективную оценку качества ответа: `лучше`, `так же`, `хуже`;
- число случаев, когда пришлось вручную вытаскивать исходник без сжатия;
- заметную задержку: `нет`, `маленькая`, `заметная`.

Минимальная полезная форма журнала пилота:

```text
Дата | Режим | Сценарий | Вход | Экономия | Качество | Retrieval | Задержка | Комментарий
```

## Практический порядок запуска

### Вариант A. Быстрый пилот через обёртку

1. Установить `Headroom`.
2. Запустить `headroom wrap codex`.
3. Повторить 3-5 типичных задач по `Axiom`.
4. После каждой задачи записать наблюдения в локальный журнал пилота.

### Вариант B. Осторожный пилот через MCP

1. Установить MCP-режим `Headroom`.
2. Подключить `headroom_compress`, `headroom_retrieve`, `headroom_stats`.
3. Использовать их только для тяжёлых документов и логов.
4. Сравнить удобство с обычным чтением и с локальным `scripts/ai-context.ps1`.

## Где Headroom особенно подходит для Axiom

- длинные append-only документы;
- большие логи тестов;
- большие результаты поиска по репозиторию;
- сводки `git diff`;
- повторяющиеся обзорные задачи по состоянию проекта.

## Где нужно быть осторожным

По документации `Headroom` есть важные ограничения:
- код не всегда хорошо сжимается и часто даёт меньший выигрыш, чем логи и JSON;
- короткий текст и маленькие фрагменты могут не окупать накладные расходы;
- иногда нужен retrieval исходника, если важна полная точность;
- выигрыш особенно хорош там, где помогают стабилизация префикса и сжатие повторяющихся структур.

Для `Axiom` это означает:
- не нужно прогонять через `Headroom` каждый маленький `.cs`-файл;
- не нужно насильно сжимать короткие ручные проверки;
- нужно целиться в документы, логи и широкие сводки.

## Локальный запасной слой без внешней зависимости

Даже без `Headroom` в репозитории теперь есть собственный минимальный слой:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/ai-context.ps1
powershell -ExecutionPolicy Bypass -File scripts/ai-context.ps1 -Topic CANVAS,RGB,DRAWRECT
```

Он не заменяет `Headroom`, но закрывает две практические задачи:
- быстро собрать компактный бриф по активному состоянию проекта;
- быстро вытащить тематические фрагменты из основных документов без чтения всего массива.
