# Внешние инструменты экономии контекста и задач для Axiom

Этот документ фиксирует проектное решение по четырём внешним репозиториям:
- `rtk-ai/rtk`
- `eyaltoledano/claude-task-master`
- `chopratejas/headroom`
- `JuliusBrussee/caveman`

Он не заменяет `AGENTS.md`, `docs/PLANS4.md` или `docs/WORKLOG5.md`.
Его задача — один раз зафиксировать, что из этих идей подходит `Axiom`, а что нет.

## Исходная задача

Для `Axiom` важно экономить контекст, потому что репозиторий держит:
- очень большие append-only документы;
- крупный manual;
- большие acceptance-, smoke- и benchmark-логи;
- длинные `git diff` и поисковые выборки.

Но при этом у проекта уже есть жёсткое правило единственного источника правды:
- `docs/PLANS4.md`;
- `docs/WORKLOG5.md`;
- активная спецификация и архитектура.

Поэтому любой внешний слой оценивается не по красоте идеи, а по четырём вопросам:
1. Что именно он экономит?
2. Что он может исказить?
3. Почему локальный `docs/agent/`-слой этого уже не покрывает?
4. Не создаёт ли он второй источник правды?

## 1. `chopratejas/headroom`

### Что ценно

Для `Axiom` это самый полезный из четырёх внешних инструментов.

Полезные свойства:
- он нацелен не только на shell-вывод, а на более широкий контекст: tool outputs, logs, files, RAG и history;
- у него есть режимы proxy, library, middleware и MCP;
- по собственной документации и README он хранит оригиналы и даёт retrieval-путь `headroom_retrieve`, то есть не заставляет навсегда жить только в сжатом тексте;
- в сравнительной таблице сам `Headroom` прямо позиционируется как более широкий слой, чем `RTK`, а `RTK` указан как вложенный CLI-компонент для shell-output rewriting.

### Что у нас уже применено

Линия `Headroom` уже частично отражена в репозитории:
- `docs/agent/HEADROOM_PILOT.md`;
- `docs/agent/README.md`;
- `README.md`;
- локальный скрипт `scripts/ai-context.ps1`;
- короткий retrieval-слой `docs/agent/`.

То есть у нас уже реализована не установка самого `Headroom`, а его проектная идея:
- не читать всё подряд заново;
- делать компактный локальный слой;
- поднимать тематические фрагменты вместо полного массива.

### Что применять дальше

Для `Axiom` имеет смысл:
- оставить `Headroom` как необязательный внешний ускоритель;
- использовать его прежде всего для длинных логов, больших `git diff`, широких search-результатов и тяжёлых сводок;
- не делать его обязательной зависимостью проекта;
- не переносить в него проектный план, журнал или продуктовые решения.

### Решение

Статус:
- `да, как внешний необязательный слой`.

Форма применения:
- пилотный и вспомогательный инструмент;
- не источник правды;
- не обязательная часть рабочего контура каждого разработчика.

## 2. `rtk-ai/rtk`

### Что ценно

`RTK` очень полезен как узкий слой именно для shell-команд:
- он режет шум `ls`, `read`, `grep`, `git`, test output, lint output и подобные CLI-результаты;
- по README он даёт существенную экономию на типичных dev-командах;
- это хорошая идея для тяжёлых логов и больших test-выводов.

### Что ограничивает его у нас

Для `Axiom` есть два жёстких ограничения:
- по README `RTK` сильнее всего раскрывается через Bash-hook auto-rewrite;
- на native Windows этот hook не работает полноценно, и сам проект рекомендует WSL для полного режима;
- кроме того, даже у Claude Code built-in tools `Read`, `Grep` и `Glob` bypass-ят Bash hook.

У нас это особенно важно, потому что:
- основной репозиторий живёт на Windows;
- активная среда здесь часто идёт через PowerShell;
- нам нужен не только shell-output, но и компактная навигация по большим markdown-документам.

### Что применять

Для `Axiom` разумно брать из `RTK` не установку как обязательного слоя, а рабочий принцип:
- сначала адресный хвост, фильтр, first failure, scoped grep и компактный diff;
- затем только при необходимости полный сырой вывод.

Практически:
- на Windows native — только как необязательный явный CLI-инструмент;
- в WSL — можно как локальный эксперимент для тяжёлых `git` и `dotnet`-выводов;
- не стоит делать его обязательным правилом проекта.

### Решение

Статус:
- `частично, только как необязательный CLI-ускоритель`.

Форма применения:
- WSL или явный ручной вызов;
- не базовый стандарт проекта;
- не замена локальному `docs/agent/`-слою.

## 3. `eyaltoledano/claude-task-master`

### Что ценно

У `Task Master` сильная сторона — разложение большой работы на задачи, подзадачи, зависимости и workflow вокруг PRD.

Для некоторых типов больших фич это может быть полезно как временный внешний planning-helper.

### Почему он плохо совпадает с Axiom как основной контур

У `Axiom` уже есть собственная жёсткая система:
- `docs/PLANS4.md` — активный план;
- `docs/WORKLOG5.md` — активный журнал непрерывности;
- append-only договор эволюции проекта.

Если поверх этого завести второй task-реестр, появляются риски:
- расхождение между `.taskmaster`-структурой и `docs/PLANS4.md`;
- дублирование статусов;
- потеря точного контекста, почему решение принято именно так;
- искушение обновлять внешний task-manager вместо канонических документов.

Для `Axiom` это слишком дорогой обмен:
- выигрыш в оркестрации есть;
- но риск второго источника правды ещё выше.

### Что можно взять без установки системы целиком

Можно взять только идею:
- крупную тему иногда полезно сначала разложить на явные подшаги, зависимости и блокеры;
- но итоговый план должен всё равно попадать в `docs/PLANS4.md`, а результат — в `docs/WORKLOG5.md`.

### Решение

Статус:
- `нет, как основной task-контур`;
- `да, только как необязательная внешняя техника декомпозиции`.

Форма применения:
- разовый внешний brainstorming;
- без проектного переноса источника правды в `.taskmaster`.

## 4. `JuliusBrussee/caveman`

### Что ценно

`Caveman` ценен не как система памяти, а как радикальный урок краткости:
- очень короткие инструкции;
- сокращение лишней болтовни;
- идея уменьшать постоянные memory-файлы, а не только ответ модели;
- автоматический короткий режим с первого сообщения.

### Что не подходит напрямую

В чистом виде для `Axiom` это нельзя брать как есть:
- у проекта русскоязычная документация;
- у нас нужны точные формулировки договоров, диагностик и архитектурных решений;
- грубая телеграфная манера может ухудшить точность и сделать проектные документы хуже.

### Что можно адаптировать под нас

Адаптировать стоит не persona, а принципы:
- держать `docs/agent/CURRENT_STATE.md` очень коротким;
- не раздувать `docs/agent/PLAYBOOKS.md`;
- выносить повторяющийся агентный мусор из основных документов;
- требовать, чтобы вспомогательные агентные файлы были короче и практичнее канонических документов;
- в финальных ответах и агентных сводках предпочитать краткость без потери фактов.

Именно это мы уже частично делаем через:
- `scripts/ai-context.ps1`;
- `docs/agent/`;
- новый раздел компактного агентного режима в `AGENTS.md`.

### Решение

Статус:
- `да, как принцип редакционной краткости`;
- `нет, как готовая persona/надстройка для проекта`.

Форма применения:
- локальные короткие agent-файлы;
- компактные сводки;
- без копирования речевой маски и без навязывания "пещерного" стиля репозиторной прозе.

## Итог по применимости

### Что имеет смысл для Axiom прямо сейчас

1. Усиливать локальный слой `docs/agent/` и `scripts/ai-context.ps1`.
2. Держать `Headroom` как необязательный внешний ускоритель для тяжёлых логов и сводок.
3. Заимствовать у `RTK` привычку сначала брать короткий shell-срез, а не весь вывод.
4. Заимствовать у `Caveman` редакционную краткость для agent-файлов.

### Что не стоит делать

1. Не делать `Task Master` вторым официальным журналом проекта.
2. Не делать `RTK` обязательным стандартом на native Windows.
3. Не заменять канонические документы внешними memory/task-слоями.
4. Не переносить в репозиторные документы агрессивную речевую маску `Caveman`.

## Практическое проектное решение

Для `Axiom` утверждается такой порядок:

1. Базовый и обязательный контур:
   - `AGENTS.md`
   - `PROJECT.md`
   - `docs/SPECIFICATION3.md`
   - `docs/ARCHITECTURE.md`
   - `docs/PLANS4.md`
   - `docs/WORKLOG5.md`

2. Первый вспомогательный локальный контур экономии токенов:
   - `docs/agent/CURRENT_STATE.md`
   - `docs/agent/ARCHITECTURE_MAP.md`
   - `docs/agent/PLAYBOOKS.md`
   - `scripts/ai-context.ps1`

3. Второй, необязательный внешний контур:
   - `Headroom` для тяжёлых логов и сводок;
   - `RTK` только как явный CLI-ускоритель или WSL-эксперимент;
   - `Task Master` только как разовая внешняя декомпозиция;
   - `Caveman` только как источник идей по краткости.
