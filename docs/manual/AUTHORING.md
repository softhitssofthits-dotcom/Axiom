# Стандарт документации языка Axiom

## Статус документа

Этот документ — нормативный стандарт HTML-справочника `docs/manual/`.
Он детализирует действующие правила `AGENTS.md` (разделы 4, 4.1, 4.1.a, 4.1.b, 10, 10.1, 9.1) и фиксирует сложившуюся практику лучших страниц справочника.
При конфликте приоритет остаётся за `AGENTS.md` и русскоязычной проектной документацией; при конфликте между любой документацией и фактическим поведением языка истиной считаются исходный код, тесты и запускаемые примеры `samples/`.

Стандарт построен по результатам сравнительного анализа архитектуры документации Python, Rust Reference, Go Language Specification, C# Language Reference, Google Technical Writing Style Guide и метода book-to-skill.
Из каждого источника взяты только принципы, подходящие статическому HTML-справочнику небольшого BASIC-подобного языка; заимствование текстов и формулировок запрещено.

---

## 1. Архитектура документации

### 1.1. Слои входа

Справочник обязан отвечать на три разных вопроса читателя:

1. **Я новичок** — куда идти: `getting-started.html` с главной страницы.
2. **Я знаю имя конструкции** — где точное правило: `reference.html` (алфавитный указатель) и поиск `search.html`.
3. **Я знаю тему, но не имя** — где обзор раздела: тематические маршруты с главной страницы и sidebar.

Прогрессивное раскрытие знаний (принцип book-to-skill): **главная → обзорная страница раздела → атомарная страница сущности → запускаемый пример**.
Каждый следующий слой раскрывается только по потребности читателя; ссылка на следующий слой обязана присутствовать на предыдущем.

### 1.2. Типы страниц

В справочнике существуют ровно следующие типы страниц.
Новый тип страницы вводится только отдельным решением в `docs/PLANS4.md`.

| Тип | Назначение | Примеры |
| --- | --- | --- |
| Навигационная | вход и поиск: главная, указатель, поиск | `index.html`, `reference.html`, `search.html` |
| Обучающая | первый маршрут по языку, чтение подряд | `getting-started.html` |
| Обзорная страница раздела | карта темы, переходы к атомарным страницам | `arrays.html`, `data-types.html`, `loops.html`, `graphics.html` |
| Атомарная страница оператора | точное правило одного оператора | `if.html`, `for.html`, `print.html`, `dim.html` |
| Атомарная страница встроенной функции | точное правило одной функции | `inkey.html`, `keydown.html`, `pmap.html` |
| Страница семейства функций | несколько тесно связанных функций | `string-functions-slices-and-length.html` |
| Страница подсистемы | связка типа, операторов и функций одной подсистемы | `images.html`, `sprites.html`, `tilesets.html` |
| Приложение | таблицы, схемы, примеры, шпаргалка | `data-type-limits.html`, `characters.html`, `cheat-sheet.html`, `examples.html`, `arrays-1d-visual.html` |
| Диагностика | модель ошибок языка | `diagnostics.html` |

Обучающий и справочный материал не смешиваются на одной странице: обучающая страница ведёт от примера к понятию, reference-страница ведёт от точного правила к примеру.
Обзорная страница не подменяет атомарные: она объясняет структуру раздела и отсылает дальше, а не собирает все синтаксисы в один список.

### 1.3. Самоограничение страниц

Каждый тип страниц отвечает за своё и ссылается дальше (принцип «документ объявляет, чем он не является»):
- обзорная страница не приводит полные правила поведения — она ссылается на атомарные страницы;
- атомарная страница не обучает языку в целом — она предполагает `getting-started.html`;
- страница диагностики не дублирует правила — она классифицирует коды.

## 2. Обязательный каркас HTML

Каждая страница справочника содержит (проверено по всем 102 страницам; отступление недопустимо):

```html
<!doctype html>
<html lang="ru">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Справочник Axiom - <Имя страницы></title>
    <link rel="stylesheet" href="styles/manual.css">
</head>
<body data-page="<id из навигации>">
```

- шапка `header.topbar` с `a.brand`, `div.topbar__meta` (короткая тема страницы) и кнопкой `data-nav-toggle`;
- `aside.sidebar` с `nav#manual-nav` (заполняется `scripts/manual.js`);
- `main.content`:
  - `nav.breadcrumbs` с `aria-label="Хлебные крошки"`: Главная / … / текущая страница;
  - `p.eyebrow` — тип сущности (см. раздел 4);
  - `h1.page-title` — имя страницы;
  - `p.lead` — первая фраза-определение;
  - секции `section.article-section` с `h2`;
  - `div#page-pager.pager` перед закрытием `main`;
- подключение `scripts/manual.js` в конце `body`.

Требования к файлам:
- кодировка UTF-8 **без** BOM;
- переводы строк CRLF;
- семантический HTML: секции, списки, таблицы; заголовки по иерархии без пропуска уровней;
- только существующие классы `styles/manual.css`; новый визуальный класс вводится только вместе с изменением стандарта.

## 3. Нотация синтаксиса

Нотация описывается один раз до использования (принцип «сначала учи читать формализм») — легенда закреплена на странице `getting-started.html` в разделе «Как читать записи синтаксиса».

Правила записи синтаксиса:
- синтаксис даётся блоком `<pre><code class="language-basic">`;
- `<угловые скобки>` — место, куда читатель подставляет свою конструкцию; текст в скобках описывает её роль (`<счётчик>`, `<список вывода>`);
- `[...]` — необязательная часть записи;
- каждая поддерживаемая форма — отдельный визуально разделённый блок; разные формы нельзя сваливать в одну конструкцию;
- ключевые слова языка пишутся как есть: `IF`, `THEN`, `END IF`;
- в одной строке даётся одна форма; пояснения выносятся из блока синтаксиса в текст.

## 4. Канонические названия разделов и порядок

### 4.1. Eyebrow-метка типа сущности

`p.eyebrow` принимает одно из значений:
- `Оператор` — страница одного оператора;
- `Встроенная функция` — страница одной встроенной функции;
- `Процедура` — страница `SUB`;
- `Функция` — страница пользовательского `FUNCTION`;
- `Раздел` — обзорная страница раздела;
- `Тип, функции и операторы` — страница подсистемы со смешанными сущностями (всегда во множественном числе);
- `Встроенные функции` — страница семейства встроенных функций;
- `Операторы` — страница двух и более равноправных операторов;
- `Указатель`, `Приложение` — навигационные и справочные приложения.

Число (единственное или множественное) следует числу описанных сущностей: страница двух операторов получает `Операторы`, страница операторов с одной функцией — `Операторы и функция`.

### 4.2. Атомарная страница оператора

Порядок разделов (эталоны: `if.html`, `for.html`, `print.html`, `dim.html`):

1. `lead` — первая фраза прямо называет сущность: `<CODE> — оператор языка Axiom, который ...`.
2. **Когда использовать <ИМЯ>** — зачем оператор нужен и когда выбирают его, а не соседний.
3. **Где работает оператор <ИМЯ>** — если поведение зависит от режима или подсистемы (`SCREEN`, `CANVAS`); для операторов без такой зависимости раздел опускается.
4. **Синтаксис** — все формы, каждая отдельным блоком.
5. **Части записи** — поэлементное объяснение каждой части синтаксиса, включая типовой договор (`координаты должны быть целыми числами`).
6. **Как <оператор> работает** — поведение: порядок вычисления, что происходит при выполнении (может носить конкретное имя: «Как условие выбирает ветвь»).
7. **Правила и ограничения** — списком; сюда же blockquote отличий от QuickBASIC, если отличие важно при чтении старых BASIC-материалов.
8. **Пример <поведения>** — вводное предложение, код, «Результат:».
9. **Ручная проверка** — ссылки на запускаемые `.axm` из `samples/`.
10. **Диагностика** — коды по случаям (`<code>MBxxxx</code> — когда возникает`).
11. **См. также**.

Страница подсистемы (`images`, `sprites`, `tilesets`, `tilemaps`) следует тому же порядку, но вместо «Как работает» содержит разделы по каждой функции и оператору подсистемы: «Что такое тип X» → «Когда использовать X» → «Где работает X» → «Синтаксис» → «Части записи» → разделы функций и операторов → «Правила работы» → «Пример» → «Диагностика» → «См. также».

### 4.3. Атомарная страница встроенной функции

Порядок разделов (эталон: `inkey.html`):

1. `lead` — `<CODE> — встроенная функция языка Axiom, которая ...`.
2. **Для чего нужна функция <ИМЯ>**.
3. **Где работает функция <ИМЯ>** — режимы и подсистемы, от которых зависит поведение; выполнение в `BytecodeVm`.
4. **Синтаксис** — все формы вызова.
5. **Аргументы** — по одному; для функции без аргументов — явная фраза об этом.
6. **Что возвращает функция <ИМЯ>** — тип результата и таблица ситуаций, если поведение зависит от состояния.
7. **Правила работы** — ограничения и пограничные случаи.
8. **Пример** — вводное предложение, код, при детерминированном результате — «Результат:».
9. **Ручная проверка**.
10. **Диагностика**.
11. **См. также**.

### 4.4. Страница семейства функций

Эталон: `string-functions-slices-and-length.html`.

Каждая функция получает собственный `h2` с именем (`LEN`, `LEFT`, ...). Внутри раздела функции единый порядок подразделов `h3`:

1. вводный абзац — что делает функция;
2. **Синтаксис** — сигнатура блоком `language-basic`;
3. **Аргументы** — компактный абзац с типовым договором каждого аргумента; подраздел опускается, если у функции нет аргументов или договор единственного аргумента уже описан во вводном абзаце или разделе поведения;
4. смысловой заголовок поведения или возвращаемого значения (например «Позиция начала и длина фрагмента») — тип результата, поведение на пустой строке и на выходе за границы, коды диагностики;
5. **Пример <поведения>** — код и, при детерминированном результате, блок «Результат:».

Завершают страницу «Ручная проверка» и «См. также». Блок «Результат:» добавляется только для проверяемого вывода: строковые операции, целочисленная арифметика, логические проверки. Для зависящих от времени, файловой системы или случайных значений примеров блок не ставится.

### 4.5. Обзорная страница раздела

1. `lead` — что за раздел и какие группы сущностей в него входят.
2. **Что такое <тема>** — понятие до синтаксиса.
3. **Как устроена <тема>** — структура и состав.
4. Карта раздела — переходы к атомарным страницам по форме использования («Как выбрать страницу по форме массива»).
5. **Ручная проверка** — если есть показательные примеры.
6. **См. также**.

Обзорная страница не приводит полный синтаксис сущностей и не перечисляет их диагностику.

### 4.6. Названия разделов, которые нельзя варьировать

Синонимические варианты запрещены; используется только каноническое название:

| Каноническое название | Запрещённые варианты | Где применяется |
| --- | --- | --- |
| Ручная проверка | Проверочные программы, Примеры для проверки | все страницы с samples |
| Части записи | Параметры (для операторов), Части оператора, Объяснение параметров | атомарные страницы операторов |
| Аргументы | Параметры (для функций) | атомарные страницы встроенных функций |
| Синтаксис | Форма записи, Запись оператора | все страницы с формами |
| Диагностика | Ошибки, Коды ошибок | страницы с кодами |
| См. также | See also, Смотрите также | все страницы |

## 5. Терминологический словарь

Термин фиксируется один раз и применяется без синонимов (аналог word-list из Google Style Guide).

| Термин | Значение в Axiom | Запрещённая замена |
| --- | --- | --- |
| оператор | ключевая конструкция языка, выполняющая действие: `PRINT`, `DIM`, `FOR` | инструкция, команда, statement |
| встроенная функция | функция, предоставляемая языком: `LEN`, `INKEY` | builtin, системная функция |
| процедура | пользовательский `SUB ... END SUB` без возвращаемого значения | подпрограмма |
| функция | пользовательский `FUNCTION ... END FUNCTION` с результатом | — |
| параметр | имя в объявлении `SUB`/`FUNCTION` | — |
| аргумент | значение в месте вызова | — |
| выражение | конструкция, вычисляемая в значение | — |
| переменная | именованное изменяемое место хранения, объявленное `DIM` | — |
| константа | именованное неизменяемое значение `CONST` | — |
| массив | составное значение с индексированными элементами | список, вектор |
| элемент | одно значение массива | ячейка |
| индекс | номер элемента; нижняя и верхняя границы включительны | ключ, смещение |
| тип данных | `INTEGER`, `STRING`, `BOOLEAN`, `TYPE` и другие | — |
| запись | значение пользовательского типа `TYPE` | структура, объект |
| область видимости | часть программы, где имя доступно | скоуп, контекст видимости |
| диагностика | сообщение об ошибке с кодом `MBxxxx` и координатами | исключение (кроме контекста `TRY`/`ERROR`) |
| ошибка времени выполнения | диагностика, возникающая после успешного запуска программы | рантайм-ошибка, крэш |
| запускаемый пример | файл `.axm` из `samples/` | тестовый скрипт |

Дополнительные правила словоупотребления:
- сущность называется явно в каждом месте, где читатель может потерять предмет: «оператор FOR», «встроенная функция LEN», а не «он», «данная форма», «это»;
- кодовые имена не склоняются и не спрягаются: «оператор PRINT выполняет...», а не «PRINT-ится»;
- поведение описывается в настоящем времени и активным залогом: «Axiom вычисляет условие», а не «условие будет вычисляться» или «происходит вычисление»;
- обращение к читателю — на «вы»;
- условия ставятся до инструкций: «если программа не вызвала оператор SCREEN, вывод попадает во вкладку Output», а не инструкции с оговоркой в конце.

## 6. Правила текста

1. Один смысл на абзац; главный вывод — первым предложением абзаца.
2. Абзац длиннее пяти-шести предложений — кандидат на разделение или на список.
3. Полные предложения вместо телеграфного стиля в объяснениях (перечисления в таблицах и списках — исключение).
4. Сначала понятный смысл, затем точное правило, затем синтаксис, затем пример.
5. Техническая точность не приносится в жертву понятности: при затруднении упрощается способ объяснения, а не само правило.
6. Все имена операторов, функций, типов, ключевых слов, файлов и путей — в `<code>`; русское предложение при этом остаётся грамотным русским предложением.
7. Новая проза в репозитории пишется по-русски; английские слова не вставляются при наличии русского эквивалента (правило 9.1 из `AGENTS.md`).
8. Никаких обещаний несуществующих возможностей: страница документирует только проверенное поведение (код, тесты, `samples/`).

## 7. Правила примеров

1. Перед примером — вводное предложение, заканчивающееся двоеточием и объясняющее, что пример показывает.
2. После кода — абзац «Результат:» с блоком ожидаемого вывода, если результат детерминирован.
3. Один пример показывает одно поведение или одну очень маленькую группу связанных поведений.
4. Пример самодостаточен: объявления переменных входят в пример.
5. Пользовательские строки, подсказки и комментарии в примерах — на русском языке; английский — только для точных технических токенов (правило 10.1 из `AGENTS.md`).
6. Пример обязан быть проверен против фактической реализации: через существующий `.axm` из `samples/`, через тесты или через запуск в `Electron IDE`.
7. Пропуски в длинном коде обозначаются комментарием на языке Axiom (`' ... остальной код`), а не многоточием.
8. Интерактивные и графические примеры сопровождаются указанием, что нужно сделать пользователю (нажать клавишу, подождать кадр).

## 8. Правила диагностики

1. Раздел «Диагностика» перечисляет коды по случаям: `<code>MBxxxx</code> — когда возникает`.
2. Указывается момент обнаружения: при чтении и разборе, при проверке смысла или во время выполнения.
3. Префиксная модель: `MB0xxx` — чтение текста, `MB1xxx` — разбор, `MB2xxx` — смысловые, `MB3xxx` — время выполнения. Коды `MB4xxx` — служебные коды инфраструктуры выполнения (покрытие байт-кода, захват состояния) и в пользовательский контракт языка не входят.
4. Общая модель ошибок описывается один раз на `diagnostics.html`; на страницах сущностей — только специфические для них коды.
5. Код, упомянутый на странице, обязан существовать в `src/Axiom.Core/DiagnosticCodes.cs`; новый код вносится в `diagnostics.html` в той же задаче.
6. Отрицательные запускаемые примеры живут в `samples/acceptance/negative/` и подключаются в «Ручной проверке».

## 9. Ссылки и «См. также»

1. «См. также» обязателен на каждой странице и содержит: обзорную страницу своего раздела, ближайшие связанные конструкции, `diagnostics.html` — при наличии раздела диагностики.
2. Текст ссылки описывает цель; «здесь», «эта страница» и голые ключевые слова без контекста запрещены.
3. Все внутренние ссылки ведут на существующие страницы; проверка целостности (страницы + `samples/`) обязательна перед завершением задачи, меняющей ссылки.
4. Ссылки на запускаемые примеры даются относительными путями `../../samples/...` и снабжаются человеком читаемым описанием поведения.

## 10. Навигация и поиск

1. Sidebar строится из массива `nav` в `scripts/manual.js`; новая страница обязательно вносится в него с уникальным `id`, совпадающим с `data-page` страницы.
2. Запись в `scripts/search-index.js` обязательна для каждой новой страницы: `title`, `href`, `kind` (тип сущности из раздела 4.1), `category` (раздел навигации), `description`, `keywords` (включая английское имя сущности и русские синонимы).
3. Хлебные крошки повторяют путь навигации: Главная / раздел / страница.
4. Порядок элементов в `nav` соответствует порядку чтения от простого к составному: типы → объявления → выражения → управление → процедуры → данные → ввод-вывод → файлы → графика → события → функции → ошибки.

- идентификаторы нормативных правил с отдельными якорями (Rust) — на текущем масштабе достаточно обычных якорей разделов.
