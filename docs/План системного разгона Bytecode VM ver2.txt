# План системного разгона `Bytecode VM` ver2

## Зачем нужна версия 2

План `ver1` хорошо отработал как план первого большого этапа: он вытолкнул байткодную VM из состояния явного проигрыша и привёл проект к режиму, где байткод уже регулярно быстрее интерпретатора на части сценариев и в целом опирается на более здоровую внутреннюю архитектуру.

Но `ver1` нельзя считать полностью закрытым:
- общий набор `compare-engines` всё ещё не даёт состояния «байткод не медленнее интерпретатора везде по базовому эталонному набору»;
- часть архитектурных пунктов закрыта полностью, часть закрыта только частично;
- текущая работа сместилась из крупных перестроек в более узкий разгон горячих участков и в выравнивание всего профильного набора, а не одного `array_cube_rollup.axm`.

Поэтому `ver2` фиксирует уже не стартовую перестройку VM, а второй этап: доведение результата до системной устойчивости на всём эталонном наборе.

## Статус плана ver1

### Закрыто

1. Постоянная программа измерений в целом создана:
- `compare-engines` закреплён как основной стенд;
- профильный набор расширен и уже включает документные, файловые, regex- и array-heavy сценарии;
- в репозитории есть постоянные сценарии `document_batch_repair.axm`, `file_batch_roundtrip.axm`, `regex_log_analysis.axm`, `regex_modes_pipeline.axm`, `array_cube_rollup.axm`, `array_transform_chain.axm`, `high_rank_metadata.axm`.

2. Основной дескрипторный слой built-in в VM в значительной части внедрён:
- есть прямое отображение `builtin id -> vm handler`;
- есть отдельные быстрые тракты по арности `0`, `1`, `2`, `3` и variadic;
- большая часть built-in уже идёт не через один огромный runtime-`switch`, а через подготовленный диспетчинг `BuiltinExecution`.

3. Общий накладной расход VM заметно снижен:
- обычный запуск отделён от отладочных снимков и логики остановки;
- удешевлён доступ к операндам инструкции и к частым слотам VM;
- обычные локали читаются и пишутся без shared-slot ветки;
- часть горячих стековых операций переведена на `PushUnchecked(...)`.

4. Первый общий проход по массивам и плотным циклам уже выполнен:
- `LoadGlobal` для части top-level глобалей снят через перевод в локальные слоты entry routine;
- `PushConst` частично разгружен через `PushIntegerZero` и `PushIntegerOne`;
- проверена и отклонена как неубедительная отдельная 3D-специализация;
- принят общий integer-путь ускорения для индексов массива.

### Частично закрыто

1. Правило «оптимизируем по всему набору, а не по одному примеру» оформлено методически, но в последних сессиях не всегда соблюдалось как жёсткий выпускной барьер:
- для локальных шагов мы часто мерили прежде всего `array_cube_rollup.axm`;
- полный набор прогонялся не после каждого шага.

2. Архитектура built-in сильно улучшена, но не добита до конца:
- при вызове built-in как значения функции в VM всё ещё есть fallback-линейный поиск по `_builtins.Values` в редком пути;
- variadic built-in всё ещё могут создавать новый массив аргументов через `ToArray()`.

3. Отдельный этап плотных циклов только начат:
- `FOR/NEXT` уже лучше виден в профиле;
- но специального завершённого прохода по `JumpIfForDoneLocal`, `AdvanceForLoopLocal` и соседней арифметике ещё не было.

### Не закрыто

1. Стоимость маленьких пользовательских `FUNCTION`/`SUB` и кадров VM отдельно ещё не разобрана как самостоятельный этап.
2. Критерий «байткод не медленнее интерпретатора на базовом эталонном наборе» пока не выполнен по факту последнего полного прогона.
3. Правило «новый built-in сразу дружит с VM» архитектурно почти готово, но ещё не доведено до режима без старых fallback-путей.

## Актуальная картина по эталонному набору

По полному прогону `compare-engines` от `2026-04-30 22:26:38`:
- быстрее интерпретатора: `document_batch_repair.axm`, `array_cube_rollup.axm`;
- близко к паритету, но ещё шумно: `regex_modes_pipeline.axm`;
- всё ещё медленнее: `file_batch_roundtrip.axm`, `regex_log_analysis.axm`, `array_transform_chain.axm`, `high_rank_metadata.axm` по runtime или total.

Это значит:
- первый этап дал реальный архитектурный прогресс;
- но следующий фокус должен быть не в ещё одной локальной победе на одном массивном benchmark, а в выравнивании набора по нескольким классам нагрузки.

## Цель версии 2

Цель `ver2`: довести байткодную VM до состояния, где она:
- не проигрывает интерпретатору на основном эталонном наборе `compare-engines`;
- сохраняет уже полученный выигрыш на массивных и документных сценариях;
- получает дальнейший прирост не за счёт подгонки под один benchmark, а за счёт добивания оставшихся общих горячих слоёв.

## Приоритеты ver2

### 1. Снова сделать полный набор главным критерием выпуска
- После каждого значимого шага прогонять не только целевой `--filter`, но и весь текущий набор `compare-engines`.
- Держать отдельные узкие прогоны только как инструмент локального профилирования, а не как окончательный критерий успеха.
- Считать шаг принятым только если он не портит соседние классы нагрузки.

### 2. Добить оставшиеся архитектурные хвосты built-in
- Убрать fallback-линейный поиск built-in при вызове встроенной функции как значения функции.
- Проверить, где ещё variadic built-in тянут лишние выделения аргументов, и не нужен ли там более дешёвый общий путь.
- Закрепить правило: новая встроенная функция попадает в bytecode VM через тот же дескрипторный слой без нового special-case.

### 3. Пройтись по арифметике и каркасу плотных циклов
- Проверить `Add`, `AddLongInteger`, `Multiply`.
- Отдельно проверить `JumpIfForDoneLocal` и `AdvanceForLoopLocal`.
- Если выигрыш подтверждается, оформлять его как общий разгон цикла, а не как подгонку под `array_cube_rollup.axm`.

### 4. Отдельно пройтись по стоимости пользовательских вызовов
- Разобрать цену маленьких `FUNCTION`/`SUB`.
- Проверить создание кадра, упаковку аргументов, возврат значения и захваты.
- Если здесь есть заметный остаточный проигрыш, это должно улучшить не только массивные, но и более «прикладные» сценарии.

### 5. Вернуться к массивам только если это снова подтвердит профиль
- Не плодить новые 2D/3D-ветки без сильного сигнала.
- Возвращаться в массивный слой только если полный набор и opcode-профиль снова покажут, что именно он мешает следующему системному шагу.

## Порядок реализации

1. Зафиксировать текущий базовый отчёт полного `compare-engines` как опорную точку для `ver2`.
2. Закрыть редкие fallback-пути built-in и лишние выделения в вызове встроенных функций.
3. Пройтись по арифметике и `FOR/NEXT`-каркасу.
4. Отдельно проверить пользовательские вызовы и стоимость кадров VM.
5. После каждого шага повторять:
- полный `compare-engines`;
- целевой `compare-engines --filter` для текущего горячего сценария;
- opcode-профиль через `.artifacts/repro-bytecode`, когда шаг относится к внутреннему hot path VM.

## Критерии готовности ver2

- Полный эталонный набор `compare-engines` больше не показывает устойчивых проигрышей байткода интерпретатору на базовых сценариях.
- Уже достигнутые выигрыши на массивных и документных сценариях не потеряны.
- В VM не остаётся старого fallback-линейного поиска built-in в обычных путях вызова.
- Следующие оптимизации снова становятся скорее выбором развития, чем вынужденным устранением базового проигрыша.
