# Проверка графики SCREEN — 15 октября 2026 года

Проверено состояние после коммита `1953c206b6bc80384b605e74c053f5c51165b029`. Язык и компилятор 0.1.14, IDE 0.5.2. Это проверка существующей реализации перед возможным переводом рисования SCREEN на DirectX. Реализация в этой задаче не менялась; найденные ошибки остаются открытыми.

## Устройство вывода

Цепочка исполнения: синтаксис и связывание → BytecodeVm → IGraphicsHost → GraphicsHostService → ScreenFramebuffer → NativeGraphicsScreenWindow → Direct3D11SwapChainRenderer.

SCREEN уже использует Direct3D 11 для показа готовой текстуры и её масштабирования. Рисование примитивов, заливка, составление текста и получение полного снимка выполняются на CPU. Каждая публикация нового снимка создаёт массив BGRA и загружает его в текстуру. Поэтому перевод SCREEN на DirectX означает перенос хранения и изменения изображения, а не только замену оконного вывода.

CANVAS использует отдельную рабочую и опубликованную GPU-поверхности. Механически заменить SCREEN этим холстом нельзя: у SCREEN есть палитровые индексы, четыре страницы, VIEW/WINDOW и общий текстовый слой.

## Подтверждённые проблемы

### 1. PAINT с фоновым узором может не завершаться — высокий приоритет

Минимальная программа:

```basic
SCREEN 1
COLOR 6, 0
LINE (0, 0)-(4, 4), 9, B
PAINT (1, 1), CHR(0), 9, CHR(0)
PRINT "DONE"
```

BytecodeVm успешно компилирует программу, но не возвращается из заливки. Проверочный процесс принудительно остановлен через 5000 мс; незавершённых процессов этой проверки не оставлено.

Причина в `GraphicsFloodFill.PaintPattern/Flood`: при наличии фонового узора пиксель допускается к обходу, если его цвет равен начальному цвету или соответствующему цвету фона. После записи того же цвета условие остаётся истинным. Отдельного признака посещения нет, соседние строки повторно добавляются в стек. На независимой области 4×4 запись превысила защитный предел 10000 операций. Этот предел введён только в проверочном делегате; в продукте его нет.

Ошибка находится в общем алгоритме, используемом также совместимым PAINT на CANVAS. Перенос текстур на GPU сам по себе её не исправит. Нужна гарантия однократного посещения или иной алгоритм завершения при совпадающих цветах. Отдельную приёмку остановки зависшей программы из IDE в этой задаче не выполняли.

### 2. Короткая дуга CIRCLE теряет пиксели — высокий приоритет

```basic
SCREEN 1
CIRCLE (160, 100), 60, 12, 0, 0.01
PRINT POINT(220, 100)
```

Ожидаемый индекс начальной точки дуги — 12, фактический — 0. BytecodeVm завершается успешно без сообщения об ошибке. Контрольная полная окружность с теми же центром и радиусом даёт 12.

Причина: `GraphicsEllipseRasterizer.ComputeMaxIterations` сокращает допустимый обход для дуги коэффициентом `max(0.5, sweepFraction)`, хотя сам обход эллипса стартует с верхней точки и затем отбирает точки по углу. Для малой дуги около правой точки обход прекращается до нужной области. Ограничитель должен учитывать путь алгоритма до дуги либо дуга должна строиться другим способом с сохранением пиксельного договора.

Проблема дополнительно подтверждена через настоящую Electron IDE и захват клиентской области нативного SCREEN: полная окружность слева видна; начальная точка короткой дуги справа чёрная. Захват 320×200: полный круг BGRA `[85,85,255,255]`, короткая дуга `[0,0,0,255]`; ошибок страницы нет. Локальные файлы: `.artifacts/screen-audit/short-arc-native.png`, `native-arc-result.json`, `native-arc.cjs`.

### 3. LINE/B/BF обходят невидимую геометрию — высокий приоритет

```basic
SCREEN 1
LINE (-3000, -3000)-(-1, -1), 12, BF
```

Рисунок полностью вне экрана, однако `GraphicsHostDrawing.DrawAbsoluteBox` перебирает каждую строку, а `DrawAbsoluteLine` — каждый пиксель. Проверка видимости выполняется только внутри `PlotAbsolutePixel`. Для BF стоимость определяется исходной площадью, для обычной линии — исходной длиной. В этих циклах нет проверки отмены.

Последний измеренный запуск через действующую графическую службу: невидимая линия длиной 1000000 — 44,53 мс; невидимый BF 1000×1000 — 45,48 мс, BF 3000×3000 — 412,39 мс. Это одиночные диагностические замеры, а не стабильный сравнительный тест. Предыдущие запуски BF 3000×3000 дали 417,98 и 448,69 мс. Разрешённые координаты доходят до ±1000000000, поэтому возможны существенно более долгие операции. Самые большие случаи намеренно не запускались.

Исправление требует отсечения до перебора и сохранения существующего результата растеризации диагоналей, текущей позиции, STEP, VIEW и WINDOW. Для BF следует заполнять только пересечение прямоугольников. Такой дефект нельзя считать устранённым одним ускорением показа кадра.

### 4. VIEW: справочник допускает то, что отвергает реализация — средний приоритет

`docs/manual/view.html` требует непустого пересечения области с экраном. `GraphicsHostService.TrySetViewportCore` требует, чтобы обе вершины находились внутри экрана. Вызов области `(-1,0)-(10,10)` на SCREEN 1 возвращает false, хотя пересечение непустое; VM преобразует отказ хоста в MB3007.

Нужно отдельно согласовать договор: исправить формулировку справочника или реализовать частичное пересечение. В рамках проверки поведение и справочник не изменялись.

## Дополнительные затраты и пробелы проверок

- Все четыре страницы выделяются сразу, даже при использовании одной. Каждая содержит массив индексов int, полноцветных пикселей uint и признаков bool — примерно 9 байт на пиксель, 36 байт на пиксель для четырёх страниц, без снимка и текстур.
- Измеренные выделения в потоке при открытии SCREEN: режим 1 — 2568816 байт, режим 8 — 82960360 байт, режим 9 — 147473408 байт. Это управляемые выделения за операцию открытия, а не полный объём занятой памяти процесса и видеокарты. Снимок режима 8 дополнительно содержит 8294400 байт BGRA, режима 9 — 14745600 байт; новый снимок создаётся при каждой публикации.
- GET на SCREEN не использует групповое чтение `CaptureAbsolutePixels`: хост возвращает null и код читает пиксели отдельно. PUT также записывает их по одному. Для GPU эти пути потребуют отдельного решения о чтении/записи областей.
- Проверка с названием `DrawLine_FilledBoxUsesSingleClippedFill` проверяет итоговые пиксели, но не число операций и время. Она проходит при нынешнем полном переборе. Название `Paint_StartOutsideScreenLeavesFramebufferAndPositionUnchanged` расходится с собственными утверждениями: позиция ожидается равной (-1,-1). Это недостатки точности тестов, не отдельные доказанные ошибки языка.
- Проверка нескольких мониторов, физических событий мыши, разных системных DPI и всех разрешений 1..10 визуально не выполнялась. Автоматические оконные события не заменяют такую приёмку.

## Исправления по результатам проверки — 15 октября 2026 года

В рабочей версии языка и компилятора 0.1.15 устранены три воспроизведённые ошибки. IDE остаётся 0.5.2. Исправления выполнялись поверх 46d722c; исходные результаты аудита выше сохранены как история.

- PAINT с фоновым узором отмечает посещённые пиксели в битовых масках строк. Маска создаётся только для обработанных строк и только при наличии фонового узора. Совпадение записываемого и исходного цвета больше не допускает повторного обхода. На исходной области 4×4 теперь ровно 16 записей; исходная программа успешно завершается через BytecodeVm.
- CIRCLE сохраняет достаточный предел обхода эллипса независимо от длины дуги; защита от патологически большого обхода по размеру экрана сохранена. Начальная точка короткой дуги теперь имеет индекс 12, как и контрольная полная окружность.
- LINE вычисляет только те точки исходной линии Брезенхема, главная координата которых попадает в экран и VIEW. Точная целочисленная формула использует UInt128 для произведений после преобразования WINDOW; повторное построение между отсечёнными концами не применяется. Полностью невидимая геометрия отбрасывается сразу, BF перебирает только видимый прямоугольник. Сохранены конечная графическая позиция, направления и правила округления. Проверка сравнивает 2401 сочетание концов с прежним независимым обходом; отдельно проверены B/BF и допустимые координаты до миллиарда.
- Справочник VIEW теперь явно требует обе вершины внутри экрана. Поведение реализации не расширялось; четыре новые проверки подтверждают отказ частичной области без изменения текущей позиции и настройки VIEW.

Добавлены постоянные проверки ScreenGraphicsRegressionTests, уточнена проверка бюджета дуги, исправлено вводящее в заблуждение название проверки внешней точки PAINT. На прежней реализации новая выборка дала 8 отказов и 3 прохода; после исправления и добавления проверок прямоугольников все 13 случаев входят в успешный полный Runtime-прогон.

Запускаемые примеры: samples/operators/paint/background_repeat.axm, samples/operators/circle/short_arc.axm, samples/operators/line/clipped_bounds.axm. Сценарий graphics-screen-regression-boundaries открывает все три через Electron, проверяет фактический пиксель нативного SCREEN, отсутствие диагностик и закрытие окна после остановки. Каталог Electron обновлён до 417 сценариев; полный каталог не запускался.

Измерение того же невидимого BF 3000×3000 через графическую службу после исправления дало 17,47 мс против прежних 412–449 мс. В это время входит публикация кадра, а не только расчёт геометрии. Вывод о сложности дополнительно подтверждён ограничением числа обращений к хосту, без зависимого от скорости компьютера порога теста. Размеры четырёх страниц и выделения памяти не менялись; их оптимизация остаётся частью будущего переноса.

Полный Runtime: 1130/1130. Адресная выборка графических служб, окна, вывода и CanvasGpuSurfaceTests: 156/156. Справочник: свежая выгрузка реестра, 122 страницы, 4883 ссылки; шесть проверок подсветки/синтаксиса/поиска и три браузерные проверки прошли. При обновлении снимка устранено отставание его контрольной суммы от ранее добавленного однострочного IF; перечень 271 имени, 335 форм и 68 операторных записей сохранён.

Первый запуск Electron был остановлен до приёмки из-за непересобранного DesktopHost: редактор не достиг #app.ready. Изолированные процессы остановлены, DesktopHost Debug и CLI Release пересобраны успешно; проверка свежести хоста подтвердила fresh, CLI сообщает 0.1.15.
