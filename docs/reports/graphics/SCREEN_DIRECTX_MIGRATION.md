## Что изменено

Обычный DesktopHost включает `GraphicsHostService.UseGpuScreen`. Графические режимы SCREEN 1..10 используют общий Direct3D 11 контекст, очередь команд и нативный показ, ранее применённые для CANVAS. SCREEN 0 сохраняет текстовый путь. Прежний CPU-путь остаётся контрольной реализацией для сравнительных проверок.

Рабочие страницы хранят пары видимого цвета BGRA и палитрового индекса в текстурах R32G32_UInt. Индекс 0xffffffff обозначает полноцветный пиксель. Четыре страницы создаются по мере обращения, а не выделяются сразу. Каждая имеет свою палитру из 256 значений. PALETTE изменяет палитру активной страницы и перекрашивает индексные пиксели шейдером; полноцветные изображения сохраняются. PCOPY копирует текстуру и палитру без чтения кадра на CPU.

При публикации GPU копирует видимую страницу и накладывает общий текстовый слой. Слой составляется на GPU из кешированных глифов, включая кириллицу и фон ячеек, и переиспользуется при неизменных ячейках и палитре. Текст не записывается в рабочие пиксели страницы, не меняет POINT и не переносится через PCOPY. Автоматический показ SCREEN сохранён; оператор PRESENT не требуется.

| Операции | Исполнение |
|---|---|
| PSET/PRESET | GPU-запись индекса и соответствующего цвета текущей палитры. |
| LINE, B, BF, VIEW с рамкой/заливкой | GPU-команды с отсечением; сохранены координаты VIEW/WINDOW, округление и текущая позиция. |
| Обычная целая окружность радиуса до 1024 | GPU-растеризация с прежними правилами пикселей. |
| Дуги, эллипсы, радиальные отрезки, редкая большая геометрия | Точные координаты готовятся существующим CPU-алгоритмом, затем рисуются на GPU одним набором точек; полный CPU-кадр не создаётся. |
| DRAW | Команды используют те же пути точек, линий и заливки. |
| Изображения и спрайты | GPU-масштабирование и точное смешивание альфа с текущим цветом страницы. |
| POINT | Синхронное чтение одного пикселя с сохранением индексного договора. |
| GET/PUT | Чтение необходимой области; PUT записывает индексные пиксели GPU-командами. Это не обещание одной GPU-команды на весь PUT. |
| PAINT | Исправленная CPU-заливка временной копии области и обратная загрузка; палитра восстанавливается на GPU. |
| SMOOTH | Фильтрация опубликованного кадра на GPU, без изменения пикселей и координат. |

Выбор устройства остаётся общим: аппаратный Direct3D 11, при недоступности подходящего устройства — WARP. Ошибки графической очереди передаются в DesktopHost и отменяют программу. Нативное окно сохраняет заголовок SCREEN, первоначальные размеры, ввод, фокус, изменение размера и освобождение ресурсов.

## Изменённые компоненты

- `CanvasGpuSurface.Screen.cs`: страницы, палитры, PCOPY, кешированный текстовый слой и наборы точек.
- `CanvasGpuSurface.cs`, `CanvasGpuShaders.cs`: общие GPU-команды, составление слоёв и безопасная арифметика больших линий.
- `CanvasRenderSession.cs`: публикация SCREEN в той же ограниченной очереди графического потока.
- `GraphicsHostService.ScreenGpu.cs` и основная часть службы: включение GPU-пути, координаты, текст, страницы, примитивы, ресурсы и читающие операции.
- `NativeGraphicsScreenWindow.cs`, `DesktopHost.cs`: подключение сеанса SCREEN к нативному окну и обычному запуску.
- `ScreenGpuSurfaceTests.cs`, `ScreenGpuHostTests.cs`, новый сценарий Electron и пример `samples/operators/screen/directx_pages_input.axm`.

Язык, синтаксис, набор опкодов и рабочая подсветка Monaco не изменялись. Повышена только IDE: 0.5.2 → 0.6.0.

## Найденное и исправленное при переносе

1. Рамка VIEW первоначально использовала стандартный цвет вместо текущей палитры. Независимое сравнение CPU/GPU воспроизвело различие; рамка теперь использует индексный GPU-путь.
2. Прежняя подготовка очень большой линии CANVAS использовала знаковое Int128-произведение. Проверка концов около границ LONG обнаружила потерю видимых пикселей; произведения переведены в UInt128. Этот общий путь используется также SCREEN.
3. Первый общий .NET-прогон остановлен после зависания тестового процесса; завершённые 91 проверки не выдаются за полный результат. Диагностический повтор прошёл 163/163. Новые проверки, создающие нативные окна, затем изолированы непараллельной коллекцией; итоговый запуск после добавления кеша — 164/164. Первоначальное зависание повторно не воспроизвелось; его точная причина не установлена.
4. В оконной автоматизации Enter сначала отправлялся без WM_CHAR, а кириллица — ANSI-вариантом SendMessageTimeout. Добавлена полная последовательность Enter и явный Unicode-вызов. Проверочная программа сама сравнивает строку с «Тест» и рисует жёлтую точку только при точном совпадении. Проверка завершения нативного INPUT опирается на результат программы, а не на внутренний идентификатор запроса Electron, который прежний протокол отдельно не закрывает при нативном вводе.

## Пределы результата

- Не заявляется перенос вычисления любой геометрии и совместимой PAINT целиком на GPU. Сохранённые CPU-пути перечислены выше.
- Нулевая передача кадра подтверждена для обычных проверенных кадров; явные POINT/GET/PUT, PAINT и служебный запрос снимка могут читать GPU-память.
- Ленивое создание страниц и отсутствие обычного CPU-снимка не являются замером полного объёма памяти процесса или видеокарты. Универсального коэффициента ускорения и частоты кадров не заявляется.
- Физическая мышь, несколько мониторов, системные DPI и все размеры SCREEN визуально не принимались. Полный набор решения и полный каталог Electron не запускались.
- Тестовый CANVAS 800×400 с фоном RGB(20,40,60), замеченный автором на экране, относится к проверке масштабирования мыши. Пропорции холста 2:1 сохраняются, свободное место окна заполняется чёрным; это прежнее поведение CANVAS, не новый режим 16:9 и не оформление SCREEN.
