# StepBack после частичного отказа COPYDIR

16 октября 2026 года проверен следующий пункт файловой приёмки. Реализация не изменена: нарушение границы отката в проверенных сценариях не воспроизвелось.

## Достижимые частичные эффекты

В ядре исходный файл удерживается через FileStream с FileShare.None. COPYDIR создаёт папку назначения, затем получает отказ копирования файла; TRY/CATCH перехватывает ошибку. Четыре новых случая проверяют обе формы COPYDIR: с двумя аргументами и с явным TRUE, с остановкой в начале CATCH и после обработчика. Папка назначения действительно существует, скопированных файлов нет. CanStepBack равен false; продолжение завершается без повторного эффекта и сохраняет внешний файл.

В настоящем Electron исходная папка содержит marker.txt и вложенную папку child. В папке назначения вместо child заранее находится обычный файл. COPYDIR с TRUE копирует marker.txt, затем получает отказ создания вложенной папки. Порядок не зависит от перечисления записей: файлы текущей папки обрабатываются до извлечения вложенных папок из очереди. Остановка на первом операторе CATCH подтверждает выполненную запись marker.txt и сохранённое препятствие. StepBack недоступен и на панели, и через Ctrl+F10. После внешней правки marker.txt продолжение выводит 2 и сохраняет внешний текст: повторный COPYDIR с TRUE перезаписал бы его.

## Результаты и объяснение

`dotnet test tests/Axiom.Execution.Tests/Axiom.Execution.Tests.csproj --no-restore --filter FullyQualifiedName~StepBackFileBoundaryTests --verbosity minimal`: 9/9, включая пять ранее добавленных случаев успешной записи и открытого FILE. Четыре новых случая прошли с явным утверждением недоступности StepBack. Первоначальная попытка проверки обращалась к отсутствующему RuntimeResult.Output; это исправление проверочного кода, не дефект продукта.

`node ide/e2e/runner.js trace-partial-file.spec.js`: 1/1, 7 утверждений; отказов, падений и ошибок страницы нет. Доказательство: ide/e2e/evidence/trace-partial-file-results.json. Общий results.json восстановлен. Каталог 436, полного прогона не было.

Очистка истории после успешного встроенного вызова не доказывает её очистку при исключении. Однако в проверенном TRY/CATCH значение ERROR не поддерживает создание обратимого снимка: TryCreateValueSnapshot допускает ограниченный набор типов и возвращает false для ERROR. Поэтому эти результаты подтверждают недоступность отката в данном договоре, а не универсальное выполнение InvalidateReverseExecutionHistory при ошибке. Оснований менять VM по одному расположению вызова очистки нет.
