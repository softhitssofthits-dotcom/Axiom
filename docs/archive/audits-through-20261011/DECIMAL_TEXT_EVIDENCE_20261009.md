# Чтение DECIMAL из текста: ввод и преобразование строки

Session 1200, 2026-10-09. Независимые ожидаемые десятичные строки заданы буквально; число не проходит через CLR double для вычисления ожидания.

| Строка | INPUT в DECIMAL | CDEC(VAL(строка)) |
|---|---|---|
| 9007199254740993 | Та же строка | Не равно введённому DECIMAL |
| 1.0000000000000000000000000001 | Та же строка | Не равно введённому DECIMAL |
| 0.1234567890123456789012345678 | Та же строка | Не равно введённому DECIMAL |
| 79228162514264337593543950335 | Та же строка | MB3008 |

DecimalTextEvidenceTests выполняет четыре строки в обоих движках через IInputProvider и оператор INPUT. Проверяются один вызов поставщика, отсутствие запасного интерпретатора и внешних диагностик, точный вывод и сравнение с цепочкой VAL/CDEC. Отдельно CDEC(переменная STRING) отклоняется Binder с MB2 до исполнения в обоих движках. Реестр BuiltinFunctions.Conversion.cs содержит только числовую форму CDec. BuiltinIOHelpers.TryParseInputField для DECIMAL прямо использует decimal.TryParse, а VAL возвращает DOUBLE. В docs/archive/root-documents-20261011/FUTURE.md отдельная точная строковая форма DECIMAL не найдена; отсутствие записи не является самостоятельным доказательством отсутствия произвольного обходного решения.

Классификация: существующая возможность для интерактивного ввода; отсутствие специализированного преобразования уже сохранённой строки. Это не дефект VAL, который обещает DOUBLE, и не дефект числовой CDEC. Сценарий кандидата — читать десятичные данные из READFILE/READLINE и вычислять их в DECIMAL без промежуточного DOUBLE. ISNUMERIC не преобразует текст и не проверяет сохранение десятичной точности.

Не заявлено, что INPUT точно принимает любые десятичные строки: CLR decimal может округлять избыточную дробную точность. Не доказаны все разделители, экспоненты, локали или ошибки ввода этим набором. Пользовательский разбор цифр через FUNCTION ещё не оценён на границах; перед введением новой формы требуется проверить, насколько он прост и надёжен. Окончательное имя/строковая грамматика и ошибка переполнения не утверждены.

Десять новых случаев + NumericPresentationEvidenceTests: 88/88, ошибок/пропусков0, .artifacts/test-results/decimal-text-1200/decimal-text-1200.trx. Runtime не менялся.


## Проверка пользовательской альтернативы — Session 1201

Добавлен запускаемый пример `samples/functions/cdec/fixed_decimal_parser.axm`: пользовательская FUNCTION ParseFixedDecimal собирает DECIMAL-мантиссу и масштаб непосредственно из ASCII-цифр. Промежуточного DOUBLE нет. Формат намеренно ограничен: необязательный знак, цифры, одна точка; без пробелов, разделителей групп и экспоненты. При отсутствии цифр или постороннем символе функция выдаёт APP_DECIMAL.

FixedDecimalParserEvidenceTests проверяет 17 строк в каждом движке: восемь точных результатов, семь отказов грамматики, два отказа переполнения. Ожидаемые строки заданы независимо, не вычисляются другим вызовом разбираемой функции. Значения ±79228162514264337593543950335, 9007199254740993 и 28-разрядные дроби сохранены. Вместе с DecimalTextEvidenceTests выполнено 44/44, ошибок и пропусков нет; `.artifacts/test-results/decimal-parser-1201/decimal-parser-1201.trx`. Реальный CLI-запуск примера завершился с кодом 0 и ожидаемыми числами/MB3008.

Ограничения принципиальны для оценки альтернативы: `79228162514264337593543950335.0` представляет допустимое число, но переполняет накопленную целую мантиссу; `0.00000000000000000000000000001` переполняет масштаб. Последнее число меньше минимальной ненулевой единицы DECIMAL, поэтому пример не задаёт ему правило округления. Алгоритм не является общим аналогом decimal.TryParse. Не проверены все допустимые сочетания масштаба и значащих цифр, округление и большой вход.

Классификация уточнена: существующих средств языка достаточно для точного разбора ограниченного формата данных без нового встроенного имени. Полноценное безопасное преобразование готовой строки остаётся отсутствующей специализированной возможностью. Его полезность следует оценивать как удобство и единый договор грамматики/округления, а не как невозможность решить задачу в Axiom. Решение о новой форме CDEC не принято; Runtime и публичный договор языка не менялись.
