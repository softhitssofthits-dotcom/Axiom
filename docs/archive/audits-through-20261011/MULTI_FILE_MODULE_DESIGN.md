## 1. Резюме

**Axiom — строго однофайловый язык. Программа = один `.axm` файл.**

Подсистема MULTI-FILE MODULE DESIGN не существует как реализованная часть языка. Весь конвейер компиляции и исполнения работает с единственной строкой `string SourceText` на каждом этапе: `Lexer → Parser → Binder → Lowerer → BytecodeCompiler → Interpreter/BytecodeVm`. Модули, пространства имён, импорты, visibility modifiers и формат проектного файла — это **спланированные, но не реализованные возможности**, зафиксированные в `PROJECT.md:42` как отдельное направление проектирования.

**Вердикт: NO.** Подсистему нельзя считать стабильной для перехода к следующей подсистеме, потому что она **не реализована**. Однако текущая однофайловая программная модель, на которую модульная система должна будет нарастить, стабильна и готова к будущему расширению.

## 2. Что представляет собой эта подсистема

Подсистема MULTI-FILE MODULE DESIGN должна определять:

- **Как программы могут состоять из нескольких файлов** — модули, пространства имён, импорты.
- **Как видны символы между модулями** — visibility modifiers (PUBLIC, PRIVATE, INTERNAL).
- **Как строится проект** — формат проектного файла, зависимости между модулями.
- **Как компилируются多个 файлы** — multi-file compilation pipeline, линковка.
- **Как IDE управляет проектом** — модель проекта, навигация между модулями, дерево зависимостей.

**Текущее состояние:** ничего из перечисленного не реализовано. Каждый аспект подсистемы находится в статусе `NOT_IMPLEMENTED` или `PLANNED`.

## 4. Фактическая архитектура

### 4.1 Текущая архитектура программы

Текущая архитектура строго однофайловая:

```
.axm файл (string SourceText)
    ↓
Lexer (токенизация)
    ↓
Parser (синтаксический анализ)
    ↓
ProgramSyntax (плоский список MemberSyntax)
    ↓
Binder (семантический анализ)
    ↓
BoundProgram (GlobalStatements + Routines)
    ↓
BoundProgramLowerer (понижение)
    ↓
LoweredProgram (линейное представление)
    ↓
BytecodeCompiler (эмиссия байткода)
    ↓
BytecodeModule (модуль для VM)
    ↓
Interpreter или BytecodeVm (исполнение)
```

На каждом этапе ровно одна единица компиляции.

### 4.2 Ключевые файлы

| Файл | Ответственность |
|---|---|
| `src/Axiom.Execution\Requests\CompilationRequest.cs` | Принимает единственный `string sourceText` |
| `src/Axiom.Syntax\ProgramAndMembers.cs:123-139` | `ProgramSyntax` — плоский список `MemberSyntax` |
| `src/Axiom.Semantics\Scopes\BoundScope.cs` | Единый `_globalScope` без модульного уровня |
| `src/Axiom.Semantics\BoundNodes\BoundProgram.cs` | `GlobalStatements` + `Routines` — одна программа |
| `src/Axiom.Bytecode\Model\BytecodeModule.cs` | Один модуль, одна точка входа |
| `src/Axiom.Runtime\Execution\Interpreter.cs` | Исполнение одной `BoundProgram` |
| `src/Axiom.Runtime\Execution\BytecodeVm.cs` | Исполнение одного `BytecodeModule` |
| `src/Axiom.Ide\Files\FilesPaneViewModel.cs` | Raw filesystem browser |
| `src/Axiom.Ide\Services\Execution\ProgramRunService.cs` | Запуск одного `sourceText` |

### 4.3 Что отсутствует в архитектуре

- **Нет модульного синтаксиса** — в `TokenKind.cs` нет `MODULE`, `NAMESPACE`, `IMPORT`, `EXPORT`, `INCLUDE`, `USE`, `FROM`, `ALIAS`, `PUBLIC`, `PRIVATE`, `INTERNAL`.
- **Нет модульных синтаксических узлов** — в `SyntaxKind.cs` нет `ModuleDeclaration`, `ImportStatement`, `NamespaceDeclaration`.
- **Нет модульных областей видимости** — `BoundScope` не имеет уровня между глобальной и функциональной.
- **Нет метаданных модулей в символах** — `VariableSymbol`, `FunctionSymbol`, `TypeSymbol` не хранят информацию о модуле-владельце.
- **Нет multi-file compilation** — `CompilationRequest` принимает одну строку.
- **Нет линковки** — нет кода, объединяющего多个 модуля.
- **Нет модели проекта** — IDE работает с отдельными файлами, не с проектом.

## 5. Полный путь выполнения

### 5.1 Текущий путь (однофайловый)

```
.axm файл → string SourceText
    ↓
Lexer.SourceText → Token[]
    ↓
Parser.Parse(tokens) → ProgramSyntax
    ↓
Binder.Bind(program) → BoundProgram
    ↓
BoundProgramLowerer.Lower(bound) → LoweredProgram
    ↓
BytecodeCompiler.Compile(lowered) → BytecodeModule
    ↓
BytecodeModuleValidator.Validate(module) → BytecodeValidationResult
    ↓
Interpreter.Execute(bound) или BytecodeVm.Execute(module)
    ↓
RuntimeResult (вывод, ошибки, состояние)
```

### 5.2 Гипотетический путь (многофайловый)

```
.axmproj файл → ProjectDescriptor
    ↓
ProjectLoader.Load(descriptor) → SourceText[]
    ↓
Для каждого файла:
    Lexer → Parser → ProgramSyntax → Binder → BoundProgram
    ↓
ModuleLinker.Combine(boundPrograms[]) → LinkedProgram
    ↓
Lower → BytecodeModule
    ↓
Execute
```

**Статус:** Гипотетический путь не реализован. Конкретный дизайн multi-file pipeline не определён.

## 7. Анализ Parser

### 7.1 Текущее состояние

Парсер обрабатывает только однофайловые программы:

- `Parser.ParseProgram()` (`Parser.Declarations.cs:7-16`) → `ProgramSyntax` с плоским списком `MemberSyntax`.
- `ParseMember()` обрабатывает: `TYPE`, `SUB`, `FUNCTION`, глобальные операторы.
- Нет разбора `MODULE`, `IMPORT`, `NAMESPACE`, `DECLARE`, `EXTERN`.

### 7.2 Что потребуется для модульной системы

- Новые ключевые слова в лексере: `MODULE`, `END MODULE`, `IMPORT`, `NAMESPACE`, `PUBLIC`, `PRIVATE`, `INTERNAL`, `EXPORT`, `DECLARE`, `EXTERN`.
- Новые синтаксические узлы: `ModuleDeclarationSyntax`, `ImportStatementSyntax`, `NamespaceDeclarationSyntax`, `VisibilityModifierSyntax`.
- Изменения в `ParseMember()` для обработки модульных конструкций.
- Новый парсер проектного файла (если будет отдельный формат).

### 7.3 Оценка

**Готовность парсера к модульной системе:** 2/10. Есть чёткое разделение ответственности, но нет модульного синтаксиса.

- `BindProgram()` выполняет multi-pass регистрацию символов в `_globalScope`.

- Проверка циклических зависимостей между модулями.

### 8.3 Оценка

## 45. Definition of Done

Подсистема MULTI-FILE MODULE DESIGN считается завершённой, когда:

1. **Синтаксис:** `MODULE ... END MODULE`, `IMPORT`, `NAMESPACE`, `PUBLIC`, `PRIVATE`, `INTERNAL`, `DECLARE`, `EXTERN` парсятся без ошибок.
2. **Семантика:** Модульные области видимости работают, visibility modifiers проверяются, импорты разрешаются.
3. **Pipeline:** Multi-file compilation pipeline работает:多个 файлов → линковка → исполнение.
4. **Interpreter:** Оба движка корректно исполняют многофайловые программы.
5. **Bytecode VM:** `BytecodeModule` поддерживает модульные метаданные.
6. **IDE:** Модель проекта работает, навигация между модулями работает, подсветка модульных ключевых слов работает.
7. **Tests:** Покрыты все основные сценарии и edge cases.
8. **Documentation:** Страница manual, спецификация, формат проектного файла — всё документировано.
9. **Samples:** Есть runnable-примеры многофайловых программ.

## Главный контрольный вопрос

> Можно ли считать подсистему MULTI-FILE MODULE DESIGN достаточно стабильной, корректной и архитектурно понятной для перехода к следующей подсистеме?

**NO.**

Подсистема MULTI-FILE MODULE DESIGN **не реализована**. Она существует только как:

1. Будущее направление в `PROJECT.md:42`.
2. Эскиз в `docs/archive/root-documents-20261011/FUTURE.md:498-545`.
3. Два audit-документа, подтверждающих feature gap.

Текущая однофайловая программная модель стабильна и корректна, но модульная система не может считаться стабильной, потому что её нет.

### Основные blockers

1. **Нет проектирования:** Эскиз в FUTURE.md не промотирован в спецификацию. Конкретный дизайн модульной системы не определён.
2. **Нет реализации:** Ни один компонент модульной системы не реализован.
3. **Нет тестов:** Нет тестов модульной системы.
4. **Нет документации:** Нет спецификации, нет manual-страницы.

### Что нужно сделать в первую очередь

1. **Провести проектирование модульной системы** (DESIGN-001..005).
2. **Промотировать эскиз из FUTURE.md в спецификацию** (SPECIFICATION3.md).
3. **Определить формат проектного файла.**
4. **Определить multi-file compilation pipeline.**

### Что можно отложить

1. Реализацию модульной системы — после проектирования.
2. IDE модель проекта — после реализации модульной системы.
3. Visibility modifiers — после реализации модульной системы.

### Что не следует трогать

1. **Однофайловую программную модель** — стабильна и корректна.
2. **Multi-pass регистрацию символов** — стабильна и будет扩展ена модульным слоем.
3. **Цепочку областей видимости** — стабильна и будет扩展ена модульной областью.
4. **Entry point механизм** — стабилен и не зависит от модульной системы.
5. **Forward reference механизм** — стабилен и будет扩展ен межмодульными forward references.
6. **Блочную видимость** — стабильна и не зависит от модульной системы.
7. **Все существующие тесты** — покрывают однофайловый контракт и должны продолжать работать после реализации модульной системы.
