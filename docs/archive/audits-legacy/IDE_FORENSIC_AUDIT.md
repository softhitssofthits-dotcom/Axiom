## 1. Краткое резюме

**IDE Axiom — функциональный, хорошо спроектированный однофайловый редактор BASIC, который корректно интегрирован с реальным языковым pipeline. Это не игрушечный интерфейс — для всех операций с языком используется настоящий компилятор/parser/семантика/runtime.** Однако есть несколько нарушений архитектуры, отсутствующих инструментов разработчика и проблем синхронизации, которые требуют внимания.

**Главный вердикт: ДА, С УСЛОВИЯМИ** — IDE достаточно корректна для перехода к финальному cross-audit, при условии что найденные блокеры зафиксированы и отслеживаются.

**Критические находки:**
1. `AxiomSmartIdentifierService` напрямую использует `Axiom.Parsing` и `Axiom.Syntax`, нарушая архитектурную границу
2. `BytecodeVmStopState` протекает во внутренности runtime глубоко в ViewModel IDE
3. `ProgramConsoleService` — монолит на ~2000 строк, реализующий 7+ интерфейсов
4. Нет автодополнения, нет «Перейти к определению», нет «Найти ссылки», нет модели проекта
5. Ключевые слова дублированы в 5 местах (TokenKind, SyntaxKind, Lexer, Axiom.xshd, Axiom.Dark.xshd)
6. `STRING` попадает и в список типов, и в список встроенных функций в XSHD — тип побеждает за счёт порядка XML

## 3. Фактическая архитектура IDE

IDE — это **настольное WPF-приложение** с использованием **AvalonEdit** в качестве компонента редактора. Следует паттерну MVVM:

- **MainWindow** — тонкий code-behind для синхронизации UI
- **MainWindowViewModel** — корневая VM оболочки (разбита на 7 partial-файлов)
- **Дочерние VM** — DocumentTabViewModel, FilesPaneViewModel, BottomPaneViewModel, StatusBarViewModel
- **Сервисы** — ProgramRunService, ProgramConsoleService, DocumentWorkspaceService и др.

**Стек:** C# / .NET 10 / WPF / AvalonEdit

## 5. Отношение IDE и компилятора

**IDE использует РЕАЛЬНЫЙ компиляторный pipeline.** Это важнейшая находка.

| Компонент | Общий? | Доказательства |
|-----------|--------|----------------|
| Лексер | ДА (через pipeline) | `AxiomExecutionPipeline.CompileCore()` вызывает `Parser.Parse()` |
| Парсер | ДА (через pipeline) | Тот же `Parser.Parse()`, что и в CLI |
| Связыватель | ДА (через pipeline) | Тот же `Binder.Bind()`, что и в CLI |
| Компилятор байткода | ДА (через pipeline) | Тот же `BytecodeCompiler.Compile()` |
| Интерпретатор | ДА (через pipeline) | Тот же `Interpreter.Execute()` |
| BytecodeVm | ДА (через pipeline) | Тот же `BytecodeVm.Execute()` |

**ИСКЛЮЧЕНИЕ:** `AxiomSmartIdentifierService` напрямую вызывает `Parser.Parse()` — это обходит pipeline и нарушает архитектурную границу.

## 6. Аудит языкового контракта

### Парсер IDE vs парсер компилятора

**Это ОДИН И ТОТ ЖЕ парсер.** У IDE нет своего парсера. Весь парсинг идёт через `AxiomExecutionPipeline` → `Parser.Parse()`.

**ИСКЛЮЧЕНИЕ:** `AxiomSmartIdentifierService` вызывает `Parser.Parse()` напрямую для нормализации регистра идентификаторов. Это отдельный вызов того же парсера, а не другой парсер.

### Модель синтаксиса IDE vs модель компилятора

**Одна модель.** Обе используют `Axiom.Syntax.ProgramSyntax` и его дочерние узлы.

### Модель типов IDE vs модель компилятора

**У IDE нет модели типов.** Нет информации о типах, доступной в IDE. Нет автодополнения, нет подсказок типов, нет информации о символах.

## 9. Дрейф версий

**ВЫСОКИЙ РИСК.** Когда компилятор добавляет новое ключевое слово, IDE:
1. Не подсвечивает его (XSHD не обновлён)
2. Не форматирует его (словарь не обновлен)
3. Всё равно компилирует и запускает корректно (pipeline общий)

**Доказательства:** `COLUMN`, `ROW`, `PI` есть в XSHD, но нет соответствующих `SyntaxKind` записей. Это показывает, что дрейф уже происходит.

**Смягчающий фактор:** Тесты в `EditorFeatureTests` проверяют полноту словаря по `SyntaxKind` и `BuiltinFunctions.All`.

## 11. Корректность подсветки

### Найденные проблемы

1. **Двойная классификация `STRING`:** Попадает и в список типов, и в список встроенных функций. Тип побеждает за счёт порядка XML. Вызов функции `STRING()` будет отображаться бирюзовым вместо коричневого.

2. **Нет подсветки операторов:** Операторы (`+`, `-`, `*`, `/`, `=`, `<>` и т.д.) отображаются цветом текста по умолчанию.

3. **`COLUMN`, `ROW`, `PI` в XSHD, но нет в SyntaxKind:** Эти слова получают подсветку ключевых слов, но не отслеживаются как формальные ключевые слова языка.

4. **Незакрытые строки:** Regex `"(\""\|[^\r\n"])*"?` корректно обрабатывает незакрытые строки с помощью trailing `?`.

5. **Hex-литералы:** `&H[0-9A-F]+\b` корректно подсвечивает hex-литералы в стиле BASIC.

## 17. Подсветка ошибок

IDE **не делает** подсветку ошибок inline (подчёркивания). Ошибки отображаются на панели диагностики с навигацией к месту в коде. Это недостаток возможностей, а не баг.

## 18. Интеграция парсера

### Полный парсинг

IDE использует `AxiomExecutionPipeline.Compile()`, который вызывает `Parser.Parse()` для полного парсинга документа. Это происходит:
- При компиляции (явно)
- При запуске (если не закэшировано)
- При нормализации идентификаторов (прямой вызов — нарушение архитектуры)

### Инкрементальный парсинг

**Не поддерживается.** Каждый парсинг — полный парсинг документа. Инкрементального парсинга не существует.

### Парсинг документа

Сервис форматирования использует свой лёгкий токенизатор, а НЕ реальный парсер. Сервис умных идентификаторов использует реальный парсер.

### Диагностический парсинг

Диагностики приходят из шага компиляции pipeline, а не из отдельного парсинга.

### Восстановление

Восстановление после ошибок парсера обрабатывается самим парсером (стандартное поведение). IDE не добавляет дополнительного восстановления.

---

## 19. Инкрементальный парсинг

**Не реализован.** Каждое изменение требует полного репарсинга. Для текущих размеров документов (обычно <1000 строк) это приемлемо.

---

## 20. Восстановление после ошибок парсера в IDE

Парсер имеет встроенное восстановление после ошибок, которое продолжает парсинг после синтаксических ошибок. IDE получает все диагностики от парсера и отображает их на панели диагностики. Редактор продолжает работать с нарушенным кодом.

## 21. Pipeline диагностики

```
Parser.Parse() → syntaxDiagnostics (Diagnostic[])
Binder.Bind() → semanticDiagnostics (Diagnostic[])
BoundProgramLowerer.Lower() → BytecodeDiagnostic[] → маппинг в Diagnostic[]
BytecodeCompiler.Compile() → BytecodeDiagnostic[] → маппинг в Diagnostic[]
Interpreter.Execute() / BytecodeVm.Execute() → RuntimeResult.Diagnostics
    ↓
CompilationResult / ExecutionResult
    ↓
ProgramRunService: Diagnostic[] → ProgramDiagnosticItem.FromDiagnostic()
    ↓ (определение стадии по префиксу кода: MB0*/MB1* = Синтаксис, MB2* = Семантика, MB3* = Runtime, MB4* = Бэкенд)
ProgramRunResult.Diagnostics
    ↓
MainWindowViewModel: BottomPane.ReplaceDiagnostics()
    ↓
Панель диагностики (DataGrid с навигацией)
```

**Это чисто и корректно.** Диагностики текут от реального компилятора/runtime через тонкий адаптер к модели IDE.

## 22. Паритет диагностик

| Сценарий | Компилятор/CLI | IDE | Совпадают? |
|----------|---------------|-----|------------|
| Синтаксическая ошибка | Diagnostic с кодом/сообщением/позицией | ProgramDiagnosticItem с тем же кодом/сообщением/позицией | ✓ |
| Семантическая ошибка | Diagnostic | ProgramDiagnosticItem | ✓ |
| Ошибка runtime | Diagnostic | ProgramDiagnosticItem | ✓ |
| Ошибка бэкенда | Diagnostic | ProgramDiagnosticItem | ✓ |
| Инфраструктурная ошибка | Нет | ProgramDiagnosticItem.CreateInfrastructure() | Только IDE |

**Паритет поддерживается.** IDE использует те же коды и сообщения диагностик, что и компилятор.

## 23. Паритет позиций ошибок

`ProgramDiagnosticItem.FromDiagnostic()` маппит `Diagnostic.Location.Line`, `.Column`, `.Length` напрямую. Никакого преобразования не происходит. Строки/столбцы сохраняются точно.

---

## 24. Множественные диагностики

Все диагностики от одной компиляции/выполнения собираются и отображаются. Никакой дедупликации не происходит. Порядок следует порядку парсера/связывателя/runtime.

---

## 25. Устаревшие диагностики

**Потенциальная проблема.** Когда пользователь редактирует код после неудачного запуска:
1. Диагностики от предыдущего запуска остаются на панели диагностики
2. Они очищаются только при новом запуске/компиляции
3. Нет автоматического репарсинга при редактировании для очистки устаревших диагностик

**Это проблема UX, а не корректности.** Диагностики от последнего выполнения технически корректны.

---

## 26. Очистка диагностик

Диагностики очищаются:
- При новом запуске (BottomPane.ClearOutput() + ReplaceDiagnostics)
- При новой компиляции
- НЕ при редактировании (устаревшие диагностики остаются)

## 36. Форматтер

`AxiomCodeFormattingService` предоставляет:
- **Форматирование строк:** запускается при уходе каретки / потере фокуса
- **Форматирование документа:** полное переформатирование документа
- **Два стиля:** Classic (ВЕРХНИЙ РЕГИСТР) и Modern (Заглавные Буквы)

### Что делает:
- Нормализация регистра ключевых слов, типов, вызовов встроенных функций
- Нормализация пробелов между токенами
- Нормализация комментариев (регистр `REM`)
- Сохранение отступов (НЕ делает реиндентацию)

### Чего НЕ делает:
- Отступы блоков
- Форматирование на основе AST
- Пробелы вокруг операторов (простые правила)

---

## 37. Корректность форматтера

Форматтер использует свой лёгкий токенизатор, а не реальный парсер. Это намеренно — он должен работать с произвольным (возможно неполным) текстом редактора.

**Риск:** Токенизатор форматтера может не совпадать с реальным парсером на граничных случаях. Для простого синтаксиса BASIC этот риск невелик.

---

## 38. Паритет форматтера / парсера

**Низкий риск.** Токенизатор форматтера обрабатывает:
- Слова, числа, строки, операторы, пунктуацию
- Разделение комментариев (`'` и `REM`)
- Нормализацию операторов сдвига (`<<`, `>>`)

Реальный парсер обрабатывает полную грамматику. Форматтеру нужно только классифицировать токены для стилизации регистра, а не для семантической корректности.

## 45. Сервис запуска

Путь выполнения `ProgramRunService.Run()`:

1. Определить базовый каталог ресурсов из пути к файлу
2. Установить `Environment.CurrentDirectory` (известная проблема — TASK-006)
3. `_consoleService.BeginSession()`
4. Создать `IdeInputProvider`, оборачивающий консольный сервис
5. Проверить кэш скомпилированной программы (тот же текст?)
6. При промахе кэша: `_pipeline.Compile()`
7. При ошибке компиляции: вернуть диагностики
8. Создать `TimeoutCancellationProvider` (если установлен таймаут)
9. `_pipeline.RunCompiled(compiledProgram, request)`
10. Маппинг `ExecutionResult` → `ProgramRunResult`
11. Если не остановлено: `_consoleService.EndSession()`
12. Восстановить `Environment.CurrentDirectory`

## 46. Выбор интерпретатора / VM

**Выбирается пользователем через команды меню:**
- `UseInterpreterExecutionModeCommand`
- `UseBytecodeExecutionModeCommand`

Хранится в `MainWindowViewModel.SelectedExecutionMode` (тип `ExecutionMode`).

**Логика выбора в `AxiomExecutionPipeline.RunCompiled()`:**
- Если `ExecutionMode.Interpreter` → всегда через интерпретатор
- Если `ExecutionMode.Bytecode`:
  - Проверяет покрытие байткода (`GetBytecodeCoverageDiagnostic`)
  - Если `BytecodeModule` существует И покрытие проходит → через BytecodeVm
  - Если покрытие не проходит → возвращает `BackendFailure` (НЕТ автоматического отката)

**Нет автоматического отката на интерпретатор.** Если режим байткода не проходит покрытие, запуск завершается ошибкой с диагностикой.

## 49. Ввод из IDE

INPUT обрабатывается через `ProgramConsoleService.RequestInput()`:
1. Устанавливает `IsWaitingForInput = true`
2. Создаёт `DispatcherFrame` и вызывает `Dispatcher.PushFrame(frame)`
3. Блокирует фоновый поток выполнения, сохраняя работу WPF
4. Пользователь вводит текст в поле ввода панели вывода
5. При нажатии Enter: `SubmitInput()` устанавливает `_submittedText`, разблокирует фрейм

## 54. Отладчик vs интерпретатор

**Отладчик работает ТОЛЬКО с BytecodeVm.** `BytecodeVmStopState` — это специфичный для BytecodeVm объект. У интерпретатора нет возможности остановки/шага.

Доказательства: `IProgramRunService.Continue/StepOver/StepInto/StepOut/StepBack` все принимают `BytecodeVmStopState` как параметр.

---

## 55. Отладчик vs байткод VM

Отладчик использует `BytecodeVmStopState`, который содержит:
- `Snapshot` (BytecodeVmExecutionSnapshot) с SourceLocation, Opcode, CallDepth
- Методы `Resume()`, `StepOver()`, `StepInto()`, `StepOut()`, `StepBack()`
- Флаг `CanStepBack`

**Маппинг «строка исходника ↔ инструкция байткода»** обрабатывается через `BytecodeDebugInfo` в слое Bytecode.

---

## 56. Точность точек останова

Точки останова устанавливаются по **номеру строки исходника** (1-based). `BytecodeVm` получает `sourceBreakpointLines` и проверяет их во время выполнения.

**Точность зависит от маппинга отладочной информации байткода.** Для простых операторов (один оператор на строку) это точно. Для сложных многооператорных строк точность может варьироваться.

---

## 57. Выполнение шагов

- **Шаг с обходом:** Выполняет до следующей строки исходника в том же или внешнем контексте
- **Шаг с входом:** Выполняет один шаг (входит в вызовы функций)
- **Шаг с выходом:** Выполняет до возврата текущей функции
- **Шаг назад:** Обращает выполнение (отладка во времени)

Все операции работают с живым объектом `BytecodeVmStopState`.

## 75. Память IDE

## 76. Безопасность потока UI

- Компиляция выполняется в фоновом потоке (`Task.Run`)
- Выполнение в фоновом потоке

- INPUT блокирует фоновый поток через `Dispatcher.PushFrame()`

**Потенциальная проблема:** `Dispatcher.PushFrame()` создаёт реентерабельность. Во время ожидания INPUT другие сообщения WPF (включая команды) могут обрабатываться. IDE смягчает это блокировкой команд оболочки во время запуска/ввода.

## 90. Форматирование vs реальная грамматика

Сервис форматирования использует свой лёгкий токенизатор, а не реальный парсер. Это намеренно и приемлемо для нормализации регистра/пробелов.

**Риск:** Граничные случаи, где токенизатор форматтера не совпадает с реальным парсером. Низкий риск для простого синтаксиса BASIC.

## 91. Подсветка синтаксиса vs реальный лексер

Подсветка использует правила regex XSHD, а не реальный лексер. Это стандартно для AvalonEdit.

**Потенциальное несовпадение:** XSHD может подсвечивать что-то как ключевое слово, что лексер treats как идентификатор. Для BASIC это маловероятно.

### IDE-001: Нарушение архитектуры SmartIdentifierService

**КАТЕГОРИЯ:** АРХИТЕКТУРА
**СЕРЬЁЗНОСТЬ:** P2

**ЗАТРОНУТЫЕ КОМПОНЕНТЫ:** SmartIdentifierService, EditorFeatureTests
**РЕКОМЕНДУЕМОЕ НАПРАВЛЕНИЕ:** Маршрутизация через pipeline или создание специального сервиса парсинга для IDE
**ЗАВИСИМОСТИ:** Нет
