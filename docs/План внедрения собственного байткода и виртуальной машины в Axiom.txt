# План внедрения собственного байткода и виртуальной машины в Axiom

## Кратко

Axiom сейчас уже имеет хорошую верхнюю половину будущего компилятора: `lexer -> parser -> binder -> CompiledProgram`. Следующий шаг мы фиксируем так: не ломать текущий интерпретатор, а ввести **параллельный байткодный backend** с собственной **стековой виртуальной машиной**, при этом сохранить интерпретатор как эталон, резервный путь и инструмент сравнения.

Планируем не «временную минималку», а **полную целевую архитектуру**, которую затем внедряем по фазам. Отладочную основу закладываем сразу: карта инструкций к строкам исходника, именам процедур и служебным диапазонам. `Compile` в IDE в итоге должен готовить не только `BoundProgram`, но и `BytecodeModule`, а `Run` в режиме `Auto` должен выполнять байткод, если для текущего текста уже есть валидный байткодный артефакт.

## Целевая архитектура

### 1. Общая схема конвейера

Новый полный конвейер фиксируем так:

`SourceText -> Parse -> Bind -> CompiledProgram -> LoweredProgram -> BytecodeModule -> BytecodeVm -> RuntimeResult`

При этом сохраняются два исполняющих пути:

- `Interpreter path`: `CompiledProgram -> Interpreter`
- `Bytecode path`: `CompiledProgram -> LoweredProgram -> BytecodeModule -> BytecodeVm`

`AxiomExecutionPipeline` становится координатором двух backend-режимов, а не только frontend-подготовки.

### 2. Граница модулей

Добавляем новый отдельный проект `Axiom.Bytecode` со следующими зонами ответственности:

- `Model/` — модель байткодного модуля, инструкций, таблиц, версий и отладочных данных
- `Lowering/` — понижение `BoundProgram` в линейную backend-удобную форму
- `Emission/` — генерация `BytecodeModule` из lowered-представления
- `Diagnostics/` — ошибки генерации байткода и проверки целостности модуля

`Axiom.Runtime` расширяется, но не теряет интерпретаторную роль:

- `Execution/Interpreter*` остаются как текущий путь
- `Execution/BytecodeVm*` добавляются как второй путь
- `Values/`, `Environment/`, `Host/` остаются общим рантайм-основанием для обоих backend-ов

`Axiom.Execution` получает новую роль фасада исполнения:

- выбор режима выполнения
- кэширование frontend- и backend-артефактов
- возврат детальных метрик по стадиям
- единый контракт для IDE

### 3. Новые публичные типы и контракты

Фиксируем следующие новые типы и интерфейсы.

В `Axiom.Bytecode`:

- `BytecodeModule`
- `BytecodeHeader`
- `BytecodeFormatVersion`
- `BytecodeRoutine`
- `BytecodeInstruction`
- `Opcode`
- `ConstantPool`
- `BuiltinBinding`
- `BytecodeDebugInfo`
- `SourceInstructionMap`
- `LoweredProgram`
- `LoweredRoutine`
- `LoweredInstruction`
- `BytecodeCompiler`
- `BytecodeCompilerResult`

В `Axiom.Execution`:

- `ExecutionMode` со значениями `Auto`, `Interpreter`, `Bytecode`
- `ExecutionEngineKind` со значениями `Interpreter`, `BytecodeVm`
- расширенный `CompiledProgram`, который хранит:
  - исходный `ProgramSyntax`
  - исходный `BoundProgram`
  - опциональный `LoweredProgram`
  - опциональный `BytecodeModule`
- расширенный `CompilationResult`, который умеет отражать:
  - frontend-успех
  - backend-успех
  - доступность байткода
- расширенный `ExecutionResult`, который обязан возвращать:
  - какой движок реально использован
  - время frontend-подготовки
  - время lowering
  - время генерации байткода
  - время выполнения VM или интерпретатора
  - суммарное время
  - флаг использования кэша prepared-программы
  - флаг использования кэша байткода

В `Axiom.Ide`:

- настройка предпочтительного режима запуска
- отображение реально использованного движка
- отдельные метрики генерации байткода и времени VM

### 4. Модель байткода

Выбираем **стековую VM** как основной формат исполнения.

Фиксируем структуру `BytecodeModule`:

- `Header`
- `ConstantPool`
- `RoutineTable`
- `GlobalLayout`
- `BuiltinTable`
- `DebugInfo`

`Header` обязан содержать:

- версию формата
- версию языка/контракта модуля
- флаги возможностей
- контрольную информацию совместимости

`ConstantPool` хранит:

- числовые литералы
- строковые литералы
- логические литералы
- имена процедур и built-in для отладки и трассировки
- при необходимости позднее — шаблоны форматирования и другие константы рантайма

`RoutineTable` хранит для каждой процедуры/функции:

- стабильный индекс
- имя
- тип результата
- число параметров
- число локальных слотов
- диапазон инструкций
- карту параметров и локальных имён для отладки

`GlobalLayout` хранит:

- слот глобальной переменной
- символ и runtime-тип
- признак константы
- инициализационную стратегию

Группа управления потоком:

Группа составных значений и контейнеров:

Правило проектирования опкодов:

- built-in вызывать через таблицу built-in и `CallBuiltin`
- новые возможности языка по возможности раскладывать в уже существующие инструкции
- новые opcode вводить только когда семантика реально не выражается через текущий набор

### 6. Lowering-представление

Перед генерацией байткода вводим обязательный слой `LoweredProgram`.

Его задача:

- убрать из backend-а зависимость от высокоуровневых структур bound-дерева
- превратить `IF`, циклы, `SELECT CASE`, `EXIT`, `RETURN` в линейный поток с метками и переходами
- нормализовать вычислительный порядок выражений
- подготовить понятную точку для будущих оптимизаций без вмешательства в binder

Правило:

- `Binder` остаётся semantic-слоем и не начинает знать о байткоде
- все backend-преобразования начинаются только после `BoundProgram`

### 7. Рантайм и данные

На первом полноценном байткодном backend-е **не переписываем всю модель значений**. VM использует существующие runtime-сущности:

- `RuntimeValue`
- `RuntimeArrayValue`
- `RuntimeRecordValue`
- `RuntimeFunctionValue`
- `IRuntimeHost`

Это решение фиксируем как архитектурное:

- байткод меняет способ исполнения
- но не ломает текущий рантайм-контракт языка

Это даст совместимость по семантике и снизит риск расхождения интерпретатора и VM.

### 8. Отладочная информация

Сразу закладываем базовую отладку в формат.

`BytecodeDebugInfo` обязан содержать:

- соответствие инструкции строке и позиции исходника
- соответствие инструкции routine/function/sub
- таблицу имён параметров и локальных переменных
- диапазоны инструкций по логическим блокам процедуры

На первом этапе этого достаточно для:

- точной runtime-диагностики VM
- показа позиции ошибки в IDE
- будущих точек останова и шага по инструкциям/строкам

Полный отладчик сейчас не реализуем, но формат под него не должен мешать.

## План реализации по фазам

### Фаза 1. Фиксация документации и контрактов backend-слоя

Нужно:

- обновить `docs/ARCHITECTURE.md` полной схемой двух backend-ов
- обновить `docs/SPECIFICATION3.md` пользовательским и системным договором `Compile`, `Run`, `ExecutionMode`, `ExecutionEngineKind`
- обновить `docs/PLANS3.md` очередями внедрения
- зафиксировать в документации, что `Compile` теперь имеет две ступени:
  - frontend-подготовка
  - backend-подготовка байткода
- зафиксировать, что `Auto` во время переходного периода может делать fallback на интерпретатор только по явно описанным правилам покрытия

Критерий завершения:

- архитектурный документ полностью описывает формат, роли слоёв и этапы внедрения
- implementer не принимает решений на ходу о границах модулей и режимах запуска

### Фаза 2. Контракты исполнения и режимы запуска

Нужно:

- ввести `ExecutionMode` и `ExecutionEngineKind`
- расширить `ExecutionRequest`, `ExecutionResult`, `CompilationResult`
- научить `ProgramRunService` и IDE работать в трёх режимах:
  - `Auto`
  - `Interpreter`
  - `Bytecode`
- в IDE добавить способ увидеть фактический движок запуска
- в IDE добавить отдельные поля времени:
  - lowering
  - генерация байткода
  - выполнение VM
- сохранить уже работающие поля подготовки и общего времени

Правило режима `Auto`:

- если есть валидный байткод для текущего текста, запускать VM
- если байткода нет, но данный языковой срез уже покрыт VM, строить байткод и запускать VM
- если байткодный путь для программы пока не поддерживает конструкцию, а rollout ещё переходный, разрешён fallback на интерпретатор
- факт fallback обязан быть явно отражён в результате запуска и в статусе IDE

Критерий завершения:

- один и тот же документ можно запускать принудительно через интерпретатор или через VM
- IDE честно показывает фактический движок и стадию времени

### Фаза 3. Lowering: нормализация bound-дерева для backend-а

Нужно:

- ввести `LoweredProgram` и `LoweredRoutine`
- реализовать lowering для:
  - последовательности операторов
  - присваивания
  - выражений
  - `IF / ELSEIF / ELSE`
  - `WHILE`
  - `DO WHILE / LOOP`
  - `FOR / NEXT`
  - `EXIT FOR`
  - `EXIT DO`
  - `RETURN`
  - вызовов `SUB` и `FUNCTION`
- `SELECT CASE` тоже переводить в линейную форму с метками и переходами
- сохранить `TextLocation` на lowered-инструкциях, чтобы карта к исходнику не терялась

Критерий завершения:

- lowered-форма полностью пригодна для линейной генерации байткода
- для одних и тех же входных программ lowering даёт детерминированный результат

### Фаза 4. Модель `BytecodeModule` и формат v1

Нужно:

- реализовать в памяти полную модель модуля
- сделать версионность формата обязательной с первого дня
- ввести таблицы:
  - констант
  - процедур
  - built-in
  - глобалов
  - отладочных карт
- ввести стабильные индексы слотов и routine-id
- сделать валидацию модуля перед исполнением:
  - корректность прыжков
  - корректность индексов констант
  - корректность индексов built-in
  - соответствие сигнатур routine и стекового контракта

Решение по сериализации:

- в этой волне **канонический формат живёт в памяти**
- бинарную запись в файл не делаем до стабилизации VM
- но модель и заголовок проектируем так, как будто сериализация будет добавлена позже без ломки API

Критерий завершения:

- существует валидный `BytecodeModule`, который можно проверить и передать в VM без участия интерпретатора

### Фаза 5. Базовая виртуальная машина

Нужно реализовать `BytecodeVm` с:

- стеком значений
- стеком вызовов
- кадрами процедур
- слотами аргументов
- слотами локальных переменных
- доступом к глобальным переменным
- доступом к `IRuntimeHost`
- runtime-диагностикой с привязкой к `BytecodeDebugInfo`

Правила кадра вызова:

- каждый routine получает собственный frame
- аргументы кладутся в выделенные слоты кадра
- локалы и временные значения не смешиваются с evaluation-stack
- evaluation-stack очищается по соглашению о вызове на границе routine

Правила ошибок VM:

- любые runtime-ошибки VM обязаны преобразовываться в тот же понятный диагностический уровень, который сейчас даёт интерпретатор
- сообщение должно содержать ссылку на исходную позицию
- если точная позиция недоступна, VM обязана использовать ближайшую инструкционную карту, а не безымянную внутреннюю ошибку

Критерий завершения:

- VM умеет стабильно исполнить простой модуль со скалярными выражениями, вызовом процедур и возвратом результата

### Фаза 6. Эмиттер выражений и базовых операторов

Нужно последовательно покрыть генерацией байткода:

- литералы
- чтение и запись глобальных и локальных переменных
- арифметику
- логические операции
- сравнения
- вызовы функций и подпрограмм
- `PRINT`
- `RETURN`
- условные и безусловные переходы

Решение по built-in:

- все существующие встроенные функции сначала идут через таблицу built-in и единый runtime-bridge
- не дублировать их код в VM
- VM знает только протокол вызова built-in, а не семантику каждой функции внутри себя

Критерий завершения:

- байткодный путь проходит скалярный вычислительный слой языка и базовый вывод

### Фаза 7. Покрытие структур управления и процедурной модели

Нужно довести до паритета:

- `IF / ELSEIF / ELSE`
- `WHILE`
- `DO ... LOOP`
- `FOR / NEXT`
- `EXIT FOR`
- `EXIT DO`
- `SUB`
- `FUNCTION`
- вложенные вызовы
- глобальное и локальное состояние

Критерий завершения:

- все текущие сквозные сценарии управления потоком проходят в двух режимах с одинаковым наблюдаемым поведением

### Фаза 8. Массивы, записи, фиксированные строки и файловый слой

Нужно покрыть байткодным backend-ом текущее богатое состояние языка:

- одномерные массивы
- `REDIM`
- `ERASE`
- пользовательские `TYPE`
- доступ к полям записей
- фиксированные строки `STRING * N`
- текущий `FILE`
- `OPEN`
- `CLOSE`
- built-in работы с файлами и текстом
- текущие регулярные выражения и массивные regex-функции

Правило реализации:

- сложные типы и контейнеры не кодируем как отдельный новый формат данных в первой волне
- VM работает поверх уже существующих runtime-объектов
- это позволяет добиваться семантического совпадения до появления оптимизаций памяти

Критерий завершения:

- текущий реализованный пользовательский слой языка не делится на «работает только в интерпретаторе» и «работает только в VM»

### Фаза 9. Интеграция с `Compile` и кэшированием IDE

Нужно:

- расширить `Compile` так, чтобы успешная компиляция строила:
  - `BoundProgram`
  - `LoweredProgram`
  - `BytecodeModule`
- расширить кэш `ProgramRunService` так, чтобы он различал:
  - кэш prepared frontend
  - кэш lowered-представления
  - кэш байткодного модуля
- если текст не менялся после `Compile`, `Run` в `Auto` должен использовать уже собранный `BytecodeModule`
- если пользователь принудительно выбрал `Interpreter`, `Run` должен использовать prepared frontend без пересборки байткода
- если пользователь принудительно выбрал `Bytecode`, а байткодный артефакт устарел, его нужно перестроить

Дополнительно в IDE:

- добавить в `Run`-область отображение реального движка
- добавить сравнимые метрики для интерпретатора и VM
- при fallback явно писать, что запуск был переведён на интерпретатор, и почему

Критерий завершения:

- пользователь может воспроизводимо сравнивать интерпретатор и VM на одном и том же файле

### Фаза 10. Стабилизация, паритет и постепенное повышение роли VM

Нужно:

- завести матрицу покрытия языка backend-ом
- ввести явный критерий, когда `Auto` по умолчанию считается режимом VM-first
- оставить интерпретатор доступным как минимум до конца периода стабилизации

Условие переключения `Auto` на байткод как основной путь:

- весь текущий поддерживаемый язык исполняется через VM
- все интеграционные и smoke-сценарии проходят в двух режимах одинаково
- IDE-диагностика по строкам совпадает
- нет известных непокрытых конструкций текущего публичного языка
- на контрольных длинных сценариях VM не хуже интерпретатора по общей стабильности, а на части сценариев даёт выигрыш

После этого:

- `Auto` становится VM-first без тихих ограничений
- интерпретатор остаётся доступен как явный диагностический режим и страховка на переходный период

## План тестирования и приёмки

### Автоматические тесты

Обязательные группы тестов:

- unit-тесты lowering для каждой конструкции управления потоком
- unit-тесты эмиттера для каждого opcode и каждой формы перехода
- unit-тесты VM по стеку, кадрам вызова, локалам, глобалам и built-in bridge
- тесты валидации `BytecodeModule` на битые переходы, битые индексы и несовместимые сигнатуры
- parity-тесты «интерпретатор против VM» на одном и том же `.axm`-коде
- интеграционные тесты `Axiom.Execution` на режимы `Auto`, `Interpreter`, `Bytecode`
- IDE-тесты на отображение движка, таймингов и fallback-статуса

### Проверочные сценарии

Обязательные сценарии сравнения:

- короткая арифметическая программа
- программа с несколькими процедурами и функциями
- программа с вложенными циклами
- программа с массивами
- программа с `TYPE`
- программа с фиксированными строками
- программа с файловыми built-in
- программа с regex-функциями, возвращающими массивы
- длинный цикл для видимого сравнения интерпретатора и VM

### Ручная приёмка в IDE

Нужно вручную прогонять:

- `Compile -> Run` без изменения текста в режиме `Auto`
- принудительный `Interpreter`
- принудительный `Bytecode`
- сценарий fallback, пока rollout ещё переходный
- проверку строки состояния:
  - подготовка
  - lowering
  - генерация байткода
  - выполнение
  - общее время
  - использованный движок
  - факт использования кэша

### Критерии завершения всей ветки

Ветка считается закрытой, когда:

- байткодный backend поддерживает весь текущий реализованный язык
- `Compile` действительно подготавливает байткодный артефакт
- `Run` действительно исполняет байткод в режиме `Auto`
- интерпретатор и VM дают одинаковое наблюдаемое поведение на регрессионном наборе
- IDE умеет показать, какой движок сработал и сколько заняли стадии
- документация полностью синхронизирована с новым устройством исполнения

## Принятые допущения и зафиксированные решения

- Байткод внедряем **параллельно** текущему интерпретатору, а не заменой «одним рывком».
- Целевая VM — **стековая**, не регистровая.
- Базовую отладочную информацию закладываем **сразу**.
- `Binder` не знает о байткоде; все backend-преобразования начинаются после `BoundProgram`.
- На первой полноценной волне VM использует **существующую runtime-модель значений**, а не новый независимый формат хранения.
- Байткод сначала живёт **в памяти**, без обязательной записи в файл.
- Интерпретатор остаётся доступным как эталон, резервный путь и режим сравнения до конца стабилизации.
- `Compile` после завершения этой ветки означает: подготовить frontend и backend-артефакты для текущего текста, но не создавать `exe`.
- Если позже в язык будут добавляться новые функции и операторы, эта архитектура не выбрасывается: новые возможности будут добавляться через расширение lowering, эмиттера, таблицы built-in и, при необходимости, набора opcode.
