**План разработки графических операторов для 2D игр**
Я предлагаю дальше не тратить ближайший графический этап на `BLOAD` / `BSAVE` и другие DOS-хвосты. Графическое BASIC-ядро уже достаточно полное. Следующий сильный шаг для продукта: современный слой изображений и спрайтов поверх существующего `SCREEN`.

Главная идея: оставить `PSET`, `LINE`, `CIRCLE`, `PAINT`, `GET`, `PUT`, `PALETTE`, `PCOPY` как BASIC-основу, а поверх неё добавить удобный современный слой:

```basic
hero = LOADIMAGE("assets/hero.png")
DRAWIMAGE hero, 100, 120

sheet = LOADSPRITE("assets/hero_run.png", 32, 32)
DRAWSPRITE sheet, 0, 100, 120
```

**Ключевой Выбор**
Рекомендую делать **полноцветные изображения**, а не сжимать всё в палитру `0..255`.

Причина: пользовательская цель — красивые шаблоны, 2D-игры, спрайты. Если сразу квантовать PNG/JPEG в 256 цветов, получится слишком старомодно и слабее, чем ожидается от современной графики.

Договор с текущей BASIC-графикой должен быть таким:

| Поведение | Рекомендация |
| --- | --- |
| `PSET`, `LINE`, `CIRCLE`, `PAINT`, `PUT` | продолжают писать индексные цвета `0..255` |
| `PALETTE` | влияет только на индексные пиксели |
| `DRAWIMAGE` / `DRAWSPRITE` | пишут полноцветные пиксели BGRA/RGBA |
| `POINT(x, y)` на полноцветном пикселе | возвращает ближайший индекс палитры Axiom или отдельное согласованное значение |
| `GET` из области с полноцветной картинкой | сохраняет ближайшие индексы, то есть теряет true-color |
| `PCOPY` | копирует и индексные пиксели, и полноцветный слой |
| `CLS` / рисование индексным пикселем поверх картинки | очищает или заменяет полноцветный пиксель в этой точке |

Нужно добавить в `docs/SPECIFICATION3.md` отдельный договор, до кода.

Рекомендуемое название первого слоя:

| Сущность | Форма | Назначение |
| --- | --- | --- |
| Тип `IMAGE` | `DIM hero AS IMAGE` | значение загруженной картинки |

Первый договор должен сознательно не включать:

| Не включать в первый срез | Причина |
| --- | --- |
| поворот картинки | усложняет растеризацию и тесты |

| отдельный `CANVAS` | текущий `SCREEN` уже является поверхностью |
| отдельный `BUFFER` | уже есть экранные страницы и `PCOPY` |
| физику, столкновения, тайловые карты | это выше уровня базовой графики |

**Этап 2**
Добавить тип `IMAGE` в язык.

Текущая типовая система имеет примитивы вроде `INTEGER`, `STRING`, `FILE`, массивы, функции и пользовательские `TYPE`. Для картинок лучше не использовать числовые дескрипторы `LONG`, а добавить настоящий ссылочный тип.

План по типу:

| Файл/слой | Что потребуется |
| --- | --- |
| `Axiom.Lexing` | добавить ключевое слово `IMAGE` |
| `Axiom.Syntax` | разрешить `IMAGE` как тип |
| `Axiom.Semantics` | добавить `TypeSymbol.Image` |
| `Axiom.Runtime` | добавить `RuntimeImageValue` |
| `RuntimeValue` | добавить `FromImage`, `AsImage`, default-значение |
| `BytecodeVm` | хранить `IMAGE` как обычное ссылочное runtime-значение |
| manual | добавить описание типа `IMAGE` в раздел типов и графики |

Семантика `IMAGE`:

| Вопрос | Договор |
| --- | --- |
| Присваивание | ссылочное, без копирования пикселей |
| Передача в `SUB` / `FUNCTION` | передаётся ссылка на неизменяемые пиксели |
| Изменяемость | в первом срезе картинка неизменяема |
| Значение по умолчанию | пустая незагруженная картинка |
| `DRAWIMAGE` для пустой картинки | runtime-ошибка, например через существующий договор состояния ресурса |
| Сравнение | в первом срезе не добавлять структурное сравнение картинок |

**Этап 3**
Решить загрузку изображений через хост.

Это важный архитектурный момент.

`Axiom.Runtime` сейчас таргетит `net10.0` и не зависит от WPF. `Axiom.Ide` таргетит `net10.0-windows` и уже имеет WPF/Direct3D. Поэтому декодирование PNG/JPEG лучше не тащить напрямую в `Axiom.Runtime`.

Рекомендованный путь:

| Слой | Роль |
| --- | --- |
| `Axiom.Runtime` | хранит `RuntimeImageValue` и вызывает абстрактный хост |
| `IGraphicsHost` или новый `IImageHost` | даёт метод загрузки изображения |
| `Axiom.Ide` | реально декодирует PNG/JPEG/BMP/ICO средствами Windows/WPF |
| тестовые хосты | создают синтетические картинки без реального декодера |
| `NullRuntimeHost` | сообщает, что загрузка изображений недоступна |

Практический договор:

```csharp
LoadGraphicsImage(path) -> RuntimeImageValue или ошибка
DrawImage(image, x, y, width?, height?)
```

Путь к файлу нужно продумать отдельно. Для игр относительные пути должны быть удобными.

Рекомендация:

| Случай | База относительного пути |
| --- | --- |
| программа запущена из сохранённого `.axm` | папка файла программы |
| программа без пути | текущий каталог процесса |
| абсолютный путь | используется как есть |
| переменные окружения | можно раскрывать так же, как в файловых функциях |

Для этого, вероятно, нужно расширить `ExecutionRequest` полем вроде `WorkingDirectory` или `SourceFilePath`, а `ProgramRunService` должен передавать папку активного документа.

**Этап 4**
Добавить `LOADIMAGE`.

Пользовательские формы:

```basic
hero = LOADIMAGE("assets/hero.png")
background = LOADIMAGE("assets/background.jpg")
icon = LOADIMAGE("src/Axiom.Ide/Assets/axiom.ico")
```

Договор:

| Правило | Поведение |
| --- | --- |
| аргумент | `STRING` |
| результат | `IMAGE` |
| поддерживаемые форматы первого среза | PNG, JPEG, BMP, ICO, если декодер хоста поддерживает |
| ошибка отсутствующего файла | runtime-диагностика |
| ошибка неподдерживаемого или битого файла | runtime-диагностика |
| пустой путь | runtime-диагностика |
| альфа-канал PNG | сохраняется |
| повторная загрузка того же файла | можно пока создавать новое значение, кэш отложить |

Автотесты:

| Тест | Что проверяет |
| --- | --- |
| parser/semantics | `LOADIMAGE` виден как функция |
| runtime interpreter | успешная загрузка через тестовый хост |
| runtime bytecode | тот же сценарий через `BytecodeVm` |
| negative parity | отсутствующий файл даёт одинаковую диагностику |
| execution | sample проходит через `BytecodeVm` без отката |

Это маленький, но полезный слой для игр и ручной отладки.

Договор:

| --- | --- |
| `IMAGEWIDTH(image)` | `INTEGER` |

| --- | --- |

**Этап 6**
Добавить `DRAWIMAGE`.

Минимальные формы:

```basic
DRAWIMAGE image, x, y
DRAWIMAGE image, x, y, width, height
```

Договор первого среза:

| Правило | Поведение |
| --- | --- |
| нужен активный `SCREEN 1..10` | без него `MB3010` |
| `x`, `y` | координата левого верхнего угла |
| без `width`, `height` | натуральный размер картинки |
| с `width`, `height` | масштабирование до указанного размера |
| отрицательные размеры | runtime-диагностика |
| нулевая ширина или высота | ничего не рисует или диагностика; рекомендую диагностику |
| альфа | альфа-канал применяется автоматически |
| clipping | обрезается по экрану и `VIEW` |
| `WINDOW` | в первом срезе влияет только на координату якоря или вообще не влияет; нужно явно выбрать |
| текущая графическая позиция | после `DRAWIMAGE` становится `(x, y)` или правым нижним углом; рекомендую `(x, y)` как у якорных операций |
| `PALETTE` | не меняет уже нарисованные true-color пиксели |
| `PCOPY` | копирует true-color пиксели вместе с индексными |

Я рекомендую для первого среза: `VIEW` клиппирует, `WINDOW` преобразует только `x`, `y`, а размер остаётся в пикселях. Это проще для игр и не ломает координатную математику графиков.

**Этап 7**
Расширить внутренний кадровый буфер.

Текущий `ScreenFramebuffer` хранит только индекс цвета и палитру. Для красивых картинок нужен второй слой хранения.

Рекомендованная внутренняя модель:

| Данные | Назначение |
| --- | --- |
| `_colorIndices` | текущая BASIC-палитровая графика |
| `_palette` | отображение индексов в BGRA |
| `_directBgra` | полноцветные пиксели, нарисованные `DRAWIMAGE` / `DRAWSPRITE` |
| `0` в `_directBgra` | нет прямого пикселя, использовать палитру |

Правила записи:

| Операция | Что делает |
| --- | --- |
| `PSET` / `LINE` / `PAINT` / `PUT` | пишет индекс и очищает direct-пиксель |
| `DRAWIMAGE` | пишет direct-пиксель после альфа-композиции |
| `CLS` | очищает оба слоя |
| `PALETTE` | меняет вид только индексных пикселей |
| `PCOPY` | копирует оба слоя и палитру |
| snapshot | если direct-пиксель есть, показывает его; иначе палитру |

Это даст нормальные PNG/JPEG-изображения и сохранит старый BASIC-слой.

**Открытые Решения**
Нужно подтвердить два решения перед реализацией:

1. `POINT(x, y)` на полноцветном пикселе после `DRAWIMAGE`: возвращать ближайший индекс палитры Axiom или ввести отдельную функцию `POINTCOLOR(x, y)` для true-color?
2. Кадры `DRAWSPRITE`: использовать индексацию с `0` или с `1`?

Моя рекомендация: `POINT(x, y)` возвращает ближайший индекс палитры, а кадры спрайта идут с `0`.
