## Основной вывод

Текущая подсистема уже поддерживает SUB/FUNCTION, прямые и косвенные вызовы, вложенные подпрограммы, замыкания и передачу параметров. Обычные сценарии повторных вызовов, разделения состояний замыканий, рекурсии и возврата проверены положительно. Однако до многофайловой системы необходимо устранить различия путей вызова, завершить транзитивный анализ захватов и согласовать жизненный цикл кадров и адресуемых получателей.

Особенно опасны остановка и отладка косвенного вызова: один путь исполнения обходит основной цикл VM. Просто добавить файловую доступность поверх нынешних словарей недостаточно: у исходных позиций и символов пока нет владельца файла/модуля, а у программы один блок глобальной инициализации.

## Текущая модель и положительные проверки

- Binder сначала регистрирует верхнеуровневые объявления, связывает глобальные инструкции, затем тела процедур. Это даёт процедурам видимость глобальных переменных независимо от положения их объявления относительно тела процедуры; сами глобальные инструкции исполняются в порядке исходника.
- `BoundScope` разделяет поиск переменных и подпрограмм. Поиск регистронезависим. Вложенная подпрограмма определяется `FunctionSymbol.ContainingRoutine`; это лексическое вложение, а не закрытость внутри файла.
- Параметры по умолчанию BYVAL. Скаляр получает собственное значение; запись TYPE копируется; обычный массив сохраняет общее хранилище, но присваивание нового массива параметру не заменяет переменную вызывающего кода. Это подтверждённый договор, а не ошибка ссылочной передачи массива.
- BYREF связывает простой идентификатор точно совпадающего типа. Поле/элемент пользовательского аргумента запрещены Binder; неявный SELF методов имеет отдельный путь адресации составного получателя.
- Аргументы обычного вызова вычисляются слева направо в понижении. Для двух изменяющих счётчик аргументов получен результат 12. Это не определяет автоматически момент копирования изменяемой записи — см. SP-09.
- Два замыкания от разных вызовов фабрики сохраняют независимое состояние: 11, 101, 12. Захваченные параметры не смешиваются при повторном использовании кадра: 1, 2. Захваченный BYREF после возврата фабрики сохраняет связь с переменной: 11, 11.
- Локальная переменная без начального выражения вновь получает значение по умолчанию при повторном вызове: 1, 1. Рекурсивная вложенная функция с прямым захватом работает. Прямая и косвенная бесконечная рекурсия доходят до MB3011, ошибка перехватывается, программа продолжается.
- Достижение END FUNCTION без результата даёт перехватываемую MB3006. Обычный RETURN выполняет один FINALLY. Возвращаемая запись фиксируется до изменения локальной записи в FINALLY; возвращаемое замыкание продолжает видеть изменение захваченного значения из FINALLY. Обе формы проверены.
- Изменение обычного BYREF до пользовательской ошибки видно после CATCH. Отмена не должна превращаться в перехватываемую пользовательскую ошибку.

## SP-01 и SP-02. Косвенный вызов обходит управление запуском

Источник: `src/Axiom.Runtime/Execution/BytecodeVm.cs`, `InvokeBytecodeFunction` около строки 3851 и цикл около 3916; основной цикл `ExecuteModule` около 177; проверка остановки в `ExecuteCurrentInstruction` около 576.

Прямой вызов добавляет кадр и возвращает управление основному циклу VM. Косвенный вызов входит во вложенный C#-цикл:

```csharp
while (_callStack.Count > callStackDepth)
{
    ExecuteCurrentInstruction(callStackDepth);
}
```

В нём нет `CheckCancellationRequested()` и условия `_stopState is null`.

**Отмена.** Функция с циклом из 100 000 сложений вызвана напрямую и через переменную `FUNCTION() AS INTEGER`. Один провайдер отменяет на 64-м опросе. Прямая форма: Cancelled, 64 опроса, без результата. Косвенная: Success, вывод 100000, всего 7 опросов. Это подтверждает отсутствие опроса внутри пользовательского тела; реальный бесконечный цикл без отдельно проверяющей отмену встроенной функции может не завершиться по запросу остановки.

**Точка останова.** Минимальный исходник:

```basic
FUNCTION Work() AS INTEGER
    RETURN 42
END FUNCTION
DIM action AS FUNCTION() AS INTEGER
action = Work
PRINT action()
```

При точке останова на строке 2 отдельный процесс не вернулся за 5 секунд. Контроль с `PRINT Work()` вернулся с `Stopped = TRUE`, `stopLine = 2`. При остановке `ExecuteCurrentInstruction` сохраняет `_stopState` и возвращает без продвижения инструкции; вложенный цикл снова вызывает ту же инструкцию. Причина установлена по коду, а не только по истечению времени.

Область общего пути шире переменной FUNCTION: его вызывают также обратные вызовы массивов, клавиатуры и мыши. Их GUI-проявления в этом аудите не воспроизводились. Простая вставка `break` при `_stopState` недостаточна: C#-вызывающая сторона всё ещё ждёт результат функции, которого пока нет. Необходимо сохранить продолжение операции и состояние вызывающей стороны.

Предложение: единая модель диспетчеризации прямого/косвенного вызова и явного продолжения для обратных вызовов. Независимо проверить Cancel/Resume/StepInto/StepOver/StepOut/StepBack, остановку в обратном вызове и исключение из него. Отмена должна обходить пользовательский CATCH.

## SP-03. Не передаются транзитивные захваты

Источник: `src/Axiom.Bytecode/Emission/BytecodeCompiler.cs:286`, `CreateCaptureSlotMap`; `Binder.Routines.cs`; `BytecodeVm.ResolveCaptureBindings`.

Валидный по лексическим областям исходник:

```basic
FUNCTION Outer() AS INTEGER
    DIM x AS INTEGER = 10
    FUNCTION PeerAlpha() AS INTEGER
        RETURN PeerBeta()
    END FUNCTION
    FUNCTION PeerBeta() AS INTEGER
        x = x + 1
        RETURN x
    END FUNCTION
    RETURN PeerAlpha()
END FUNCTION
PRINT Outer()
```

Вместо 11 получается BackendFailure с BC4117: PeerAlpha не видит захваченную переменную x, нужную PeerBeta. Второй исходник Outer → Middle → Deep, где Middle возвращает Deep как значение, аналогично даёт BC4117 для LoadFunction.

Карта захватов собирается по непосредственным `instruction.Variable` и `instruction.Variables`. Зависимость через Call/LoadFunction не добавляет требуемые переменные промежуточной процедуре. Защитный валидатор правильно отвергает несогласованный байт-код; проблема раньше — в анализе замыканий, а не в самом запрете валидатора.

Предложение: явный граф прямых вызовов и загрузок функциональных значений, вычисление транзитивных наборов захвата до неподвижной точки. Проверить соседние функции, несколько уровней, взаимную рекурсию, захват параметра/BYREF и возврат функции после выхода внешнего кадра. Нельзя обходить BC4117 ослаблением валидации.

## SP-04. Составной SELF иногда передаётся через отложенную копию

Источник: `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.cs:1785–1810`, `TryLowerByRefCopyBackArgument` около 1922; адресный путь `BytecodeVm.ByRef.cs`.

В TYPE Cell объявлен метод Edit: увеличить SELF.item, напечатать `cells(1).item`, затем при необходимости вызвать ERROR. GetCells возвращает общий массив cells. Сравнение:

| Получатель | Вывод внутри метода, затем после вызова |
|---|---|
| `cells(1).Edit()`, успех | 1, 1 |
| `GetCells()(1).Edit()`, успех | 0, 1 |
| `cells(1).Edit()`, ошибка и CATCH | 1, EXPECTED, 1 |
| `GetCells()(1).Edit()`, ошибка и CATCH | 0, EXPECTED, 0 |

Массив в обеих формах один и тот же. Запасной путь понижения извлекает запись в временную переменную, вызывает метод и записывает результат обратно только после успеха. Внутри метода внешнее наблюдение видит прежнюю запись; при ошибке обратная запись пропускается.

Это расходится с описанным живым SELF составного получателя. Предложение: вычислить получателя и индексы ровно один раз, сохранить адрес фактического элемента массива и использовать его и для чтения, и для записи. Проверить побочные эффекты вычисления получателя/индексов, два алиаса, ошибки, вложенные поля и повторное изменение всего массива во время вызова. Простое добавление копирования в обработчик ошибки не исправит наблюдение внутри метода.

## SP-05. RETURN не завершает весь активный стек очистки

Источник: `BytecodeVm.TryEnterFinallyForReturn`, `ExecuteEndFinally`, `CompleteReturn`.

Два наблюдения:

1. RETURN во внутреннем TRY/FINALLY печатает inner и возвращает 7, пропуская outer. Этот вариант уже прямо описан в `manual/return.html` как ограничение текущей реализации.
2. RETURN во внутреннем TRY/CATCH без своего FINALLY, окружённом TRY/FINALLY, возвращает 8 без вывода outer. Здесь пропущен даже ближайший существующий FINALLY, а не только более внешний после уже выполненного.

Проверяется только верхний обработчик. Если у него нет FINALLY, возврат немедленно завершает кадр; после выполнения одного FINALLY `ExecuteEndFinally` тоже вызывает CompleteReturn без обхода остальных.

Предложение: общий механизм завершения кадра с последовательным выходом через все необходимые обработчики. Сохранить значение результата до очистки. Решить и закрепить взаимодействие RETURN внутри FINALLY, новой ошибки при очистке, текущей ошибки и запроса отмены. Особенно важно проверить освобождение FILE: сейчас завершение всего запуска может скрыть пропущенную очистку внутри отдельной подпрограммы.

## SP-06. Проверка readonly обходится через BYREF

Источник: `Binder.InvocationExpressions.cs`, `BindByRefArgument` около 708. Проверяются форма переменной и точное совпадение типа; `VariableSymbol.IsReadOnly` не проверяется.

CONST fixedValue = 10 передан в SUB Mutate(BYREF a AS INTEGER), которая присваивает a = 99. Программа успешно печатает 99. Это уже честно отмечено в карточках SUB/FUNCTION/calls; находка не выдаётся за новую.

Предложение: определить единый договор изменяемой ссылки, отвергать readonly при получении BYREF, проверить также захват и передачу ссылки дальше. Диагностику согласовать с действующими ошибками readonly/невалидного BYREF. Перед экспортируемыми константами и закрытыми переменными модулей этот пропуск необходимо устранить.

## SP-07. Кэш завершённых кадров удерживает значения

Источник: `BytecodeVm.CacheReusableFrame` около 4269; `BytecodeCallFrame.Reset` около 70.

После возврата кадр добавляется в `_cachedFrames` без очистки ссылок. Reset очищает его лишь при следующем использовании. Удерживаются локальные значения, аргументы, захваты, кэши функциональных значений и захваченных слотов, а в отдельных путях — состояние обработчиков ошибок.

В двух процедурах создавалась локальная строка из 8 млн символов. Между вызовами внешний IOutputWriter измерял `GC.GetTotalMemory(true)`:

| Момент | Приблизительно живых байтов |
|---|---|
| До вызовов | 725 888 |
| После первой процедуры | 16 726 752 |
| После второй процедуры | 32 727 352 |
| После повторного вызова первой | 32 727 448 |
| После завершения запуска и сборки | 715 056 |

Это удержание памяти на время VM, а не доказанная бесконечная утечка между запусками. Небольшой кэш объектов кадра фактически становится кэшем больших пользовательских данных.

Предложение: перед возвратом в пул отделять захваченные ячейки, очищать неиспользуемые ссылки и состояние, не изменяя содержимое ячеек живых замыканий. Отдельно проверить завершение через RETURN, исключение и отмену, захваты BYREF и восстановление отладочных снимков. Проверка должна измерять достижимость/память во время продолжающегося запуска.

## SP-08. Повторные копии записей

Источники: `BytecodeVm.CreateArgumentSlots` около 485, `BytecodeVariableSlot` — конструктор, Store и setter Value; `RuntimeValue.CopyForStorage`.

Для BYVAL сначала вызывается CopyForStorage, затем конструктор слота снова нормализует запись и делает глубокую копию. Store аналогично нормализует значение перед присваиванием в Value, чей setter повторяет нормализацию.

Измерение записи с фиксированным массивным полем из 10 000 INTEGER, два предварительных вызова и 30 операций:

| Путь | Выделено байтов на операцию |
|---|---|
| Одна CopyForStorage | 80 576 |
| CopyForStorage + конструктор слота, как при подготовке аргумента | 161 264 |
| Store существующего слота | 161 184 |

Отражение добавляет небольшой собственный расход, но удвоение согласуется с двумя явными путями копирования в коде. Это измерение выделений, а не доказательство ускорения будущей реализации.

Предложение: зафиксировать единственного владельца нормализации значения для каждого пути хранения. Не менять правила глубокого копирования TYPE и разделения динамических массивов. Принять оптимизацию только после матрицы алиасов и измерения выделений.

## SP-09. Когда BYVAL фиксирует изменяемое значение

`Observe(shared, Touch())` сначала получает ссылку RuntimeValue на запись shared; Touch меняет её поле с 1 на 2; копирование параметра происходит при создании кадра. Observe видит 2. При явной предварительной копии можно получить 1.

Код подтверждает позднее копирование, но имеющийся договор порядка аргументов сам по себе не обещает немедленный снимок изменяемой записи. Поэтому результат 2 не объявляется доказанной ошибкой. До межмодульного вызова нужно выбрать и описать точный момент копирования: при вычислении каждого аргумента либо при входе после вычисления всех аргументов. Проверить оба варианта, побочные эффекты последующих аргументов и стоимость.

## SP-10. Недостижимые оптимизации и кандидаты удаления

`BytecodeVm.StringFastBuiltins.cs` содержит 213 строк и 10 случаев: LEN, TRIM/LTRIM/RTRIM, CONTAINS/STARTSWITH/ENDSWITH, LCASE/UCASE и INSTR. Единственный путь к нему проходит через `executionInfo.HasFastHandler`. Метод `HasFastBuiltinHandler` не содержит ни одного из этих ID; проверенное пересечение наборов пусто. Следовательно, эти ветви недостижимы из штатного диспетчера. Строковые функции работают через общие обработчики, поэтому это не функциональный отказ.

В том же реестре остались файловые ID после удаления файлового ускоренного пути: для них выполняется безрезультатная проверка ускоренных обработчиков перед общим вызовом. Предложение: удалить недостижимый код либо отдельно доказать необходимость и корректность его подключения. Просто включить флаги нельзя: старые дубли могут обходить текущие ограничения строк, отмену и диагностику.

Ещё один кандидат упрощения — CopyBackByRefArguments: текущий CreateArgumentSlots уже помещает в Arguments тот же слот, который записан в ByRefArgumentTargets. Обратная запись записывает значение в собственную ссылку и может выполнять лишние копии. Это не объявляется чистым мёртвым кодом: у слота есть getter/setter, нормализация и составные адреса. Удаление допустимо только после доказательства отсутствия требуемых эффектов.

Запасной путь понижения BYREF также нельзя удалить целиком: пример SP-04 реально достигает его для элемента возвращённого массива. Отсутствие привычного пользовательского BYREF поля не доказывает недостижимость неявного SELF.

## Готовность к модулям

| Сейчас | Что нужно до нескольких файлов |
|---|---|
| CompilationRequest/ExecutionRequest содержат одну строку SourceText | Набор исходных единиц с устойчивой идентичностью и совместимый вход для одного файла |
| TextLocation содержит только span/строку/колонку | Идентичность документа в диагностике, карте инструкций и точках останова |
| FunctionSymbol знает имя и ContainingRoutine | Владелец-модуль и отдельная доступность; лексическое вложение сохранить отдельно |
| VariableSymbol имеет IsGlobal/IsReadOnly | Отделить длительность хранения от доступности внутри/вне модуля |
| BoundScope и таблица TYPE используют неуточнённые имена | Поиск в текущем модуле, импортируемом пространстве и экспортируемой поверхности с ясной неоднозначностью |
| LoweredProgram имеет одну точку `<global>` | Явный порядок инициализации модулей, зависимости и договор циклов |
| RoutineId назначается внутри одного результата компиляции | Связывание целей по идентичности символа; отображение модуля и имени в отладке |

Склеивание файлов в одну строку не решает эти задачи и теряет границы доступности и координаты. Нынешний запрет перекрытия глобальной переменной параметром также нельзя механически распространить на закрытые имена всех файлов: несвязанный закрытый символ другого модуля не должен случайно участвовать в поиске имени текущей подпрограммы. Наличие IsLocal сейчас не означает file-private. Приватность имени и возможность вернуть закрытую функцию как значение тоже должны быть разными правилами: существующие фабрики замыканий нельзя случайно запретить общей проверкой доступа при каждом косвенном вызове.

Не утверждены: синтаксис модулей и импортов, доступность по умолчанию, возможность верхнеуровневых операторов в библиотечных файлах, порядок инициализации, политика циклов, неоднозначность одинаковых импортированных имён и устройство проекта на диске. Эти решения перечислены в плане как вопросы автора; аудит не выдаёт их за уже реализованный язык.
