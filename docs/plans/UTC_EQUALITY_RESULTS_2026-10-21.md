# DTR-002: равенство UTCDATETIME и ARRAYDISTINCT

Результат четвёртой работы стабильности, 21 октября 2026 года. Язык 0.2.4, компилятор/CLI 0.3.3, IDE 0.8.8.

## Исправление

StructuralEqualitySupport включает UTCDATETIME среди скаляров: записи одного типа с такими полями допускают = и <>, включая вложенные записи. Сравнение самих моментов и рекурсивное сравнение полей уже существовали; расширен отсутствовавший допуск типа.

RuntimeValueEqualityComparer включает UTCDATETIME в SupportsElementType и вычисляет хеш через AsUtcDateTime().GetHashCode(). ARRAYDISTINCT выбирает существующий HashSet, сохраняя порядок первых вхождений, компактные границы результата и неизменность исходного массива. Точность до одного тика (100 нс) сохраняется. Новых форм вызова и токенов нет. Для проверки настоящего внутреннего компаратора тестовой сборке Runtime предоставлен InternalsVisibleTo; публичный API не расширялся.

## Проверки

До исправления адресные проверки дали ожидаемые отказы: Semantics 1/1, Bytecode 1 из 2, Runtime 1/1, Execution 1 из 3 (недопуск сравнения записи). Остальные два Execution уже подтверждали правильный результат ARRAYDISTINCT при медленном алгоритме; хеширование отдельно подтверждается компаратором и замером.

После исправления и расширения граничных случаев: Semantics 3/3, Bytecode 4/4, Runtime 7/7, Execution 42/42. Проверены равные и различные моменты, вложенные поля, разница в один тик, копия записи, равенство хешей для равных значений, реальный хеш по UTC-значению, выбор хеширования, повторы и порядок первых вхождений, пустой массив, одинаковые элементы и 8000 уникальных моментов.

CLI Release собран без ошибок и предупреждений. Новый постоянный пример и пример справочника выполнены через CLI с независимыми точными ожиданиями. Для постоянного примера вывод: 32000; 2024-01-01T00:00:01Z; 2024-01-01T02:13:20Z. Пример справочника печатает TRUE, TRUE. Штатная нагрузка ManualChecks прошла 1/1 (один прогрев, три повтора). Справочник проверен штатным check-manual.

Полный набор .NET и Electron не запускались. Изменений интерфейса, подсветки или новых ключевых слов нет.

## Замер до и после

Отдельный процесс CLI Release для каждого повтора. Массив заполнен до начала замера, затем выполнен один прогревающий ARRAYDISTINCT. Между двумя чтениями ELAPSEDSECONDS измеряются четыре прохода и подсчёт длины результатов. Для каждого размера пять процессов, ниже медианы миллисекунд. Каждый повтор проверяет суммарную длину 4 × размер. Данные, сценарий и выборки сохранены в .artifacts/stability-equality-20261021/measure.py и perf-before/after.json.

| Уникальных элементов | До, мс | После, мс |
|---|---|---|
| 2000 | 118.5 | 16.4 |
| 4000 | 446.3 | 21.2 |
| 8000 | 1747.0 | 25.9 |

Удвоение размера раньше увеличивало время примерно в четыре раза. После исправления наблюдается существенно меньший рост. Это измерение конкретной нагрузки на данном компьютере, а не обещание универсального коэффициента ускорения. Сборка массива и подготовка программы сюда не входят.

Постоянная нагрузка samples/smoke/engine-compare/array_distinct_utc_unique.axm зарегистрирована в benchmark-bytecode. Она включает заполнение массива, четыре прохода и вывод. Её отдельный штатный замер дал медиану исполнения 43.1 мс, полного времени 44.0 мс; эти числа нельзя смешивать с изолированным замером 25.9 мс выше. Отчёт benchmark.json содержит текстовый формат штатного инструмента, несмотря на выбранное расширение; рядом сохранён benchmark.log.
