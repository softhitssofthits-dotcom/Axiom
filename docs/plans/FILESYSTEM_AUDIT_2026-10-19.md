## FS-01. Маска меняет каталог перечисления

Источник: `src/Axiom.Runtime/Execution/BytecodeVm.Builtins.FileSystem.cs`, EvaluateGetFilesBuiltin, EvaluateGetDirsBuiltin, EnsureSearchPattern.

EnsureSearchPattern отвергает только пустую строку. Затем маска передаётся непосредственно Directory.EnumerateFiles/EnumerateDirectories. Системное перечисление допускает в маске части пути.

Воспроизведение: создать папку `root/nested` и файл `root/nested/hidden.txt`. Следующий исходник возвращает один файл, хотя он лежит не непосредственно в root:

```basic
DIM files() AS STRING
files = GETFILES("<root>", "nested\*.txt")
PRINT ARRAYLENGTH(files)
PRINT files(1)
```

`GETFILES("<root>\nested", "..\*.txt")` возвращает файлы родительского каталога, причём строка результата содержит `nested\..\имя`. Справочник обещает маску имён непосредственно в заданном каталоге и нерекурсивный обход. GETDIRS устроен аналогично; отдельное динамическое воспроизведение для него в этом аудите не выполнялось.

Предложение: проверять именно маску имени, отвергать разделители каталога и корневые/дисковые формы до перечисления. Сохранить допустимые `*` и `?`; не применять к маске запрет всех символов обычного имени файла. Добавить независимые ожидания для GETFILES и GETDIRS с обеими масками, обычной маской и отсутствующими совпадениями. Проверить каноничность возвращаемых путей.

Это нарушение ограничения области поиска, но не обход защитной песочницы: язык в целом имеет доступ к доступным пользователю путям.

## FS-02. Отмена не доходит внутрь файловых алгоритмов

Источники: `BuiltinDirectoryHelpers.GetDirectorySize/CopyDirectory`, `RuntimeTextFile.Read.cs`, `RuntimeTextFile.Position.cs`, `RuntimeTextFile.Encoding.cs`, `BuiltinTextEncodingHelpers.ValidateStream`.

Эти собственные циклы не получают провайдер/делегат отмены. Для программы `PRINT DIRSIZE(path)` провайдер опрошен ровно пять раз и для пустого дерева, и для дерева из 1000 файлов. Чтение кода подтверждает отсутствие обращений внутри обхода.

Практическое следствие: запрос остановки во время большого дерева будет замечен после завершения встроенной операции. COPYDIR может продолжать создавать файлы после запроса. Длительность на сетевом диске не измерялась. Отдельный уже начатый синхронный системный вызов имеет свои ограничения прерывания.

Предложение: передавать существующий механизм отмены VM в собственные циклы, проверять между элементами каталога и блоками текста, не превращать отмену в перехватываемый MB3007. Для COPYDIR явно определить состояние уже скопированной части. Добавить управляемый провайдер, который отменяет именно внутри операции, и проверить отсутствие последующих записей.

## FS-03. Пропуск строки материализует строку

Источник: `RuntimeTextFile.SkipLine` вызывает `ReadLineCore`; тот собирает List<byte>, создаёт byte[] и декодирует STRING, который затем выбрасывается.

На строке из 1 000 000 ASCII-символов выделено около 5,10 МБ, из 4 000 000 — 20,39 МБ в текущем потоке. Последний диагностический запуск: 14,8 и 65,1 мс соответственно. Это одиночные измерения без статистической оценки, не сравнительный тест версий.

Строка из 16 777 217 ASCII-символов: SKIPLINE выдаёт MB3007, FILEPOS остаётся 0. В этот момент результат типа STRING пользователю не возвращается. Следовательно, ограничение строки неожиданно ограничивает саму возможность пропуска. При наличии явно закреплённого общего ограничения на длину обрабатываемой строки это могло бы быть договором, но в текущей карточке SKIPLINE такого объяснения нет.

Предложение: отдельный блочный алгоритм пропуска с постоянной памятью. Сохранить CR/LF/CRLF, корректность кодировки, восстановление позиции при ошибке, UTF-16 и отмену. Не отменять проверку кодировки без отдельного решения. READLINE тоже стоит перевести с побайтовой сборки на буферизированный проход, сохранив предел возвращаемой строки.

## FS-04. Непоследовательная проверка NUL

Источник: EvaluateCombinePathBuiltin и EvaluateIsAbsolutePathBuiltin обходят NormalizeFileSystemPath, где находится явный запрет NUL.

Подтверждённые результаты:

```basic
PRINT LEN(COMBINEPATH("a", CHR(0))) ' 3: строка с разделителем и NUL
PRINT ISABSOLUTEPATH("C:\" & CHR(0)) ' TRUE
```

Общий текст карточек файловых средств запрещает нулевой символ в пути. При последующей передаче результата файловой операции запрет срабатывает позднее.

Предложение: выделить общую проверку допустимости строкового пути, применяемую и к функциям, которым не нужна нормализация. Для COMBINEPATH проверять оба аргумента отдельно, для ISABSOLUTEPATH — до раскрытия окружения. Закрепить MB3007 и точное имя аргумента.

## FS-05. Диагностика указывает другой аргумент

Источник: общие try/catch в BytecodeVm.Builtins.FileSystem.cs.

`COPYFILE(CHR(0), "<обычный путь назначения>")` внутри TRY возвращает через CATCH сообщение `COPYFILE: Invalid built-in argument. Context: 'destination', 'path'.` Невалиден source, но catch всегда передаёт destination. Это не отсутствие файла, поэтому предварительная EnsureFileExists не исправляет ситуацию.

Аналогичный шаблон есть у MOVEFILE/COPYDIR/MOVEDIR; у GETFILES/GETDIRS имя аргумента общего исключения выбирается по наличию перегрузки с pattern, даже если отказал путь. Для этих дополнительных форм вывод сделан по коду, без отдельных воспроизведений.

Предложение: разделить проверку/нормализацию каждого аргумента и собственно системную операцию; хранить контекст стадии отказа. Не разбирать текст системного исключения ради определения аргумента. Добавить проверки сообщения CATCH для невалидного source, destination, path, pattern и encoding. Исправление не должно менять исторический общий код MB3007 без отдельной необходимости.

## FS-06. Временные объекты создаются с окном гонки

Источник: BuiltinFileSystemHelpers.CreateTemporaryFile/CreateTemporaryDirectory.

Файл: File.Exists, затем File.Create. Последний допускает обнуление объекта, появившегося между проверкой и созданием. Каталог: Directory.Exists, затем Directory.CreateDirectory; создание существующего каталога может вернуть успех. Кроме того, проверяется только ожидаемый вид объекта, а не конфликтующий файл/каталог другого вида.

Случайная коллизия маловероятна; конкурентная подмена не воспроизводилась. Это подтверждённая структура алгоритма, а не доказанный инцидент потери данных.

Предложение: FileMode.CreateNew и ограниченный повтор именно при конфликте имени; ошибки доступа не скрывать повтором. Для каталога использовать механизм, гарантирующий создание нового объекта, с сохранением пользовательского префикса; простая замена Directory.Exists на PATHEXISTS гонку не устраняет. Для проверки предусмотреть управляемый генератор кандидатов и конфликт перед созданием. Уже существующий RuntimeTextWriteBuffer использует CreateNew, что даёт проектный образец для файла.

## FS-07. Частичное COPYDIR требует явного договора

Существующий тест `DirectoryFailureEvidenceTests.CopyFailureIsNotAtomicButPreservesSourceAndConflictingFile` прошёл в этом аудите. Он подтверждает: первый файл уже скопирован, а конфликт во вложенной папке завершает вызов MB3007. Источник и конфликтующий файл сохраняются, но назначение уже отличается от состояния до вызова.

Справочник описывает отказ, однако явно не предупреждает о сохранении ранее скопированной части. Частичное рекурсивное удаление при ошибке также требует явного описания; отдельно отказ диска или ACL во время удаления здесь не воспроизводился.

Предложение: сначала явно документировать текущую неатомарность. Предварительная проверка известных конфликтов уменьшит число частичных операций, но не обеспечит атомарность при гонках и сбоях. Полную транзакционность не обещать; если она понадобится, проектировать запись в отдельный каталог и публикацию отдельно, учитывая существующее назначение и разные тома.

## FS-08. Повторная строгая допись имеет дорогой общий путь

BuiltinTextEncodingHelpers.Write при каждом APPENDFILE с encoding полностью вызывает ValidateStream перед дописью. Серия из k вызовов при исходном размере N читает порядка kN байт плюс повторно читает ранее добавленный текст. При постоянном размере добавления рост суммарной работы квадратичен по k.

Локальная проба: 80 добавлений одного ASCII-символа к файлу из 4 000 000 байт. Без явной кодировки — 20,6 мс; с UTF-8 — 311,5 мс. Условия различаются наличием строгой проверки, поэтому это не доказательство, что её можно удалить. Наблюдение уже известно по BYTECODE_PERF_MATRIX и не считается новой регрессией.

Предложение: для серий рекомендовать OPEN APPEND с явной кодировкой и WRITE, где проверка выполняется при открытии. Не кешировать кодировку только по пути: файл может измениться извне. Измерять отдельно рост числа вызовов и размера исходного файла, проверять итоговые байты и сохранение отказа при несовместимой кодировке.

## FS-09. Определение кодировки и чтение используют разные дескрипторы

RuntimeTextFile сначала вызывает DetectInputEncoding(path), где файл открывается, целиком проверяется и закрывается. Затем конструктор повторно открывает path для чтения. Между открытиями путь может быть заменён другим процессом, и выбранная кодировка/BOM будут относиться к предыдущему объекту.

Гонка не воспроизводилась; наличие двух открытий и промежутка между ними установлено по коду. Полная предварительная проверка также означает линейную стоимость OPEN даже перед чтением первой короткой строки. Простое удаление проверки изменит текущий договор автоматического выбора UTF-8/1251.

Предложение: открыть один поток, определить кодировку на нём и вернуть позицию на начало содержимого. Добавить проверяемый переход между определением и началом чтения; сохранить правила BOM и fallback. Отмену добавить в сам проход проверки.

## Структура и разделение файлов

Самый крупный профильный файл — `BytecodeVm.Builtins.FileSystem.cs`, 937 строк. Он объединяет чтение текста целиком, пути, операции файлов, каталоги, метаданные, диски и временные объекты. Именно здесь повторяются большие catch-блоки с ошибочным контекстом аргумента.

Предлагаемое разделение по ответственности:

| Предлагаемая часть | Ответственность |
|---|---|
| BytecodeVm.Builtins.FileText.cs | READFILE/READALLLINES/WRITEFILE/APPENDFILE |
| BytecodeVm.Builtins.Paths.cs | Части пути, нормализация, проверка масок |
| BytecodeVm.Builtins.FileOperations.cs | Создание/удаление/копирование/перенос файлов |
| BytecodeVm.Builtins.Directories.cs | Каталоги, обход, рабочая папка |
| BytecodeVm.Builtins.FileMetadata.cs | Даты, размеры отдельных файлов, атрибуты |
| BytecodeVm.Builtins.Storage.cs | Диски и временные объекты |

Сохранить partial-класс и текущие имена методов: это позволяет отдельно проверить механический перенос без изменения диспетчера. Повторяющуюся обработку ошибок объединять только после определения точного контекста аргумента; одна универсальная обёртка с фиксированным именем аргумента повторит FS-05.

`RuntimeTextFile` уже разумно разделён: основной файл 245 строк, Encoding 109, Position 86, Read 308, Write 66. Полная новая иерархия потоков не обоснована. В Read стоит выделить блочный сканер/пропуск с общей поддержкой кодировки и отмены. `BuiltinFileIOHelpers` содержит 446 строк; возможен отдельный блок проверки ресурса и блок операций, но это менее срочно, чем исправления поведения. `BuiltinDirectoryHelpers` — 99 строк: дробить его ради размера не нужно, следует добавить контекст отмены и явные правила отказа.

Разделение исходников само по себе не ускорит файловую систему. Ускорение ожидается от блочного чтения, отсутствия лишнего декодирования, повторного использования открытого файла и устранения повторного полного сканирования там, где договор позволяет.

1. FS-01, FS-04, FS-05: небольшие проверяемые исправления масок, NUL и контекста ошибок; отдельные независимые ожидания и согласование справочника.
2. FS-02, FS-03, FS-09: единый открытый поток, блочные алгоритмы чтения/пропуска, отмена внутри собственных циклов. Проверить позиции, BOM, Unicode и состояние после отказа.
3. FS-06: исключительное создание временных объектов с проверяемыми коллизиями.
4. FS-07: явный договор частичных изменений, затем только обоснованное уменьшение частичных отказов.
5. Механически разделить крупный VM-файл отдельным этапом; после переноса повторить тематические проверки.
6. FS-08: сохранить строгий договор, измерить отдельные нагрузки; оптимизировать только после подтверждения результата по байтам.

При реализации поведенческих исправлений потребуются номера языка/компилятора по VERSIONING и изменения справочника. В этом аудите версии не повышаются, поскольку реализация и действующий договор не изменены.

| FS-02 | Отмена передаётся в собственные циклы обхода, перечисления, чтения, сканирования строк и проверки кодировки; начатые синхронные вызовы .NET сохраняют своё ограничение прерывания |

| FS-09 | Определение кодировки и последующее чтение INPUT используют один открытый поток |

Дополнительно обнаружено дублирование файловой реализации в TryExecuteFastFileSystemBuiltin основного BytecodeVm.cs. Оно не давало исправлению общего обработчика изменить результат некоторых вызовов. Дублированный путь и три его служебных обработчика удалены (549 строк), все формы проходят общие обработчики. Бывший файл файловых функций разделён на FileText, Paths, FileOperations, Directories, FileMetadata, Storage и общий FileSystem. Новые слова или формы языка не вводились.

Проверки до реализации: новые ожидания масок/NUL/source — 11 отказов; отмена — 4 отказа; длинные строки — 3 отказа; коллизии временного файла — 2 отказа; контекст encoding — 3 отказа. Дополнительный тест выделений коротких строк выявил необходимость повторных буферов. Независимая проверка нашла создание каталога COPYDIR до проверки отмены; отдельный тест воспроизвёл этот отказ, проверка перенесена перед созданием. Повторный просмотр существенных замечаний не выявил.

Добавлены 42 адресные постоянные проверки: 23 Execution и 19 Runtime. Общий набор Execution дополнительно автоматически подхватил три новых запускаемых примера. Итоговые прогоны и их точная последовательность записаны в WORKLOG5. Проверка справочника и девять браузерных/структурных тестов прошли. Локальные журналы реализации находятся в .artifacts/filesystem-audit/; измерения и ограничения приведены в BYTECODE_PERF_MATRIX. Сетевые файловые системы, заполнение диска и конкурентные подмены остаются пределом доказательств, а не объявляются проверенными этим изменением.

Дополнительная проверка отказа чтения блока под Windows-блокировкой воспроизвела выдачу предыдущего блока после неудачного обновления кэша. Длина кэша теперь обнуляется до ReadAtLeast; после снятия блокировки повторное чтение получает правильный блок. Проверяющий подтвердил защиту. Также проверен автоматический переход к WINDOWS-1251 при невалидном байте после Unicode-символа на границе блоков.
