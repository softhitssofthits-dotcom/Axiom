## Подтверждённые дефекты

### R1. P1 — повторное вычисление литерала изменяет прежний результат

Место: `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.Expressions.cs:44`. Каждое выполнение одного места с литералом загружает прежний скрытый массив и делает REDIM этого же объекта. Нового независимого массива при повторном выполнении не возникает.

```basic
DIM first[] AS INTEGER
DIM current[] AS INTEGER
FOR i = 1 TO 2
    current[] = [i]
    IF i = 1 THEN first[] = current[]
NEXT i
PRINT first[1]
```

Ожидается `1`: первое вычисление создало массив с единицей. Фактически `2`: второе вычисление изменило объект первого результата. Это приводит к незаметному изменению сохранённых данных; аналогично может инвалидировать сохранённые представления. Требуется создавать новый объект при каждом вычислении литерала. Воспроизведение: `.artifacts/arrays-roadmap-review/literal-alias.axm`.

### R2. P1 — FOR EACH BYREF молча выполняется как BYVAL

Место: `src/Axiom.Semantics/Binding/Binder.ControlFlowStatements.cs:362`. Парсер сохраняет модификатор, но связыватель не проверяет его и всегда создаёт `BoundForEachStatement` с `byRef: false`.

```basic
DIM values[] AS INTEGER = [1, 2]
FOR EACH BYREF item IN values[]
    item = 99
NEXT
PRINT values[1], values[2]
```

`check` успешен, выполнение выводит `1 2`. Согласно текущему справочнику и дорожной карте неподдержанный BYREF должен отклоняться при проверке. Молчаливое принятие создаёт ложное впечатление записи в исходный массив. На текущем этапе требуется явный отказ, а не обязательная досрочная реализация BYREF. Воспроизведение: `byref-ignored.axm`.

### R3. P2 — STEP вне сортировки завершает компилятор необработанным исключением

Место: `src/Axiom.Semantics/Binding/Binder.SyntaxHelpers.cs:43`. В `GetLocation(ExpressionSyntax)` отсутствует новый `StepDirectionArgumentExpressionSyntax`. Например, обработчик ARRAYMAP запрашивает координаты аргумента до выдачи предметной диагностики.

```basic
DIM a[1 TO 2] AS INTEGER
PRINT ARRAYMAP(a[], STEP 1)
```

Вместо диагностики недопустимого STEP возникает `ArgumentOutOfRangeException` со стеком `BindPolymorphicArrayMapBuiltInCall` → `GetLocation`. Код завершения процесса Windows: `-532462766`. Передача `STEP 1` пользовательскому BYREF-параметру также аварийно завершается. Нужны обработка нового синтаксического узла и проверка отказа во всех путях вызова. Воспроизведения: `step-map.axm`, `step-byref.axm`.

### R4. P2 — обход единственного элемента с верхней границей INTEGER_MAX завершается ошибкой

Место: `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.ForEach.cs:146`. После последнего элемента счётчик INTEGER безусловно увеличивается на единицу, до проверки завершения диапазона.

```basic
DIM values[2147483647 TO 2147483647] AS INTEGER
values[2147483647] = 7
FOR EACH item IN values[]
    PRINT item
NEXT
PRINT "done"
```

Допустимый массив содержит всего один элемент. Ожидается `7`, затем `done`; фактически после `7` выдаётся MB3008 о переполнении `+`. Требуется проверять исчерпание диапазона до переполняющего увеличения либо использовать безопасное представление счётчика. Воспроизведение: `foreach-max.axm`.

### R5. P2 — пустой литерал теряет известный тип в CONST и круглых скобках

Места: `src/Axiom.Semantics/Binding/Binder.Expressions.cs:19`, `src/Axiom.Semantics/Binding/Binder.DeclarationStatements.cs:149`.

Обе формы отклоняются с MB2059:

```basic
DIM values[] AS INTEGER = ([])
```

```basic
CONST values[] AS INTEGER = []
```

Тип элементов известен из объявления. В первом случае контекст не передаётся через узел группировки, а во втором инициализатор сначала связывается без ожидаемого типа; последующее повторное связывание не удаляет уже выданную ошибку. Требуется передавать контекст до первого связывания литерала. Воспроизведения: `parenthesized-empty.axm`, `const-empty.axm`.

### R6. P2 — числовое расширение заменяет явно заданный тип литерала

Место: `src/Axiom.Semantics/Binding/Binder.Expressions.cs:178`. `ResolveArrayLiteralElementType` использует `PromoteNumericType` также при заранее известном типе элементов.

```basic
DIM values[] AS INTEGER = [1, 2.5]
```

Вместо проверки каждого элемента на совместимость с INTEGER строится DOUBLE[] для переменной INTEGER[]. Ошибка обнаруживается только валидатором байт-кода: BC4116 на `StoreLocal`. Программа должна отклоняться на этапе связывания с диагностикой пользовательского типа, без создания несовместимого связанного объявления. Воспроизведение: `numeric-context.axm`.

### R7. P2 — литерал обходит проверку ожидаемого скалярного типа

Место: `src/Axiom.Semantics/Binding/Binder.Expressions.cs:32`. Безусловный возврат для `ArrayLiteralExpressionSyntax` пропускает общую проверку типа даже при ожидаемом скалярном результате.

```basic
FUNCTION F() AS INTEGER
    RETURN [1, 2]
END FUNCTION
PRINT F()
```

Связывание принимает возврат INTEGER[] из функции INTEGER. Только валидатор сообщает BC4116 на `Return`. Требуется отклонять несовместимый тип при связывании, сохраняя корректность связанного дерева и редакторской диагностики. Воспроизведение: `scalar-return.axm`.

### R8. P2 — имя поля сортировки ограничено литералом вопреки описанию константы

Место: `src/Axiom.Semantics/Binding/Binder.BuiltinInvocations.cs:531`. Проверка принимает только непосредственный строковый `LiteralExpressionSyntax`.

```basic
TYPE Product
    Price AS INTEGER
END TYPE
CONST fieldName AS STRING = "Price"
DIM basket[1 TO 2] AS Product
ARRAYSORT(basket[], fieldName)
```

Фактически MB2057: имя поля якобы не известно при проверке программы. Та же ошибка возникает для `ARRAYSORT(basket[], ("Price"))`. Действующие спецификация, справочник, дорожная карта и само сообщение говорят о строковой константе, известной до выполнения. Требуется поддержать такой договор либо явно согласовать и описать ограничение непосредственным литералом. Воспроизведения: `sort-const-key.axm`, `sort-parenthesized-key.axm`.

## Незавершённые договоры этапа 6, влияющие на BYVAL

Текущая дорожная карта явно отложила следующие свойства на продолжение этапа 6. Поэтому они не выданы за незаявленные регрессии закрытого этапа. Однако исходный подробный договор требует их в обоих режимах; реализация BYREF сама по себе не устранит наблюдаемые проблемы BYVAL.

1. **Отдельные ячейки итераций отсутствуют.** `BoundProgramLowerer.ForEach.cs:179` сохраняет очередное значение в тот же слот. Воспроизведение `closure-cells.axm`: функция `Capture(BYREF value AS INTEGER)` возвращает локальную функцию, читающую `value`; две функции, созданные для элементов 1 и 2, после цикла выводят `2 2` вместо предусмотренных подробным планом `1 2`.
2. **Изменение формы не инвалидирует обход BYVAL.** Воспроизведение `foreach-redim.axm`: REDIM того же массива внутри цикла заменяет последующие читаемые значения, цикл выводит `1`, `0`, `done`. В `foreach-last-push.axm` ARRAYPUSH после единственного элемента вообще не обнаруживается, вывод `1`, `done`. Подробный договор требует MB3014 на следующем продвижении, включая продвижение после последнего элемента. Это нужно явно закрыть также для BYVAL и действительных представлений.

Прежние `CheckBoth` в новых классах Execution фактически вызывают один `Run`; имя метода не доказывает отдельную проверку наблюдаемого исполнения или восстановления байт-кода. Для новых состояний обхода требуется самостоятельная приёмка отладки, снимков и сериализации по плану этапа 6.
