# Направление развития составных типов Axiom

Дата: 22 октября 2026 года. Основание: просьба автора самостоятельно оценить дальнейшее развитие массивов, списков, кортежей и других составных данных, повторно изучив документы проекта и два внешних мнения.

Статус: аналитическое предложение. Новый синтаксис, названия, сроки и очередь реализации этим документом не утверждаются. Реализация языка и IDE не менялась. Текущая очередь пользовательской приёмки тем и восстановления сеанса сохраняется.

## Основной вывод

Сейчас разумно сохранить массивы основной последовательностью Axiom. Они уже умеют динамически расти, принимать вставки и удаления, поэтому отдельный список нельзя обосновать одной необходимостью добавлять элементы без REDIM. Прямые массивы массивов также не являются ближайшей необходимостью: строки разной длины уже выражаются массивом записей TYPE с динамическим массивным полем.

Предлагаемое направление: удобный обход существующих коллекций и литералы массивов; следующая самостоятельная структура — типизированный словарь; затем множество на согласованных правилах равенства и хеширования. Кортежи полезны для кратких составных результатов и распаковки, но уступают словарю по новизне возможностей: именованный результат уже возвращается через TYPE. Отдельный список и прямые вложенные массивы следует выбирать по программам, где нынешняя запись действительно мешает.

Это порядок по полезности для нынешнего языка, а не формальная зависимость всех этапов. Например, словарь можно проектировать без предварительной реализации литералов, кортежей, пользовательских обобщённых типов и генераторов.

## Оценка внешних мнений

### Отчёт Qwen

Источник: `C:\Users\comp\Downloads\jтчет qwen.md`.

Верны различие прямоугольных и нерегулярных массивов, польза словаря, возможность краткого возврата нескольких результатов и необходимость думать об общем обходе коллекций.

Однако вывод «кортежи и списки обязательно в следующем выпуске» не обоснован:

- Списки предлагаются ради автоматического роста, вставки, удаления и поиска, которые уже есть у массивов. Одномерный ARRAYPUSH уже использует запас ёмкости; REDIM на каждом добавлении не нужен.
- Пользовательская запись TYPE уже возвращает несколько разнородных полей. Кортеж сократит объявления, но не впервые сделает такой результат возможным.
- Вложенные списки вводят ту же задачу вложенных контейнеров, от которой отчёт предлагает отказаться в случае массивов. Замена названия эту сложность не устраняет.
- Запись `arr[0][1]` не обязательна для вложенных массивов. Синтаксис следует выбирать отдельно с учётом BASIC, нынешних круглых скобок и частичного индексирования, которое уже означает представление прямоугольного массива.
- Кортеж с разными типами компонентов не обязан участвовать в общем однородном обходе: иначе понадобится общий динамический тип, объединение или специальное правило.
- Словарь полезен для JSON, но одного однородного словаря недостаточно для произвольного рекурсивного JSON. Сам JSON можно реализовать и без встроенного словаря.

Фрагменты примеров в отчёте повреждены: вместо программ оставлены строки вроде `123456`. Они не подтверждают предложенный синтаксис или его согласованность с Axiom.

## Какие составные сущности стоит различать

Запись, кортеж и коллекция решают разные задачи. Первые связывают фиксированные компоненты одного значения; коллекции хранят изменяемое или фиксированное множество элементов. Вариантный тип выбирает одну из альтернатив, а не хранит все поля сразу.

| Сущность | Что представляет | Роль для Axiom |
|---|---|---|
| Запись TYPE | Именованные поля, возможно разных типов: человек, координата, результат поиска | Уже есть; основной выбор для предметных данных и публичных результатов функций. |
| Кортеж | Фиксированное число компонентов с типом каждой позиции | Краткий локальный результат и распаковка. Не является переменным списком; неизменяемость не следует из самого понятия кортежа и требует отдельного решения. |
| Массив | Однородные элементы с индексами и формой | Уже основной числовой, табличный и последовательный контейнер; поддерживает изменение размеров. |
| Динамический список | Упорядоченная последовательность, обычно с автоматическим ростом | Как возможность уже во многом покрыт одномерным массивом. Отдельный тип оправдан отличающимся договором, например единой индексацией и самостоятельным набором методов. |
| Связный список | Узлы и связи между ними | Другая структура, не синоним динамического списка. Низкий ближайший приоритет; требует модели ссылок или явных индексов узлов. |
| Словарь | Поиск значения по ключу | Наибольшая новая практическая польза: частоты слов, индексы, настройки, соответствия имён и ресурсов. |
| Множество | Уникальные элементы и операции принадлежности, объединения, пересечения | Полезно после договора равенства и хеширования. ARRAYDISTINCT уже решает одноразовое удаление повторов, но не заменяет изменяемое множество с повторными запросами. |
| Стек, очередь, двусторонняя очередь | Порядок добавления и извлечения | Стек частично уже выражается ARRAYPUSH/POP. Эффективная очередь требует отдельной организации, например кольцевого буфера; удаление начала массива не даёт автоматически постоянной стоимости. |
| Представление диапазона массива | Область существующего хранилища | Уже есть; не следует вводить второй общий тип среза без отличающейся потребности. |
| Перечисление | Закрытый набор именованных вариантов: направление, состояние | Отдельное полезное направление типизации, но не коллекция элементов. Принятого договора не найдено. |
| Объединение с признаком варианта | Одна из разных форм значения: число, строка, узел | Для разнородного JSON, сообщений, состояний и синтаксических деревьев. Требует правил проверки активного варианта; разумный более поздний этап. |
| Необязательное значение и результат операции | Значение либо отсутствие; успех либо ошибка | Небольшие специальные случаи объединений. Пока многие задачи решаются TYPE с BOOLEAN, BYREF и TRY/CATCH; новые формы нужно проектировать отдельно. |
| Дерево и граф | Связи между узлами | Обычно строятся из коллекций, записей и ссылок либо индексов. Прямой массив массивов сам по себе не создаёт поддержку циклических графов и рекурсивных типов. |

Итераторы и генераторы относятся к способу получения и обхода элементов. Они не обязательны для первого словаря или множества и не должны автоматически превращать каждый составной тип в коллекцию.

## Предлагаемый порядок развития

### 1. Удобство существующей модели

Рассмотреть FOR EACH сначала для массивов и короткие литералы однородных массивов как две самостоятельные небольшие задачи. Для обхода заранее определить порядок координат, значение или ссылку в переменной цикла, поведение при изменении формы исходника и работу с представлениями. Не требуется сразу вводить публичные интерфейсы и генераторы.

Перед выбором нового контейнера сравнить три короткие программы: накопление записей неизвестной длины, подсчёт частот по строковому ключу, возврат результата поиска с признаком успеха. Первая уже решается массивом, вторая лучше показывает пользу словаря, третья позволяет оценить удобство TYPE против будущего кортежа.

### 2. Типизированный словарь

Начать с конкретных задач доступа по ключу. Для первого договора достаточно ограниченных ключей — например, STRING и целых чисел; значения одного экземпляра словаря должны иметь один объявленный тип. Полноценные пользовательские обобщённые типы не являются обязательной предпосылкой встроенного параметризованного контейнера.

До реализации выбрать:

- сравнение строковых ключей, включая регистр; регистронезависимые имена Axiom не означают автоматически такой же договор строковых данных;
- повторное добавление ключа, замену значения и отсутствие ключа; безопасный поиск должен отличать отсутствие от нулевого или пустого значения;
- порядок обхода и его устойчивость;
- присваивание словаря, BYVAL/BYREF, хранение TYPE и массивов в значениях;
- изменение словаря во время обхода, снимки состояния и восстановление шагом назад.

Для первой безопасной формы поиска достаточно логического результата и выходного BYREF либо конкретной записи TYPE для результата: ждать кортежей и отдельного необязательного типа не нужно. Общего пользовательского Result<T> сейчас нет. Конкретное имя операции здесь не выбирается.

В RuntimeValueEqualityComparer уже есть поддержка хеширования скалярных и временных типов для ARRAYDISTINCT. Общего пригодного структурного хеша TYPE нет: неподдержанный вид получает 0. Изменяемые записи, массивы и произвольные DOUBLE-ключи с особыми значениями требуют отдельного договора; включать их в первую версию только ради универсальности не следует. [Текущий сравниватель](../../src/Axiom.Runtime/Values/RuntimeValueEqualityComparer.cs#L14).

### 3. Множество

Использовать согласованные со словарём правила равенства и хеширования. Проверять пользу на многократном добавлении, удалении и запросе принадлежности, а не только на операции, которую уже выполняет ARRAYDISTINCT. Не требуется предварительно публиковать универсальную иерархию контейнеров.

### 4. Кортежи и распаковка

Добавлять ради удобства небольших временных результатов, когда объявления TYPE повторяются и мешают чтению. Сначала решить тип каждой позиции, доступ к компонентам, правила присваивания/передачи и распаковки, сравнение и хранение вложенных изменяемых значений. Автоматическая глубокая неизменяемость не возникает от скобок вокруг массива.

Именованный TYPE должен сохранять свою роль: результат с полями Found и Index понятнее в публичном договоре, чем нерасшифрованные первая и вторая позиции. Кортежи и TYPE могут сосуществовать без вытеснения одного другим.

### 5. Прямые вложенные массивы и отдельный список

Это независимые решения, выбираемые по неудобству реальных программ. Для вложенных массивов нужны типы внутренних элементов, повторное индексирование, правила невыделенных внутренних массивов, общие ссылки и клонирование, ARRAYMAP, сериализация байт-кода и отображение в отладчике. Просто убрать запрет в ArrayTypeSymbol недостаточно.

Для отдельного списка сначала показать, какую задачу неудобно решать нынешним динамическим массивом и почему набора методов или удобной формы объявления недостаточно. Если нужен список списков, его семантика вложенности всё равно должна быть спроектирована. Связный список не предлагается как замена эффективному последовательному хранилищу.

Ни эта рекомендация, ни историческая отсрочка не означают отказа от списков или вложенных массивов навсегда.

## Общие правила, которые нельзя оставить неявными

Нынешняя семантика уже неоднородна и описана в справочнике:

- обычное массивное значение разделяет объект массива при присваивании и BYVAL;
- TYPE копирует скалярные поля и вложенные записи;
- фиксированные массивные поля копируются;
- обычное динамическое массивное поле сохраняет общий массив;
- строковые массивные поля фиксированной длины копируются с нормализацией;
- наличие массивного поля исключает структурное сравнение TYPE.

Это существующий договор, а не установленная этим аудитом ошибка. Новые контейнеры должны явно определять свои правила и согласовываться с ним; общей переделки всех типов перед словарём не требуется. Снимки для отладочного шага должны сохранять структуру общих ссылок и независимость от продолжающегося исполнения; обычный CopyForStorage не подменяет снимок графа.

Названия новых форм следует отдельно проверить по семейству BASIC и допустимым проектным прецедентам. Написания LIST, DICTIONARY, MAP, SET и обозначения обобщённых типов в обсуждении называют понятия, а не утверждают ключевые слова или синтаксис Axiom.
