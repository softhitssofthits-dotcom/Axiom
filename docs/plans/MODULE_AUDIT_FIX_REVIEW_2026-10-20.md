## 2. Дополнительно подтверждённые и исправленные дефекты

### P1. Снимок терял структуру вложенных функциональных типов

Место: `src/Axiom.Bytecode/Serialization/BytecodeModuleSerializer.cs`, методы `TypeReference`, `ResolveFunctionType`, `TryResolveArrayType`. При восстановлении `FUNCTION(FUNCTION(Box, INTEGER) AS INTEGER) AS INTEGER` разделение по каждой запятой и первому `) AS` разрушало вложенную сигнатуру. Окончание массива также смешивало массив функций с функцией, возвращающей массив. Ожидалось сохранение точного типа, ранга и BYREF; фактически возникало исключение либо другой тип. Это нарушало выполнение и проверку сохранённого байт-кода.

Исправление: рекурсивные ссылки по идентичности TYPE, поиск парной скобки и разделение параметров только на верхнем уровне. Схема 3 группирует массивы функций: `(FUNCTION() AS Box)()`. Для схемы 2 сохранён прежний порядок разбора. Тесты `ModuleArtifactIdentityRegressionTests` проверяют пять вложенных сигнатур и структурно различают массив функций и функцию, возвращающую массив. Падения до исправления сохранены в локальных журналах проверки.

### P1. Неоднозначная ссылка могла снова объединить закрытые TYPE

Места: тот же сериализатор, `BytecodeModuleValidator.MatchesTypeIdentity`, `BytecodeVm.Records.MatchesTypeIdentity`. После введения `модуль::Имя` оставалось безусловное сравнение по короткому имени при поиске CreateRecord. Неизвестный тип мог превращаться в пустой пользовательский TYPE, повторное определение идентичности игнорировалось. При повреждённом либо вручную составленном снимке это позволяло выбрать неверную запись вместо отказа.

Исправление: CreateRecord сопоставляется с точной идентичностью; неоднозначные ссылки и повторные определения отклоняются. Короткие имена старых снимков поддерживаются, поскольку у восстановленных типов схемы 2 сама идентичность является коротким именем. Регрессии проверяют повторное определение, неоднозначную ссылку параметра, неоднозначный операнд CreateRecord и выполнение восстановленных независимых записей с разными начальными значениями.

Совместимость подтверждена не удалением поля версии из нового JSON: `Fixtures/record-schema2.json` создан старым сериализатором из проверяемого commit, встроен в тестовую сборку, восстанавливается, проходит валидатор и печатает 17.

### P2. Отменённый переход отладчика мог запустить повторное открытие

Место: `ide/src/renderer/trace-controller.js`, ветка открытия закрытого документа. После отменённого либо неудачного `openFile` повторный `mark` мог начать новое чтение с уже другой моделью редактора. Для события без stopId выбиралась любая текущая остановка. Следствие — повторные попытки и возможный переход к старому документу после намеренного действия пользователя.

Исправление: фиксируется исходная остановка; повторная установка маркера допустима только при действительно открытой целевой модели, которая остаётся активной. `trace-late-open.test.cjs` содержит семь сценариев, включая Stop, новую остановку, намеренную смену модели, отказ чтения и восстановление без явно переданного stopId. Проверки выполняют настоящие методы открытия файла и установки маркера с управляемой задержкой чтения.

### P2. Ошибка файловой системы имела нулевые координаты JSON

Место: `src/Axiom.Cli/CliApp.cs`, `TryLoadDependencies`. Новая MB4004 создавалась с `default(TextLocation)`: `check --json` возвращал line=0 и col=0 вместо принятой в CLI нумерации с единицы. Исправлено на диапазон начала файла, 1:1. `CliDependencyFailureTests` проверяет код завершения 2, код MB4004, корректный JSON и координаты; отсутствие модуля отдельно остаётся MB2049 с кодом завершения 1. В новом тесте также исправлено ошибочное ожидание имени поля `column`: существующий договор использует `col`.

## 3. Неоднозначности и потенциальные проблемы

Категории экспортов уточнены по существующим путям связывания и закреплены тестами: SUB/FUNCTION; DIM/CONST; TYPE. Неоднозначность возникает внутри категории. Разные категории могут иметь одинаковые имена; при вызове порядок — конструктор TYPE, переменная, подпрограмма. Вызов INTEGER-переменной не выбирает одноимённую функцию автоматически, а даёт MB2020. Это задокументированное существующее поведение, а не изменение языка ради предпочтения проверяющего.

Предельный размер графа модулей, бюджет памяти и отмена длительного связывания не измерялись. Без измерений и утверждённого ограничения они не объявляются дефектом. Безопасное переименование, квалифицированный доступ и вложенные папки не добавлялись: это отдельные возможности, не обязательные исправления аудита.

## 4. Мёртвый и дублирующийся код

Новых доказанных участков мёртвого кода не найдено. Проверено устранение живого дублирования проходов Binder: однофайловый и модульный пути используют общие объявления и связывание с разной политикой экспорта. Общий `BoundTreeTraversal` используется индексом символов и графом вызовов; тесты проверяют вложенные контейнеры и отдельные рёбра обработчиков. Публичные API и диагностические коды не удалялись на основании одного текстового поиска.

## 5. Организация кода

Принято разделение `Binder.Modules.cs`: `ModuleModels.cs` содержит модели, `Binder.Modules.Graph.cs` — граф и порядок, `Binder.Modules.Exports.cs` — импорт, экспорт и доступность. Общие проходы остаются в Binder. `BoundTreeTraversal` расположен в Semantics, DesktopHost зависит от него; обратной зависимости нет. Практическая польза — одна реализация каждого прохода и обхода при сохранении разной политики потребителей. Дополнительного разделения только из-за размера файлов не предлагается.
