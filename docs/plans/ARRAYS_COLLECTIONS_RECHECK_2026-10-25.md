# Повторная проверка исправлений массивов и FOR EACH

Дата: 25 октября 2026 года. Основание — отчёт агента о закрытии R1–R8 и Session 1652. Проверено текущее рабочее дерево поверх `d46bc11`: исправления ещё не закоммичены. Исходный [отчёт проверки](ARRAYS_COLLECTIONS_REVIEW_2026-10-25.md) сохранён.

Повторный запуск прежних воспроизведений подтвердил исправление их конкретных случаев. Однако объявлять R1–R8 полностью закрытыми преждевременно: дополнительные случаи выявили четыре проблемы. Реализация при повторной проверке не менялась.

## Подтверждённые оставшиеся проблемы

### S1. P2 — экспорт строковых констант аварийно завершается при совпадении имён

Место: `src/Axiom.Semantics/Binding/Binder.Modules.Exports.cs:156`. В новый словарь экспорта попадают все зарегистрированные строковые константы с подходящим именем, а не только символы из `publicVariables`. Отвергнутое локальное объявление всё равно зарегистрировано в `_boundStringConstants`, и `ToDictionary` получает два одинаковых ключа.

```basic
PUBLIC CONST priceField AS STRING = "Price"
SUB F()
    CONST priceField AS STRING = "Name"
END SUB
```

Команда `check` завершает процесс с необработанным `ArgumentException: An item with the same key has already been added. Key: priceField`, код Windows `-532462766`. Ожидается обычная диагностика недопустимого повторного имени. Воспроизведение не требует IMPORT: PUBLIC достаточно для модульного пути связывания.

Исправить выбор экспортируемых констант по идентичности публичных символов, сохранив нормальную диагностику ошибочной программы. Простая замена `ToDictionary` с подавлением повторов не решает неверный отбор локальных символов.

Программа и полный стек: `.artifacts/arrays-roadmap-review-round2/duplicate-string-constant.axm`, запись в `new-cases.json`.

### S2. P2 — контекст DECIMAL не применяется к числовым элементам литерала

Место: `src/Axiom.Semantics/Binding/Binder.Expressions.cs:225`. Новая предварительная проверка использует только совпадение типа и `CanConvert`. Она отклоняет элемент до того, как `ApplyExpectedType` смог бы применить `TryConvertConstant` и разобрать текст числа в ожидаемом типе.

Положительный контроль:

```basic
DIM amount AS DECIMAL = 0.1
PRINT amount
```

Контроль успешно выполняется, вывод `0.1`. Соответствующий массив:

```basic
DIM amounts[] AS DECIMAL = [0.1]
PRINT amounts[1]
```

Отклоняется с MB2060: DOUBLE якобы несовместим с DECIMAL. Хотя ожидаемый тип известен и обычное связывание числового литерала поддерживает точный DECIMAL, новая предварительная проверка не даёт его применить. Нужно использовать тот же договор контекстного преобразования для элементов, сохранив отказ действительно недопустимого сужения вроде `[1, 2.5]` в INTEGER[].

Воспроизведения: `decimal-scalar.axm` и `decimal-array.axm` в каталоге повторной проверки. Это незакрытая часть R6, а не повторение прежней ошибки BC4116.

### S3. P2 — пустой литерал всё ещё теряет контекст во встроенных вызовах

Место: `src/Axiom.Semantics/Binding/Binder.BuiltinInvocations.cs:254`. Специальная обработка распознаёт только непосредственный `ArrayLiteralExpressionSyntax { IsEmpty: true }`, а не литерал внутри круглых скобок.

```basic
PRINT JOIN([], "-")
```

Успешно выполняется и выводит пустую строку. Эквивалентная группировка:

```basic
PRINT JOIN(([]), "-")
```

Отклоняется с MB2059, хотя параметр JOIN уже задаёт STRING[]. Скобки внутри вызова не должны лишать выражение этого контекста. Исправление передачи типа через скобки действует в DIM/CONST/присваивании, но начальный вызов связывания встроенного аргумента здесь всё ещё выполняется без типа.

Сходный подтверждённый пропуск — `Binder.BuiltinInvocations.cs:460`: второй аргумент ARRAYCONCAT связывается без ожидаемого типа уже известного первого массива.

```basic
DIM a[] AS INTEGER = [1]
DIM b[] AS INTEGER = ARRAYCONCAT(a[], [])
PRINT ARRAYLENGTH(b[])
```

Фактически MB2059 вместо массива длиной 1. Для второго аргумента тип INTEGER[] уже известен. Этот пробел существовал до последней правки; повторная проверка обнаружила его как незавершённую передачу контекста, а не как доказанную новую регрессию.

Воспроизведения: `join-empty.axm`, `join-grouped-empty.axm`, `arrayconcat-empty.axm`.

### S4. P2 — цепочка известных строковых констант не подходит для сортировки

Место: `src/Axiom.Semantics/Binding/Binder.DeclarationStatements.cs:181`. Реестр `_boundStringConstants` пополняется только для непосредственного `BoundLiteralExpression`; константное имя справа не разрешается через уже накопленные значения.

```basic
TYPE Product
    Price AS INTEGER
END TYPE
CONST firstField AS STRING = "Price"
CONST secondField AS STRING = firstField
DIM basket[1 TO 2] AS Product
ARRAYSORT(basket[], secondField)
```

Фактически MB2057: имя поля якобы неизвестно при проверке. Оба объявления констант допустимы, и значение `firstField` уже известно. Прямое использование `firstField` работает, косвенное через `secondField` — нет. Поэтому R8 закрыт только для непосредственного литерального инициализатора. Сохранение значения константы должно использовать уже добавленный `TryResolveConstantStringName` либо эквивалентное разрешение известных констант.

Воспроизведение: `const-alias.axm`.
