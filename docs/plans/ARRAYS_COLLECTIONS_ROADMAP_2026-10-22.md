# План развития массивов и коллекций Axiom

Дата: 22 октября 2026 года. Статус: составление и обсуждение плана; реализация ещё не выполняется.

**Цель:** сначала устранить подтверждённые недочёты массивов, затем улучшить запись и обработку данных, после этого вводить новые структуры с самостоятельной пользой.

**Технический подход:** сохранить действующие типы и правила хранения, переиспользовать функциональные параметры, отдельно проверять новые синтаксические формы. Каждый этап должен давать законченный результат с проверками и запускаемыми примерами. Крупные изменения внутреннего хранения выполнять последними, через измеряемый опыт.

**Стек:** C#/.NET 10, BytecodeVm, Electron/Monaco, действующие группы проверок из `docs/TESTING.md`.

Основание — [независимый аудит](ARRAYS_EVOLUTION_INDEPENDENT_AUDIT_2026-10-22.md) и последующие решения автора. Этот документ задаёт последовательность по теме массивов; действующая очередь других задач IDE не переопределяется. Начало реализации требует отдельного поручения автора. Старый [подробный план FOR EACH](FOR_EACH_IMPLEMENTATION_2026-10-22.md) используется внутри этапа 6, а не как команда немедленно начать работу.

## Принятые решения

1. Поддержать массивные инициализаторы **с явным и с выведенным типом**. Последнее решение автора отменяет промежуточный выбор только явного типа. Прежний вывод типа скалярных переменных сохраняется.
2. `FOR EACH` внедряется **одним завершённым этапом с обоими режимами — `BYVAL` и `BYREF`**. Внутренние действия выполняются последовательно, но этап не объявляется завершённым после одного режима.
3. При обсуждении каждого нового договора показывать короткие программы Axiom с фруктами, оценками, инвентарём и ожидаемым результатом. Предлагаемый синтаксис явно отличать от уже работающего.
4. Предпочтение явного типа в учебных по смыслу пояснениях и примерах можно использовать для читаемости; обязательный запрет неявной формы не вводится. В справочнике сохраняется его формальный жанр.

## Общая последовательность

| Этап | Результат | Почему расположен здесь |
|---|---|---|
| 1 | Быстрые вставка и удаление в конце массива | Самое локальное изменение существующего выполнения |
| 2 | Работающие массивные инициализаторы | Устранение подтверждённого разрыва между связыванием и понижением |
| 3 | Эффективное удаление повторов записей `TYPE` | Завершение адресных улучшений существующих массивов |
| 4 | Сортировка массива записей по выбранному полю | Переиспользование имеющихся функциональных параметров |
| 5 | Простое создание массивов из набора значений | Новая краткая форма с проверяемым договором типов и границ |
| 6 | `FOR EACH` с `BYVAL` и `BYREF` | Новый синтаксис, области видимости, адреса элементов и отладочные снимки |
| 7 | Типизированный словарь | Первая новая самостоятельная коллекция |
| 8 | Типизированное множество | Использует уже проверенные правила хеширования словаря |
| 9 | Кортежи и распаковка | Новые составные типы, вывод типов и правила доступа |
| 10 | Экономное внутреннее хранение числовых массивов | Наиболее широкое изменение представления данных и VM |

Сначала идут локальные исправления, затем новые формы и типы, последней — перестройка хранения. Это порядок по сложности и зависимостям, а не обещание, что каждый следующий этап обязательно потребует больше строк кода: множество после готового словаря может оказаться проще самого словаря.

## Этап 1. Быстрые вставка и удаление в конце

- [ ] Поднять проверки из аудита для `ARRAYINSERT` в конец и `ARRAYREMOVE` последнего элемента.
- [ ] В `src/Axiom.Runtime/Execution/BytecodeVm.Builtins.Array.cs` направлять применимые одномерные случаи к существующим быстрым операциям `RuntimeArrayValue`, сохранив общий путь для остальных случаев.
- [ ] Проверить пустой массив, произвольную нижнюю границу, переполнение верхней границы, фиксированные строки, `TYPE`, представления и инвалидирование. Порядок проверок и наблюдаемые диагностики сохраняются.
- [ ] Повторить измерение последовательностей операций для нескольких размеров. Показать уменьшение выделений/времени на одинаковом результате; не устанавливать зависимые от машины пороги в функциональных тестах.

Понятный работающий пример:

```basic
DIM fruits() AS STRING
REDIM fruits(1 TO 0)
ARRAYINSERT(fruits, 1, "яблоко")
ARRAYINSERT(fruits, 2, "банан")
PRINT ARRAYREMOVE(fruits, 2)
PRINT fruits(1)
```

Результат остаётся `банан`, затем `яблоко`. Меняется стоимость действий, а не содержимое корзины.

Основные файлы: `src/Axiom.Runtime/Execution/BytecodeVm.Builtins.Array.cs`, `src/Axiom.Runtime/Values/RuntimeArrayValue.cs`, существующие `tests/Axiom.Execution.Tests/ArrayEmptyInsertContractTests.cs`, `ArrayDynamicShapeContractTests.cs`, `ArrayMutationUnicodeEvidenceTests.cs`. Постоянную отдельную проверку добавить рядом с этими тестами для обоих быстрых путей. Приёмочные программы — `samples/functions/arrayinsert/append_at_upper_bound.axm` и `samples/functions/arrayremove/remove_last_element.axm`.

Проверки: `scripts/test.ps1 execution -Filter Array`, при затрагивании хранения также `scripts/test.ps1 runtime -Filter Array`; команды выполнять последовательно. Готовность: прежний договор и диагностики сохранены, представления инвалидируются в тех же случаях, измерение подтверждает устранение повторного пересоздания хранилища в выбранных случаях.

## Этап 2. Массивные инициализаторы

- [ ] Добавить независимые проверки обеих выбранных автором форм с результатом `банан`.
- [ ] В `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.Declarations.cs` довести принятый связывателем массивный инициализатор до вычисления выражения и сохранения значения в переменную вместо отказа `BC3001`.
- [ ] Сохранить однократное вычисление выражения и нынешние правила общего массива, копирования записей, фиксированных строк и преобразования типов. Отдельно проверить инициализацию представлением.
- [ ] Проверить ранг, несовместимые типы, пустой/невыделенный результат, функцию с побочным эффектом, локальные и глобальные объявления, исполнение восстановленного байт-кода.

Будущие рабочие формы после этого этапа:

```basic
DIM fruits = SPLIT("яблоко,банан,апельсин", ",")
PRINT fruits(2)
```

```basic
DIM fruits AS STRING () = SPLIT("яблоко,банан,апельсин", ",")
PRINT fruits(2)
```

Обе программы выводят `банан`. Во второй тип читается непосредственно из объявления, в первой определяется по результату `SPLIT`. Разрешение инициализатора в отдельной форме `DIM fruits() AS STRING = ...`, где скобки стоят у имени, не следует автоматически из этих двух примеров: прежде чем расширять и её, отдельно согласовать смысл объявления с заданными границами.

Основные файлы: `src/Axiom.Semantics/Binding/Binder.DeclarationStatements.cs`, `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.Declarations.cs`; новые адресные проверки в `tests/Axiom.Execution.Tests/` и существующие проверки объявлений/понижения в `tests/Axiom.Bytecode.Tests/`. Приёмочные программы — `samples/operators/dim/array_initializer_explicit.axm`, `array_initializer_inferred.axm`.

Проверки: `scripts/test.ps1 bytecode -Filter Array`, `scripts/test.ps1 execution -Filter Array`; при изменении связывания — адресная группа `semantics`. Готовность: обе формы выполняются свежей сборкой, неподдержанные сочетания получают согласованные диагностики, `check` и `run` не расходятся. В справочнике `dim.html` и главе массивов описаны обе формы.

## Этап 6. FOR EACH — оба режима одним завершённым этапом

- [ ] Сначала адресно воспроизвести указанную старым планом проблему `CONTINUE` в смешанных циклах. Если подтверждена, исправить её как подготовительную часть с отдельными ожиданиями, включая `TRY/FINALLY`.
- [ ] Реализовать общий синтаксис и связывание обоих режимов по [подробному плану](FOR_EACH_IMPLEMENTATION_2026-10-22.md), сохраняя числовой `FOR` и существующие имена `EACH`/`IN` вне контекста заголовка.
- [ ] Реализовать обход значений и адресов элементов, однократное вычисление источника, произвольные границы, многомерные массивы и представления. Определённая прежним планом реакция на изменение формы проверяется также после последнего элемента.
- [ ] Проверить отдельные ячейки итераций, захват через вызванные функции, фиксированные строки, `TYPE`, `EXIT`, `CONTINUE`, исключения, сохранение байт-кода и обратный шаг.
- [ ] Доставить оба режима в форматтер, подсветку, навигацию и отладчик. Этап закрывается только после приёмки обоих режимов.

Предлагаемые новые формы. Исходный массив оценок содержит 3 и 4:

```basic
FOR EACH grade IN grades
    grade = grade + 1
NEXT grade
```

Массив сохраняет оценки 3 и 4: меняется переменная цикла.

```basic
FOR EACH BYREF grade IN grades
    grade = grade + 1
NEXT grade
```

Массив получает оценки 4 и 5: меняются его ячейки. Для записей и вложенных динамических массивов действуют правила обычного копирования Axiom, а не обещание глубокой независимости.

Файлы и подробная приёмка перечислены в старом предметном плане: синтаксис/парсер, связывание и понижение циклов, адреса слотов VM, `RuntimeSnapshotFactory.cs`, `BytecodeVm.Debug.cs`, `ide/src/renderer/lang-features.js`, `semantic-colors.js`, темы, форматтер и `BlockLineClassifier`. Примеры — `samples/control-flow/for/each_byval.axm`, `each_byref.axm`, `each_multidimensional.axm`, `each_resize_invalidates.axm`.

Группы по затронутому подэтапу: `syntax`, `parser`, `semantics`, `bytecode`, `runtime`, `execution`, `ide-backend`, `ide-unit-renderer`, выбранные Electron-проверки редактора и отладки. Для длинного Electron-прогона использовать `-Out` и при продолжении `-From`. Без завершения обоих режимов этап остаётся открытым.

## Что пока не включено в обязательные десять этапов

Прямые массивы массивов остаются отдельным кандидатом для графов и вложенных данных. Сначала показать реальную программу, где массив `TYPE` с массивным полем заметно мешает. При подтверждении её полезность может оказаться выше кортежей; тогда автор явно меняет порядок очереди.

Отдельный динамический список, связный список, разнородная универсальная коллекция, пользовательские обобщённые типы, ленивые последовательности и генераторы не добавляются ради полноты набора. Для каждого нужен самостоятельный пользовательский сценарий и отличимый договор.

## Правила исполнения каждого этапа

1. До изменения новых форм согласовать только относящиеся к этапу вопросы через короткие программы и ожидаемый вывод. Решённые вопросы повторно не поднимать без нового противоречия.
2. Перед реализацией сверить существующие тесты и добавить адресные ожидания для изменяемого поведения. Для найденного дефекта сначала получить воспроизведение. Измерения не подменяют функциональные проверки.
3. После изменения языка обновить `docs/SPECIFICATION3.md`, соответствующие страницы `docs/manual/`, IDE-поддержку новых сущностей и запускаемые примеры. При изменении архитектуры обновить `docs/ARCHITECTURE.md`.
4. При изменении покрытия/семейств измерений обновить `BYTECODE_COVERAGE.md`/`BYTECODE_PERF_MATRIX.md` по их назначению. Для изменения только внутренней скорости не заявлять новую языковую форму.
5. Выбирать наименьшие группы по `docs/TESTING.md`; .NET-команды выполнять последовательно. Полный `all` не запускать без отдельного основания.
6. Повышать только фактически изменившиеся продуктовые компоненты по `docs/VERSIONING.md`. План и обсуждение не требуют повышения. До завершения выполнять `node scripts/versioning.mjs check`, `node scripts/versioning.mjs check --base HEAD`, `git diff --check`.
7. В конце каждого этапа записать выполненное, доказательства и следующий шаг в `WORKLOG5.md` и добавить состояние в конец `PLANS4.md`. Не переходить к следующему этапу незаметно для автора, когда его поручение ограничено текущим этапом.
