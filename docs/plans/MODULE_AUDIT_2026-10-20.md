# Аудит многомодульных программ Axiom — 20 октября 2026 года

Проверяемый commit: `d4042653592f3e61897cce146735157c76c5d290`. Аудит выполнен без исправления исходников. Подтверждения и изолированные программы: `.artifacts/module-audit-20261020/`. Номера: язык 0.2.1, компилятор 0.2.3, IDE 0.6.35.

## 1. Вывод, договор и карта подсистемы

Основной многомодульный путь реализован: файл является модулем; SUB, FUNCTION, TYPE, DIM и CONST закрыты по умолчанию; PUBLIC открывает имена; IMPORT задаёт явные зависимости. Работают инициализация зависимостей, закрытые функции и переменные с одинаковыми именами, функциональные значения, BYREF, снимки открытых зависимостей, документные диагностики, отладка, граф вызовов и переходы по символам. Найдены семь подтверждённых дефектов. Наиболее существенный — потеря идентичности одноимённых закрытых TYPE после связывания. Она блокирует обычную компиляцию корректной программы и отдельно искажает сериализованный модуль.

Действующий договор взят из PROJECT, SPECIFICATION3, ARCHITECTURE, последних записей PLANS4/WORKLOG5 и справочника modules.html, import.html, visibility.html. Исследование MULTIFILE_RESEARCH_2026-10-19 и исходные пункты ROUTINES_AND_MULTIFILE_PLAN описывают предыдущие состояния. Их незакрытые исторические флажки не являются доказательством отсутствия позднее реализованной возможности. Завершение модулей записано после ROUTINES_IMPLEMENTATION_REVIEW_2026-10-19; затем выполнены PROJECT_SNAPSHOTS, MODULE_NAVIGATION и PROJECT_SYMBOL_INDEX.

Не входят в принятый объём: циклы IMPORT, псевдонимы, квалифицированные имена, вложенные папки, автоматическое обнаружение всех импортирующих файлов, безопасное межфайловое переименование и встроенные окна провайдеров Monaco. Их отсутствие не объявляется багом.

## 2. Подтверждённые дефекты

### MOD3-001 — P1. Короткое имя TYPE подменяет идентичность модуля

**Места:** `src/Axiom.Bytecode/Emission/BytecodeCompiler.Emission.cs:644–646`; `src/Axiom.Bytecode/Diagnostics/BytecodeModuleValidator.cs:3538–3604`; `src/Axiom.Runtime/Execution/BytecodeVm.Records.cs:77–149,211`; `src/Axiom.Bytecode/Serialization/BytecodeModuleSerializer.cs:539,580,609–613`.

**Сценарий:** main импортирует first и second. Оба файла объявляют закрытый TYPE Box; в первом поле Item имеет тип INTEGER, во втором STRING. FirstRead и SecondRead создают локальный Box и возвращают поле. Ожидание по SPECIFICATION3: закрытые имена разных файлов независимы; вывод 11 и hello. Фактически Compile и Run завершаются BackendFailure/BC4116: «ожидает ... Box, но получила Box». Сбой повторён через настоящий CLI, а не только API. Даже без явного конструктора, при DIM item AS Box, ошибка сохраняется.

**Причина:** LoweredInstruction ещё содержит ValueType, но EmitCreateRecord передаёт в константу только DisplayName. Валидатор находит первый TYPE с таким Name среди всего модуля, а VM ведёт кэш по тому же короткому имени. Связывание правильно различило типы, последующие слои различие потеряли.

**Отдельное подтверждение сериализации:** корректный модуль с двумя подпрограммами, принимающими каждый свой закрытый Box, компилируется без создания записей. До ToArtifact/FromArtifact типы параметров различны, поля INTEGER и STRING. TypeDefinitions содержит одну запись; после восстановления типы тождественны, оба поля INTEGER. Это наблюдение над публичным API сериализатора; внешняя загрузка сохранённой программы как отдельный продуктовый путь здесь не объявляется реализованной.

**Последствия:** независимые модули нельзя безопасно компоновать при совпадении частного имени TYPE; снимок может молча потерять различие типов. Одного исправления словаря сериализатора недостаточно.

**Исправление:** ввести устойчивую идентичность TYPE внутри компиляции и артефакта, использовать её в CreateRecord, валидаторе, VM и ссылках типов, сохранив Name для сообщений. Согласовать версию схемы/совместимость артефакта. Проверить вложенные массивы и функциональные сигнатуры.

**Регрессионные тесты:** Compile/Run для двух одинаково названных частных TYPE с одинаковыми и разными полями; обычная инициализация, конструкторы и методы; отрицательная передача одного типа вместо другого; ToArtifact/FromArtifact должны сохранить две идентичности и обе схемы полей.

**Доказательства:** private-types/*.axm, private-types/check.json, private-types/stderr.txt; harness/Program.cs; случаи same-private-type-names, same-private-type-defaults и serialization-private-types в matrix-output.txt.

### MOD3-002 — P2. Ошибка чтения зависимости выходит из axiom check исключением

**Места:** `src/Axiom.Cli/CliApp.cs:184,194–199`; загрузка `src/Axiom.Execution/Requests/SourceProject.cs:58–62`; отсутствие общего перехвата в `src/Axiom.Cli/Program.cs:46`.

**Сценарий:** main импортирует helper, файл helper открыт другим владельцем с FileShare.None. Входной main читается успешно. Ожидается контролируемое сообщение stderr и ненулевой код команды, как для основной программы и для run. Фактически CliApp.Run команды check выбрасывает IOException. Тот же run возвращает 1 и сообщение axiom: The process cannot access the file.

**Причина:** ReadSource защищает только точку входа. RunProgram перехватывает сбои LoadDependencies, а RunCheck/CheckSource — нет. Обычная точка входа не перехватывает выброшенное исключение; вывод о необработанном завершении exe следует из этого пути. Сам аварийный процесс exe в опыте не запускался: использован внутренний метод CLI через отражение, с сохранением исходного IOException.

**Последствия:** нарушение договора CLI и потеря корректного JSON-ответа у check --json при внешнем сбое файла.

**Исправление:** общий контролируемый путь загрузки исходников/зависимостей для check и run с определённым результатом ошибки и контрактом JSON. Не скрывать отсутствие модуля как ошибку файловой системы: неизвестный IMPORT должен остаться языковой диагностикой.

**Регрессионный тест:** блокировка, удаление или недоступность зависимости в момент чтения; check и check --json не выбрасывают исключений, run остаётся согласованным. Сохранённый опыт locked-dependency-check/run находится в matrix-output.txt; код блокировки — harness/Program.cs.

### MOD3-003 — P2. Фоновая проверка главного файла удаляет ошибку исполнения зависимости

**Место:** `ide/src/renderer/app.js:1314–1317`, AxiomIDE.runLiveCheck.

**Сценарий:** ошибка выполнения helper уже записана с executionSnapshot, main активен, затем завершается фоновый document.analyse(main), ошибок компиляции не обнаружено. Тексты снимка не менялись. Ожидание: сохранить действующую ошибку запуска независимо от файла происхождения. Фактически _lastDiagnostics становится пустым: фильтр сохраняет только d.file === filePath. При очистке только активной модели маркер helper может остаться без соответствующей записи панели.

**Причина:** однофайловое ограничение в защите неизменённого снимка. Комментарий этого же участка прямо обещает сохранность ошибки исполнения при позднем фоновом ответе; проверка diagnosticMatchesSnapshot уже умеет проверять документную идентичность.

**Исправление:** сохранять актуальные ошибки всех документов текущего снимка, согласовать очистку списка и маркеров, не возвращать ошибки после правки/закрытия/повторного открытия другой модели.

**Регрессионный тест:** main + helper, ранняя фоновая проверка main и позднее выполнение helper; неизменённая ошибка сохраняется, после правки соответствующего документа исчезает. Реальный runLiveCheck проверен в изолированном каркасе: 7 прежних случаев проходят, новый падает.

**Доказательства:** ide-snapshot/runtime-preservation.test.cjs:104 и runtime-preservation.log. Это модульное воспроизведение на настоящем методе IDE, а не утверждение о выполнении нового сценария Electron.

### MOD3-004 — P2. Отладчик активирует старый документ после Stop

**Места:** `ide/src/renderer/trace-controller.js:39–42`; фактическое открытие и активация `ide/src/renderer/app.js:898–916`.

**Сценарий:** остановка в закрытой зависимости начинает медленное чтение файла; пользователь нажимает Stop или переходит к другой остановке; чтение заканчивается. Ожидается отмена устаревшего перехода. Фактически helper открывается и становится активным уже после Stop.

**Причина:** mark передаёт openFile только путь; доступный параметр isCurrent не используется. stopId сравнивается в then, когда openFile уже создал модель и вызвал switchToFile. Аналогичный переход ProgramAssistant использует защитную функцию.

**Исправление:** проверять сессию и остановку до открытия и после чтения через существующий isCurrent; при необходимости учитывать намеренную смену модели пользователем. Отмена не должна удалять уже открытый пользователем документ.

**Регрессионный тест:** задержать API.readFileContent, начать mark, выполнить Stop/новую остановку, завершить чтение; прежний документ не активируется и маркер не восстанавливается. Проверены реальные TraceController и AxiomIDE.openFile, подменено только файловое чтение и минимальное окружение редактора.

**Доказательства:** navigation/trace-real-open.cjs и trace-real-open.json: realTraceController=true, realOpenFile=true, afterStop=[helper.axm].

### MOD3-005 — P2. Ошибка одного выражения удаляет подсказки импортов

**Места:** `src/Axiom.DesktopHost/DocumentCommands.cs:54–61`; возврат неуспешной компиляции в AxiomExecutionPipeline; `Binder.EditorHover.cs:16–22`.

**Сценарий:** правильный helper экспортирует Answer. В main записаны IMPORT helper и PRINT Answer(). Подсказка Answer есть. Добавление отдельного PRINT missing удаляет её; добавленный корректный локальный localCount продолжает иметь подсказку.

**Ожидание:** корректно связанный импортированный символ не должен терять редакторскую информацию из-за ошибки другого выражения. Это подтверждается уже существующим терпимым путём GetEditorHovers: локальные символы собираются после связывания с диагностикой, а не требуют исполнимой программы. Фактическая асимметрия проверена сравнением двух классов символов через настоящий DesktopHost.

**Причина:** импорты для редакторского связывания извлекаются только из успешного compilation.CompiledProgram. При ошибке CompiledProgram=null, после чего GetEditorHovers получает пустой список импортов. Доступность импортов оказывается зависима от выпуска байт-кода всего main.

**Исправление:** строить редакторские метаданные на частичном модульном связывании с сохранением экспортов корректных зависимостей, без обязательной успешной компиляции всего проекта. Ошибочные или закрытые имена не подменять предположениями.

**Регрессионный тест:** корректный импорт при посторонней семантической и синтаксической ошибке; различать неверный экспорт и ошибку независимой строки. Доказательство: host-probes.cjs/json, valid, invalid и invalid-local-control; в последнем остаётся localCount, но исчезает Answer.

### MOD3-006 — P3. Самоимпорт единственного файла ошибочно объявляется неизвестным модулем

**Места:** `src/Axiom.Execution/Pipeline/AxiomExecutionPipeline.cs:143–151`; `src/Axiom.Semantics/Binding/Binder.cs:66–70`.

**Сценарий:** main.axm содержит IMPORT main. CLI получает только точку входа; загрузчик правильно не добавляет её повторно. Ожидается MB2052 о самоимпорте. Фактически MB2049 сообщает, что модуль <single> импортирует несуществующий main. При добавлении в API любого неиспользуемого документа появляется правильный MB2052.

**Причина:** однофайловая ветвь передаёт дерево в Binder.Bind, а модульному пути назначается искусственное имя <single>, несмотря на известный SourceName.

**Исправление:** сохранять реальное имя именованной точки входа и в случае пустых зависимостей. Сохранить совместимость безымянного однофайлового API.

**Регрессионный тест:** самоимпорт сохранённого файла через Compile, Run и CLI с пустыми/непустыми AdditionalDocuments; одинаковый код и корректный документ. Программа всё равно отвергается, поэтому это ошибка диагностики, а не обход запрета циклов.

**Доказательства:** self-import/*.axm, check.json, stderr.txt; self-alone и self-with-extra в matrix-output.txt.

### MOD3-007 — P3. Подсказка скрывает настоящий THIS и показывает неявный SELF

**Места:** `src/Axiom.Semantics/Binding/Binder.EditorHover.cs:39`; создание скрытого параметра `Binder.Declarations.cs:881`; правильный соседний путь `src/Axiom.DesktopHost/EditorCallGraph.cs:122`.

**Сценарии:** метод Counter.Set(value AS INTEGER) показывается как SUB Set(BYREF SELF AS Counter, value AS INTEGER), хотя вызов item.Set(2) имеет один пользовательский аргумент. Обычная FUNCTION EchoThis(THIS AS INTEGER) показывается как FUNCTION EchoThis() AS INTEGER, хотя THIS — настоящий параметр.

**Причина:** фильтр удаляет все параметры с именем THIS; язык создаёт скрытый параметр SELF. Принадлежность к методу и позиция параметра не учитываются.

**Исправление:** скрывать только реальный неявный первый SELF метода по семантическому признаку, согласовать формирование сигнатур с графом вызовов. Не удалять произвольные пользовательские параметры по имени.

**Регрессионные тесты:** метод с одним явным аргументом, обычная функция с THIS, корректный параметр SELF там, где он разрешён договором, одинаковые сигнатуры навигации и подсказки. Через настоящий Host подтверждены implicit-self-hover и ordinary-this-parameter в host-probes.json. Последний исходник дополнительно выполнен CLI: код 0, вывод 5, следовательно THIS является допустимым пользовательским параметром; результат сохранён в this-parameter-run.txt.

## 3. Потенциальные проблемы и неоднозначности

1. Восстановление стрелки после отказа команды отладки вызывает mark без stopId (`execution-controller.js:235–236`). Если файл в этот момент ещё закрыт, сравнение stopId после открытия не позволит восстановить маркер. Полная достижимая последовательность пользовательских действий с такой ошибкой команды не воспроизведена; это кандидат, а не восьмой подтверждённый дефект.
2. Разные категории одноимённых экспортов. PUBLIC-переменная Token из одного импорта и функция Token из другого не вызывают MB2054 при внедрении; вызов Token() получает MB2020 из-за переменной. При этом локальное совпадение классов имён специально разрешено с предупреждением в Binder.ScopeHelpers.cs. Общая фраза справочника о двух одинаковых открытых именах не уточняет категории. Требуется решение, распространяется ли эта модель на импорты, и точные отрицательные/положительные примеры. Собственное предпочтение единого пространства имён не объявляется требованием.

## 4. Мёртвый и дублирующийся код

Доказанного мёртвого кода в выбранной области не найдено. В частности, ветвь ModuleStatementSyntax в BindProgram жива: GetEditorHovers вызывает BindProgram напрямую, минуя Binder.Bind. EntryModuleName — публичное API; MissingEntryModule/MB2056 достижим через публичный BindModules с отсутствующей точкой входа. Отсутствие текущего внутреннего потребителя не является основанием удалять их.

Подтверждённое дублирование:

- Binder.cs:82–85 повторяет последовательность DeclareModule из Binder.Modules.cs:344–350.
- Второй проход BindProgram в Binder.cs:102–120 повторяет BindModuleBodies в Binder.Modules.cs:395–415. Это живые пути, не мёртвые копии.
- Binder.EditorSymbols.cs:73–90 и EditorCallGraph.cs:75–105 независимо обходят контейнеры связанного дерева через отражение. У второго есть кэш свойств; оба должны узнавать новые формы узлов. Практический риск — разное покрытие ссылок и вызовов после расширения языка, а не сам факт применения отражения.
- Проход глобальных операторов объединять механически нельзя: модульный путь дополнительно регистрирует доступность экспортов. Резервные ключи символов сериализатора связаны с совместимостью артефакта и не признаны неиспользуемыми.

## 5. Организация и смысловые границы файлов
