# Аудит подсистемы дат и времени и план её развития

Дата: 18 октября 2026 года. Исходная ревизия: `c77220e0ababfc0b9fa21e17bdbfab439e3e56de`.
Версии: язык 0.1.19, компилятор 0.1.19, IDE 0.6.22.
Статус: исследование завершено в указанных ниже границах. Этапы 1 (DTA-002, DTA-003), 2 (DTA-001), DTA-004, DTA-005, DTA-007, DTA-008..DTA-014 реализованы 18 октября 2026 года; открыты DTA-006 (длительность и монотонное измерение) и DTA-015 (измерения). Итог реализации — в разделах 10–20.

## 1. Главный вывод

Подсистема уже имеет собственные типы. `DATE` хранит `DateOnly`, `TIME` — `TimeOnly`, `DATETIME` — `System.DateTime`. Переменные этих типов не содержат строки. Строковыми остаются внешняя запись, некоторые неявные преобразования и даты файлов. Поэтому переводить всю подсистему со строк на числа заново не требуется.

Разделение календарной даты и времени суток выбрано правильно. Основные проблемы находятся в другом месте: не согласованы точность и текстовая запись, запрет потери компонентов обходится через другие конструкции языка, а один `DATETIME` используется и для местного календарного времени, и для UTC без различия в системе типов.

Рекомендация: сохранить `DATE`, `TIME`, `DATETIME`, сначала устранить дефекты преобразований, затем отдельно спроектировать однозначный момент времени, длительность и монотонное измерение интервалов. Не заменять все три типа одним числом или строкой. Новые имена и синтаксис в этом документе не утверждаются.

## 4. Подтверждённые дефекты

Приоритет P1 означает потерю данных или противоречивое обычное поведение; P2 — ограниченный дефект или существенное улучшение; P3 — последующее развитие. Приоритет не означает, что все предложения уже утверждены к реализации.

### DTA-001 / P1. Текстовая запись теряет скрытые доли секунды

`TIME()`, `NOW()`, `UTCTIME()` и `UTCNOW()` получают полную точность источника часов. Фабрики RuntimeValue не нормализуют её. Форматы `HH:mm:ss` и `yyyy-MM-dd HH:mm:ss` не сохраняют дробную часть. Сравнение и хеширование учитывают её.

Воспроизведение при фиксированном источнике `2024-02-29 12:34:56.125 +03:00`:

```basic
DIM original AS DATETIME = NOW()
DIM text AS STRING = original
DIM restored AS DATETIME = text
PRINT original
PRINT restored
PRINT original = restored
PRINT original = text
```

Получено: две одинаковые строки `2024-02-29 12:34:56`, затем `FALSE`, `FALSE`. Аналогичный путь TIME → STRING → TIME возвращает неравное значение. Следствие: сохранение даты-времени в текстовый файл меняет значение; одинаковые видимые даты могут по-разному сравниваться и оставаться разными элементами множества.

Нужно выбрать и закрепить единицу точности. Рекомендуется сохранять точность значений и добавить обратимую техническую запись с дробной частью; обычную печать разрешается оставить краткой, если она явно отделена от сериализации. Альтернатива — нормализовать все значения до секунды на каждой границе создания; это проще, но сознательно теряет точность. Одного изменения PRINT недостаточно: нужны согласованные преобразования, разбор, интерполяция, файловая запись, равенство и отладочное отображение.

### DTA-002 / P1. Защита присваивания зависит от синтаксической оболочки

```basic
' MB2003: потеря времени запрещена.
DIM rejected AS DATE = "2024-02-29 12:34:56"
```

Отдельные программы ниже успешно выполняются и теряют время:

```basic
DIM accepted AS DATE = ("2024-02-29 12:34:56")
PRINT accepted
```

```basic
DIM text AS STRING = "2024-02-29 12:34:56"
DIM accepted AS DATE = text
DIM clockTime AS TIME = text
PRINT accepted
PRINT clockTime
```

Причина: `TryGetStringLiteralText` распознаёт только непосредственный LiteralExpressionSyntax; общий `TryConvertTemporalValue` разрешает извлечение DATE/TIME из полного текста. Скобки меняют допустимость программы без изменения значения выражения.

Исправление: общий договор преобразования с указанием, разрешена ли потеря компонента. Не ограничиваться снятием скобок: переменная, CONST, результат функции и интерполяция должны подчиняться тем же правилам. Рекомендуется запретить неявную потерю и оставить явные DATEVALUE/TIMEVALUE. Для строк с неизвестным содержимым проверять отсутствие лишнего компонента во время исполнения с документированной диагностикой и сохранением прежнего значения цели.

### DTA-003 / P1. Вызовы, RETURN и сравнения обходят запрет усечения

```basic
FUNCTION CalendarPart(value AS DATE) AS DATE
    RETURN value
END FUNCTION
DIM moment AS DATETIME = "2024-02-29 12:34:56"
PRINT CalendarPart(moment)
```

Получено `2024-02-29` без диагностики. Функция `FUNCTION CalendarPart(value AS DATETIME) AS DATE`, возвращающая `value`, также успешно отбрасывает время. Общий `CanConvert` допускает эти переходы, а защита в объявлениях не распространяется на остальные контексты.

Ещё один подтверждённый пример:

```basic
DIM dayValue AS DATE = "2024-02-29"
PRINT dayValue = "2024-02-29 12:34:56"
PRINT dayValue < "2024-02-29 12:34:56"
```

Получено `TRUE`, `FALSE`: полная строка преобразуется к DATE и теряет время. Результат отличается от сравнения с типизированным DATETIME, где выбирается DATETIME и полночь сравнивается с полуднем.

Исправление проводить вместе с DTA-002 через общие правила. Проверить BYVAL, RETURN, литералы TYPE, поля, элементы массива, функции как значения и перегрузки. BYREF должен сохранять точный тип адресуемого значения; нельзя исправлять задачу добавлением временной копии с потерей части значения. Извлечение YEAR/HOUR и явные функции выбора части остаются законными операциями.

### DTA-004 / P2. Чтение текущего времени в поясе выпускает исключение .NET

При IRuntimeClock, возвращающем `DateTimeOffset.MaxValue`, каждый из вызовов `DATE("Asia/Tokyo")`, `TIME("Asia/Tokyo")`, `NOW("Asia/Tokyo")` внутри TRY/CATCH выпускает `System.ArgumentOutOfRangeException` за границы `AxiomExecutionPipeline.Run`. Обработчик языка и инструкция после END TRY не выполняются.

Причина: `ConvertUtcToTimeZoneDateTime` проверяет выход за диапазон, но эти три обёртки не преобразуют исключение в MB3007. TOUTC/FROMUTC такую защиту имеют. Для обычной текущей даты ошибка практически недостижима; воспроизведение требует управляемых предельных часов, а не реального перевода системных часов компьютера.

Исправление: одинаковая языковая диагностика во всех входах конвертации; проверить обе границы, положительные и отрицательные смещения, сохранение цели и продолжение после CATCH. Не скрывать ошибку насыщением до минимальной/максимальной даты.

### Два разных момента могут стать одинаковым DATETIME

`2024-11-03 05:30:00 UTC` и `2024-11-03 06:30:00 UTC` отличаются на 3600 секунд. После `FROMUTC(..., "America/New_York")` оба значения равны `2024-11-03 01:30:00`: сравнение даёт TRUE, DATEDIFF — 0. Обратный TOUTC закономерно даёт MB3007 из-за неоднозначности. Это подтверждено программой `ambiguous-collapse`.

Текущее поведение FROMUTC правильно для получения местного календарного времени. Ошибка архитектуры возникнет, если использовать результат как идентификатор события, ключ журнала или точное время записи. Сохранить рядом исходный UTC-момент необходимо уже при текущей модели. Смещение само по себе также не заменяет именованный пояс: для будущих расписаний нужны правила пояса, которые могут меняться.

### Календарный день отличается от 24 прошедших часов

Между местными `2024-03-09 12:00:00` и `2024-03-10 12:00:00` в New York календарная разность DATETIME равна 24 часам, а после перевода обоих концов в UTC — 23. DATEADD("d", 1, ...) и DATEADD("h", 24, ...) в текущем календарном DATETIME дают одинаковую запись. Это ожидаемая арифметика календарного типа, не дефект DATEDIFF. Для расчёта фактической длительности нужен однозначный момент и отдельный договор арифметики.

### TIMER и SLEEP

При управляемых часах с переходом `23:59:59 → 00:00:00` разность TIMER равна `-86399`. Это документированное свойство BASIC-подобного TIMER, а не основание молча менять его смысл. Коррекция через прибавление 86400 решает только один переход суток, но не перевод системных часов и многосуточное измерение.

SLEEP принимает миллисекунды в пределах 0..Int32.MaxValue и ждёт частями до 10 мс с проверкой отмены; без аргумента ждёт клавишу. Он не использует TIMER как крайний срок, поэтому названный переход TIMER сам по себе не ломает SLEEP. Точность ожидания зависит от планировщика и числа частичных ожиданий; его нельзя объявлять точным измерителем длительности. Нативная проверка отмены и точности SLEEP этим аудитом не проводилась.

## 6. Выбор направления развития

| Вариант | Плюсы | Цена и оценка |
|---|---|---|
| Все даты хранить строками | Простой текстовый обмен | Потеря типизации, ошибки формата и сравнения. Отклонить |
| Всё заменить числом секунд или исторической дробной датой | Простая арифметика на одной шкале | Теряется смысл даты/времени суток, дробная точность и календарные правила требуют отдельного договора. Отклонить как универсальную модель |
| Все типы заменить DateTimeOffset | Однозначные события со смещением | Дата рождения и время открытия магазина не являются моментами; фиксированное смещение не хранит правила пояса. Не применять ко всем данным |
| Сохранить три календарных типа и добавить недостающие понятия | Ясный смысл значений, постепенная совместимость | Потребуются типы, операции, сериализация и обновление всех слоёв. Рекомендуемый путь |

Предлагаемая модель:

1. DATE — календарный день без времени и пояса; DateOnly остаётся достаточным представлением.
2. TIME — время суток, без даты и пояса; TimeOnly остаётся достаточным представлением.
3. DATETIME — календарные дата и время без пояса; нормализовать внутренний DateTimeKind, чтобы он не создавал скрытого второго договора. Сейчас фабрика принимает DateTime разных Kind, а преобразования часто вновь собирают Unspecified; пользовательских свойств Kind у языка нет.
4. Момент — однозначная позиция на шкале UTC. Возможное внутреннее представление: UTC ticks либо DateTimeOffset с оговорённой нормализацией. Нельзя сравнивать с календарным DATETIME без явного контекста пояса.
5. Длительность — знаковое прошедшее время, возможно больше суток; не TIME. Для календарных месяцев/лет нужна отдельная операция, поскольку месяц не равен постоянному числу секунд.
6. Пояс — именованные правила преобразования, не просто целое число минут. Отдельный языковой тип пояса необязателен для первого этапа; достаточно проверенного аргумента и ясных ошибок.
7. Монотонное измерение — отдельный счётчик с явно заданными единицами и областью действия, не календарная дата и не TIMER.

Это рекомендация, а не внесённое изменение спецификации. До введения новых сущностей сравнить имена в QuickBASIC, классическом BASIC, Visual Basic и подходящих близких диалектах. Существующие DATEADD, DATEDIFF, DATESERIAL, TIMESERIAL, DATEVALUE, TIMEVALUE и TIMER имеют понятную BASIC-родословную, но Axiom уже сознательно отличается строгими аргументами, Monday-first нумерацией и отсутствием нормализации невозможной даты. Нельзя менять эти правила ради механической совместимости с VB.

## 11. Реализация этапа 2 (DTA-001) — 18 октября 2026 года

Выбран первый из двух путей аудита: сохранять точность значений и добавить обратимую техническую запись, оставив краткую печать для значений с точностью до секунды. Запись. `FormatCanonicalTime` и `FormatCanonicalDateTime` печатают краткую форму при нулевой дробной части и форму с точкой и от одной до семи цифр без конечных нулей иначе (`HH:mm:ss.FFFFFFF`, `yyyy-MM-dd HH:mm:ss.FFFFFFF`). ## 12. Реализация DTA-008 (SELECT CASE) — 18 октября 2026 года

`SELECT CASE` больше не отвергает временные значения. Причина дефекта была в связывании: `CanBindSelectCaseEquality` и `CanBindSelectCaseOrdering` перечисляли только числовые и строковые виды, хотя обычные сравнения `DATE`, `TIME` и `DATETIME` уже поддержаны и понижение селектора к ним сводится.

Договор. Точное значение, `CASE IS` и диапазон `TO` допустимы внутри одного временного вида. Смешение видов (`DATE` с `TIME`, `DATE` с `DATETIME`) отклоняется как MB2003 — так же, как в `DATEADD`/`DATEDIFF`/`DATEPART`, где смешение видов не выполняется неявно. Строковый селектор разбирается в вид выражения выбора: `CASE "2024-02-29"` работает для `DATE`, а `CASE "2024-02-29 12:34:56"` для `DATE` отвергается тем же правилом потери компонента, что и в присваивании, и подсказывает `DATEVALUE`. Доли секунды участвуют в сравнении, поэтому значения, различающиеся только дробной частью, попадают в разные ветви. Обратный диапазон по-прежнему не подходит ни одному значению.

Реализация. `NormalizeSelectCaseSelectorExpression` направляет временной селектор через общий `ApplyExpectedType`, а не через безусловное `BoundConversionExpression`. Это единственное изменение в связывании: понижение, байткод и валидатор не менялись, потому что селектор выражается уже поддержанными операциями сравнения. Сообщение MB2015 расширено упоминанием временных значений.

Проверки. `TemporalSelectCaseContractTests` — 8 тестов: точное значение для трёх видов, типизированный селектор без текста, диапазон и `CASE IS` с включительными границами, обратный диапазон, различие по долям секунды, отказ смешения видов, отказ потери компонента в строковом селекторе, прежние правила числовых селекторов. Итоги: Semantics 532/532, Runtime 1194/1194, Bytecode 248/248, CLI 30/30, Execution 3291/3293 (два известных отказа Maze Chase). Пример `samples/control-flow/select_case/temporal_values.axm`; справочник — `select-case.html`.

## 13. Реализация DTA-012 (сборка и разбор без текста) — 18 октября 2026 года

Добавлены три зарегистрированные формы. `DATETIMESERIAL(date, time)` собирает `DATETIME` из готовых `DATE` и `TIME` и переносит обе части целиком, включая доли секунды. `DATEVALUE` и `TIMEVALUE` получили вторую форму с аргументом `DATETIME`, поэтому части извлекаются типизированно, без промежуточной строки. Раньше `DATETIME` собирался только через текст, а `TIME → DATETIME` подставлял минимальную дату.

Имена выбраны по линии BASIC: `DATETIMESERIAL` продолжает `DATESERIAL` и `TIMESERIAL`, а `DATEVALUE`/`TIMEVALUE` сохраняют своё назначение разбора и расширены типизированной формой вместо нового имени.

Договор. `DATETIMESERIAL` принимает `DATE` и `TIME`; строка с канонической записью допустима, потому что разбор выполняет сама функция. Значение `DATETIME` вместо одного из аргументов отвергается общим правилом потери компонента с подсказкой `DATEVALUE` или `TIMEVALUE`. Часовой пояс не добавляется: результат остаётся календарным временем без пояса. Сборка и разбор обратимы: `DATETIMESERIAL(DATEVALUE(moment), TIMEVALUE(moment))` равно `moment`.

Реализация. Новые члены `BuiltinFunctionId` добавлены в конец перечисления, чтобы не сдвигать сохранённые идентификаторы. ## 14. Реализация DTA-010 (агрегаты массивов) — 18 октября 2026 года

`ARRAYMIN` и `ARRAYMAX` больше не отвергают временные элементы. Реализация. `RequiresOrderedAggregateArray` исключает временные типы из отказа; `Extreme` выбирает вид сравнения через `ResolveExtremeComparisonKind` и вызывает `RuntimeValueHelpers.Compare` для временных значений. Числовые и строковые ветви не менялись.

## 19. Реализация DTA-005 (однозначный момент) — 18 октября 2026 года

По решению автора введён четвёртый временной тип. Имя `UTCDATETIME` описывает содержимое: дата-время на шкале UTC. Оно выбрано как явное проектное решение, потому что в линии BASIC готового имени для момента нет. Запись `2024-02-29T12:34:56Z` повторяет распространённую форму и не совпадает с канонической записью `DATETIME`, поэтому текст двух видов нельзя спутать.

Модель. `DATE`, `TIME` и `DATETIME` остаются календарными типами. `UTCDATETIME` — момент: однозначная точка на общей шкале, хранится как `DateTime` с `Kind = Utc`, пояс и смещение не хранятся. Различие проходит через все слои: лексер, парсер, связывание, байткод, валидатор, `RuntimeValue`, сравнение, поля `TYPE`, сериализация артефакта, `INPUT`, агрегаты массивов, `SELECT CASE` и подсветка IDE.

Договор. Момент не смешивается неявно с календарными видами: сравнение `UTCDATETIME` с `DATETIME`, сужение момента до `DATE`/`TIME` и присваивание календарного значения моменту отвергаются при проверке программы как MB2003. Перевод выполняют явные функции, потому что для него нужен пояс: `TOINSTANT` (местное время плюс пояс → момент) и `FROMINSTANT` (момент → местное время). `TOINSTANT` проверяет пропущенное и повторяющееся время перехода часов; `FROMINSTANT` закономерно допускает совпадение местных записей у разных моментов. `INSTANTVALUE` разбирает текст с признаком `Z`, `NOWINSTANT` читает текущий момент с точностью до секунды. Смещение `+03:00` не принимается: в языке пока нет формы, которая сохраняла бы смещение, и молчаливое приведение скрыло бы потерю.

Главная проверка. Сценарий аудита `ambiguous-collapse` теперь решается правильно: `2024-11-03T05:30:00Z` и `2024-11-03T06:30:00Z` в Нью-Йорке дают одинаковую местную запись `2024-11-03 01:30:00`, но остаются разными значениями — сравнение даёт FALSE и TRUE, печать показывает оба момента с `Z`.

Проверки. `InstantTypeContractTests` — 11 тестов. Попутно обнаружено и исправлено расхождение подсветки IDE: `DATETIMESERIAL` и `DATETIMEVALUE` из этапов 12–13 не были добавлены в файлы `.xshd`, а словарь встроенных функций не был отсортирован; оба файла приведены к порядку реестра, и проверки подсветки проходят (55/55). Итоги: Semantics 533/533, Runtime 1194/1194, Bytecode 248/248, CLI 30/30, Execution 3359/3361 (два известных отказа Maze Chase), Ide 1006/1009 (два предсуществующих отказа ожиданий приглашения INPUT и один нестабильный), `audit-bytecode-coverage` PASS, `check-manual` пройден.
