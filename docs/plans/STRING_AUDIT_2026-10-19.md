# Повторный аудит строковой подсистемы Axiom — 19 октября 2026 года

Документ продолжает [STRING_AUDIT_2026-10-18.md](STRING_AUDIT_2026-10-18.md) и
[STRING_AUDIT_INVENTORY_2026-10-18.md](STRING_AUDIT_INVENTORY_2026-10-18.md).
Проверяемая область: строки, функции и операторы работы со строками.

## 1. Краткий вывод

Строковая подсистема в целом исправна. Все исправления предыдущего аудита
(STR-001…STR-017) подтверждены независимыми воспроизведениями; справочник
детальный и совпадает с реализацией во всех проверенных пунктах, включая
«неудобные» закреплённые правила (`INSTRREV("", "") = 0` против
`INSTRREV(1, "", "") = 1`, первая кодовая единица UTF-16 как заполнитель,
пустой набор `TRIM`, отказ по рангу массива в `JOIN`).

Новые существенные проблемы сосредоточены не в исполнителях строковых функций,
а в лексическом автомате интерполяции и в мёртвом коде:

- спецификатор формата с пробелом молча печатает сам формат вместо числа;
- перевод строки внутри `$"…"` принимается, хотя в обычном литерале на том же
  месте выдаётся MB0002;
- слой «быстрых» строковых встроенных функций недостижим ни в одной конфигурации;
- 281 строка вручную сопровождаемого списка поддержки builtins в конвейере не
  используется нигде.

## 2. Подтверждённые дефекты

### STR2-001 — P2: пробел в спецификаторе формата интерполяции молча меняет результат

Места: `src/Axiom.Lexing/Lexer.Strings.cs:216` (`content.ToString().Trim()` в
`Value` токена), `src/Axiom.Semantics/Binding/Binder.Expressions.cs:110`
(`formatSpecifier = exprPart.FormatSpecifierToken.Text`), исполнение —
`src/Axiom.Runtime/Execution/BytecodeVm.StringOperations.cs:36-44`.

Воспроизведение `.artifacts/strings-audit-2/probe_format_spaces.axm`,
`axiom run`, код возврата 0, диагностик нет:

```basic
DIM n AS INTEGER = 42
PRINT $"[{n:F2}]"     ' [42.00]
PRINT $"[{n: F2}]"    ' фактически [ F2]
PRINT $"[{n:F2 }]"    ' фактически [F2 ]
PRINT $"[{n: F2 }]"   ' фактически [ F2 ]
```

Ожидается: пробелы вокруг формата не значимы — лексер явно их обрезает, а для
выравнивания пробел после запятой работает (`$"[{n, 5}]"` → `[   42]`,
проверено). Либо формат применяется, либо, согласно
`docs/manual/string-literals.html` («Неверный числовой формат … вызывает
перехватываемую ошибку MB3007»), выдаётся диагностика.

Фактически: байндер передаёт сырой текст, поэтому в .NET уходит `" F2"`. Это
уже не стандартный, а пользовательский формат, где буквы копируются буквально, —
программа печатает текст формата. Обрезанное `Value` токена не читает ни один
потребитель.

Причина: два представления текста интерполяции — лексер вычисляет `Value`,
байндер использует `Text`. Для спецификатора формата расхождение меняет смысл
формата, а не только запись.

Последствия: молча неверный пользовательский вывод без диагностики; опечатка
переносит привычку ставить пробел после запятой на двоеточие; `axiom fmt`
сохраняет запись дословно (проверено), поэтому форматирование проблему не лечит.

Исправление: читать в байндере обрезанное значение токена либо обрезать `Text`
там же; закрепить правило «пробелы по краям спецификатора не значимы» в
справочнике. Если решено сохранить значимость пробелов — убрать `Trim()` из
лексера и описать правило явно.

Необходимый тест: лексический — токен формата записи `{n: F2 }` имеет
`Value == "F2"`; Execution-тест с буквальным ожиданием `42.00` для `{n: F2}`;
пример `samples/expressions/interpolation_format_spaces.axm`.

### STR2-002 — P2: перевод строки внутри интерполированного литерала принимается

Места: `src/Axiom.Lexing/Lexer.Strings.cs:121-175` (`ReadInterpolatedStringText`
без проверки `IsNewLine`) против `Lexer.Strings.cs:31` (`ReadStringLiteral`) и
`Lexer.Strings.cs:207` (`ReadFormatSpecifier`), где такая проверка есть.

Воспроизведение 1 — многострочный литерал принимается
(`.artifacts/strings-audit-2/probe_interp_newline.axm`):

```basic
PRINT $"abc
def"
```

`axiom check` → код 0, диагностик нет; `axiom run` → печатает `abc` и `def`;
`axiom fmt` воспроизводит запись дословно.

Воспроизведение 2 — тот же текст в обычном литерале
(`probe_plain_newline.axm`): `axiom check` → `MB0002 Незакрытая строковая
литерала` на строке 1 и на строке 2.

Воспроизведение 3 — проглоченный код и смещённая диагностика
(`probe_interp_swallow.axm`):

```basic
PRINT $"oops
DIM x AS INTEGER = 1
PRINT x
PRINT "tail"
```

Единственная диагностика — MB0002 на строке 4, позиция 12. Строки 2–3 молча
стали содержимым строкового литерала; источник ошибки на строке 1 не указан.

Ожидается: одно правило конца строки для обеих форм одного конструкта.
`docs/manual/string-literals.html` говорит «Незавершённый литерал вызывает
MB0002» без разделения форм; многострочная интерполяция нигде не обещана.

Последствия: расхождение двух форм литерала; непреднамеренное превращение кода в
данные; диагностика в нерелевантном месте. Полностью молчаливую компиляцию
проглоченного кода построить не удалось — во всех вариантах остаток всё же давал
MB0002, но уже на другой строке.

Исправление: прерывать `ReadInterpolatedStringText` на `IsNewLine(Current)` и
сообщать MB0002 от позиции начала литерала, как в `ReadStringLiteral`; либо явно
ввести многострочную интерполяцию как возможность языка — тогда то же правило
нужно для обычного литерала и для подсветки.

Необходимый тест: лексические проверки `$"abc<NL>def"` (ожидание — MB0002 на
позиции `$`), незакрытой `$"abc` на конце файла, незакрытого внутреннего уровня
вложенности; Execution-проверка, что многострочная запись отклоняется.

### STR2-003 — P2/P3: слой «быстрых» строковых встроенных функций недостижим

Место: `src/Axiom.Runtime/Execution/BytecodeVm.StringFastBuiltins.cs:17-208`
(10 обработчиков: `LEN`, `TRIM`, `LTRIM`, `RTRIM`, `CONTAINS`, `STARTSWITH`,
`ENDSWITH`, `LCASE`, `UCASE`, `INSTR`).

Цепочка недостижимости: `BytecodeVm.cs:3238`
(`if (executionInfo.HasFastHandler && TryExecuteFastBuiltin(...))`) →
`BytecodeVm.cs:4000` (`HasFastBuiltinHandler(builtin.CanonicalId)`) →
`BytecodeVm.cs:400-443` — список содержит только графические и файловые
идентификаторы, строковых в нём нет.

Доказательство 1 (статическое). Поиск по репозиторию:
`TryExecuteFastStringBuiltin` вызывается только из `TryExecuteFastBuiltin`
(`BytecodeVm.cs:3281`), тот — только из `ExecuteBuiltinCall` под фильтром
`HasFastHandler`; поле `HasFastHandler` присваивается только из
`HasFastBuiltinHandler`. Отражения над закрытыми членами VM и генераторов кода
нет (единственные `*.g.cs` — `GlobalUsings`).

Доказательство 2 (покрытие).
`dotnet test tests/Axiom.Execution.Tests --filter "FullyQualifiedName~String"
--collect:"XPlat Code Coverage"` → 268/268, `coverage.cobertura.xml`:
в `BytecodeVm.StringFastBuiltins.cs` из 128 инструментированных строк выполнены
6 — строки 11, 12, 13, 15, 210, 212 (вход в метод, `result = Void`,
`var stack`, `switch`, `default: return false`, закрывающая скобка), по 4
попадания каждая. Ни одна строка тел `case` (17–208) не выполнена. Четыре входа
— это файловые и графические builtins, для которых `HasFastHandler` истинно и
которые проходят мимо графического обработчика.

История. `git log -S "TryExecuteFastStringBuiltin"` → добавлен в `ef6d8c02`
(2026-08-20); `git show ef6d8c02:src/Axiom.Runtime/Execution/BytecodeVm.cs`
показывает, что вызов уже тогда был под фильтром `HasFastHandler`.
`git log -S "or BuiltinFunctionId.Len"` по `BytecodeVm.cs` пуст — строковых
идентификаторов в фильтре не было никогда. Код родился недостижимым, а в
`0cd22163` (этап S13 предыдущего аудита) был вынесен в отдельный файл и
приобрёл вид действующего слоя оптимизации.

Последствия: ускорение самых частых строковых форм не работает — все они идут
через делегатный диспетчер; рядом живут две реализации одних правил, которые уже
расходятся в деталях (быстрый `TRIM` всегда создаёт новый `RuntimeValue`,
медленный сохраняет исходный при отсутствии изменений; быстрый `LCASE`/`UCASE`
сравнивает через `ReferenceEquals`, медленный — через `string.Equals`); правка
одной копии не проверяется исполнением.

Исправление: выбрать одно — добавить строковые идентификаторы в
`HasFastBuiltinHandler` и оставить ровно одну семантическую реализацию на
функцию (быстрый слой проверяет типы и стек, затем вызывает тот же помощник)
либо удалить файл. Третий вариант (оставить как есть) — худший.

Необходимый тест: при сохранении пути — проверка входа в быстрый обработчик и
паритетный тест «быстрый путь равен общему» на матрице значений (пустая строка,
NUL, суррогаты, отсутствие изменений); при удалении — замер
`samples/smoke/engine-compare/string_primitive_scan.axm` до и после.

### STR2-004 — P3: экраны в тексте интерполяции распознаются сканером, но не применяются

Места: `src/Axiom.Lexing/Lexer.Strings.cs:144-163` (ветви `\{`, `\"`, `\\`
добавляют в `content` распакованный символ), `:174` (`Value = content.ToString()`),
`src/Axiom.Semantics/Binding/Binder.Expressions.cs:95`
(`textPart.TextToken.Text`).

Воспроизведение `.artifacts/strings-audit-2/probe_interp_escapes.axm`:

```basic
PRINT $"a\"b"    ' a\"b
PRINT $"c\\d"    ' c\\d
PRINT $"e\{f"    ' e\{f
PRINT $"g\ng"    ' g\ng
```

Ожидается: либо `\{`, `\"`, `\\` — экраны (тогда результат `a"b`, `c\d`, `e{f`),
либо они не экраны вовсе (тогда `\"` должен завершать литерал, как удвоение
завершает обычный). Справочник описывает только сохранение `{{`/`}}`; правила для
обратной косой черты нет.

Последствия:

- в интерполированном литерале нельзя получить двойную кавычку: `$"a""b"`
  завершает литерал на первой кавычке и даёт MB2040 (проверено), `$"a\"b"` даёт
  `a\"b`; рабочий обход — `$"q{CHR(34)}q"` (проверен);
- `\{` не даёт `{`, а `{{` тоже даёт `{{`, поэтому одиночную открывающую скобку
  в тексте интерполяции получить нельзя вовсе;
- на каждый текстовый фрагмент создаётся `StringBuilder` и выполняется
  распаковка, результат которой не читается (`rg InterpolatedStringTextToken`
  даёт только объявление вида, создание токена и сопоставление вида в парсере);
- расхождение с IDE: `ide/src/renderer/app.js:262` в состоянии
  `interpolatedString` имеет правило `[/""/, 'string.escape']`, то есть
  подсветка считает `""` внутри `$"…"` экраном, а компилятор на этом месте
  закрывает литерал; `\"` подсветка не знает.

Исправление: одно представление текста интерполяции. Либо байндер берёт
распакованное `Value` (тогда экраны начинают работать, и это нужно закрепить в
справочнике и в SPECIFICATION3, поскольку текущая формулировка «правило
сохранения исходной записи … не изменено» требует явной ревизии), либо
распаковка удаляется из лексера, а правила завершения литерала и подсветка
приводятся к одному договору.

Необходимый тест: лексические проверки `\"`, `\\`, `\{`, `{{`, `""` внутри
`$"…"`; Execution-тест с буквальным ожиданием выбранного договора; сценарий
`e2e-language` на подсветку той же записи.

## 4. Что проверено и не является дефектом

Чтобы не выдавать предпочтение за требование проекта, ниже закреплены правила,
совпадающие со справочником, спецификацией и тестами:

- первая кодовая единица UTF-16 как заполнитель в `STRING`, `PADLEFT`,
  `PADRIGHT`, `CENTER` с возможным образованием несвязанных суррогатов — прямо
  описано в `docs/manual/string-functions-build-and-split.html` и закреплено
  `StringFillMalformedUnicodeEvidenceTests`; воспроизведение
  `probe_surrogate_fill.axm` даёт ровно документированный результат;
- `TRIM(text, "")` оставляет текст без изменения; специальной ошибки для
  пустого текста и пустого набора нет — описано в
  `docs/manual/string-functions-trim-and-case.html`;
- MB3007 при пустом фрагменте в `REPLACE`, `SUBSTRCOUNT`, `SPLIT`; пустой
  `SPLIT` даёт массив длины 0;
- спецификатор формата у нечисловых значений игнорируется — описано в
  `docs/manual/string-literals.html`;
- `PRINT USING` при нехватке значений для строковых полей подставляет пустую
  строку или пробелы, для числовых — ошибка; `\abc\` не является строковым полем
  и печатается буквально;
- `STRING * N` допустим только в `DIM` и полях `TYPE` (MB2026 для параметров),
  диапазон 1–65535 (MB2026 вне диапазона); присоединение к фиксированной строке
  отбрасывает добавленный текст — эквивалентно обычному пути с обрезанием;
- `ISNUMERIC` требует конечный результат, поэтому `1e400` даёт FALSE;
- `INSTRREV("", "") = 0` и `INSTRREV(1, "", "") = 1` — описано буквально;
- сравнение строк порядковое, регистр изменяется инвариантно, NUL считается
  обычной единицей (`probe_nul.axm`: `LEN`, `INSTR`, `REPLACE`, `SPLIT`, `TRIM`
  согласованы);
- `JOIN` отклоняет многомерный массив при проверке программы (MB2003), поэтому
  отсутствие проверки ранга в исполнителе не достижимо.

## 10. Реализация рекомендаций — 19 октября 2026 года
