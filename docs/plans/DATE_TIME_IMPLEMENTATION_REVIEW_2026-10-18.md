Дата: 18 октября 2026 года, 18:31, Москва. Проверена ревизия `e9622a00`; исходная точка аудита — `c77220e0`.
Версии: язык 0.1.34, компилятор 0.1.34, IDE 0.6.24.

## Заключение

Заявление «DTA-001..DTA-015 закрыты полностью, остаются только внешние границы» не подтверждается. Основная реализация выполнена, исходные ошибки преобразований исправлены в проверенных сценариях, появились UTCDATETIME, новые функции и типизированные метаданные. Однако независимая проверка обнаружила пять программных недочётов DTR-001..DTR-005. Исправлений этих недочётов в рамках проверки не выполнялось.

Настоящий INPUT в консоли Electron проверен и работает в двух конкретных сценариях. Обратный шаг с UTCDATETIME не работает в проверенном сценарии из-за ограничения кода снимков. Получасовой сезонный переход доступен через обычный программный идентификатор пояса Australia/Lord_Howe, специального оборудования не требует. Физический перевод системных часов не выполнялся, но это не основание объявлять весь оставшийся объём аппаратным.

## DTR-001 / P2. Внедряемый монотонный источник часов не используется

Место: `src/Axiom.Execution/Hosting/ExecutionRuntimeHostAdapter.cs:537`; тот же пропуск есть у ProfilingRuntimeHost в `src/Axiom.ManualChecks/Program.cs:1046`.

IRuntimeClock получил GetMonotonicSeconds, но адаптер пересылает только GetLocalNow, GetLocalTimeZone и TryResolveTimeZone. Для нового метода применяется реализация интерфейса по умолчанию через Stopwatch, даже когда ExecutionRequest.runtimeClock передал собственную реализацию.

Независимое воспроизведение: часы возвращают 1000, 1010, 1020 при последовательных чтениях GetMonotonicSeconds и считают вызовы. Программа:

```basic
PRINT ELAPSEDSECONDS()
PRINT ELAPSEDSECONDS()
PRINT NOWINSTANT()
```

При происхождении отсчёта 1000 первые два результата должны быть 10 и 20. Фактически получены реальные доли секунды, например 0.052 и 0.060. Счётчик вызовов GetMonotonicSeconds равен **0**, а GetLocalNow — 1. Следовательно, переданные часы работают для календарного времени, но игнорируются для монотонного.

Почему существующие тесты проходят: CounterMeasuresElapsedTime содержит настоящий SLEEP 150 и проверяет лишь диапазон 0.1..5 секунд. Реальный Stopwatch удовлетворяет ему. CounterIgnoresCalendarClockChanges вообще не вызывает GetLocalNow из программы; его JumpingClock вычисляет календарное время, но это вычисление не происходит. Тест подтверждает положительность реального секундомера, а не заявленный сценарий управляемого скачка часов.

Исправление: переслать GetMonotonicSeconds через все обёртки IRuntimeClock. Добавить точную проверку результатов и числа обращений без SLEEP. Для сценария скачка действительно прочитать меняющиеся календарные часы, одновременно проверяя известные монотонные результаты. Производственный Stopwatch сам по себе работает; дефект находится в договоре внедрения источника и достоверности тестов.

## DTR-002 / P2. UTCDATETIME не включён в структурное равенство TYPE

Место: `src/Axiom.Semantics/Symbols/StructuralEqualitySupport.cs:41`.

В IsScalar перечислены DATE/TIME/DATETIME, но отсутствует UTCDATETIME. Поэтому обычная запись с новым скалярным полем теряет поддержку операторов = и <>:

```basic
TYPE Stamp
    Value AS UTCDATETIME
END TYPE
DIM first AS Stamp
DIM second AS Stamp
PRINT first = second
```

Получено MB2003: оператор = неприменим к Stamp и Stamp. Контрольная программа, отличающаяся только типом поля DATETIME, успешно печатает TRUE. Само равенство отдельных UTCDATETIME в RuntimeValueHelpers уже реализовано, поэтому отказ не объясняется отсутствием операции у значения.

Исправление: включить UTCDATETIME в общий договор структурного равенства и проверить Binder, валидатор байткода и исполнение. Нужны одинаковые и разные моменты, вложенный TYPE и обе операции =/<>. Проверка агента InstantWorksInRecordsArraysAndSelectCase читает поле и работает с массивом, но не сравнивает записи целиком.

## DTR-003 / P2. INPUT и начальные значения полей используют другой разбор

Места:

- `src/Axiom.Runtime/Builtins/BuiltinIOHelpers.cs:145` — TIME/DATETIME в INPUT; аналогичный код есть и в строковой перегрузке, начиная со строки 68.
- `src/Axiom.Semantics/Binding/Binder.Declarations.cs:337` — начальные TIME/DATETIME/UTCDATETIME полей.

Общий BuiltinDateTimeHelpers специально отвергает точку без цифр после неё. Новые пути напрямую вызывают TryParseExact с FFFFFFF и не повторяют эту проверку. В результате допустимость одного текста зависит от места его использования.

Подтверждённая матрица:

| Текст и целевой тип | Обычное присваивание из STRING | INPUT | Начальное поле TYPE |
|---|---|---|---|
| `12:34:56.` → TIME | MB3005 | Принимается как 12:34:56 | Принимается как 12:34:56 |
| `2024-02-29 12:34:56.` → DATETIME | MB3005 | Принимается | Принимается |
| `2024-02-29T12:34:56.Z` → UTCDATETIME | MB3005 | MB3003 | Принимается |

Пример поля:

```basic
TYPE Stamp
    Value AS TIME = "12:34:56."
END TYPE
DIM item AS Stamp
PRINT item.Value
```

Программа печатает 12:34:56, хотя обычное преобразование этой же строки отвергается. Ошибка присутствует и при разборе UTCDATETIME-поля, для которого INPUT уже использует общий строгий разбор.

Исправление: общий строгий низкоуровневый разбор для связывания полей, присваивания, функций и INPUT. Семантический слой не должен зависеть от Runtime, поэтому общие правила следует вынести в подходящий нижний слой либо обеспечить одну общую спецификацию и независимые проверки всех путей. Проверить также NUL, пробелы, точку без цифр и 8 цифр; один контроль правильной даты недостаточен.

## DTR-004 / P2. Обратный шаг для временных значений — незавершённая реализация

Место: `src/Axiom.Runtime/Execution/BytecodeVm.cs:5667`, метод TryCreateValueSnapshot.

Список поддержанных скаляров заканчивается BOOLEAN/VOID и не включает DATE, TIME, DATETIME, UTCDATETIME. В RuntimeSnapshotFactory есть общее копирование скаляров, но перед ним отдельный путь снимков стека отвергает временное значение.

В настоящем Electron выполнена программа:

```basic
TYPE Stamp
    Value AS UTCDATETIME
END TYPE
DIM item AS Stamp
item.Value = "2024-02-29T12:00:01.125Z"
item.Value = TOINSTANT(DATEADD("s", 1, FROMINSTANT(item.Value, "UTC")), "UTC")
PRINT item.Value
```

Обычные шаги дошли до строки 6, затем до строки 7. На строке 7 получено canStepBack=false. Проверка восстановления и повторного выполнения поэтому не смогла продолжиться. Это воспроизведённый отказ доступности обратного шага, а не доказательство неверного восстановления после отката.

Ограничение старых календарных скаляров существовало до добавления UTCDATETIME. Оно не является новой регрессией всех трёх старых типов, но распространяется на новый тип и противоречит заявлению, что завершению препятствует только внешняя среда.

Исправление: включить все четыре неизменяемых временных скаляра в снимки; проверить отдельно переменную, поле TYPE, аргумент, локальную переменную и промежуточный стек. Оконный тест должен выполнить изменение, откат и повтор и отличать результат после восстановления от результата без восстановления.

## DTR-005 / P2. Новые чтения часов и файлов ошибочно считаются обратимыми

Место: `src/Axiom.Runtime/Execution/BytecodeVm.cs:294`, IsBuiltinReverseExecutionSafe.

Существующие DATE/TIME/NOW/TIMER и FILEDATE/FILECREATEDATE/FILEACCESSEDDATE/DIRDATE имеют false. Новые NowInstant, ElapsedSecondsSinceStart и четыре UTC-функции метаданных не добавлены; для них действует ветвь по умолчанию true.

Оконное сравнение проведено для двух программ, отличающихся только вызовом:

```basic
DIM marker AS INTEGER = 0
DIM value AS DOUBLE = ELAPSEDSECONDS()
PRINT value
```

После перехода на строку 3 и одного обратного шага на строку 2:

- контроль TIMER(): canStepBack=false — история до чтения внешних часов разорвана;
- ELAPSEDSECONDS(): canStepBack=true — можно перейти дальше назад за чтение счётчика.

Первый обратный шаг сам по себе допустим в обоих случаях: он может восстановить состояние после чтения перед записью результата. Дефект подтверждает именно сохранение дальнейшей истории через внешнее чтение у новой функции. Поэтому сравнение одного canStepBack на строке 3 было бы недостаточным доказательством.

Исправление: классифицировать новые функции по эффекту, а не по новизне. Чтение текущих часов, монотонного счётчика и метаданных файлов — внешние операции; чистые INSTANTVALUE, DATETIMESERIAL и ELAPSEDSECONDS(from,to) должны сохранять обратимость. Проверить каждый новый идентификатор отдельно.

## Дополнительные замечания

1. Центральный справочник типов и основной реестр не согласованы с новым типом: `docs/manual/data-types.html` и таблица диапазонов `data-type-limits.html` не содержат UTCDATETIME; README и `docs/registries/LANGUAGE.md` по-прежнему заявляют 14 типов, 271 функцию и 335 форм. Текущий check-manual сообщает 282 функции и 351 форму, а реальный Electron получает 15 имён типов. Структурная проверка справочника проходит и не обнаруживает это смысловое расхождение.
2. RuntimeValueEqualityComparer.SupportsElementType не включает UTCDATETIME. ARRAYDISTINCT даёт правильный результат в проверенном случае, но для нового типа выбирает прежний попарный путь вместо хеш-множества. Это замечание к полноте интеграции и возможной квадратичной стоимости на уникальных массивах, а не измеренный в этой проверке отказ производительности.
3. В DTA-015 разные нагрузки выполняют 400, 120 и 300 проходов и разные наборы операций. Их медианы относятся к программам целиком. Из меньшей медианы программы поясов нельзя заключать, что отдельный поиск пояса дешевле отдельного разбора или календарной операции. Нагрузки полезны, но для такого вывода нужен нормированный объём и разделение операций. Повторного измерения здесь не было.
4. Решение не вводить отдельный тип длительности и использовать DOUBLE зафиксировано в документах как выбор автора; оно не объявляется дефектом этой проверки. Также не пересматривается зафиксированное секундное разрешение функций текущих часов.

## Очередь исправлений

1. DTR-001: пересылка GetMonotonicSeconds и точные тесты без ожиданий.
2. DTR-003: согласованный строгий разбор INPUT и начальных значений полей.
3. DTR-002: структурное равенство TYPE с UTCDATETIME.
4. DTR-004 и DTR-005: снимки временных значений и правильные границы обратимого исполнения; затем адресный оконный повтор.
5. Согласовать справочник типов, таблицу диапазонов, реестр и обзор; уточнить ограничения измерений и проверить путь DISTINCT нового типа.
6. Повторно сверить DTA-001..015 по независимым критериям; только после этого менять заключение о полном закрытии.

В этой задаче изменены только сопровождающие документы. Реализация не исправлялась, продуктовые версии не повышались, коммит и отправка не выполнялись.
