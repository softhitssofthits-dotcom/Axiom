# План полного перехода массивов Axiom на квадратные скобки

Дата: 22 октября 2026 года. Статус: план подготовлен для обсуждения, реализация не начата.

**Цель:** однозначно разделить обычное имя, массив и вызов функции: `fruit`, `fruits[]`, `fruits[2]`, `MakeFruits()`. Перевести на этот договор весь язык, проектные программы и IDE. Сохранить отдельный цвет массивов во всех четырёх темах и подробные подсказки типа элементов и числа измерений.

**Исходное состояние:** язык 0.2.10, компилятор/CLI 0.3.9, IDE 0.8.15. Этапы 1 и 2 прежнего плана и последующее уточнение круглых скобок находятся в рабочем дереве вместе с редактурой справочника. Опубликован только более ранний коммит плана и независимого аудита ed3741bd. Сначала сохранить и различить эти изменения, не выдавая рабочее дерево за чистую базовую ревизию.

**Приоритет:** [план развития массивов и коллекций](ARRAYS_COLLECTIONS_ROADMAP_2026-10-22.md) отложен отдельным решением автора. ARRAYDISTINCT, сортировка записей, литералы, FOR EACH и новые коллекции не реализуются в рамках перехода. Выполненные ускорения, правила владения, цвет и подсказки сохраняются. Новое поручение отменяет прежний выбор круглых скобок для массивов, но пока не меняет реализацию.

## 1. Целевой договор для обсуждения

Ниже приведён будущий синтаксис. Он ещё не работает.

### Обычное имя, массив целиком, элемент и функция

```basic
DIM fruit AS STRING = "яблоко"
DIM fruits[] AS STRING = SPLIT("яблоко,банан", ",")
DIM basket[] = fruits[]
PRINT fruit
PRINT basket[2]
```

Ожидаемый вывод:

```text
яблоко
банан
```

| Запись | Смысл |
|---|---|
| `fruit` | Обычная переменная или другое обычное имя согласно его объявлению |
| `fruits[]` | Массив целиком |
| `fruits[2]` | Элемент одномерного массива |
| `grid[2, 3]` | Элемент двумерного массива |
| `fruits[1 TO 2]` | Представление выбранной части массива |
| `grid[2]` | Частичное индексирование многомерного массива по прежним правилам |
| `MakeFruits()` | Вызов функции, в том числе возвращающей массив |
| `MakeFruits()[2]` | Элемент результата вызова, возвращающего массив |
| `bag.fruits[]` | Массивное поле записи целиком |

**Строгость конечного состояния:** если `fruits` объявлен массивом, употребление его имени в выражении без `[]` отклоняется с подсказкой правильной записи. `fruits()` и `fruits(2)` также отклоняются как прежние массивные формы. Вызовы функций и скобки математических выражений сохраняют `()`.

Это не создаёт две независимые сущности с именем `fruits`: объявленному массиву требуются квадратные скобки при обращении. Имя без скобок не превращается автоматически в отдельную строку или число. Правила существующей области видимости сохраняются.

`[]` не означает пустоту, копирование, перебор или выделение элементов. Во всех выражениях массива целиком используется `[]`, в том числе для многомерного массива; число измерений выясняется из его типа. Переменная-массив и её элементы сохраняют принятый цвет категории массива на самом имени.

Вызов функции, возвращающей массив, сам является массивным выражением: `DIM basket[] = MakeFruits()` допустим без дополнительного `[]` после вызова. Обязательное обозначение относится к обращению через массивное имя или поле; повторный суффикс `MakeFruits()[]` не нужен для основной записи. Его необходимость не включена в обязательный договор перехода.

### Объявления, границы и ранг

```basic
DIM fruits[] AS STRING
DIM fruits[] AS STRING = SPLIT("яблоко,банан", ",")
DIM fruits[] = SPLIT("яблоко,банан", ",")
DIM grades[1 TO 3] AS INTEGER
DIM grid[,] AS INTEGER
DIM grid[1 TO 2, 1 TO 3] AS INTEGER
REDIM fruits[1 TO 3]
REDIM PRESERVE fruits[1 TO 5]
ERASE fruits[]
```

Строки с повторяющимися именами показывают отдельные формы, а не одну программу. В объявлении `[]` задаёт ранг 1, `[,]` — ранг 2 и так далее. В выражении `grid[]` обозначает весь массив любого ранга; `grid[,]` без индексов не служит второй записью массива целиком.

Объявление без AS по-прежнему требует начального выражения. Если оно возвращает массив, требуется запись массивного имени со скобками: `DIM fruits[] = ...`. `DIM fruits = SPLIT(...)` в конечном строгом режиме должно получить понятную диагностику, а не скрыто объявить массив. Тип элементов выводится по прежним правилам, ранг проверяется по скобкам.

Объявление с явно заданными границами и начальным выражением остаётся запрещённым: переход меняет скобки, а не это правило. Пределы выделения, допустимость пустого диапазона, нижние границы, нормализация фиксированных строк и значения по умолчанию сохраняются.

Для объявления переменных основной и единственный целевой способ обозначить массив — скобки после имени. Прежнюю альтернативу `DIM fruits AS STRING () = ...` переводить в `DIM fruits[] AS STRING = ...`; не вводить для DIM вторую конкурирующую запись `DIM fruits AS STRING[] = ...`. Это предлагаемое следствие требования автора о визуально явном массивном имени, которое следует подтвердить при рассмотрении плана.

### Параметры, возвращаемые типы и присваивание

Предлагаемая единая запись:

```basic
SUB ShowBasket(values[] AS STRING)
    PRINT values[2]
END SUB

FUNCTION MakeFruits() AS STRING[]
    DIM result[] AS STRING = SPLIT("яблоко,банан", ",")
    RETURN result[]
END FUNCTION
```

```basic
DIM fruits[] AS STRING = MakeFruits()
DIM basket[] = fruits[]
basket[2] = "груша"
PRINT fruits[2]
ShowBasket(fruits[])
```

Ожидаемый вывод второй программы при наличии объявлений процедуры и функции выше: две строки `груша`. Присваивание сохраняет общую память. Независимая копия по-прежнему создаётся через `ARRAYCLONE(fruits[])`.

В анонимных описаниях типов, возвращаемом типе и других местах без имени используются суффиксы типа `STRING[]`, `INTEGER[,]`. Списки параметров процедур и функциональных типов остаются круглыми. Для параметров с именами предлагаются `values[] AS STRING`, `grid[,] AS INTEGER`, включая существующие BYVAL/BYREF. Эти формы отдельно проверить на совместимость с моделью ParameterSyntax, а не считать простой заменой знаков.

Строка примера `ShowBasket(fruits[])` содержит одновременно обе роли: круглые скобки вызова и квадратные массива. Вложенная запись `fruits[ChooseFruit()]` должна сохранять вызов функции внутри индекса.

## 2. Сохраняемые свойства и границы задачи

- Не менять типы элементов, модель памяти, общую память, ARRAYCLONE, состояния выделения, границы и ранги, смысл частичного индексирования и TO, инвалидирование представлений, фиксированные строки, TYPE, BYREF, снимки и отладочный откат.
- Сохранить ускорение вставки/удаления в конце массива из этапа 1 и работу начальных выражений из этапа 2, переведя их внешнюю запись.
- Сохранить цвета и подсказки четырёх тем. Подсказки и подписи типов должны показывать новые скобки и действительную категорию массива.
- Не вводить литералы, прямые массивы массивов, новые контейнеры и новые имена встроенных функций вместе с заменой скобок.
- Скобки графических операторов, математических выражений, функций, строкового текста и комментариев не меняются автоматически.
- Существующие файлы пользователя переводятся только по явному поручению; проектные образцы и испытательные программы входят в переход. Преобразователь сначала показывает изменения и не переписывает ошибочный или неоднозначный фрагмент по догадке.

## 3. Порядок реализации

Этапы идут по зависимостям. Их стоимость не обязана строго возрастать: перенос большого числа программ может оказаться трудоёмче изменения парсера. На каждом этапе фиксировать проверяемый результат в журнале. До конца перехода отдельные промежуточные ветви не выдавать за готовый строгий язык.

### Этап 1. Зафиксировать договор и полную карту затронутых мест

1. Подтвердить целевые формы из раздела 1: обязательность `[]` у массивного имени, объявление только со скобками после имени, параметры и возвращаемые типы, ранг объявления и массив целиком.
2. Снять перечень массивных узлов и привязок по текущему исходному коду, включая REDIM/ERASE, TYPE, функциональные значения, модули, вложенные процедуры, интерполяцию, отладочные выражения, нормализацию имён, навигацию и переименование.
3. Разделить прежние формы на преобразуемые автоматически и требующие разбора ошибочного исходника. Указать существующие локальные изменения и подготовить отдельный проверяемый набор без чужой редакторской работы.
4. Записать исходные контрольные программы и результаты по текущему языку, чтобы дальнейшее изменение ожидаемых строк не скрывало семантические ошибки.

**Файлы:** действующие спецификация, архитектура и реестр языка; Parser.*; Binder.*; перечисления токенов; существующие проверки, samples, генераторы и документы. Новый перечень миграции размещать рядом с этим планом в docs/plans.

**Готовность:** утверждённые формы и карта миграции без неопределённости о том, где требуются скобки. На этапе не менять выполнение массивов.

### Этап 2. Квадратные токены и отдельные узлы синтаксиса

1. Добавить `[` и `]` в TokenKind, Lexer, SyntaxKind и соответствие токенов Parser.Helpers.cs. Проверить координаты и восстановление после незакрытой скобки.
2. Разделить вызов и массивное обращение в AST: CallExpressionSyntax обслуживает `()`, отдельный массивный узел — `[]`, индекс и диапазон. Если прежние узлы границ и типа содержат свойства OpenParenToken/CloseParenToken, согласованно переименовать их без маскировки нового знака старым именем.
3. Обновить Parser.Expressions.cs, Parser.Declarations.cs, Parser.Statements.cs и Parser.DataStatements.cs: объявления, параметрические списки, типы, REDIM, ERASE, составные цели и вложенные обращения.
4. Не переносить ошибочные пустые/лишние индексы в выполнение; различать ранг декларации и пустой суффикс выражения.

**Проверки:** группы lexer, syntax, parser; адресные примеры `fruits[ChooseFruit()]`, `MakeFruits()[2]`, `bag.fruits[]`, `grid[-1, 7 TO 8]`, `[ ]`, незакрытая скобка, `grid[,]` в неправильном контексте, строки и комментарии со скобками. Отдельные ожидания AST для функции и массива.

**Готовность:** новые формы корректно разбираются и диагностируются независимо от семантики. Круглые группирующие скобки, процедуры и графические формы сохранены.

### Этап 3. Связывание, строгие массивные имена и выполнение

1. Обновить Binder.Expressions.cs, Binder.InvocationExpressions.cs, Binder.ArrayInvocations.cs, Binder.DeclarationStatements.cs, Binder.Declarations.cs и Binder.TypeResolution.cs для отдельных узлов и новой формы параметров.
2. Разделить разрешение имени как цели квадратного обращения и как обычного выражения. Массивное имя без `[]` должно давать адресную диагностику; имя типа, обычная переменная, функция и встроенная функция сохраняют свои правила.
3. Сохранить BoundArrayAccessExpression и существующие связанные формы там, где меняется только запись. `fruits[]` разрешается в массивную цель; индексы и TO сохраняют прежний смысл. Проверить чтение и запись, включая целый массив и BYREF.
4. Обновить представление ArrayTypeSymbol в подписях и метаданных. Сначала проверить, не используется ли Type.Name как ключ сериализации или идентичности: не менять формат байт-кода только ради отображения.
5. Проверить PUBLIC/IMPORT, локальные области, массивные поля, массивы TYPE, фиксированные строки, функциональные значения, результаты функций и интерполяцию.

**Проверки:** адресные semantics, bytecode, execution и runtime по массивам и затронутым объявлениям; независимые ожидаемые результаты BytecodeVm; контроль сериализации, валидатора и повторного выполнения. .NET-команды выполнять последовательно, не делить obj между параллельными запусками.

**Готовность:** простые и сложные программы с квадратными скобками выполняются по прежним правилам. Необходимость изменения формата байт-кода решается по фактам, а не предполагается заранее.

## 4. Контрольные случаи, которые нельзя потерять

- В одной строке встречаются функция, массив и группировка: `fruits[ChooseFruit() + (offset * 2)]`.
- Функция возвращает массив, а параметр другого вызова принимает его: `ShowBasket(MakeFruits())`.
- Массив функциональных значений или функциональный тип исследуется по реально допустимой модели; не вводить новый тип ради проверки записи. Существующая функция, возвращающая массив, не должна ошибочно окрашиваться массивом.
- Частичное индексирование, диапазоны, фиксированные массивные поля TYPE, массивы записей и доступ через поле остаются разными проверяемыми случаями.
- Неизменённые границы, состояния выделения и инвалидирование представлений, ARRAYCLONE и общая память, BYREF, снимки и откат сохраняются.
- Строки и комментарии содержат `fruits(2)`, `fruits[]`, кавычки и скобки; интерполяция содержит действительные массивные выражения. Преобразование меняет только код.
- Имя локальной переменной совпадает с именем функции/массива в другом модуле. Решение принимается по связанному символу и конкретной позиции.
- Ошибочный незавершённый файл не получает выдуманную миграцию. Исправленная вручную программа после повторного запуска преобразователя остаётся неизменной.

## 5. Текущий следующий шаг

Обсудить целевой договор раздела 1. В частности, подтвердить следствия полного различения: массивное имя без `[]` запрещено, выведенное объявление пишется `DIM fruits[] = ...`, а параметры — `values[] AS STRING`. Затем по отдельному поручению начать этап 1. В этой задаче изменены только документы; проверки реализации и преобразование программ не выполнялись, продуктовые версии не повышались.
