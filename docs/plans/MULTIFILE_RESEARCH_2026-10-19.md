# Исследование многофайловой программы: варианты и влияние

Дата: 19 октября 2026 года. Основание: [аудит подпрограмм](ROUTINES_AUDIT_2026-10-19.md), [план](ROUTINES_AND_MULTIFILE_PLAN_2026-10-19.md), этапы 8–9. Реализация в этом задании не выполнялась: по решению автора сначала требуется исследование договора.

Решения автора, зафиксированные при подготовке этого документа:

- договор многофайловой программы пока только исследуется, синтаксис и модификаторы не вводятся;
- состав проекта на диске предполагается как папка с исходниками и явная точка входа; точный формат остаётся открытым.

## Что уже готово и чего не хватает

Текущая модель: `CompilationRequest`/`ExecutionRequest` содержат одну строку `SourceText`; `TextLocation` знает только span, строку и колонку; `FunctionSymbol` знает имя и `ContainingRoutine`; `VariableSymbol` различает глобальность и `IsReadOnly`; `LoweredProgram` имеет одну точку `<global>`; `RoutineId` назначается внутри одного результата компиляции.

Этого достаточно для одного файла и недостаточно для нескольких: нет владельца файла у позиций и символов, нет отдельной доступности, нет проекта как набора исходных единиц. Склеивание файлов в одну строку теряет границы доступности и координаты и поэтому не рассматривается.

## Вариант A. Файл = модуль, открытые имена по умолчанию

Один `.axm` — один модуль. Верхнеуровневые процедуры, функции и типы доступны другим файлам без модификаторов. Закрытость вводится позже отдельным модификатором. Импорт явный: файл перечисляет зависимости по имени модуля.

Влияние:

- минимальное изменение существующих программ: одиночный файл ведёт себя как раньше;
- `FunctionSymbol` получает владельца-модуль, но доступность по умолчанию остаётся открытой;
- разрешение имени должно учитывать текущий модуль, импортированные модули и неоднозначность одинаковых имён;
- инициализация: верхнеуровневые операторы допустимы только в точке входа, иначе появляется неявный порядок выполнения библиотек.

Риск: открытые по умолчанию имена облегчают случайные конфликты и затрудняют последующее закрытие без несовместимости.

## Вариант B. Файл = модуль, закрытые имена по умолчанию

Всё закрыто, наружу выходит только явно помеченное. Импорт явный, вызовы требуют либо импорта, либо уточнения именем модуля.

Влияние:

- требуется новый модификатор и его регистрация в парсере, IDE-подсветке, форматировании и справочнике;
- действующие одиночные программы сохраняются, если точка входа считается модулем с неявно открытыми именами;
- появляется отдельное правило для закрытых функциональных значений: публичная фабрика может вернуть функцию с закрытым именем, и вызов уже полученного значения не должен требовать доступа к имени;
- закрытость имени не означает глубокую неизменяемость данных: возвращённый массив сохраняет общее хранилище.

Риск: больше синтаксиса и диагностики до того, как появится первый реальный сценарий из нескольких файлов.

## Вариант C. Модуль из нескольких файлов

Модуль — отдельная единица доступности, состоящая из нескольких файлов. Доступность задаётся на уровне модуля, файл перестаёт быть границей.

Влияние:

- нужен синтаксис группы файлов или отдельный файл проекта, связывающий файлы в модуль;
- владелец символа — модуль, а не файл; координаты диагностики всё равно должны различать файлы;
- сложнее объяснить пользователю, почему два файла одного модуля видят друг друга, а два модуля — нет.

Риск: самый большой объём изменений при неясной выгоде для первых сценариев.

## Общие требования к любому варианту

1. Исходная единица с устойчивой идентичностью: путь или логическое имя, различающее два файла с одинаковыми именами и строками.
2. Владелец символа: модуль, файл, лексическое вложение и длительность хранения разделяются.
3. Разрешение имени: текущий модуль, импортированное пространство, экспортируемая поверхность; одинаковая неоднозначность должна давать диагностику, а не выбирать файл по порядку.
4. Связывание по идентичности символа, а не по короткому имени; `RoutineId` не должен быть глобальной идентичностью между результатами компиляции.
5. Инициализация: явный порядок, правила циклов, повторный запуск; верхнеуровневые операторы библиотеки либо запрещены, либо получают определённый порядок.
6. Документная идентичность в диагностике, карте инструкций, стеке вызовов и точках останова: две точки останова на одной строке разных файлов должны различаться.
7. Кэши и повторное использование результатов: ключ должен учитывать содержимое и идентичность зависимостей, а не только текст точки входа.

## Влияние на IDE

- DesktopHost получает состав проекта и версию снимка; правка одного файла должна перепроверять зависимые.
- Дополнение, hover, диагностика, навигация, граф вызовов, переименование и отладка должны различать документы.
- Новые пользовательские слова и формы одновременно обновляют Monaco, семантические категории, форматирование и проверки `ide/tests`/`ide/e2e`.
- Пути ресурсов и рабочая папка не должны самопроизвольно меняться из-за появления нескольких исходников.

## Минимальная матрица приёмки будущей реализации

Два файла; одинаковые закрытые имена; запрещённое внешнее обращение; открытая сигнатура с `TYPE` из другого модуля; рекурсия между модулями; возврат закрытого замыкания; мутация BYREF; инициализация и её ошибка; повторный запуск; две точки останова на одной строке разных документов; изменение зависимости и устаревший ответ IDE.

## Рекомендация по порядку

1. Утвердить единицу доступности и доступность по умолчанию (варианты A или B).
2. Ввести модель исходной единицы и владельца символа без нового синтаксиса: набор исходников, идентичность документа, владелец модуля. Это уже позволяет диагностике и отладке различать файлы.
3. Затем ввести импорт и правила неоднозначности.
4. Только после этого — порядок инициализации и формат проекта.
5. IDE подключать последней, когда контракт компиляции стабилен.

До утверждения варианта новые модификаторы и операторы не регистрируются в парсере и IDE как работающие возможности.
