# Предложение: самостоятельный проект Axiom

Статус: предложение принято автором 21 октября 2026 года командой «Внедряй». Ход реализации и результаты приведены ниже; действующий договор закреплён в docs/PROJECTS.md и SPECIFICATION3. Исходное предложение сохранено для понимания решений. Подготовлено 21 октября 2026 года после замечания об организации папки проекта. Удаление «Прочих файлов» из панели выполнено отдельно и не означает принятия нового формата.

## Что установлено по реализации

ProjectSession получает рекурсивный список .axm из выбранной папки. Принадлежность определяется путём под projectDir; все найденные исходники при обычном открытии становятся вкладками. Выбор запуска хранится в projectEntries локального профиля, с запасным выбором корневого main.axm либо единственного исходника. Профиль также хранит последнюю папку. Внешняя активная вкладка запускается самостоятельно. Импорты и состав исполняемой программы определяет DesktopHost, а не список вкладок.

Обнаружение файлов в подпапках уже работает, но действующая модель IMPORT ограничена модулями рядом с точкой входа. Новое дерево папок и маски включения сами по себе это ограничение не устраняют. Отдельный файл проекта, поддержка его CLI и единая переносимая точка входа пока отсутствуют.

## Варианты

1. Оставить папку и профиль. Наименьшая стоимость, но выбор запуска не переносится вместе с программой, нет явного описания состава и общей команды проверки проекта.
2. Файл проекта с явным списком каждого исходника. Точный состав, но создание и переименование каждого файла требует согласованного изменения списка; часты конфликты при совместной работе.
3. Файл проекта с точкой входа и правилами включения файлов. Рекомендуемый вариант: новые исходники автоматически попадают в проект, исключения задаются явно, настройки программы переносятся вместе с папкой. Стоимость — загрузчик, проверка путей и небольшой строго определённый договор масок.

Современный .NET SDK тоже позволяет включать исходники по маскам по умолчанию, а не перечислять каждый .cs вручную. Из .csproj заимствуется идея переносимого описания проекта; MSBuild, XML, система целей сборки и все настройки .NET Axiom не требуются.
Источник сравнения: https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview . Этот источник не задаёт семантику Axiom.

## Предлагаемый первый формат

Предлагаемое расширение — .axproj, содержимое — JSON UTF-8. Имя файла может отличаться от отображаемого имени. Пример предполагаемого описания Maze Chase:

```json
{
  "formatVersion": 1,
  "name": "Maze Chase",
  "entry": "main.axm",
  "sources": ["*.axm"],
  "assets": ["art/**"],
  "exclude": []
}
```

Это иллюстрация будущего формата, не существующий файл приёмки. Конкретные ресурсы и данные игры надо сверить при её переводе; пример не объявляет полный состав ресурсов Maze Chase.

Корень проекта — каталог файла .axproj. entry обязателен, должен указывать на существующий исходник из sources после исключений. name задаёт заголовок проекта; при отсутствии можно использовать имя файла проекта. sources задаёт исходники; assets — ресурсы и другие данные, которые отображаются в дереве и должны учитываться при будущей поставке программы. exclude исключает элементы обеих групп. Точный набор обязательных полей и значения по умолчанию фиксируются перед реализацией.

Для первой версии достаточно относительных путей и ограниченных масок: буквальный путь, * внутри одного сегмента и ** для вложенных каталогов. Не вводить полный язык шаблонов, переменные среды, выражения, условные свойства и команды оболочки. Служебные каталоги .git, .artifacts, node_modules, bin и obj исключаются по умолчанию. Пустой или повреждённый проект не подменяется молча открытием папки.

Абсолютные пути, выход через .. и неявные внешние ссылки не поддерживаются в первой версии. Проверять не только строковый префикс: нормализованный путь, регистр и фактический выход через ссылки/точки повторной обработки Windows должны иметь отдельные тесты. Неизвестная версия формата вызывает понятный отказ; точные диагностики надо определить при реализации, не приписывать им заранее языковые коды MB.

## Проект и исполнение

Файл проекта задаёт принадлежность, ресурсы и точку входа. IMPORT сохраняет явные зависимости: попадание .axm в sources не означает выполнение его верхнеуровневых инструкций или появление всех его имён в общей области видимости. Не менять незаметно существующий порядок инициализации модулей.

Предлагается различать «Проверить проект» и «Запустить проект». Проверка охватывает все включённые исходники: сначала граф точки входа, затем недостижимые исходники в самостоятельных допустимых контекстах, без двойных диагностик и принудительного объединения модулей. Такой договор требует отдельной реализации и тестов. Запуск и отладка исполняют граф entry. Попытка импортировать исключённый или внешний модуль должна выдавать ошибку принадлежности, а не обходить sources.

Для первого этапа сохраняется нынешнее ограничение соседних модулей. Разрешение импортов из подпапок, поиск по нескольким каталогам, зависимости между проектами и циклы — отдельные решения. Ошибочно обещать поддержку этих возможностей только потому, что дерево показывает подпапки.

Относительные пути ресурсов при запуске проекта предлагается считать от его корня. До изменения нужно отдельно сверить действующее поведение файловых операторов, CANVAS/SCREEN, CLI и DesktopHost; новый файл не должен самовольно менять результаты существующих программ. Запуск отдельного .axm сохраняет существующий договор.

## Работа в IDE

- Открытие .axproj создаёт один сеанс проекта, показывает настоящее дерево его папок, исходников и ресурсов. Внешние открытые документы остаются вкладками, в дерево проекта не добавляются.
- Открытие проекта не обязано открывать все файлы вкладками: открыть entry, остальные — по запросу или восстановлению локального сеанса. Состав проекта не зависит от числа вкладок.
- Точка входа принадлежит проекту и сохраняется в .axproj. Действующий постоянный список «Файл запуска» предлагается заменить свойством проекта и командой «Назначить файлом запуска»; выбранный файл отмечается в дереве. Это предложение по интерфейсу, не уже выполненная правка.
- При открытом проекте F5 и обычная команда запуска должны однозначно запускать проект даже при активной внешней вкладке. Для внешнего документа нужна отдельная явная команда запуска текущего файла. Изменение нынешнего поведения надо утвердить и показать в подсказках команд.
- Переименование entry обновляет .axproj согласованно с переименованием файла. Удаление entry требует выбора замены либо оставляет проект в явно неготовом состоянии; не выбирать случайный первый исходник.
- Новый исходник создаётся внутри проекта; исключение из проекта и удаление с диска — разные действия. Не выдавать одно за другое.
- При смене проекта не терять несохранённые документы. Переключение и закрытие должны учитывать принадлежность исходников, ресурсов и самого описания проекта.

Положения окна, высоты панелей, вкладки, курсоры, тема и другие личные параметры остаются в профиле IDE. В переносимый .axproj они не попадают. Переезд папки не меняет относительные пути entry и ресурсов.

## Архитектура и переход

Один общий загрузчик и проверка описания в службах .NET используются CLI и DesktopHost. Electron получает проверенное описание через IPC; не создавать второй независимый парсер с другой семантикой путей. Список, запуск, диагностика, снимки несохранённых файлов, помощник и отладка используют один сеанс проекта и одну точку входа. Сам JSON может редактироваться IDE с атомарной записью, проверкой внешних изменений и защитой от потери правок.

Открытие отдельного .axm сохраняется. Старый режим открытия папки сохраняется как временный режим совместимости: предложить создать .axproj из текущей папки и явно подтверждённой точки входа, но не записывать его автоматически. При одном описании проекта папка может предлагать открыть его; при нескольких требуется выбор. Восстановление последнего проекта должно хранить путь к описанию, а не только путь к папке.

Предлагаемая последовательность реализации:
1. Утвердить минимальный формат, правила состава, запуск при внешней вкладке и отображение ресурсов.
2. Общий загрузчик, проверка путей/масок, ошибки и атомарное сохранение; адресные тесты служб.
3. Открытие .axproj и дерево IDE, свойства точки входа, создание/переименование и восстановление сеанса.
4. Согласовать CLI, запуск, проверку, отладку, помощник и несохранённые модели.
5. Перевести копию Maze Chase, проверить перенос папки и работу ресурсов, затем обычное открытие отдельного .axm.

Первый выпуск такой подсистемы потребует повышения версии IDE; версии компилятора и языка зависят от фактического изменения CLI/служб и семантики. В этой задаче формат не реализуется и язык не меняется.

Приёмка: перенос проекта на другой путь без локального projectEntries; независимость состава от вкладок; новый исходник по маске; исключения; отсутствующая entry; повреждённый JSON; неизвестная версия; пути за корнем и Windows-ссылки; переименование и удаление точки входа; ресурсы; внешняя вкладка; несохранённые зависимости; открытие отдельного .axm; отказ записи описания; перезапуск IDE. Полная многофайловая проверка должна иметь независимые ожидаемые диагностики, а не только совпадение двух запусков одной реализации.
