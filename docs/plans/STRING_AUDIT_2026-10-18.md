## 4. Ошибки, подтверждённые выполнением

### STR-001 — P1: оптимизация `s = s + F()` меняет порядок чтения

Места: `src/Axiom.Bytecode/Lowering/BoundProgramLowerer.cs:833`, `src/Axiom.Runtime/Execution/BytecodeVm.cs:1422`.

Понижение исключает чтение левой переменной и оставляет вычисление правой части с последующим `AppendString`. VM читает значение назначения уже после вызова функции. Обычный бинарный путь сначала вычисляет левый операнд (`BoundProgramLowerer.cs:1691`).

```basic
DIM s AS STRING = "A"
s = s + Change()
PRINT s
FUNCTION Change() AS STRING
    s = "X"
    RETURN "B"
END FUNCTION
```

Получено `XB`; при обычном порядке чтения требуется `AB`. Контрольный случай с `DIM old AS STRING = s` и `s = old + Change()` возвращает `AB`. Это наблюдаемое изменение результата из-за оптимизации. Проверить также `&`, глобальные/локальные значения, `BYREF`, захваченные переменные и `STRING * N`.

Исправление: сохранять значение слева до вызова либо запрещать преобразование при недоказанном отсутствии влияния правой части на назначение. Доказательство безопасности должно учитывать косвенные вызовы и захваченные значения. Простая проверка имени функции недостаточна.

### STR-002 — P1: изменяемый накопитель меняет уже вычисленный операнд

Места: `BytecodeVm.cs:611`, `BytecodeVm.cs:1459`, `BytecodeCallFrame.cs:136`, `RuntimeStringAccumulator.cs:15`.

```basic
DIM s AS STRING = "A"
s = s + "B"
DIM t AS STRING = s + Change()
PRINT t
PRINT s
FUNCTION Change() AS STRING
    s = s + "C"
    RETURN "D"
END FUNCTION
```

Получено `ABCD`, затем `ABC`. Ожидается `ABD`, затем `ABC`: вычисленный левый операнд должен сохранять своё значение. В стек попадает объект со ссылкой на накопитель, а функция меняет тот же накопитель. Здесь целевая переменная `t` другая, поэтому одного исправления STR-001 недостаточно.

Исправление: определить владение накопителем и момент получения неизменяемого значения. Рассмотреть снимок при чтении из слота либо копирование при последующей записи в разделяемый накопитель. Не вводить безусловную полную копию при каждом чтении без измерений: это может вернуть квадратичное накопление. Проверить также сравнение, аргументы последующих вызовов, массивы, поля, `BYVAL`, `RETURN` и снимки отладки.

### STR-003 — P1: `PRINT USING` меняет знак отрицательной экспоненты

Место: `src/Axiom.Runtime/Builtins/BuiltinPrintUsingHelpers.cs:334`, особенно строки 350–359.

`PRINT USING "###.##^^^^"; 0.001` вернул `  1.00E+03`; требуется `  1.00E-03`. При выделении цифр экспоненты знак уже отброшен, а затем вычисляется из положительного числа. Ошибка меняет числовой смысл текста на шесть порядков. Узкая маска `#.##^^^^` скрывает проблему за штатным результатом переполнения поля `%0.001`; для воспроизведения нужна достаточная ширина.

Исправление: разбирать экспоненту вместе со знаком или сохранять знак отдельно. Ожидания для отрицательной/нулевой/положительной степени задавать буквально, без вызова проверяемого форматтера.

### STR-004 — P2: экспоненциальный вывод целых и DECIMAL теряет точность через DOUBLE

Место: `BuiltinPrintUsingHelpers.cs:338`.

`PRINT USING "####################.################^^^^"; 9007199254740993` вернул мантиссу `9.0071992547409920E+15` вместо `9.0071992547409930E+15`. Значение LONG сначала превращается в DECIMAL, а затем принудительно сужается до DOUBLE. Здесь маска запрашивает достаточно разрядов, чтобы различие было видимым.

Исправление: форматировать исходный числовой тип напрямую; нормализацию экспоненты выполнять уже над его корректным текстом. Проверить LONG около `2^53`, большие DECIMAL, отрицательные значения и округление последнего разряда.

### STR-005 — P1: длинная маска `PRINT USING` выводит исключение .NET за границу языка

Места: `BuiltinPrintUsingHelpers.cs:320`, `BytecodeVm.PrintUsing.cs:15`, обработчик инструкции `BytecodeVm.cs:525`.

Длина маски ограничена 2048 единицами UTF-16, но число дробных разрядов не проверяется до `Math.Round`:

- `PRINT USING "#.#############################"; 1` — 29 разрядов, `ArgumentOutOfRangeException` от Decimal;
- `PRINT USING "#.################"; 1.0` — 16 разрядов, аналогичное исключение от Double.

Оба случая воспроизведены: `Run` выбрасывает исключение вместо возврата результата с диагностикой. `TRY/CATCH` Axiom не получает штатного отказа. Это не просто слишком длинный вывод.

Исправление: отдельно определить допустимую точность формата и способ округления каждого типа; либо поддержать её корректным алгоритмом, либо выдать MB3007 до вызова .NET. Не молча обрезать маску. Проверить границы 15/16 и 28/29, исходную и вычисляемую строку маски, `TRY/CATCH` и продолжение программы.

### STR-006 — P2: служба вывода IDE теряет начальные пустые строки

Места: `src/Axiom.Ide.Backend/Services/Input/ConsoleOutputService.cs:37`, `:45`; публикация — `src/Axiom.DesktopHost/DesktopHost.cs:327`.

Пустая история и история из одной пустой строки имеют одинаковое представление `""`. Два вызова `AppendTranscriptLine("")`, затем `AppendTranscriptLine("X")` дали только `X`, контрольные точки после пустых строк — `0`, итоговая — `1`. Воспроизведение выполнено на самой службе. Соответствующая программа: два пустых `PRINT`, затем `PRINT "X"`.

Нужны раздельное состояние наличия строк и их содержимое, корректные контрольные точки и восстановление. Проверить также программу только с пустыми строками, очистку и переход к ожиданию INPUT. Оконный эффект по цепочке службы/снимков ожидаем, но в этом аудите реальное окно Electron не запускалось. Существующий сценарий пустой строки после непустой не покрывает потерю в начале.

### STR-007 — P2: вложенная интерполяция не разбирается

Места: `src/Axiom.Lexing/Lexer.cs:460`, `:597`; `src/Axiom.Parsing/Parser.Expressions.cs`.

`PRINT $"{$"x"}"` возвращает `SyntaxFailure`, MB0002 и несколько MB1001. Парсер допускает рекурсивную интерполяцию как выражение, но лексер хранит в стеке только позиции начала и использует общее состояние нахождения внутри вставки. Внутренняя строка получает состояние внешней вставки.

Это рассогласование общей модели выражений и автомата лексера. Справочник не выделяет вложенность как отдельную гарантированную форму; при исправлении нужно явно зафиксировать поддержку, а не молча менять восстановление ошибок. Тест `Execute_InterpolatedStringNested` в `LanguageContractTests.cs:1125` фактически проверяет соседние вставки, а не вложенную строку.

Исправление: стек полного состояния интерполяции, включая нахождение во вставке и служебную глубину; проверки вложенных литералов/вызовов, кавычек, форматов, незавершённого внутреннего выражения и корректного восстановления после него.

### STR-009 — P2: длительные обычные строковые операции не проверяют отмену

Места: `RuntimeStringReplaceMany.cs:23`, `:84`, `BuiltinStringHelpers.cs:107`, `BuiltinStringUnitHelpers.cs:48`. VM проверяет отмену между инструкциями, но внутри этих циклов её нет.

У `REPLACEMANY` правила группируются только по первой кодовой единице. Худший случай — длинный текст из `a` и множество правил с длинным общим префиксом и несовпадающим последним символом; порядок работы может достигать `O(N × K × L)`. Внутренние циклы реализации `SUBSTRCOUNT` и построения границ Unicode также могут занимать длительное время в одной инструкции. Обычные циклы исходной программы состоят из нескольких инструкций и имеют промежуточные проверки отмены. RegEx уже имеет проверки отмены между совпадениями — его старую проблему нельзя повторно объявлять неустранённой.

Нужно добавить контролируемые точки отмены в собственные длительные циклы и отдельно исследовать поиск по нескольким правилам. При выборе дерева префиксов/другого алгоритма сохранить нынешний договор: одновременная замена, самое длинное совпадение, при равной длине — порядок правил. Прерывание одиночного синхронного вызова .NET этим автоматически не гарантируется. Физическое завершение процесса обычного запуска IDE и кооперативная отмена VM — разные проверки.

### STR-010 — P2: Unicode-срезы строят полный индекс ради короткого результата

Места: `BuiltinStringUnitHelpers.cs:23`, `:37`, `:48`.

`LEFT(text,1,"CODEPOINT")` создаёт `List<int>` всех границ и затем `ToArray`. `MID(text,2147483647,1,"CODEPOINT")` делает то же перед возвратом пустого результата. Для N ASCII-символов это `O(N)` времени и дополнительной памяти; одновременно существуют хранилище списка и его копия. `LEN(...,"GRAPHEME")` тоже строит массив границ, хотя возвращает только количество.

Нужны последовательный проход до нужной границы для LEFT/MID, ранний отказ при `start > text.Length`, подсчёт без полного массива для LEN. Для RIGHT сравнить двухпроходный вариант с ограниченным буфером границ. Сохранить изолированные суррогаты и все нынешние Unicode-ожидания. Не вводить глобальный кэш исходных строк: он может удерживать большие документы дольше необходимого.

### STR-011 — P2: `LINENUMBER` повторно читает весь префикс файла

Места: `RuntimeTextFile.cs:215`, `:673`.

Каждое обращение проходит от начала содержимого до текущей позиции с восстановлением позиции потока. В последовательном цикле `READLINE` + `LINENUMBER` суммарная работа растёт квадратично. Нужен учёт номера строки при последовательном чтении либо разреженный индекс; отдельно определить инвалидирование после SEEK/записи, CR/LF/CRLF, UTF-16 и ошибки декодирования. Замеры 10/20/40 тысяч строк должны подтверждать и скорость, и независимые номера.

### STR-012 — P2: файловая запись удерживает весь несброшенный результат и копирует его при FLUSH

Места: `RuntimeTextFile.cs:18`, `:301`, `:405`.

Каждый WRITE создаёт байты, добавляет их в `List<byte>`; FLUSH делает `ToArray`, то есть полную копию накопления. После `Clear` ёмкость списка остаётся. Без явного сброса большой результат хранится до закрытия/другого действия, вызывающего сброс.

Нужно ограниченное буферизованное хранение или запись блоками без полной копии. Сохранить наблюдаемый договор FLUSH, FILEPOS/FILELEN, SEEK и ошибки кодирования до изменения файла. Автоматическая запись до явного FLUSH может менять видимость для других читателей: это требует сверки договора, а не механической замены списка на поток.

### STR-013 — P2: накопление истории консоли копирует и пересчитывает весь текст

Места: `ConsoleOutputService.cs:37`, `:47`, `:60`.

На каждую строку создаётся `старый текст + перевод строки + новая строка`, затем `OutputCheckpoint` разбивает весь текст. Для N коротких строк — квадратичная суммарная работа. Нужны отдельный счётчик строк и блоки/список истории; полный снимок формировать по необходимости. Проверить, не возвращает ли публикация полного снимка прежнюю стоимость на каждом шаге. Сохранить принадлежность вывода сессии, INPUT и обратный шаг. В отличие от исправления STR-006, здесь обязательны измерения времени и памяти DesktopHost.

### STR-014 — P2: явный APPENDFILE каждый раз проверяет всё прежнее содержимое

Места: `BuiltinTextEncodingHelpers.cs:44`, `:56`.

При непустом файле `Write(...,append:true)` вызывает `ValidateStream`, который декодирует весь файл перед добавлением. Цикл добавления небольших фрагментов с явной кодировкой повторно читает растущий префикс. Это цена строгой проверки существующего текста, а не доказательство неправильной кодировки.

Нельзя просто убрать проверку: это отменит защиту от несовместимого BOM/повреждённого содержимого. Сначала измерить и сопоставить с уже доступным OPEN FOR APPEND и WRITE; для частых записей рекомендовать открытый FILE. Любой кэш проверки должен учитывать внешнее изменение файла и не доверять одному имени пути.

### STR-017 — P2: договор VAL не определяет неполную экспоненту достаточно явно

Обещание чтения числового начала позволяет ожидать `12`, но точная обработка незавершённой экспоненты отдельно не задана.

Сначала утвердить правило максимального корректного числового префикса и набор цифр. Рекомендация: ASCII-цифры для числовой грамматики, включение экспоненты только при наличии её цифр, сохранение прежнего нуля для отсутствия числа и непредставимого результата. `ISNUMERIC` проверяет всю строку и конечность — объединять её с VAL так, чтобы исчезло различие полного разбора и префикса, нельзя.

## 7. Что не следует «исправлять» без изменения договора

- UTF16-формы LEFT/RIGHT/MID, строковые поля PRINT USING, STRING/fill и `STRING * N` могут разрезать суррогатную пару; это закреплённый договор кодовых единиц, а не автоматически новый дефект.
- CODEPOINT и GRAPHEME уже поддержаны явными формами LEN/LEFT/RIGHT/MID. Изолированные суррогаты сохраняются; заменять их на U+FFFD в этих операциях нельзя.
- REVERSE сохраняет пары суррогатов, но не обещает разворот целых графем. TRIM со списком символов работает по `char`. Изменение на графемы будет изменением поведения.
- `INSTRREV("", "") = 0`, пустой SPLIT и границы пустых массивов имеют собственные ожидания в тестах. Не нормализовать их по чужому языку.
- Сравнение строк порядковое, поиск регистрозависимый, регистр меняется инвариантно; автоматическая нормализация Unicode и зависимость от языка ОС не предусмотрены.
- Справочник прямо сохраняет исходную запись `{{`/`}}` в текстовой части интерполяции. Различие `Text`/`Value` требует прояснения архитектуры, но не самовольного сворачивания скобок.
- `INPUT` одной строки сохраняет логическую строку; несколько целей не являются универсальным CSV. READTEXT считает кодовые точки, файловая позиция остаётся байтовой.
- Чтение UTF-8/UTF-16, границы буфера, BOM, строгие явные кодировки и восстановление позиции после ошибки уже имеют адресные тесты. Новый дефект этих механизмов не подтверждён.
- Графический текст и измерения могут использовать UTF-16-ячейки согласно действующему справочнику. Это не обещание типографской ширины графем или полноценного формирования сложного текста.
- RegEx уже исправлен в предыдущем аудите: отмена между совпадениями, кэш до 128 сочетаний, экономный подсчёт, буквальная замена и конкретные ошибки. Одна попытка поиска может занимать до пяти секунд; ограничение числа записей не является ограничением их суммарного объёма.

## 8. Поэтапный план исправлений

Порядок: семантика и управляемые ошибки → корректность интерфейса/лексера → ресурсы → измеренные ускорения → физическое разделение. Структурный перенос нельзя смешивать с исправлением семантики: иначе трудно проверить причину изменения результата.

Для каждого этапа: сначала постоянная проверка с независимым ожиданием и воспроизведение отказа, затем минимальное исправление, затем наименьший затронутый набор. При изменении поведения обновить соответствующую страницу справочника, спецификацию и записи покрытия; при изменении нагрузки — реестр измерений. Версии выбирать по фактически изменённому компоненту. Полный набор проекта не является обязательным шагом каждого пункта.

## 9. Измерения и ограничения завершения

Существуют `string_primitive_scan.axm`, `string_concat_accumulator.axm`, `string_array_loop_pipeline.axm`, нагрузки файлов и RegEx. Отдельные измерения ISNUMERIC и CODEPOINT/GRAPHEME уже отмечены открытыми в BYTECODE_PERF_MATRIX. Их нельзя объявить выполненными по результатам обычных тестов.

Кандидаты новых отдельных нагрузок: короткий Unicode-префикс большого текста; REPLACEMANY с общим префиксом правил; повторный PRINT USING одной маски; последовательный READLINE+LINENUMBER; мелкие записи с FLUSH и без; повторный APPENDFILE с явной кодировкой; история вывода. Для каждой фиксировать вход, независимый результат, прогрев, повторы, время VM/полного запуска и выделенную память. Обещаний конкретного ускорения до замеров нет.

Отдельный остаток доказательств: транспортировка изолированных суррогатов через JSON/консоль/файл; настоящий Electron для начальных пустых строк и отказа форматирования; отображение/StepBack строк после побочных эффектов; отмена внутреннего исполнения; память больших результатов. Если пользовательский договор допускает UTF16-фрагмент, потеря фрагмента при дальнейшей передаче должна проверяться как отдельная граница, а не скрываться заменой единицы измерения исходной функции.

 Следующий логический шаг — **S01**, затем **S02**: сначала исправить наблюдаемую семантику строкового значения. Исполнение плана требует отдельного поручения автора; сейчас подготовлены только анализ и очередь.

## Устранение отказа `single-line-if` — 19 октября 2026 года

Адресная проверка подтвердила, что провайдер подсказок для `CATCH problem` корректен при LF и CRLF, на русском и английском языках. После изменения адресный сценарий прошёл 11/11, группа `e2e-language` — 12/12.
