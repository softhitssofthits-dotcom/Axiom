Рекомендации по дизайну имён: NIT-001 и NIT-003

Как правильно решить «переменная vs процедура» и «поле без SELF» с точки зрения современных языков · 2026-08-26

Кратко

Оба пункта проверены шестью дополнительными прогонами на актуальной сборке (проверки № 41–46 отчёта VARIABLES_SCOPE_AUDIT). Вывод: семантику менять не нужно — язык уже реализует современные модели; нужно задокументировать правила и улучшить диагностику. Ниже — обоснование и конкретные шаги.

NIT-001: переменная и процедура с одним именем

Факты о текущем поведении (проверено запусками)

ПроверкаПримерРезультат
№ 38DIM Foo = 7 + SUB Foo: PRINT Foo7 — в выражении побеждает переменная
№ 41Глобальная переменная + вложенная SUB Foo внутри другой SUB7 7 — сосуществование на любом уровне вложенности
№ 42Локальная переменная с именем глобальной процедуры5 — конфликта нет, классы имён разделены
№ 43Локальная переменная с именем поля TYPE внутри метода5 — поля тоже отдельный класс
№ 44f = Make, где Make — и функция, и переменнаяMB2003 «ожидался FUNCTION…, получен INTEGER» — сообщение не подсказывает, что Make — ещё и функция

Правило фактически действует: имена разделены на классы (переменные/константы/параметры, процедуры, поля TYPE); внутри класса — запреты MB2002/MB2016, между классами — свободное сосуществование.

Модели современных языков

МодельЯзыкиПоведение
Единое пространство имён, коллизия = ошибкаC, Go, Java; C# для локальных и методовзапрет на этапе компиляции
Раздельные пространства имён по ролиRust (типы vs значения), C++ (теги), C# (тип vs метод)сосуществование, разрешение по синтаксису
Единое пространство, функции — значенияPython, JavaScriptпереприсваивание имени перекрывает функцию

Ключевой аргумент в пользу сохранения: в Axiom нет классической BASIC-схемы «имя функции = возвращаемое значение» (возврат только через RETURN), поэтому сосуществование имён не создаёт ловушек, из-за которых VB-языки запрещают такие совпадения.

Рекомендация: оставить раздельные классы имён (как в Rust/C#) и:
  1. задокументировать правило как первоклассное: «имена разных классов не конфликтуют, внутри класса конфликтуют»;
  2. добавить предупреждение (не ошибку) при совпадении имени переменной и процедуры — по образцу CS0108 в C#: «Имя 'Foo' используется и как переменная, и как процедура — проверьте, не опечатка ли это»;
  3. в MB2003 при ожидании FUNCTION-типа добавлять примечание «возможно, вы хотели присвоить ссылку на функцию 'Make'» (проверка № 44).

Не рекомендуется полный запрет в стиле C (сломает рабочие программы без выигрыша в корректности) и единое пространство в стиле Python/JS (противоречит статической проверке и семейству BASIC).

NIT-003: «голое» имя поля в методе TYPE

Факты о текущем поведении (проверено запусками)

ПроверкаПримерРезультат
№ 31x = x + dx без SELF в методеMB2001 «Имя 'x' не объявлено» — общая диагностика без подсказки
№ 43DIM Value внутри метода при поле Valueуспех — локальная и поле не конфликтуют
№ 46SELF.Valu (опечатка) при поле ValueMB2023 «Тип Counter не содержит поле 'Valu'» — специализированная диагностика уже есть

Модели современных языков

МодельЯзыкиПоведение
Неявный приёмникC#, Java, Kotlin, Swift, VB.NETголое имя = this/Me.поле; локальная переменная побеждает поле
Явный приёмникRustобязательно self.поле; при пропуске — специализированная подсказка (rustc, аналог E0425: «используйте self.x»)
Рекомендация: сохранить явный SELF (это выбор Rust и философия Axiom «всё явно»), исправить качество диагностики:
  1. новая специализированная диагностика для «голого» имени поля: «Поле 'Value' доступно только через SELF: напишите SELF.Value» (по образцу подсказок rustc E0425, новый код рядом с MB2023);
  2. улучшить MB2023: при опечатке подсказывать ближайшее похожее поле («Возможно, вы имели в виду поле 'Value'»).

Не рекомендуется переход на неявный приёмник без отдельного решения: он вводит правило «локальная побеждает поле», противоречащее чистой модели «поля — отдельный класс» и запрету перекрытия MB2016. Если эргономика VB нужна — это отдельное изменение семантики с явным правилом приоритета.

Дополнительно: NIT-005 (новый)

Проверка № 45: CALL Foo даёт MB2001: Имя 'CALL' не объявлено — оператора CALL в Axiom нет, вызовы только Foo(). Для мигрантов из BASIC: если первое слово строки — CALL, выдавать подсказку «оператора CALL нет: просто напишите Foo()». Поведение не менять. P4

Что нужно от команды языка

  1. Принять ли рекомендации NIT-001 (документирование классов имён + предупреждение + подсказка в MB2003)?
  2. Принять ли рекомендации NIT-003 (спец. диагностика «поле без SELF» + подсказка опечаток в MB2023)?
  3. Добавлять ли подсказку для CALL (NIT-005)?
