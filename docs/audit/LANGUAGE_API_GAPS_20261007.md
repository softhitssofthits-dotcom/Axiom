# Что Axiom стоит добавить в стандартную библиотеку

Дата: 2026-10-07. Проверенная база: `2603b3d`. Это анализ потребностей, а не утверждённый план реализации. Названия и сигнатуры ниже являются предложениями и не описывают уже работающий синтаксис.

Проверены 249 зарегистрированных имён, формы в binder, действующая спецификация, `FEATURE_LEDGER.md`, `FUTURE.md`, runnable-примеры и существующие альтернативы. Отсутствие функции в реестре не означает отсутствие операции: например, форматирование выполняется интерполированными строками, а короткое замыкание — операторами.

## MUST — необходимое для надёжной работы текущих средств

### G01 — явный выбор кодировки существующих файловых операций — ADD

- Категория: MISSING ESSENTIAL FEATURE; файловый обмен. Приоритет: высокий после исправления LA26-010/011.
- Сценарий: дописывание русского текста в существующий Windows-1251-файл, чтение заведомо UTF-16-файла, строгий отказ вместо угадывания кодировки.
- Текущее решение: чтение угадывает UTF-8/1251, запись всегда UTF-8; ручное восстановление повреждённого текста через строковые операции не обеспечивает корректный обмен произвольными файлами.
- Доказательство: сценарий `append-cp1251`: исходный байт C0 («А»), затем WRITE в APPEND строки «я» создаёт C0 D1 8F. READFILE возвращает «АСЏ». Первоначальные байты не уничтожены; смешанная кодировка подтверждена. Отдельно имеются дефекты автоопределения LA26-010.
- Почему неудобно: программист не может потребовать заданную кодировку или проверить совместимость перед дописыванием. Исправление эвристики не решает UTF-16 и неоднозначные байтовые последовательности.
- Предлагаемые перегрузки: `READFILE(path AS STRING, encoding AS STRING) AS STRING`, `WRITEFILE(path AS STRING, text AS STRING, encoding AS STRING) AS BOOLEAN`, `APPENDFILE(path AS STRING, text AS STRING, encoding AS STRING) AS BOOLEAN`; согласованная форма выбора кодировки для OPEN требует отдельного синтаксического решения. Для READALLLINES — аналогичная перегрузка с результатом STRING-массивом.
- Договор: ограниченный явно перечисленный набор кодировок, строгое декодирование, правило BOM и проверка APPEND. Не открывать пользователю весь реестр CLR-кодировок автоматически.
- Совместимость: сохранить существующую форму; риск средний из-за BOM, позиций и старых файлов. Сложность: средняя. Необходимы байтовые тесты в обоих движках и обновление manual.
- Имена сохраняют существующие проектные READFILE/WRITEFILE/APPENDFILE. Исторический VB подтверждает развитие файловых режимов, но не задаёт Axiom контракт параметра encoding.

## SHOULD — полезно, но требуется отдельное решение об объёме

### G02 — строгая проверка числовой строки — CONSIDER

- Категория: OPTIONAL ENHANCEMENT; ввод и преобразования. Приоритет: средний.
- Сценарий: отличить корректный ноль от нечислового ввода, не принимать `12abc` как число.
- Текущее решение: REGEXISMATCH с собственной грамматикой, затем VAL; TRY не помогает, поскольку VAL возвращает 0 или читает префикс.
- Почему неудобно: дублируется грамматика знака, экспоненты и конечности; regex может пропустить число, которое не помещается в DOUBLE. Это больше одного простого выражения.
- Предложение: BASIC-наследуемое `ISNUMERIC(text AS STRING) AS BOOLEAN` с договором полного инвариантного конечного числа; возможная дополнительная форма строгого преобразования должна обсуждаться отдельно. Тип результата предиката — BOOLEAN, перегрузка по числовым типам не нужна.
- Риск: средний — у VB ISNUMERIC иная широта, отличие нужно явно описать. Сложность: низкая/средняя после единого числового парсера. Не меняет префиксный VAL. Наличие у VB не является самостоятельным основанием добавления.

### G03 — ограниченный двоичный файловый доступ — CONSIDER

- Категория: OPTIONAL ENHANCEMENT / отдельное проектируемое направление. Приоритет: средний только при подтверждённом сценарии сохранения данных/ресурсов.
- Сценарий: записать и прочитать произвольные байты без потери и перекодирования.
- Текущее решение: отсутствует общий путь; GET/PUT работают с графикой, CHR/ASC кодируют символы, а не обеспечивают байтовое соответствие. Текстовое экранирование возможно для собственного формата, но не для произвольного двоичного файла.
- Предлагаемый договор: BASIC-наследуемый режим `OPEN … FOR BINARY`; чтение `FILE × LONG(position) × INTEGER(count) → INTEGER()` со значениями 0..255, запись `FILE × LONG(position) × INTEGER() → BOOLEAN`. Окончательное написание форм GET/PUT и пересечение с графическими операторами **не выбрано**: требуется проектирование, не механическое копирование QuickBASIC.
- Перегрузки: сначала последовательный/позиционный доступ к байтам; random-record layout отложить. Риск: высокий, затрагивает FILE и модель ошибок. Сложность: высокая. Не вводить BYTE, буферы и сериализацию объектов в одном срезе.
- Вывод: реальное ограничение API, но отсутствие двоичного режима не является регрессией текущего текстового FILE.

### G04 — opt-in режим Unicode для длины и срезов — CONSIDER

- Категория: OPTIONAL ENHANCEMENT; пользовательский текст. Приоритет: средний после LA26-012.
- Сценарий: ограничить отображаемое имя до нескольких символов, не разрезав эмодзи, combining sequence или ZWJ-последовательность.
- Текущее решение: UTF-16 LEN/LEFT/MID, REVERSE сохраняет корректные пары; ASCW/CHRW позволяют вручную восстанавливать скаляры, но нет готовой сегментации grapheme clusters.
- Почему неудобно: цикл по скалярам ещё возможен, корректная сегментация видимых символов существенно сложнее; замена всех строковых функций новой семантикой сломает действующие программы.
- Предложение для проектирования: перегрузки существующих имён `LEN(text AS STRING, unit AS STRING) AS INTEGER`, `LEFT(text AS STRING, count AS INTEGER, unit AS STRING) AS STRING`, затем согласованные RIGHT/MID при необходимости. Набор unit и окончательные формы **не утверждены**; code point и grapheme должны быть разными режимами.
- Риск: средний/высокий, особенно при смешении индексов INSTR/MID. Сложность: средняя/высокая. Имена LEN/LEFT наследуются из BASIC, новые оригинальные названия не назначаются.
- Вывод: полезная возможность для пользовательского текста, а не доказательство того, что нынешний UTF-16 LEN сломан.

## Запланированные возможности

Массивные литералы, FOR EACH, MAP/словарь, необязательные параметры, лямбды, многострочные строки и DATA/READ/RESTORE отражены в `FUTURE.md`/`FEATURE_LEDGER.md`. Отсутствие соответствующего синтаксиса не считается регрессией. Они могут улучшить удобство, но новый аудит не превращает их автоматически в обязательную реализацию.

LINE INPUT — запланированная форма консольного чтения. Для файлового чтения целой строки уже есть READLINE(FILE); это не эквивалент чтения строки из консоли. Модули остаются отдельным проектируемым направлением. Классы, указатели и полная QB-совместимость также не являются найденными «пропущенными функциями».

## Источники исторических имён

Официальная документация [VB Hex](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.conversion.hex?view=net-10.0) подтверждает BASIC-прецедент числового HEX, а [QB64 HEX$](https://qb64.com/wiki/HEX%24.html) — историческую форму с суффиксом. В Axiom отдельная функция для этого сценария сейчас не нужна благодаря формату X.

[VB Format](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.strings.format?view=net-10.0) служит справкой о происхождении имени, но его договор не переносится в Axiom: обычные числовые форматы уже есть в интерполяции.

[VB FileOpen](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.filesystem.fileopen?view=net-10.0) подтверждает BASIC-семейство файловых режимов, включая Binary. Это аргумент для названия режима при будущем проектировании, а не основание копировать всю файловую библиотеку VB.

[VB IsNumeric](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.information.isnumeric?view=net-10.0) подтверждает происхождение имени предиката. Предлагаемый строгий строковый договор Axiom существенно уже VB-предиката, который работает с разными типами и дополнительными числовыми формами; это отличие должно быть явным.

## Вывод анализа API

Подтверждён один наиболее существенный пробел текущей библиотеки: управляемый кодировочный договор. Три следующих направления для обсуждения — строгая числовая проверка, ограниченный двоичный доступ и opt-in Unicode-операции. Остальные кандидаты ниже по приоритету либо уже выражаются текущими средствами. Четыре направления не означают четыре одобренные задачи: сначала требуется закрыть дефекты существующего языка.

## Session 1127 — статус G01: PARTIAL

Работают READFILE(path, encoding), READALLLINES(path, encoding), WRITEFILE(path, text, encoding), APPENDFILE(path, text, encoding). Выбраны четыре фиксированные кодировки с проверенной строгостью; подробности EXPLICIT_TEXT_ENCODING_G01.md. Старые формы сохранены. WINDOWS-1251 читает BOM-подобные префиксы буквально, иначе действительный текст «яю» потерял бы возможность чтения. Unicode BOM согласуется с выбранным Unicode-форматом. Полное решение 3633/3633. Форма OPEN и связанный потоковый FILE-договор ещё не реализованы; G01 не закрыт полностью. Остальные предложения не становятся автоматически утверждёнными возможностями.

### Session 1130 — G01 реализован в выбранном объёме

Функции целого файла и OPEN USING encoding поддерживают UTF-8, WINDOWS-1251, UTF-16LE, UTF-16BE. Независимые отрицательные проверки выявили и исправили два отказа интеграции: строгая запись и LINENUMBER теперь дают перехватываемую MB3007. Договор, ограничения и доказательства EXPLICIT_TEXT_ENCODING_G01.md и EXPLICIT_OPEN_RECHECK_20261008.md. Классификация G01: необходимой возможности действительно не хватало, теперь IMPLEMENTED для согласованного текстового API. Это не доказательство завершения всего аудита и не основание добавлять кандидаты SHOULD/CONSIDER без проверки реальных сценариев.

### Session 1131 — классификация потребностей REGEX

Явные числовые номера групп и остановка после count уже входили в существующий API; RX26-001/002 исправляются как BROKEN FUNCTION, без новых имён. Успешное пустое совпадение можно отличить от отсутствия совпадения функцией REGEXISMATCH: дополнительная функция для этого не нужна. Unicode-поведение REGEX следует .NET/UTF-16, а не отдельной модели графем; это документированное ограничение, не основание добавлять весь Unicode API. Форма извлечения по строковому имени группы действительно отсутствует, но номера, включая явно задаваемые номера, покрывают текущие подтверждённые задачи; обязательное расширение не утверждается без самостоятельного сценария. Широкие новые наборы REGEX-функций не добавляются по аналогии с Python/.NET.

## Session 1135 — потребности DateTime

DT26-001/003 исправляют существующие формы DIM/DATEADD; новые функции не требуются. DATETIME из канонической строки уже получается через типизированное объявление или присваивание, например DIM moment AS DATETIME = "2024-02-29 23:59:59"; отдельный DATETIMESERIAL для этого сценария не обязателен. Разбор произвольных локализованных дат, дробных секунд и расширенная календарная библиотека не входят в доказанный договор и не добавляются по аналогии с .NET. WEEKYEAR из старого вступления manual — ошибка документации, не подтверждённое требование продукта.

## Session 1136 — Unicode-потребности

UTF-16-позиции и точный поиск подтверждены, это существующий договор. Графемы/нормализация отсутствуют, обязательный сценарий этим срезом не доказан. Безрегистровое сопоставление уже возможно REGEXISMATCH с i; оно не заменяет нормализацию. Отчёт STRING_SEARCH_RECHECK_20261008.md.

## Session 1137 — существующие строковые альтернативы

STRING повторяет первую единицу UTF-16; для повтора всего фрагмента, включая эмодзи, уже есть REPEAT. SPLIT с явным строковым разделителем уже принимает эмодзи/несколько единиц UTF-16. Новые дубли этих API не нужны. Графемы/нормализация/экранная ширина не доказаны строковым набором; расширения не добавлены.

## Session 1138 — обрезка, регистр и коды символов
