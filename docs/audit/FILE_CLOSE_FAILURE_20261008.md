# FILE26-001: отказ записи при закрытии файла

При ошибке сброса буфера RuntimeTextFile.Dispose пропускал освобождение FileStream. CloseAllOpenFiles прекращал обход на первом отказе, оставляя другие ресурсы открытыми. Оператор CLOSE вызывал общий код закрытия без перевода IOException в диагностику языка. Это дефект существующего средства, а не отсутствие нового API.

## Независимое воспроизведение

FileCloseFailureEvidenceTests открывает настоящий временный файл, добавляет текст в буфер Axiom и блокирует диапазон 0..4095 отдельным FileStream-читателем в Windows. До исправления оба теста не проходили: IsOpen оставался TRUE и реестр содержал оба ресурса после первого отказа. После исправления оба теста проходят, второй файл содержит ожидаемый текст, первый доступен для эксклюзивного открытия после снятия блокировки.

FileFinalizationFailureEvidenceTests вводит такую же блокировку через IOutputWriter в заранее определённой точке программы. Проверены два движка и два сценария: явный CLOSE внутри TRY/CATCH и автоматическое завершение. До исправления 0/4; после 4/4. В первом сценарии обработчик получает MB3007 и ISOPEN возвращает FALSE. Во втором результат RuntimeFailure содержит MB3007. Во всех сценариях второй файл сохранён, ресурс первого освобождён; Bytecode не переходит на интерпретатор.

Тесты диапазонной блокировки относятся к Windows и не подтверждают такую же модель блокировок на других ОС. Проверка отсутствия CLR-исключения подтверждена вызовом настоящего AxiomExecutionPipeline.Run, а не только отдельным Dispose.

## Исправление

- Dispose освобождает FileStream в finally и отмечает ресурс закрытым.
- CloseFile удаляет закрытый ресурс из реестра даже при отказе.
- CloseAllOpenFiles пытается закрыть весь набор и сообщает каждую файловую ошибку движку; прямой вызов без обработчика повторно выдаёт первую ошибку после обхода.
- Явный CLOSE переводит файловое исключение в MB3007 и RuntimeFailureException для TRY/CATCH.

После отказа закрытия сохранение всего текста не гарантируется. Освобождение ресурса не превращает неудачную запись в успешную и не обещает откат уже записанных байтов. FLUSH и CLOSE имеют разные последствия: повторный FLUSH после временного отказа требует отдельной проверки, а CLOSE уже завершает жизненный цикл ресурса.

Справочник close.html обновлён. Пример samples/operators/close/write_failure_state.axm проверяет состояние двух файлов после закрытия; без внешней блокировки это обычный успешный путь. Контролируемое воспроизведение отказа находится в автоматизированных тестах.

Редакционный ориентир — Зельднер, CLOSE, страница 187. Запасной текущий жанровый ориентир: https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.filesystem.fileclose?view=net-10.0 . Историческое закрытие всех файлов оператором без аргумента не добавлено в Axiom.
