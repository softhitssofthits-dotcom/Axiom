# Повторный сброс после временной блокировки файла

Session 1173 проверяет продолжение работы после MB3007 функции FLUSH и сохранение исходной ошибки программы при дополнительном отказе автоматического закрытия. Новая встроенная функция или изменение Runtime не потребовались.

## Независимые случаи

В FileFinalizationFailureEvidenceTests.FlushAfterUnlockWritesBufferedTextExactlyOnce проверены два движка, OUTPUT/APPEND и две длины текста: «А😀» и 4096 букв «А» с emoji. Большая запись превышает внутренний буфер FileStream. Реальная Windows-блокировка диапазона 0..4095 вводится отдельным читателем перед FLUSH и снимается после обработчика CATCH.

После отказа FLUSH:

- обработчик получает MB3007;
- ресурс остаётся открытым;
- FILEPOS/FILELENGTH сохраняют учёт принятого в буфер текста;
- после снятия блокировки добавление «Я», повторный FLUSH и ещё один пустой FLUSH успешны;
- итоговые байты совпадают с независимо заданным UTF-8-текстом без дублирования; APPEND сохраняет исходное «Начало».

В AutomaticCloseFailurePreservesPrimaryProgramError проверены оба движка: после записи и блокировки программа вызывает ERROR "APP1173", "Первичная ошибка". Итог RuntimeFailure сохраняет сначала APP1173 с исходным текстом, затем MB3007 закрытия. После снятия блокировки возможно эксклюзивное повторное открытие файла. Bytecode не переходит на интерпретатор.

## Что это доказывает и чего пока не доказывает

Восемь случаев повторного FLUSH и два случая сохранения диагностики прошли. Вместе с четырьмя прежними проверками CLOSE класс дал 14/14; совместный набор файлового чтения, записи, кодировок и закрытия — 120/120, ошибок и пропусков 0. TRX: `.artifacts/test-results/file-flush-1173/file-flush-1173-neighbors.trx`.

Проверки выполнены на Windows; платформенная ветка на других ОС не исполняет блокировки. Подтверждён временный отказ из-за блокировки диапазона, а не любой отказ носителя, заполнение диска или отключение устройства. Успешный повторный FLUSH не является обещанием атомарности, отката частичной записи или физической сохранности при потере питания. CLOSE завершает жизненный цикл ресурса даже при отказе, поэтому повторный FLUSH применим к оставшемуся открытому файлу после ошибки самого FLUSH, а не после ошибки CLOSE.

Последний полный прогон из Session 1172 — 5032/5032. В этой сессии добавлены десять тестовых случаев и ограничены Windows-веткой вызовы Lock/Unlock вспомогательного писателя; Runtime не менялся, полный набор заново не запускался. Новый runnable-пример поведения языка не требуется: семантика не изменена. Существующий samples/operators/close/write_failure_state.axm остаётся ручной проверкой обычного жизненного цикла, а не воспроизведением временной блокировки.

Следующая независимая проверка — COPYDIR/MOVEDIR: вложенное назначение, совпадающие пути, символические ссылки/точки повторного анализа и сохранение исходных данных при отказе. Сначала проверить существующие ограничения и альтернативы; не вводить API только по отсутствию отдельного имени.
