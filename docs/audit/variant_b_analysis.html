Вариант B: «счётчик FOR всегда локальный»

Подробный разбор · решение принято и реализовано в сессии 1107 · Axiom

Решение (сессия 1107): вариант B принят. Счётчик FOR всегда локальный — одна модель вместо двух. Причины: проще учить и объяснять; новичок не может случайно изменить свою переменную циклом; ловушка вложенных циклов исчезает на уровне контракта (MB2042 не нужен); ментальная модель совпадает с C#/Python/JS. Реализация: переиспользование имени — ошибка MB2016, неподходящий тип — MB2009; MB2042/MB2043 удалены; корпус сэмплов мигрирован (включая maze_chase.axm — копирование итога внутри тела); рекомендация ниже («остаться на варианте A») исторически заменена решением команды языка.

Что это значит

Сегодня в Axiom два режима счётчика (вариант A):

РежимПримерПосле NEXT
Неявный счётчик (создаётся циклом)FOR i = 1 TO 3 ... NEXTнедоступен MB2001 при обращении
Переиспользование объявленной переменнойDIM i: FOR i = 1 TO 3 ... NEXTдоступен содержит итог («на шаг за концом» = 4)

Вариант B — оставить только первый режим: FOR на уже существующей переменной становится ошибкой, счётчик всегда живёт только внутри цикла. Считывание итога — только через копирование в другую переменную внутри тела.

Важно: неявный счётчик в Axiom уже ведёт себя «по варианту B» (умирает после NEXT). Вариант B — не новая механика, а запрет второго режима.

Ключевой аргумент — не числа, а живой пример: maze_chase ищет стартовую позицию игрока циклом и читает координаты из счётчиков после NEXT. Это ровно тот паттерн QuickBASIC, ради которого режим переиспользования существует.

Как выглядела бы миграция

Сэмплы, которые не читают счётчик после цикла (просто переиспользуют имя), чинятся механически — удалить DIM: неявный счётчик уже работает и ведёт себя так же.

DIM rowIndex AS INTEGER          ' ← удалить
FOR rowIndex = 1 TO 5
    ...
NEXT

Сэмплы, которые читают итог (maze_chase, predeclared_counter, …), требуют рефакторинга — копирование внутри тела:

DIM foundRow AS INTEGER
FOR rowIndex = 1 TO 5
    IF maze(rowIndex) = "P" THEN
        foundRow = rowIndex        ' копия до NEXT
        EXIT FOR
    END IF
NEXT
PRINT foundRow                     ' было: PRINT rowIndex

Что это даст и что отнимет

Плюсы

  • Одна модель вместо двух — проще учить и объяснять;
  • Новичок физически не может случайно изменить свою переменную циклом (главный источник путаницы, из-за которого придуман MB2043);
  • Ловушка вложенных циклов исчезает на уровне контракта, а не диагностики (MB2042 становится не нужен);
  • Ментальная модель совпадает с C#/Python/JS.

Минусы

  • Разрыв с BASIC-линейкой: «после NEXT счётчик равен шагу за концом» — классическая идиома QuickBASIC, а Axiom позиционируется как BASIC-совместимый язык;
  • Ломается документированный паттерн «нужно значение после цикла» и флагманский сэмпл maze_chase;
  • Разовая цена миграции: ~11 сэмплов, ~15 тестов, 5 документов;
  • MB2042/MB2043, только что реализованные в сессии 1106, становятся мёртвым кодом.

Промежуточные варианты (строгость без разрыва)

Вывод

Вариант B решает проблему, которую вариант A закрывал диагностиками: ловушка вложенных циклов — ошибкой MB2042, неожиданное изменение переменной — предупреждением MB2043. При этом B ломает BASIC-идиому, собственный флагманский сэмпл и требует миграции корпуса.

Первоначальная рекомендация («остаться на варианте A») была исторически заменена решением команды языка: переход на B принят как осознанное стратегическое решение «Axiom отходит от BASIC-совместимости в сторону современных языков» и реализован в сессии 1107 (см. баннер в начале документа).
