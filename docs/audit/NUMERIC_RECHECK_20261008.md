## NUM26-001 — потеря знака нуля в пуле констант

P2, подтверждённый дефект компилятора. ConstantKey использовал object-равенство double: +0.0 и -0.0 равны и получали один индекс. После свёртки унарного минуса результат зависел от ранее зарегистрированного нуля. Это наблюдаемо через SETSIGN и ATN2. BytecodeCompiler.RegisterConstant теперь формирует ключ DOUBLE через BitConverter.DoubleToInt64Bits, а сохраняемое значение константы остаётся DOUBLE. Разные знаки больше не объединяются; одинаковые биты по-прежнему используют общий индекс. Новых инструкций и языковых сущностей нет.

Две проверки BytecodeCompilerTests проверяют оба порядка, два значения и повторное использование идентичной константы. Четыре проверки языкового пути подтверждают +3/-3, стороны ATN2 и смену знака. Пример samples/functions/setsign/signed_zero.axm нужен для ручной приёмки в IDE. Первый CLI-запуск до полной сборки использовал старую копию Axiom.Bytecode в каталоге CLI и повторил исходный дефект; это не итоговое доказательство исправления. Окончательный запуск записывается после сборки.

## Договор и потребности

Новая функция переноса знака не нужна: уже есть SETSIGN, исправлено сохранение констант. SGN(-0.0)=0 определяет отношение к нулю и не заменяет SETSIGN. MIN/MAX/CLAMP сохраняют точность целых при целочисленных аргументах; смешанная числовая арифметика следует продвижению типов. Общий вывод о точности всех математических значений не делается.

Неконечные результаты EXP/POW/SINH/COSH отклоняются MB3008, неверные области дают MB3007. VAL("NaN")/VAL("Infinity") уже возвращает 0; предыдущие отдельные внутренние тесты CINT/CLNG проверяют неконечные значения. Ввод искусственного NaN во все функции и все сочетания продвижения типов в этой сессии не проверены. Ни отсутствие публичного конструктора NaN, ни успешные примеры не доказывают всю внутреннюю устойчивость.

Manual SETSIGN поясняет контекст, типы, знак нуля, отличие от SGN и переполнение минимального INTEGER. Первый ориентир для числового знака — Зельднер ABS/SGN (275–277); SETSIGN у него не найден. Запасной жанровый ориентир — [Microsoft Learn: математические функции Visual Basic](https://learn.microsoft.com/en-us/dotnet/visual-basic/language-reference/functions/math-functions). Семантика NaN/Sqrt из VB не переносилась. CSV содержит 61 вариант и ровно 31 уникальный ID. Общий аудит и визуальная приёмка IDE не завершены.

Полное решение — 4290/4290, девять TRX, без ошибок и пропусков (.artifacts/numeric-1139-full.log и .artifacts/test-results/numeric-1139-full/). CLI после пересборки: TRUE/3/-3/TRUE/TRUE, код 0. git diff --check чистый.

## Session 1140 — смешанные типы и NUM26-002

NumericPromotionContractTests проверяет все 96 сочетаний INTEGER/LONG/DOUBLE/DECIMAL для MIN/MAX/CLAMP: 74 допустимых вызова имеют правильный общий тип аргументов/результата и результат обоих движков, 22 сочетания DECIMAL+DOUBLE отклоняются при связывании с одинаковыми координатами. CSV NUMERIC_PROMOTION_EVIDENCE_20261008.csv сохраняет каждое сочетание. Дополнительно проверены LONG.MinValue/MaxValue, DECIMAL порядка 9e27, точность целочисленного выбора, ABS/SETSIGN на минимальном LONG и явное преобразование.

Исходный прогон — 96/98: оба движка выбросили InvalidOperationException на CDBL(CDEC(2)). NUM26-002 P1: EvaluateCdbl использовал AsDouble, который намеренно не выполняет неявного преобразования DECIMAL. Исправлен именно явный CDBL: для DECIMAL используется явное приведение к double, другие ветви сохранены. RuntimeValue.AsDouble не расширялся. Это дефект существующей функции, а не отсутствие API. Итоговый набор с прежними числовыми проверками 232/232 (.artifacts/numeric-1140-fixed.log/TRX).

NumericNonFiniteOperandTests: NaN, +Infinity, -Infinity искусственно передаются в общий ToDoubleMathOperand и отклоняются через callback аргумента и RuntimeFailureException до вычисления, координаты сохранены; 3/3. Это проверка общей границы математических функций, не всех внутренних путей SGN/MIN/SETSIGN. Прямое получение таких значений через VAL уже запрещено прежним договором.

NUM26-003 P4: manual ошибочно обещал отсутствие потерь CDBL для любого целого типа. LONG выше 2^53 может округляться. Исправлен договор и добавлен inline-пример CDBL(CDEC(...)), смешанные аргументы и явный выбор DOUBLE. samples/functions/cdbl/decimal_precision.axm показывает 2/9007199254740992/TRUE/2; окончательный CLI-запуск проверяется после пересборки. Первый редакционный ориентир — Зельднер CDBL (288), пример о влиянии исходной точности; запасной — [Microsoft Learn Type Conversion Functions](https://learn.microsoft.com/en-us/dotnet/visual-basic/language-reference/functions/type-conversion-functions). Семантика округления CINT/CLNG из VB не переносилась.

Новых имён, токенов или измерений быстродействия нет. Все значения и комбинации операций не доказаны. Следующий срез — неагрегатные формы массивов: границы, выделение, копирование/срезы, сравнение доступных средств с реальными пробелами API. Общий аудит и визуальная приёмка IDE продолжаются.

Полный прогон решения — 4394/4394, девять TRX, без ошибок/пропусков (.artifacts/numeric-1140-full.log/TRX).
