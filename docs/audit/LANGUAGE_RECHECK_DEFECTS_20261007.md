## LA26-001 — скалярный результат считается массивом

- Функции: `ARRAYSUM`, `ARRAYMIN`, `ARRAYMAX`.
- Файлы: `src/Axiom.Semantics/Symbols/Builtins/BuiltinFunctions.Array.cs`, `BuiltinFunctions.cs`, `src/Axiom.Semantics/Binding/Binder.InvocationExpressions.cs`.
- Воспроизведение: сценарии `aggregate-scalar-type-ARRAYSUM` и `aggregate-inferred-type-ARRAYSUM`, аналогичные сценарии MIN/MAX; `.axm`: `samples/functions/arraysum/audit_scalar_result.axm`.

```basic
DIM a(1 TO 2) AS INTEGER
a(1)=2
a(2)=3
DIM result AS INTEGER
result=ARRAYSUM(a)
PRINT result
```

- Ожидается: `5`, результат типа `INTEGER`; для MIN — `2`, MAX — `3`.
- Interpreter: `SemanticFailure`, `MB2003`. BytecodeVm: тот же отказ до исполнения. Даже `DIM result = ARRAYSUM(a)` затем `PRINT result + 1` отклоняется.
- Причина: `CreateArraySameType` задаёт `SameAsFirstArgument` и объявленный массивный результат вместо типа элемента. Прямой PRINT маскирует проблему: runtime возвращает скаляр, а связыватель не требует от PRINT конкретного типа.
- Влияние: результат практически нельзя использовать в арифметике, присваивании и передаче числовому параметру.
- Исправление: отдельный дескриптор агрегата с `ElementTypeOfFirstArrayArgument`; проверить реальный разрешённый тип, не только печать.
- Необходимые тесты: INTEGER/LONG/DOUBLE/DECIMAL/STRING для MIN/MAX, присваивание, выведение типа, арифметика, возврат из FUNCTION и callback в обоих движках.
- Риск: средний, исправляется контракт связывания существующих функций.
- Документация: manual уже обещает тип элемента, менять этот договор не нужно. IDE: требуется согласование метаданных с политикой результата, см. LA26-014.

## LA26-002 — неперехваченное переполнение ARRAYSUM

- Файлы: `src/Axiom.Runtime/Builtins/BuiltinArrayAggregateHelpers.cs`, `Execution/Interpreter.Builtins.Array.cs`, `Execution/BytecodeVm.Builtins.Array.cs`.
- Воспроизведение: `sum-overflow`, `sum-long-overflow`, `sum-catch`; `.axm`: `samples/functions/arraysum/audit_checked_overflow.axm`. Массив содержит `2147483647` и `1` либо `LONG.MaxValue` и `1`.
- Ожидается: `MB3008`; внутри TRY ошибка должна попасть в CATCH, FINALLY должен исполниться.
- Interpreter и BytecodeVm: публичный `AxiomExecutionPipeline.Run` выбрасывает `System.OverflowException`. Обработчик ошибки языка не получает MB3008.
- Причина: `checked(acc + value)` находится внутри общего помощника без преобразования `OverflowException` в диагностику; обёртки движков тоже не перехватывают исключение.
- Влияние: выход из предусмотренной модели ошибок, срыв обработчика и выполнения программы; конкретное поведение внешней оболочки зависит от её перехвата исключений. Падение всего процесса IDE этим аудитом не утверждается.
- Исправление: превратить переполнение каждого числового типа в MB3008 на месте вычисления с сохранением координат.
- Тесты: все три checked-типа, положительное/отрицательное переполнение, TRY/CATCH/FINALLY, оба движка, CLI-код возврата.
- Риск: низкий/средний; нельзя заменять checked-арифметику насыщением или оборачивать все исключения без различения причины.
- Документация: уточнить диагностические случаи при необходимости, сохранить обещание проверяемой суммы. IDE: новых токенов нет.

## LA26-003 — CINT проверяет неусечённое число

- Файлы: `src/Axiom.Runtime/Values/RuntimeArithmeticHelpers.cs`, `src/Axiom.Runtime/Builtins/BuiltinNumericHelpers.cs`.
- Воспроизведение: `cint-upper-fraction`, `cint-lower-fraction`; `.axm`: `samples/functions/cint/audit_truncation_boundary.axm`.
- Ожидается: `CINT(2147483647.9) = 2147483647`, `CINT(-2147483648.9) = -2147483648` по принятому договору усечения к нулю.
- Interpreter и BytecodeVm: `RuntimeFailure`, `MB3008` в обоих случаях.
- Причина: `ToInt32Checked(double)` сравнивает исходное значение с границами до приведения. Аналогичный порядок у decimal-перегрузки требует регрессии; её отдельный пограничный сценарий в этом аудите не выполнен.
- Влияние: валидные преобразования у границы отвергаются.
- Исправление: проверить конечность, усечь, затем проверять диапазон. Не менять общую семантику всех пользователей помощника без проверки их договоров.
- Тесты: обе границы, следующий выходящий за диапазон целый результат, DECIMAL, DOUBLE, CINT/INT и неявные преобразования, если используют тот же помощник.
- Риск: средний из-за общего помощника. Документация: договор усечения уже есть. IDE: без изменений токенов.

## LA26-004 — верхняя граница CLNG и NaN

- Файл: `src/Axiom.Runtime/Builtins/BuiltinNumericHelpers.cs`, `CheckedDoubleToLong`.
- Воспроизведение: `clng-upper-exclusive`, `clng-upper-neighbour`, `clng-lower`, `clng-lower-outside`, `clng-nan`; `.axm`: `samples/functions/clng/audit_upper_boundary.axm`.
- Ожидается: `CLNG(9223372036854775808.0)` — MB3008; NaN также не является допустимым LONG. Соседнее представимое значение ниже границы должно приниматься.
- Interpreter и BytecodeVm на проверенной x64/.NET 10 среде: `Success`, соответственно `9223372036854775807` и `0`. Нижняя граница и ближайшее меньшее верхней значение прошли.
- Причина: при сравнении `double` с `long.MaxValue` последний округляется к `2^63`, поэтому условие `>` пропускает равенство. NaN проходит оба сравнения. Последующее приведение не checked.
- Влияние: молчаливое неверное преобразование вне диапазона.
- Исправление: исключённая верхняя граница `2^63`, включённая нижняя `-2^63`, отдельная проверка конечности и защищённое приведение.
- Тесты: два соседних DOUBLE у каждой границы, NaN/±Infinity через доступные пути, decimal-границы и оба движка.
- Риск: низкий для валидных входов; поведение вне диапазона должно стать диагностикой. Документация: уже обещает MB3008. IDE: без новых имён.

## LA26-005 — VAL создаёт NaN и Infinity

- Тесты: NaN/±Infinity, переполнение экспоненты, числовой префикс с хвостом, культура, нормальные числа; оба движка.
- Риск: средний, есть программы, которые могли использовать недокументированное поведение. Документация: устранить противоречие между страницами VAL, не объявлять текущую утечку новым договором. IDE: новых токенов нет.

## LA26-006 — CINT(NaN) выбрасывает OverflowException

- Файлы: `src/Axiom.Runtime/Values/RuntimeArithmeticHelpers.cs`, `ToInt32Checked(double)`; вызов из `BuiltinNumericHelpers.EvaluateCint`.
- Воспроизведение: `cint-nan`: `PRINT CINT(VAL("NaN"))`.
- Ожидается: диагностика MB3008 на недопустимое преобразование; после исправления VAL обычный пользовательский путь может исчезнуть, но сам помощник всё равно должен иметь определённое поведение.
- Interpreter и BytecodeVm: `System.OverflowException` через `AxiomExecutionPipeline.Run`.
- Причина: NaN проходит сравнения, `checked((int)value)` выбрасывает исключение вне защитной обёртки.
- Влияние: нарушение модели обработки ошибок. Исправление: конечность перед приведением и преобразование переполнения в диагностику.
- Тесты: напрямую на помощнике и через VAL/CINT, оба движка; негативные проверки не должны зависеть только от исправления VAL.
- Риск: низкий. Документация: сохранить MB3008 для непредставимого результата. IDE: без новых имён.

## LA26-007 — ARRAYAVERAGE переполняет промежуточную сумму

- Файл: `src/Axiom.Runtime/Builtins/BuiltinArrayAggregateHelpers.cs`, `Average`.
- Воспроизведение: `average-positive`; `.axm`: `samples/functions/arrayaverage/audit_large_finite_mean.axm`. Два элемента равны `VAL("1e308")`.

- Риск: средний — изменение порядка арифметики меняет погрешность. Документация: при необходимости описать точность DOUBLE; IDE: без новых токенов.

## LA26-009 — BOOLEAN-массив из одного элемента проходит MIN/MAX

- Исправление: единая проверка типа массива/первого значения; по возможности диагностика binder для статически неподдерживаемого типа.

## LA26-010 — неверное определение кодировки OPEN

- Файл: `src/Axiom.Runtime/Values/RuntimeTextFile.cs`, `DetectInputEncoding`, `IsStrictUtf8`.
- Воспроизведение: `encoding-cp-short` (байт DF), `encoding-cp-three` (C0 C1 C2), `encoding-invalid-prefix`, `encoding-utf-cross-header` (D0 B0 D0 B1), `encoding-utf-emoji` (F0 9F 98 80). Один файл читается READFILE и OPEN/READTOEND.
- Ожидается: одинаковый текст, весь файл проверяется как строгий UTF-8, иначе Windows-1251.
- Interpreter и BytecodeVm: READFILE возвращает правильный текст; OPEN/READTOEND для короткой Windows-1251 выдаёт MB3007; для «аб» возвращает «Р°Р±», для эмодзи — декодирование четырёх UTF-8-байтов как Windows-1251. Длинный cp1251, BOM и двухбайтовое «я» — контрольные прошедшие случаи.
- Причина: проба заголовка читает до трёх байтов; поток не возвращается на начало перед `IsStrictUtf8`. Проверяется хвост без первых байтов, иногда с середины многобайтового символа.
- Влияние: повреждение прочитанного текста, которое пользователь может затем сохранить; разрушение исходного файла этим сценарием не проверялось и не утверждается.
- Исправление: правильно позиционировать поток до проверки, отдельно учитывать подтверждённый BOM, охватить все байты.
- Тесты: длины 0–5, все положения многобайтового символа относительно границы 3/4096, invalid prefix/middle/tail, BOM, cp1251, READLINE/READTEXT/READTOEND/READFILE, оба движка.
- Риск: средний. Документация: договор уже корректен. IDE: новых сущностей нет.

## LA26-011 — READTEXT на эмодзи выходит ArgumentException

- Файлы: `src/Axiom.Runtime/Values/RuntimeTextFile.cs`, `ReadDecodedText`; `src/Axiom.Runtime/Builtins/BuiltinFileIOHelpers.cs`, `IsFileIoException`.
- Воспроизведение: `readtext-emoji-one`. Файл содержит UTF-8 BOM, затем «😀x»; `READTEXT(f,1)`.
- Ожидается: определённое чтение либо диагностика Axiom с восстановлением позиции. Возможность вернуть половину пары или целый scalar должна быть отдельно определена договором; конкретный результат здесь не выдумывается.
- Interpreter и BytecodeVm: публичный конвейер выбрасывает `System.ArgumentException`: выходной char-буфер слишком мал.
- Причина: выходная ёмкость декодера ограничена одной UTF-16-единицей, а эмодзи требует две. `IsFileIoException` не включает ArgumentException.
- Влияние: обычный корректный текст выводит программу из модели ошибок; TRY/CATCH языка не получает диагностику.
- Исправление: определить единицу READTEXT и корректно работать с парами/остатком декодера; одного расширения catch недостаточно для полноценного чтения.
- Тесты: count 0/1/2/3, эмодзи первым и после ASCII, BOM/no-BOM после LA26-010, FILEPOS/SEEK/REWIND, rollback, оба движка.
- Риск: средний/высокий, затронут договор байтовых позиций и символьного чтения. Документация: описать точную единицу count и пограничный случай. IDE: без новых имён.

## LA26-012 — REVERSE расходится на одиночном суррогате

- Файлы: `src/Axiom.Runtime/Builtins/BuiltinStringHelpers.cs`, `EvaluateReverse`; `src/Axiom.Runtime/Execution/BytecodeVm.Builtins.String.cs`, `EvaluateReverseBuiltin`.
- Воспроизведение: `unicode-reverse-twice-cut`; `.axm`: `samples/functions/reverse/audit_surrogate_parity.axm`.
- Ожидается: оба движка одинаково обрабатывают `REVERSE(REVERSE(LEFT("😀",1))) = LEFT("😀",1)`. UTF-16-срез сам по себе разрешён действующим договором.
- Interpreter: `FALSE`, помощник заменяет одиночный суррогат на U+FFFD при `EnumerateRunes`. BytecodeVm: `TRUE`, оптимизация возвращает строки длины ≤1 без обработки.
- Причина: оптимизированный путь не эквивалентен общему на допустимых значениях STRING.
- Влияние: выбор движка меняет результат валидной программы; также возможна необратимая замена строкового содержимого.
- Исправление: определить обращение с непарными суррогатами, реализовать одинаково; предпочтительно сохранить UTF-16-данные и существующие корректные пары.

- Риск: средний. Документация: уточнить непарные суррогаты отдельно от code units и grapheme clusters. IDE: новых токенов нет.

## LA26-013 — CRLF вместо LF

- Файл: `src/Axiom.Runtime/Values/RuntimeTextFile.cs`, `Write`; общий вызов WRITELINE и NEWLINE через `BuiltinFileIOHelpers`.
- Воспроизведение: `file-newline-bytes`: WRITELINE записывает «я» в OUTPUT, затем FILESIZE и реальные байты.
- Ожидается: D1 8F 0A, длина 3 по спецификации и manual `file-system-functions-open-files.html`.
- Interpreter и BytecodeVm: D1 8F 0D 0A, длина 4.
- Причина: `text + Environment.NewLine` на Windows. NEWLINE использует тот же путь, но отдельный байтовый запуск NEWLINE здесь не выполнен.
- Влияние: нарушены обещанные размеры, смещения и обмен текстовыми файлами.
- Исправление: выбрать и выполнить один явный договор. При сохранении действующего LF-договора заменить платформенную строку на LF, проверить существующих потребителей.
- Тесты: сырые байты WRITELINE/NEWLINE, OUTPUT/APPEND, FILEPOS/FILELENGTH, чтение LF/CRLF, обе реализации.
- Риск: средний из-за уже записанных файлов и внешних потребителей. Документация: не выдавать наблюдаемый CRLF за согласованное изменение договора. IDE: без новых имён.

## LA26-014 — метаданные теряют реальные формы и типы

- Файлы: `src/Axiom.Cli/AxiomMetadata.cs`, `src/Axiom.Semantics/Symbols/BuiltinFunctionDescriptor.cs`, `Binding/Binder.InvocationExpressions.cs`, `ide/src/renderer/lang-features.js`.
- Воспроизведение: `dotnet .artifacts/bin/Axiom.Cli/Debug/net10.0/axiom.dll metadata`; сравнить `bound-dimension` и политику дескрипторов в матрице.
- Ожидается: метаданные отражают допустимые формы и зависимость результата от типов аргументов.
- Факт: LBOUND/UBOUND имеют только одноаргументную сигнатуру, хотя `LBOUND(a,2)` и `UBOUND(a,2)` исполняются обоими движками; ABS рекламируется как DOUBLE→DOUBLE без полиморфной политики; ARRAYSUM рекламируется как INTEGER()→INTEGER().
- Причина: две формы LBOUND/UBOUND создаются отдельно внутри binder; CLI выгружает только объявленный тип, не `OperandBindingPolicy`/`ResultTypePolicy`. Electron строит подписи из этих полей. Проверка фактического открытого hover-окна в этом аудите не проводилась.
- Влияние: редактор показывает неполный/неверный договор, внешние инструменты не могут восстановить полиморфизм. ARRAYSUM дополнительно связан с LA26-001; ошибка типа в binder и потеря политики в метаданных — разные проблемы.
- Исправление: один источник допустимых форм, экспорт политик или абстрактных типов, тесты фактических типов вызовов против metadata.
- Тесты: LBOUND/UBOUND с dimension, ABS/INT/MIN/MAX/ARRAYMAP/агрегаты, декларативный тип и разрешённый тип, CLI JSON и подписи Electron.
- Риск: средний, меняется схема внешнего JSON; нужна совместимость потребителя. Документация: контракт metadata и справочник типов; IDE: существенное исправление подписи, подсветка уже синхронна.
