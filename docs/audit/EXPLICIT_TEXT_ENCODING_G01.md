# G01: явная кодировка существующего файлового API

Session 1127, 2026-10-08. Это реализация первого согласованного этапа G01, а не закрытие всей задачи. Явный выбор кодировки для OPEN ещё не реализован.

## Зачем требуется расширение

Автоопределение UTF-8/1251 не позволяет читать заведомо UTF-16-файлы или правильно дописывать текст в Windows-1251. Одни байты могут быть допустимы сразу в двух кодировках. Исправление эвристики не заменяет явно заданный формат внешних данных. Новые имена функций не нужны: расширены уже существующие READFILE, READALLLINES, WRITEFILE и APPENDFILE.

## Работающие формы

```basic
text = READFILE(path, encoding)
lines = READALLLINES(path, encoding)
result = WRITEFILE(path, text, encoding)
result = APPENDFILE(path, text, encoding)
```

Все аргументы должны быть строками; результаты прежние: STRING, STRING(), BOOLEAN, BOOLEAN. Прежние формы без encoding сохранены. Имя кодировки обрезается по краям и сравнивается без учёта регистра. Разрешены только UTF-8, WINDOWS-1251, UTF-16LE и UTF-16BE; остальные имена вызывают MB3007. Общий помощник BuiltinTextEncodingHelpers обслуживает оба движка; новые идентификаторы дескрипторов добавлены в конец enum, прежние числовые значения не изменены.

## Правила текста и BOM

UTF-8 и UTF-16 строго отвергают повреждённые последовательности и непарные суррогаты. WINDOWS-1251 строго отвергает непредставимые символы при записи. Явное чтение не переключается на другую кодировку при ошибке.

UTF-8 записывается без BOM, WINDOWS-1251 тоже. Новый UTF-16LE-файл получает FF FE, UTF-16BE — FE FF. При чтении Unicode допускается отсутствие BOM; совпадающая метка пропускается, распознанная противоречащая метка вызывает MB3007. Метки UTF-32 не определяются как отдельная поддерживаемая кодировка. Первое EF BB BF при чтении UTF-8 всегда считается BOM: если записанный текст начинается U+FEFF, эта подпись при последующем чтении не возвращается как символ. Это явно оговорённое правило текстового файлового API, не двоичный договор.

При явном WINDOWS-1251 метки Unicode не распознаются: все байты относятся к выбранной однобайтовой кодировке. Иначе, например, корректный текст «яю» с байтами FF FE невозможно было бы прочитать тем же API после записи. Проверены FF FE, FE FF и EF BB BF как обычные префиксы текста Windows-1251. Совместимость текста без метаданных нельзя доказать по байтам: неверно выбранный WINDOWS-1251 может успешно декодировать файл другого формата. Ответственность за выбор остаётся у договора внешнего формата.

WRITEFILE кодирует весь новый текст до открытия файла на создание/обнуление. Ошибка имени кодировки или представимости оставляет прежний файл неизменным и не создаёт отсутствующий файл. APPENDFILE тоже заранее кодирует новый текст; затем открывает файл с запретом конкурирующей записи, проверяет существующее содержимое через потоковый строгий декодер и только после проверки добавляет байты. Повторный BOM не добавляется; исходный файл без BOM таким и остаётся. Отсутствующий или пустой файл создаётся по правилам выбранной кодировки. Пустое дополнение всё равно проверяет существующий файл.

Перевод строки автоматически не добавляется. Пустое чтение даёт пустую строку или пустой массив 1 TO 0. Родительские папки автоматически не создаются. Относительные пути используют CurrentDirectory текущего запуска. Ошибка ввода-вывода после начала записи не делает операцию транзакционной.

## Имена и редакционные источники

Имена сохранены из действующего Axiom. Изучены книжные примеры Зельднера с OPEN/INPUT/PRINT # и перекодированием русских текстов. Классический договор не содержит этой Unicode-перегрузки. Современный Visual Basic имеет ReadAllText с аргументом Encoding и WriteAllText с аргументами append/Encoding; это подтверждает жанр расширения существующего файлового API. В Axiom передаётся ограниченное строковое имя, а не объект Encoding или весь реестр CLR. Источники: https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.fileio.filesystem.readalltext?view=net-10.0 и соответствующая страница writealltext. Они использованы как редакционный ориентир; правила BOM и строгости выбраны и проверены отдельно для Axiom.

## Session 1128 — подготовлен файловый исполнитель для OPEN

RuntimeTextFile получил необязательный explicitEncodingName на уровне C#, использующий тот же BuiltinTextEncodingHelpers.Resolve. При явном INPUT существующий поток строго проверяется; при OUTPUT пишется выбранный BOM; при APPEND существующий текст проверяется до записи, а отсутствие BOM сохраняется. Все пользовательские позиции и длины исключают распознанный BOM. Неудачная проверка закрывает уже открытый поток, что подтверждено последующим открытием с FileShare.None.

UTF-16 построчно читается по двухбайтовым единицам с правильным порядком байтов. Байты 0A и 0D внутри обычной буквы не считаются переводами строк. CR, LF и CRLF поддерживаются; LINENUM считает декодированные единицы. READTEXT продолжает считать скалярные значения и сохраняет байтовые позиции. Нечётная позиция UTF-16 и середина суррогатной пары отвергаются при чтении с сохранением позиции; READTEXT с нулевым количеством не читает файл. Проверены UTF-16LE/BE, эмодзи, буквы Ċ и ਁ с байтом 0A, BOM/без BOM, режимы и сохранность буфера после отказа строгого кодирования.

Выбрана проектная форма OPEN path FOR mode AS fileVariable USING encoding. Она ещё не подключена к языку в Session 1128: это следующий этап. USING уже существует в BASIC-линии и Axiom для форматирования PRINT; использование для выбора файлового формата — явно проектное расширение, не утверждение совместимости с QuickBASIC. Такая форма не резервирует слово encoding и позволяет сохранить одноимённые переменные существующих программ. Набор кодировок остаётся прежним, новых функций не требуется.

12 новых Runtime-проверок прошли; полное решение 3645/3645. Синтаксис OPEN, связывание и байткод пока прежние; G01 остаётся PARTIAL. Следующий этап должен проверить число и типы элементов стека OpenFile с дополнительной кодировкой, верификатор, оба движка и пользовательские примеры.

### Session 1129 — потоковая форма подключена к языку

OPEN path FOR mode AS fileVariable USING encoding работает через Parser/Binder/BytecodeVm/Interpreter. Рабочая форма описана в manual/open.html. Поддержаны четыре выбранные кодировки и три режима; прежняя инструкция байткода остаётся с двумя операндами. Проверены точные байты и позиции всех режимов в обоих движках. G01 реализован в выбранном объёме текстового API; это не утверждение о завершении всего аудита языка. Отдельная проверка чтения после произвольного SEEKFILE в языке и дополнительные отрицательные случаи верификатора остаются полезным следующим независимым контролем, несмотря на существующие проверки RuntimeTextFile.

Редакционный ориентир OPEN: Зельднер, раздел OPEN, страницы 184–185 (открытие, режимы, параметры); запасной текущий жанровый ориентир — https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.filesystem.fileopen?view=net-10.0 . Исторические номера файлов, RANDOM/BINARY и условия ACCESS не переносятся в Axiom. USING encoding записано как проектное расширение.
